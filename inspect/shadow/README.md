# シャドー (shadow) フィルタ リバースエンジニアリング解析

対象: `data/exedit.auf`(AviUtl 拡張編集の標準フィルタプラグイン)、32bit PE、
`ImageBase = 0x10000000`。以下のアドレスはすべて VA(`RVA = VA - 0x10000000`)。

## 再現方法

すべてのスクリプトは本プロジェクトの `main.py` を踏み台にして実行する。
`main.py` はコマンドラインで指定されたスクリプトに対して、DLLパス
(デフォルト `data/exedit.auf`)とヘッダー一覧(デフォルト `data/filter.h`)を
渡す役割を持つ。

```
uv run main.py inspect/shadow/<script>.py
uv run main.py tools.<tool>            # エフェクト非依存の共通ツール。一覧はリポジトリ直下の README
```

| スクリプト                          | 確認していること                                                                                                                                                                |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| `tools.track_scale --name シャドー`  | `+0x74` 拡張ブロック `0x100b8538`。スケール `{0,0,10,0}`、`X`/`Y` の**グループ化マーカーはポインタごと NULL**                                                                    |
| `decompile_shadow.py`               | `func_proc`・4つのぼかしパス・2つのエンコーダ・`func_WndProc`・ラベル再構築の angr デコンパイル。浮動小数点はエンコーダにしか無いので、そこ以外はほぼそのまま読める              |
| `disasm_params.py`                  | `func_proc` 全域(12区間)と4パスの要所の注釈付き生逆アセンブル。`esp+0x..` のスロットに名前を付けているのはここ                                                                  |
| `verify_params.py`                  | `濃さ` だけが `/1000` を通ること、`X`/`Y` のクランプが符号を保つこと、`拡散` が**残りの余白に対してだけ**クランプされること、`g_X = max(X,0)` の死んだ `- r`、`w`/`h` に対するクランプが無いこと |
| `verify_blur_chain.py`              | 4パスの向き・カーネル・入出力、除数が常にカーネル幅であること、2パス合成が**半幅ちょうど `拡散` の三角形**になること、パス1が読むのはアルファ(`+6`)だけであること               |

| `verify_ex_data.py`                 | 260バイトの `ex_data` レイアウト(`kind=2` = 文字列、本プロジェクト初出)、2つのボタンが**同じコントロールID `0x1e1b` を共有**し `HIWORD(wParam)` で区別されること、色とパターンが排他であること |
| `simulate_shadow_reference.py`      | 上記すべてを積んだ整数忠実リファレンス実装。ASCIIアートと2本の走査線比較                                                                                                        |

## 1. 登録エントリ ―― 1つだけ、コード全域は約4.2KB

`ライト`・`閃光`・`境界ぼかし`・抜き系3エフェクトと同じく、`シャドー` は
`FILTER_DLL` 配列に**1回しか登録されていない**(`fp->flag & 0x20` による
オブジェクト/フレームの分岐は存在しない)。

| 項目           | 値                                                                             |
| -------------- | ------------------------------------------------------------------------------ |
| `FILTER_DLL`   | `0x100b8560`(配列の [34] 番目)、`flag = 0x40000020`                            |
| `func_proc`    | `0x10087fb0`                                                                   |
| `func_WndProc` | `0x10088da0`                                                                   |
| `FILTER+0x58`  | `0x10089010`                                                                   |
| `ex_data`      | **260バイト**、`ex_data_def` = `0x10231fb0`(全ゼロ)、`+0x70` フィールド表 `0x100b84b0` |
| `+0x74`        | `0x100b8538`。表示スケール `{0,0,10,0}` / グループ化マーカー **NULL** / ドラッグ範囲(下記) |
| 入力バッファ   | `*(fpip+0xAC)`。**読むのはアルファだけ**、書き込みは一切しない                 |
| 対バッファ     | `*(fpip+0xB0)`。影を塗る新キャンバス                                           |

このエフェクト固有のコードは `0x10087fb0`〜`0x10089024` の連続した**約4.2KB**
(直後の `0x10089030` は `シャープ` の `func_proc` で、無関係)。

`flag` の bit30(`0x40000000`)は AviUtl SDK では `FILTER_FLAG_MAIN_MESSAGE`
だが、exedit の内部テーブルでは `標準描画`・`拡張描画`・`パーティクル出力`・
`縁取り`・`部分フィルタ`・`グループ制御`・`カメラ制御`・`放射ブラー`/
`方向ブラー` の2つめの登録にも立っており、**exedit 内での意味は未追跡**(§11)。
`縁取り` とは `flag` も `ex_data` レイアウトも UI の作りも揃っているが、
**`影を別オブジェクトで描画` に相当するチェックボックスを持つのは `シャドー`
だけ**である(`縁取り` はチェックボックスを1つも持たない、
[`縁取り` §1](../border/README.md))ので、このビットの手掛かりにはならない。

配列には `シャドー(カメラ制御)`(`0x100a31b0`、`func_proc = 0x10023cc0`)という
名前の似た別エントリもあるが、トラックバーが `光源X/Y/Z`・`濃さ`・`精度` の
5本で実装も完全に別物であり、本解析の対象外。

### トラックバーとチェックボックス

`tools.filter_table --name シャドー` の生出力:

| トラックバー | raw 既定 | raw 範囲      | 表示スケール | 表示範囲      | スライダー範囲 |
| ------------ | -------: | ------------- | -----------: | ------------- | -------------- |
| `X`          |      -40 | -1000〜1000   |        (1)   | -1000〜1000   | **-200〜200**  |
| `Y`          |       24 | -1000〜1000   |        (1)   | -1000〜1000   | **-200〜200**  |
| `濃さ`       |      400 | 0〜1000       |           10 | 0.0〜100.0    | 0.0〜100.0     |
| `拡散`       |       10 | 0〜500        |        (1)   | 0〜500        | **0〜50**      |

| チェック   | 既定                       | 種別                     |
| ---------- | -------------------------- | ------------------------ |
| `check[0]` | `影を別オブジェクトで描画`(0) | チェックボックス       |
| `check[1]` | `影色の設定`(-1)            | ボタン(色選択ダイアログ) |
| `check[2]` | `パターン画像ファイル`(-1)  | ボタン(ファイル選択)     |

スケール配列は `{0, 0, 10, 0}` で、`X`/`Y`/`拡散` は **1 ではなく 0** が入って
いる(AviUtl 側は 0 も 1 も「スケールしない」として扱う。他のエフェクトは
一律 1 なので、この表記ゆれは `シャドー` 固有)。

**`X` と `Y` はグループ化されていない。** `+0x74` のスロット[1](多成分
コントロールのグループ化マーカー、[`param_scaling.md` §1](../common/param_scaling.md))
はポインタごと NULL で、`閃光` の `X`/`Y` が `+1, -1` を持つのとは対照的である
―― UI 上は対に見えるが、内部的には独立した2本のトラックバーとして扱われる。

### `ex_data` ―― 260バイト、色 + ファイルパス

`+0x70` フィールド表(`0x100b84b0`)が宣言しているのは3本:

```
[0] kind=3 size=  3 name="color"     -- R, G, B (Win32 COLORREF と同じバイト順)
[1] kind=0 size=  1 name=(なし)      -- 未使用のパディング1バイト
[2] kind=2 size=256 name="file"      -- パターン画像のパス(NUL終端)
合計 260 バイト = ex_data_size
```

`kind=2`(固定長文字列)は本プロジェクトで初めて出てきた種別
([`filter_registration.md` §5](../common/filter_registration.md) にあるのは
0 = パディング / 1 = int / 3 = 色 の3つだけだった)。`ex_data_size` が 260 なのも
解析済みで最大である。

`ex_data_def` は **260バイトすべてゼロ**、つまり新規追加時は
**影色 = RGB(0,0,0) の真っ黒、パターン画像なし**。`発光`/`閃光`/`グロー` が
持つ bit24 の「指定なし」フラグは無く、4バイト目は `ライト` と同じ単なる
パディングである([`rgb_ycbcr.md` §1](../common/rgb_ycbcr.md))。

## 2. パラメータ変換 ―― `/1000` を通るのは `濃さ` だけ

`func_proc`(`0x10087fb0`)冒頭、`濃さ = 0` なら即 `return 1`(キャンバスも
バッファも一切触らない)。**早期リターンを持つのはこの1本だけ**で、
`拡散 = 0` でも `X = Y = 0` でもパイプラインは最後まで走る(カーネル幅が
1 になり、ボックス平均が恒等写像になるだけ)。

```
density = trunc(濃さ_raw * 4096 / 1000)        // 共通のマジックナンバー除算 0x10624dd3
X, Y    = track[0], track[1]                    // 画素数そのまま
r       = track[3]                              // 拡散。画素数そのまま
```

エフェクト全域に `0x10624dd3` は**1個しか無い**(`verify_params.py` §1)。
`拡散` が `/1000` を受けないのは `グロー`・`ライト` と同じ流儀。

### オフセットのクランプ ―― 確保済みバッファに収まるまで縮める

```
if w + |X| > stride(fpip+0xEC):  X = sign(X) * (stride - w)
if h + |Y| > rows  (fpip+0xF0):  Y = sign(Y) * (rows   - h)
```

2本の分岐は引き算の向きが違うだけで、どちらも `sign(X) * (stride - w)` に
着地する ―― **符号は必ず保たれる**(左向きのオフセットが右向きになることは
無い、`verify_params.py` §3)。

### 半径のクランプ ―― オフセットが使い残した余白に対してだけ

```
if 2r > stride - (w + |X|):  r = trunc((stride - (w+|X|)) / 2)
if 2r > rows   - (h + |Y|):  r = trunc((rows   - (h+|Y|)) / 2)
```

この順序には2つの帰結がある(`verify_params.py` §4/§5)。

- **`X` を大きくすると `拡散` が効かなくなる。** 余白という1つの予算を
  オフセットとぼかしが取り合い、オフセットが先に食う。
- **`r` は `w` や `h` と一度も比較されない。** `ライト` は
  `trunc(寸法/2) - 2`、`発光` は `寸法/2 - 1` を最初に通すが、`シャドー` には
  相当するものが無い。オブジェクトがカーネルより細いと、各軸**最初の**パスの
  中段ループ回数 `寸法 - カーネル幅` が負になり、
  - 立ち上がりフェーズがオブジェクトの外の行(列)からアルファを読む
  - 出力本数が `寸法 + カーネル幅 - 1` ではなく `2*カーネル幅 - 1` になる

  という2つが起きる。書き込みがスクラッチのプレーン1をはみ出すのは
  **高さ1〜2画素かつ `拡散` が奇数のときだけ**で、最大2行(`verify_params.py` §5
  が総当たりで確認)。溢れた先はプレーン2の領域で、次のパスが上書きするので
  実害は無い。問題は読み出しのほうで、これは [`box_blur.md` §4](../common/box_blur.md)
  が `クロマキー`/`カラーキー`/`境界ぼかし` について挙げているのと同じ形の穴である。
  2本目のパスは入力長が `寸法 + カーネルB - 1` あるので、`カーネルA ≤ カーネルB`
  より絶対に破綻しない。

### 半径の2分割

```
r1 = trunc(拡散 / 2)        カーネルA = 2*r1 + 1      (0x10231f98)
r2 = 拡散 - r1              カーネルB = 2*r2 + 1      (0x10231f94)
```

## 3. キャンバスとレイアウト

キャンバス(対バッファ `fpip+0xB0`)のサイズは:

```
canvasW = w + |X| + 2r        canvasH = h + |Y| + 2r
```

そこに矩形が2つ置かれる:

| 矩形         | 位置                             | サイズ           |
| ------------ | -------------------------------- | ---------------- |
| 影の箱       | `(max(X,0), max(Y,0))`           | `(w+2r, h+2r)`   |
| オブジェクト | `(max(-X,0)+r, max(-Y,0)+r)`     | `(w, h)`         |

非対称に見えるが、**この2つの差はどの符号の組み合わせでもきっかり `(X, Y)`**
になる(`verify_geometry.py` §1 が 134×58×4 通りで確認)。オブジェクト側の
`+r` はぼかしの余白ぶんの中央合わせで、`max` 2つがどちらの矩形に余地を渡すかを
決めている。

`w + |X| + 2r` は「オフセットに `|X|`、ぼかしに `2r`」という2つの取り分の
単純な和で、両方が同じ側に効くのは `|X| < r` のときだけである。重なりを
引かないので、**影と反対側に `min(|X|, r)` 画素の完全に透明な帯が残る**
(`verify_geometry.py` §2)。害は無いが、AviUtl が表示する外接矩形は実際に
描かれている範囲よりわずかに大きい。

`サイズ固定` に相当するチェックボックスは**存在しない**ので、`X`/`Y`/`拡散` の
どれかが 0 でなければ外接矩形は必ず変わる(`グロー`・`ライト` と同じ性質、
[`canvas_growth.md` §6](../common/canvas_growth.md))。

### `fpip+0xD4` / `+0xD8` の補正 ―― 1/4096画素単位の2つ目の裏付け

キャンバスは `|X|` ぶん**片側にだけ**伸びるので、オブジェクトが画面上の
同じ位置に留まるにはキャンバス中心とのずれを半分だけ戻す必要がある。
`func_proc` は `(-X) << 11`(= `-X * 2048`)を `fpip+0xD4` に加える。

`2048 = 4096/2` なので、**この命令は「1画素 = 4096」でしか半画素にならない**。
`+0xD4`/`+0xD8` の単位は今まで `閃光` の補正式からの推定にとどまっていた
([`canvas_growth.md` §7](../common/canvas_growth.md))が、まったく別の式から
同じ値が出たことになる(`verify_geometry.py` §3)。対称に伸びる `2r` のほうには
補正が入らない、という整合も取れている。

## 4. ぼかし ―― アルファだけを4パス

`EXFUNC::exec_multi_thread_func`(`exfunc+0xCC`)経由で4パスが順に走る。
対象は**オブジェクトのアルファだけ**で、Y/Cb/Cr は1度も読まれない
(`verify_blur_chain.py` §5 ―― パス1の `movsx` の変位は `+6` のみ)。

| パス | 関数         | 向き | カーネル | 入力              | 出力              | スレッド分割 |
| ---- | ------------ | ---- | -------- | ----------------- | ----------------- | ------------ |
| 1    | `0x10088580` | 垂直 | B        | `fpip+0xAC` の α  | プレーン1         | 列           |
| 2    | `0x100886f0` | 水平 | B        | プレーン1         | プレーン2         | 行           |
| 3    | `0x10088840` | 垂直 | A        | プレーン2         | プレーン1         | 列           |
| 4    | `0x100889a0` / `0x10088bc0` | 水平 | A | プレーン1 | `fpip+0xB0`(エンコード) | 行 |

中間の2プレーンは16bitのアルファ専用で、`発光`/`グロー`/`クロマキー`/`ライト`
と同じスクラッチ `[0x101a5328]` から切り出す:

```
プレーン1 (0x10231f90) = [0x101a5328]
プレーン2 (0x10231fa0) = プレーン1 + stride * canvasH * 2
```

1パスは全エフェクト共通の3フェーズ・スライディングウィンドウで、**除数は
常にカーネル幅**(窓が育っている最中も同じ数で割る)。したがって画像外は
透明として数えられ、広がった縁へ自然にフェードする
([`box_blur.md` §3](../common/box_blur.md) の「常にカーネル幅で割る」変種)。
重みテーブルもガウシアン核も無い(`verify_blur_chain.py` §1)。

### 合成カーネルは半幅ちょうど `拡散` の三角形

軸ごとに `box(カーネルB) ⊛ box(カーネルA)` になり、支持長は
`カーネルA + カーネルB - 1 = 2*拡散 + 1` ―― **`拡散` の値がそのまま実効半径**
である(`verify_blur_chain.py` §2、501通り全数確認)。`拡散` が偶数なら純粋な
三角形、奇数なら上底3の台形になる。`ぼかし` の4パス分割
([`box_blur.md` §2](../common/box_blur.md))とまったく同じ仕組みを、画素では
なくアルファに適用したものである。

各パスの出力はきっかり次のパスの入力になる ―― パス2が読むのは
`h + カーネルB - 1` 行、パス3が読むのは `w + カーネルB - 1` 列、パス4が読むのは
`h + 2*拡散` 行で、いずれも直前のパスが書いた矩形そのもの
(`verify_blur_chain.py` §3)。各ワーカーがこの寸法を `fpip+0xB4`/`+0xB8` と
2つのカーネル幅から自前で再計算できるのは、`func_proc` が `w`/`h` の書き換えを
最後まで遅らせているからである。

## 5. 出力エンコード ―― 影色は素のまま入る

パス4は水平ウィンドウの**和を割らずに**持ち、割り算をスレッドごとに1回だけ
計算する x87 の定数に畳み込む。

### 影色版 `0x100889a0`

```
scale = density / (カーネルA * 4096)          // fild;fild;fdivp、スレッドごとに1回

sum == 0 : dst.a = 0                          // y/cb/cr は書かない
それ以外 : dst.y, dst.cb, dst.cr = 影色       // そのまま格納
           dst.a = trunc(sum * scale)         // fild;fmul;_ftol(0方向切り捨て)
```

`sum ≤ カーネルA * 4096` なので出力アルファは `density` を超えられず、
**クランプは必要も存在もしない**。`濃さ` の raw 上限が 1000 = Q12 の 1.0 で
あることと合わせて、`発光`/`グロー`/`ライト` にあるオーバードライブ経路が
このエフェクトには**そもそも無い**(`verify_encode.py` §1)。

**影色は Y/Cb/Cr に素のまま入り、被覆率だけがアルファに入る。**
`ライト` の後光や `閃光` は `Y = 4096` に固定して光色の Y をアルファへ載せる
アンプリマルチプライなので「暗い光色ほど効果が消える」が
([`rgb_ycbcr.md` §4](../common/rgb_ycbcr.md))、`シャドー` は逆で
**真っ黒な影も真っ白な影と同じ不透明度になる**。既定値が RGB(0,0,0) である
以上そうでなければ困る、という設計上の必然でもある(`verify_encode.py` §2)。

`sum == 0` のとき色を書かないのは、その画素のアルファが必ず 0 になるからで、
[`box_blur.md` §1](../common/box_blur.md) の `sum_a == 0` と同じ理屈である。
なお `sum != 0` でもアルファが 0 に切り捨てられる画素はあり、そちらには
影色が書かれる ―― 透明画素が2種類あることになるが、どちらも見えない。

### x87 の除算先行 ―― 平坦部が 1 足りなくなる

`scale` を先に丸めてから掛けるので、`sum = カーネルA * 4096`(完全不透明な
オブジェクトの内側)が `density` に戻らないことがある。`拡散`×`濃さ` の
全 501,501 通りのうち **27,109 通り(5.41%)で `density - 1`** になる
(`verify_encode.py` §3)。例えば `拡散 = 48`、`濃さ = 100.0%` では影の芯が
4096 ではなく 4095 になる。1/4096 は目に見えないが、リファレンス実装を
実物と突き合わせるときには効く。

なおこの節だけは **x87 の精度制御が 53bit(MSVC の既定)である**ことを
前提にしている(§11)。

### パターン画像版 `0x10088bc0`

```
scale = density / (カーネルA * 4096 * 4096)
dst.a = trunc(dst.a * sum * scale)            // dst.a = 敷き詰め済みパターンのα
```

**Y/Cb/Cr は1度も書かれない**(3つの光色グローバルへの参照が関数内に0件、
`verify_encode.py` §5)。色はタイル済みのパターン画像がそのまま供給し、
`影色の設定` はこのモードでは完全に無効になる。アルファ同士が掛かるだけなので
`濃さ` とパターンの透明度は交換可能で、パターンが加えるのは
**シルエット内部の空間的な模様と色**である。

## 6. `パターン画像ファイル` ―― 敷き詰めてから切り抜く

`ex_data+4` が空文字列でないとき、ぼかしが始まる**前に**次を行う
(`disasm_params.py` の `PATTERN` / `CLEAR` 区間):

```
ok = table[0x38]([0x101a5328], path, &patW, &patH, 0, 0)     // 0x1004c8d0 = 画像ローダ
if ok:
    for tileY in 0, patH, 2*patH, ... < canvasH - g_Y:
        for tileX in 0, patW, ... < canvasW - g_X:
            table[0x44](fpip+0xB0, g_X+tileX, g_Y+tileY, [0x101a5328],
                        0, 0, patW, patH, 0, 0x13000003)      // 単純コピー、8バイト画素
table[0x48](fpip+0xB0, ...) ×4                                // 影の箱の外を透明でクリア
```

`table[0x38]`(`0x1004c8d0`)は `画像ファイル` オブジェクト(`0x1000d5e0`)などと
共有の画像ローダで、デコード先を NULL にするとサイズだけを返す(§8 で
`func_WndProc` がそう使う)。デコード先にスクラッチ `[0x101a5328]` を借りるが、
プレーン1/2 として使い始めるのはこの後(`0x1008834d`)なので競合しない。

4本の矩形クリア(左・上・右・下)の和集合は**キャンバスから影の箱を引いた
領域ちょうど**である(`verify_geometry.py` §4)。左右は全高、上下は全幅なので
四隅は2回クリアされる。

タイルの原点が `(g_X, g_Y)` = 影の箱の左上であることに注意 ――
**パターンはフレームではなくオブジェクトに固定される**ので、オブジェクトが
動けば模様も一緒に動く。

## 7. `影を別オブジェクトで描画`

`check[0]` が立っていると、`func_proc` の**冒頭で `X` と `Y` がゼロにされる**
(`0x10088030`)。したがってキャンバスは `(w+2r) × (h+2r)` にしかならず、
`fpip+0xD4` の補正も入らない(`verify_geometry.py` §5)。

ぼかしとエンコードが終わったあと、`table[0x44]` でオブジェクトを重ねる
代わりに:

```
fpip+0xBC += X * 4096 ;  fpip+0xC0 += Y * 4096      // オブジェクト位置、1/4096画素
fpip+0xB4  = w + 2r   ;  fpip+0xB8  = h + 2r
swap fpip+0xAC <-> fpip+0xB0                        // 影のキャンバスを「画像」にする
sub_1004b200(fp+0xE4, fpip, 0x10fffff)              // 描画パイプラインへ流す
(上の書き換えをすべて元に戻す)
return 1
```

`fpip+0xBC`/`+0xC0` は `+0xD4`/`+0xD8`(中心のずれ補正)とは別の、オブジェクトの
**位置**そのものを持つフィールドで、単位は同じ 1/4096 画素。ここでは
`shl 0xc` = 整数画素の `X` をそのまま入れている。

**元のオブジェクトは1バイトも変わらずに `func_proc` を出る** ―― 影は
別オブジェクトとして先に描かれ、オブジェクト自身は外接矩形も含めて無傷の
まま効果チェーンを続ける。チェックボックスの名前どおりの挙動である。

`sub_1004b200` の中身(第3引数 `0x10fffff` の意味を含む)は未追跡(§11)。

## 8. UI ―― 2つのボタンが1つのコントロールIDを共有する

`func_WndProc`(`0x10088da0`)は `WM_FILTER_COMMAND`(`0x702`)だけを見て、
`LOWORD(wParam)` が `0x1e1b`(ボタン押下)か `0x1e16`(ファイル名の通知)の
どちらかのときだけ動く。

**`シャドー` は本プロジェクトで初めて「ボタンを2個持つ」エフェクト**であり、
`0x1e1b` だけでは区別が付かない。区別は `HIWORD(wParam)` にある:

```c
if (message == 0x702) {
    if (LOWORD(wParam) == 0x1e16) goto file_accepted;     // exedit がパスを lParam で渡してきた
    if (LOWORD(wParam) != 0x1e1b) return 0;
    if (HIWORD(wParam) == 1) {                            // check[1] = 影色の設定
        table[0x80](fp+0xE4, 0);
        if (!table[0x6c](fp, ex_data, 2)) return 0;       // 色選択ダイアログ。フラグ 2 = ライトと同じ
        ex_data[4] = '\0';                                // ★ パターンのパスを消す
        sub_1004a7e0(fp+0xE4, "color");
        sub_10088f40(fp, ex_data);                        // ラベル再構築
        return 1;
    }
    /* HIWORD != 1 -> check[2] = パターン画像ファイル */
    if (sub_10020900(&localPath, table[0x3c](ex_data+4)) != 1) return 0;   // モーダルのファイルダイアログ
file_accepted:
    table[0x80](fp+0xE4, 0);
    if (LOWORD(wParam) == 0x1e16) lstrcpyA(localPath, (char*)lParam);
    if (table[0x38](NULL, localPath, &pw, &ph, 0, 0) != 1)
        MessageBoxA(NULL, "画像ファイルの読み込みに失敗しました…", fp->name, 0x42010);
    else if (pw * ph > trunc(maxCanvasW * maxCanvasH / 2))
        MessageBoxA(NULL, "画像サイズが大きすぎて読み込めません", fp->name, 0x42010);
    lstrcpyA(ex_data+4, localPath);
    sub_10088f40(fp, ex_data);
    return 1;
}
```

`HIWORD(wParam)` が `check[]` の添字であることは exedit の送信側でも確認できる
―― `0x10041453` が `shl eax, 0x10 ; or eax, 0x1e1b` でメッセージを組み立てて
おり、その添字はラベル再構築が `table[0x4c](fp+0xE4, 5, 1)` /
`(fp+0xE4, 5, 2)` に渡すもの(種別5 = ボタン、
[`filter_registration.md` §7](../common/filter_registration.md))と同じである。
`発光`/`グロー`/`ライト`/`クロマキー`/`カラーキー` はボタンが1個なので
`LOWORD` しか見ておらず、この規約は今まで表に出てこなかった。

### 色とパターンは排他

- **色を確定すると `ex_data+4` の先頭に 0 が書かれ、パターンのパスが消える**
  (`0x10088e15`)。
- **パターンが設定されている間、`影色の設定` ボタンのラベルは空文字列になる**
  (`0x10088fae`。設定されていなければ `"RGB ( %d , %d , %d )"`)。

この2行が排他の全部で、両方を同時に持つ状態は無い ―― エンコーダ側でも
パターン版が影色を1度も読まないこと(§5)と整合する。非対称なのは、
色を選ぶとパスが**消える**のに対し、パスを選んでも色のバイトは `ex_data` に
残ったまま表示されなくなるだけ、という点である。

ラベル再構築(`0x10088f40`)はパスから最後の `:` または `\` の次の文字を探して
ファイル名部分だけをボタンに出す。走査は `IsDBCSLeadByteEx` を使う cp932 対応で、
2バイト文字の後続バイトがたまたま `0x5c`(`\`)でも誤認しない。

`FILTER+0x58`(`0x10089010`)はラベル再構築を呼ぶだけの5命令で、
`ライト` の `0x1005ca90` と同じ形。

### 画像サイズの上限

選択された画像は `w * h > trunc(最大キャンバス幅 * 最大キャンバス高 / 2)` だと
メッセージボックスで拒否される([`canvas_growth.md` §1](../common/canvas_growth.md)
の `0x10196748` / `0x101920e0`)。ただし**このチェックは UI 側にしか無く**、
`func_proc` の読み込み(`0x100881ca`)は無検査である。

## 11. 未確定事項

- **`sub_1004b200`(`0x1004b200`)の中身。** `影を別オブジェクトで描画` が
  `(fp+0xE4, fpip, 0x10fffff)` で呼ぶ描画パイプラインの入口だと読めるが、
  第3引数のビットの意味も、`0x1002b0d0` / `0x10049370` / `0x10039550` へ
  分岐していく先も追っていない。`table[0x80]` と同じ
  `(fp+0xE4 & 0xffff) - 1` の添字化を冒頭で行う点だけが手掛かり。
- **`table[0x38]`(`0x1004c8d0`)がサポートする画像形式。** BMP らしき経路と
  他に2つの経路を持つことまでは見たが、それぞれの実体は追っていない。
  戻り値が 1 = 成功、デコード先 NULL でサイズのみ取得、という呼び出し規約は
  `func_proc` と `func_WndProc` の2箇所の使い方から確定させたもの。
- **`table[0x3c]`(`0x1004cc40`)が組み立てるパス。** グローバルバッファ
  `0x101539e0` に `wsprintfA` で書いてから `GetFileAttributesA` らしき
  インポートを呼ぶところまでで、相対パスの基準がどこかは未確認。
- **`flag` の bit30(`0x40000000`)。** SDK では `FILTER_FLAG_MAIN_MESSAGE` だが、
  exedit の内部テーブルで立っている12エントリの共通項が見つかっていない。
  `シャドー` の `func_proc` はこのビットを読まない。
- **x87 の精度制御。** §5 の「平坦部が 1 足りない」は精度が 53bit(MSVC の
  既定)である前提の計算で、AviUtl 本体が制御ワードをどう残しているかは
  確認していない。64bit なら影響する `拡散` の集合が変わる(他の主張は
  精度に依存しない)。
- **`fpip+0xEC` / `+0xF0` の実際の値。** クランプの上限そのものなので、
  「どのくらいの `X` から `拡散` が食われ始めるか」は確保のされ方次第。
  `拡散光` §4 / `ライト` §2 と同じ読みを踏襲しているだけで、本エフェクトでも
  書き込み側は追っていない。
- **小さいオブジェクトでのはみ出しの着地先。** §2 のとおり書き込みは高々2行
  ぶんプレーン2の領域へ落ちる(次のパスが上書きするので実害は無いはず)が、
  スクラッチバッファ `[0x101a5328]` の実サイズは確認していない。読み出しが
  オブジェクト外の行(列)に届く件も、そこに何があるかまでは追っていない。
- **`ex_data.file` の 256 バイトと `func_WndProc` の 260 バイトのスタック
  バッファの食い違い。** 長すぎるパスがどう切り詰められるかは実測していない。

以下は全エフェクト共通の未確定事項:

- `fpip->flag & 0x200`(描画品質を落としてよいフラグ)をこのエフェクトが
  読むかどうかは未確認(`disasm_params.py` の範囲では出てこない)。
- 最終的な YCbCr→RGB 変換とそのクリップは `aviutl.exe` 側にあるため、本
  プロジェクトの解析対象外([`rgb_ycbcr.md` §3](../common/rgb_ycbcr.md))。
