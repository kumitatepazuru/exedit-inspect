# クロマキー (Chroma Key) フィルタ リバースエンジニアリング解析

対象: `data/exedit.auf`(AviUtl 拡張編集の標準フィルタプラグイン)、32bit PE、
`ImageBase = 0x10000000`。以下のアドレスはすべて VA(`RVA = VA - 0x10000000`)。

## 再現方法

すべてのスクリプトは本プロジェクトの `main.py` を踏み台にして実行する。
`main.py` はコマンドラインで指定されたスクリプトに対して、DLLパス
(デフォルト `data/exedit.auf`)とヘッダー一覧(デフォルト `data/filter.h`)を
渡す役割を持つ。

```
uv run main.py inspect/chroma_key/<script>.py
uv run main.py tools.<tool>            # エフェクト非依存の共通ツール。一覧はリポジトリ直下の README
```

| スクリプト                             | 確認していること                                                                                                                                                        |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |

| `tools.track_scale --name クロマキー`  | `+0x74` 拡張ブロックが **NULL** ―― 3本とも表示スケール1・ドラッグ範囲指定なしで、生値がそのまま UI 表示値                                                              |
| `decompile_chroma_key.py`              | `0x10012000`〜`0x10015000` に絞った `CFGFast` + angr デコンパイル。func_proc・7ワーカー・`func_WndProc`・ラベル更新の全体像(x87 の `fpatan` はリフトされない)              |
| `disasm_params.py`                     | func_proc 全域の注釈付きダンプ。`ex_data.status` の早期 return、5つのグローバル、2×2の分岐と3回のワーカー起動。ワーカー側のパラメータ変換も併せて出力                    |

| `verify_border_chain.py`               | `境界補正` の3パス。ボックス平均のフェーズ構成が閉じた式と一致すること、コントラスト伸張定数 `A`/`B`、`t(4096)==4096`、そして**小さい画像での書き込み溢れ**              |
| `simulate_chroma_key_reference.py`     | 上記すべてを織り込んだ整数忠実リファレンス実装(4経路すべて)。18項目の自己検証つき                                                                                        |

## 1. 登録エントリ ―― オブジェクト効果1個だけ

`クロマキー` の登録は `0x100a0e28` の1個だけで、`境界ぼかし` と同じく
**フレーム(映像)フィルタ版が存在しない**。`fp->flag & 0x20` の分岐はコード上に
無く、画素は常に 8バイト/画素 PIXEL_YCA である。

| 項目           | 値                                                                    |
| -------------- | --------------------------------------------------------------------- |
| `FILTER_DLL`   | `0x100a0e28`、`flag = 0x20`(オブジェクトのフィルタ効果)               |
| `func_proc`    | `0x10012de0`                                                          |
| `func_WndProc` | `0x100143d0`(`func_init`/`func_exit`/`func_update` は NULL)           |
| `FILTER+0x58`  | `0x10014560`(exedit 流用の設定ウィンドウ更新エントリ)                 |
| `ex_data`      | 12バイト、`ex_data_def = 0x1011ec90`(全ゼロ)、`+0x70` 表 `0x100a0dd0` |
| `+0x74`        | **NULL** ―― 表示スケールもドラッグ範囲も持たない                      |
| 入力バッファ   | `*(fpip+0xAC)`。**完全にイン・プレース**、バッファ入れ替えもキャンバス拡張も無い |
| 作業バッファ   | `*(fpip+0xB0)`(16bitマップ2枚として使う)＋ 共有スクラッチ `0x101a5328` |

`func_proc` は画素ループを1つも持たない。やっているのは
「早期 return → グローバルを5個書く → `exec_multi_thread_func` を1回または3回」
だけである。`func_proc` と7つのワーカーが直接 `call` している先は
CRT `_ftol`(`0x10091ad8`)**1つだけ**で、合成関数もブレンドテーブルも
矩形転送も使わない(`verify_dispatch.py`)。

## 2. `ex_data` ―― キー色とスポイトの状態

トラックバーは3本ともキーの「広さ」を決めるだけで、**キー色そのものは
`ex_data` に入っている**。レイアウトは exedit 自身の `+0x70` フィールド表
(`0x100a0dd0`、[`filter_registration.md` §5](../common/filter_registration.md))が
宣言しており、宣言サイズの合計が `ex_data_size` と一致する:

| offset | size | kind | name       | 意味                                     |
| ------ | ---- | ---- | ---------- | ---------------------------------------- |
| 0      | 6    | 3    | `color_yc` | `PIXEL_YC { short y, cb, cr; }` = キー色 |
| 6      | 2    | 0    | (無名)     | アラインメント用パディング               |
| 8      | 4    | 1    | `status`   | スポイトの状態(下表)                     |

```c
struct { short y, cb, cr; short pad; int status; };   // 12 bytes
```

`status` は真偽値ではなく**3値**で、`func_proc` の1行目
(`0x10012de8`)は `status == 1` 以外をすべて弾く:

| `status` | ボタンのラベル                             | `func_proc` |
| -------- | ------------------------------------------ | ----------- |
| 0        | `< 未取得 >`                               | 即 return   |
| 1        | `YCbCr ( %d , %d , %d )`                   | **実行**    |
| 2        | `マウスをクリックして色を取得してください` | 即 return   |

`func_WndProc`(`0x100143d0`)が扱うのは `0x702`(`WM_FILTER_COMMAND`)だけで、
コントロールID2つに反応する:

- **`0x1e1b`** ―― `キー色の取得` ボタン(`check[2]`、`check_default = -1`。
  `閃光`/`グロー` の `光色の設定` と同じ ID)。`status == 2` なら
  `table[0x68](0, 0)` で解除して `status = 0`、そうでなければ
  `table[0x68](fp+0xE4, 1)` でスポイトを起動して `status = 2`。
  **解除は「元のキー色に戻る」のではなく `status = 0`**(`0x10014490`)なので、
  取得済みの状態でボタンを2回押すとキー色を失う。
- **`0x1e1d`** ―― exedit がスポイトの結果を届けてくる。`lParam` が指す
  `PIXEL_YC` を `ex_data+0/+2/+4` へコピーして `status = 1`。`lParam == 0`
  (キャンセル)なら `status = 0`。

`table[0x68]` / `table[0x4c]` / `table[0x80]` はいずれも `fp+0x64` に差し込まれた
exedit 内部の関数テーブル `0x100a41e0`
([`filter_registration.md` §4](../common/filter_registration.md))。

### キー色の輝度は使われない

`color_yc.y` を読む命令は、設定ウィンドウのラベルを組み立てる
`wsprintfA`(`0x100144fa`)**1箇所だけ**である。7つのワーカーが `ex_data` から
読むオフセットは `+2`(cb)と `+4`(cr)だけで、`+0` は現れない
(`verify_ex_data.py` が全ワーカーの本体を走査して確認)。

つまり**同じ色相・彩度で明るさだけ違うキー色は完全に等価**で、暗いところを
スポイトしても明るいところをスポイトしても、色差が同じなら結果は1ビットも
変わらない。保存もされ表示もされる値が、計算には一切効かない。

## 3. パラメータ

| トラックバー | 生値の範囲 | 初期値 | 表示スケール | 内部での使われ方                        |
| ------------ | ---------- | ------ | ------------ | --------------------------------------- |
| `色相範囲`   | 0〜256     | 24     | 1            | `hue_range = 色相範囲 << 7`             |
| `彩度範囲`   | 0〜256     | 96     | 1            | `sat_range = (彩度範囲 * key_sat) >> 8` |
| `境界補正`   | 0〜5       | 1      | 1            | ボックス平均の半径 `r` そのもの         |

| チェックボックス | 初期値 | 役割                                                     |
| ---------------- | ------ | -------------------------------------------------------- |
| `色彩補正`       | オフ   | 色差を「キー色から遠ざける」アンミックス(手順6)           |
| `透過補正`       | オフ   | 同じ被覆率でアルファも落とす。**`色彩補正` 専用の修飾子** |
| `キー色の取得`   | ―     | ボタン(`check_default = -1`)。手順2                       |

`+0x74` 拡張ブロックが NULL なので、`/1000` のマジックナンバー除算も
表示スケールも**1つも存在しない**。本リポジトリで解析した中では唯一、
[`param_scaling.md` §2](../common/param_scaling.md) のマジック除算が
まったく出てこないエフェクトである。

**トラックバーはワーカーが自分で `fp->track[]` から読む**。半径のように
グローバル経由で渡されるのは `境界補正` だけで、これも
`exec_multi_thread_func` の引数が4個しかないという共通の制約
([`filter_registration.md` §6](../common/filter_registration.md))による。

## 4. キーの距離 `d`

4つのキーイングワーカーはすべて同じ20命令で始まる。これがこのエフェクトの
言う「この画素はキー色か」の全部である。

```
key_hue = ftol(atan2(key.cr, key.cb) * 65536/(2π))     // 1周 = 65536 の2進角
key_sat = max(|key.cb|, |key.cr|)                       // チェビシェフノルム

hue = ftol(atan2(cr, cb) * 65536/(2π))
sat = max(|cb|, |cr|)

dh  = |(int16)(hue - key_hue)|                          // 円周上の最短距離
ds  = |sat - key_sat|

d   = max(0, dh - hue_range) + 8 * max(0, ds - sat_range)
```

- 定数 `0x1009a430` は `10430.378350470453` = `65536/(2π)` と**ビット単位で
  一致**する。だから `int16` への切り詰めがそのまま剰余になり、
  `abs((int16)(hue - key_hue))` は円周上の短い側の距離になる
  (`verify_key_metric.py` が全域で照合)。
- `sat` は `max(|cb|,|cr|)` ―― **チェビシェフノルムであってユークリッド距離
  ではない**。等 `sat` 線は正方形なので、対角線上のキー色は軸上のキー色より
  41% 広い彩度域を掴む。補正するコードはどこにも無い。
- **色差の平面だけを見ており、輝度 `y` は読まない**。画素側も同じで、
  白飛びした部分と正常露出の部分は同じに扱われる。

### 2つの許容範囲

| `色相範囲` | `hue_range` | 意味                                     |
| ---------- | ----------- | ---------------------------------------- |
| 0          | 0           | 色相が1目盛でも違えばペナルティ          |
| 24(既定)   | 3072        | ±0.047周(≒±16.9°)                       |
| 128        | 16384       | ±0.25周(±90°)                           |
| 256        | 32768       | **半周 = 上限。色相判定が無効化される**  |

`dh` の最大値が 32768 なので、`色相範囲 = 256` では色相の項が常に 0 になり、
彩度だけのキーになる。

`sat_range` は**キー色自身の彩度に対する割合**(`彩度範囲/256`)である。
`彩度範囲 = 96`(既定)、`key_sat = 600` なら `sat_range = 225` で、
受理される彩度帯は `[375, 825]`。**上限も下限もある帯**なので、
キー色より鮮やかすぎる画素も落ちない。

### `d` からアルファへ

```
if d < 4096:  a = (a * d) >> 12
// d >= 4096 の画素は一切触らない
```

`d == 0`(帯の内側)で完全透過、`d >= 4096` で完全不透過、その間が線形の
ソフトエッジ。色相側は 4096 目盛(= 1/16周)、彩度側は 8倍の重みが効くので
**512 目盛**で不透過に達する。実際のソフトエッジを作っているのはほぼ彩度側で、
色相側は「そもそも別の色か」を判定する粗いゲートとして働く。

### 彩度0のキー色

`key_sat = 0`(白・黒・灰色をスポイトした場合)では `sat_range` が
`彩度範囲` の値によらず 0 になり、距離は `d = 8 * sat` に潰れる。
つまり**「色相のキー」ではなく「無彩色のキー」**になり、灰色が消えて
彩度 512 以上の画素だけが残る。UI からは読み取れない挙動だが、
スポイトは黒い画素でも `status = 1` にする(`verify_spill.py`)。

## 5. `境界補正 = 0` の経路

ワーカーは1つだけ走り、`*(fpip+0xAC)` をイン・プレースで書き換える。

| `色彩補正` | ワーカー     | 書き込むフィールド     |
| ---------- | ------------ | ---------------------- |
| オフ       | `0x10012f10` | `a` のみ               |
| オン       | `0x100130b0` | `cb`, `cr`, `a`        |

スレッド分割は行方向(`y0 = tid*h/thread_num`)。`0x10012f10` は
`fp->check[]` を一度も読まない ―― **`透過補正` は `色彩補正` がオフのとき
完全に死んでいる**(`verify_dispatch.py` / リファレンス実装の自己検証)。

## 6. `色彩補正` と `透過補正` ―― スピルのアンミックス

アルファを決めたあと、`色彩補正` のワーカーは色差を**キー色から遠ざける**。

```
f = max(hue_excess, ((key_sat - sat) << 12) / max(key_sat, 1))

if 1 < f < 4096:
    cb' = clamp(key.cb + ((cb - key.cb) << 12) / f, -2048, 2048)
    cr' = clamp(key.cr + ((cr - key.cr) << 12) / f, -2048, 2048)

if 透過補正 && f < 4096:
    a' = (f * a) >> 12
```

`hue_excess` は距離の**色相の項だけ**(`max(0, dh - hue_range)`)で、
彩度の項を足し込む前の値である。`d` とは別物なので混同しやすい。

式の意味は2色混合のアンプリマルチプライそのもので、画素が前景 `c` 割・
キー色 `1-c` 割の混合なら

```
px = c*fg + (1-c)*key      =>      fg = key + (px - key)/c
```

であり、`f/4096` が exedit の見積もる `c` にあたる。`透過補正` は同じ `c` を
アルファに掛ける ―― 「キー色だった分の被覆率は捨てる」という、同じ恒等式の
もう半分である。

**この見積もりは前景が無彩色のとき厳密**になる。前景の色差が 0 なら混合後の
彩度はちょうど `(1-c)*key_sat` なので、`f/4096` が `c` を正確に復元する
(`verify_spill.py` が誤差 ±2 以内で確認)。逆に前景に色が付いていると
`f` は当てにならず、補正は行き過ぎたり足りなかったりする。

> `色彩補正` が体現しているモデルは「**キー色でないものは灰色だった**」である。
> 緑バックの髪や煙には正しく、赤いジャケットには誤る。チェックボックスに
> なっている理由はここにある。

±2048 のクランプは `f` が小さい画素の暴走を止めるための飽和で、
`f > 1` のゲートがゼロ除算を防ぐ唯一の仕掛けである。

## 7. `境界補正` ―― 16bitマットの3パス処理

`境界補正 = r > 0` にすると、画素ごとの判定ではなく**マット(16bit の被覆率
マップ)に対する小さな画像処理パイプライン**になり、ワーカーが3つ直列に走る。

作業領域は `func_proc` が用意する:

```
g_1011ec7c = *(fpip+0xB0)                        map A(2バイト/画素)
g_1011ec80 = *(fpip+0xB0) + 2*stride*h           map B(同上、A の直後)
g_1011ec84 = *(0x101a5328)                       map C(色彩補正 のときだけ)
g_1011ec88 = 2r+1                                カーネル幅
g_1011ec8c = r
```

対バッファは 8バイト/画素なので、16bit マップ2枚はその前半に収まる。
map C だけは exedit 共有のスクラッチ(`発光`・`グロー`・
`ディスプレイスメントマップ` などが同じ確保を借りる番地)を使う。

| パス | `色彩補正` オフ | `色彩補正` オン | 内容                                                          | スレッド分割 |
| ---- | --------------- | --------------- | ------------------------------------------------------------- | ------------ |
| 1    | `0x10013340`    | `0x10013500`    | `map B[y][x] = min(d, 4096)`(オンは `map C = hue_excess` も)   | 行           |
| 2    | `0x100136e0`    | `0x100136e0`    | map B を**垂直**ボックス平均して map A へ(両経路で同じコード) | **列**       |
| 3    | `0x10013880`    | `0x10013de0`    | map A を**水平**ボックス平均し、画素へ適用                    | 行           |

### パス2/3 のボックス平均

[`box_blur.md` §4](../common/box_blur.md) の3フェーズそのままで、
**除数は常にカーネル幅 `2r+1`**。つまり画像の外はゼロ(=「キー色」)として
平均される。`verify_border_chain.py` がフェーズ構成を
`sum(src[i-r : i+r+1]) / (2r+1)` と全数照合している。

これは実害のある性質で、**キー色が1画素も無い画像でも、`境界補正 > 0` なら
上下左右 `r` 行分のアルファが落ちる**(リファレンス実装の自己検証で確認)。

### パス3 ―― 積とコントラスト伸張

```
A = 4096 - 4096/r
B = 4096 - (4096/r)*r          // = 4096 mod r

v = (水平ボックス平均(map A) * map B[y][x]) >> 12      // ブレンドではなく
t = (v - A) * r + B                                     // 傾き r の伸張

if v == 0 || t <= 0:  a = 0
else:                 a = (a * t) >> 12
```

- **ぼかした値と元の値の積**を取るのが要点。単純にぼかしただけでは前景側へ
  にじむが、元のマットを掛けることでキー側は 0 のまま保たれる。
- 伸張は `t(4096) == 4096` が全 `r` で厳密に成り立つ(`B` が `4096 mod r` に
  なっているのはそのため)。不透明な内部は不透明のままである。
- `r = 1`(既定)は `A = B = 0`・傾き1、つまり**恒等**。既定値ではマットが
  3×3 でぼけるだけで、伸張は何もしない。
- `r` を上げると `A` 未満がすべてアルファ0に落ちる。`r = 5` では
  `ぼかし*元/4096 > 3277`(80%)を超えないと生き残れない。

結果として `境界補正` は**フェザーではなく、柔らかい肩を持つ収縮(erosion)**で、
境界を前景側へおよそ `r` 画素分食い込ませる(`verify_border_chain.py` の
ステップエッジ例)。緑の縁取りを削るための機能と読める。

### パス3 の色差補正

`境界補正 > 0` では、**`色彩補正` がオフでも色差が書き換わる**。違うのは
アンミックスの係数 `f` の作り方だけである:

| `色彩補正` | `f`                                   |
| ---------- | ------------------------------------- |
| オフ       | `max(t, (key_sat - sat)*4096/key_sat)` |
| オン       | `max(map C[y][x], (key_sat - sat)*4096/key_sat)` |

オフのときは伸張後の被覆率 `t` がそのまま使われるので、`t == 4096` の
内部画素は素通りし、**補正が効くのは境界の帯だけ**になる。名前のとおり
「境界」の補正であり、`色彩補正` は同じ補正を画像全体へ広げるスイッチ、
という関係になっている。

`透過補正` を読むのは `0x10013de0`(`色彩補正` オン)だけなので、ここでも
`色彩補正` オフでは無効である。

> map C は 16bit スロットに `hue_excess` をクランプ無しで書く。
> `色相範囲 = 0` かつキー色のちょうど反対側の色相を持つ画素では
> `hue_excess = 32768` が `-32768` へ折り返す。後段の `max` に潰されるだけで
> 実害は無いが、唯一のオーバーフローである。

## 10. 未確定事項

- **`境界補正` の3パスは画像が `2r+1` より小さいと枠外へ書く**。フェーズ2は
  `r+1` 回、フェーズ4は `r` 回を無条件に回し、先行・後行ポインタのどちらにも
  上限が無い。パス2の溢れは map A から map B の領域へ、パス3の溢れは画素
  バッファ内へ落ちる。`r ≤ 5` なので幅か高さが 11 未満のオブジェクトでしか
  起きず、確保済みバッファ内には収まるはずだが、**着地先は追っていない**
  ([`box_blur.md` §4](../common/box_blur.md) の既知 overrun 2件と同じ性質)。
- **`色彩補正` オフでも `境界補正 > 0` なら色差が書き換わる**ことは命令列で
  確認したが、これが意図された設計なのかコードの流用なのかは判断材料が無い。
  UI 上は「境界補正」という名前と整合するので、意図的と読んでいる。
- **`fp+0xE4`** の中身。スポイトの起動 `table[0x68]` に渡している値だが、
  exedit 側の何を指すかは追っていない。
- **`0x1e1b` / `0x1e1d` の ID 体系**。`0x1e1b` が `閃光`・`グロー` の
  `光色の設定` ボタンと同じ ID であることから「チェックボックス配列の
  ボタン枠に割り当てられる固定 ID」と読んでいるが、割り当て側は未追跡。
- **スポイトが読む画素**。`0x1e1d` で届く `PIXEL_YC` を exedit のどのバッファ
  から取っているか(合成前か後か、ズーム中の補間の有無)は本エフェクトの
  コード外にある。
- `rand()` や `fpip->frame`(`+0x1C`)を読む箇所は無いので、同じ入力に対する
  出力は完全に決定的である。

以下は全エフェクト共通の未確定事項。詳細は
[`rgb_ycbcr.md` §3](../common/rgb_ycbcr.md) 参照:

- 最終的な YCbCr→RGB 変換とそのクリップは `aviutl.exe` 側にあるため、
  本プロジェクトの解析対象外。
