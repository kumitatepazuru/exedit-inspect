# 凸エッジ (convex edge) フィルタ リバースエンジニアリング解析

対象: `data/exedit.auf`(AviUtl 拡張編集の標準フィルタプラグイン)、32bit PE、
`ImageBase = 0x10000000`。以下のアドレスはすべて VA(`RVA = VA - 0x10000000`)。

## 再現方法

すべてのスクリプトは本プロジェクトの `main.py` を踏み台にして実行する。
`main.py` はコマンドラインで指定されたスクリプトに対して、DLLパス
(デフォルト `data/exedit.auf`)とヘッダー一覧(デフォルト `data/filter.h`)を
渡す役割を持つ。

```
uv run main.py inspect/convex_edge/<script>.py
uv run main.py tools.<tool>            # エフェクト非依存の共通ツール。一覧はリポジトリ直下の README
```

## 0. 何をするエフェクトか

**アルファチャンネルの方向微分を、その画素の輝度に足す。** つまりシルエットを
高さマップとみなした**面取り(ベベル)/エンボス**である。

```
d(x,y)   = trunc( K * Σ_{k=1..steps} [ a(p + o_k) - a(p - o_k) ] )
o_k      = ( floor(k*dx / 65536), floor(k*dy / 65536) )
(dx, dy) = ( trunc(-sin(角度)*65536), trunc(cos(角度)*65536) )
K        = 高さ_raw / (200 * steps)

d >= 0 または y <= 0 :  out = (y + d, cb, cr, a)                    // 明側: 加算
それ以外             :  ny = max(0, y + d)
                        k  = trunc(4096 * ny / y)
                        out = (ny, (cb*k)>>12, (cr*k)>>12, a)       // 暗側: 乗算
```

方向ベクトルが**向いている側の縁が明るくなり、反対側の縁が暗くなる**。
既定の `角度 = -45.0` はベクトルが右下を向くので左上の縁が光る ――
「光源が左上にある」という標準的な見え方になる。

**アルファは素通りする。** キャンバスも動かない。だから `縁取り` や `シャドー`
のようにオブジェクトの外へはみ出すことはなく、陰影はすべてシルエットの内側で
完結する。

## 1. 登録エントリ ―― 846バイト、UI コードは1バイトも無い

| 項目                                                       | 値                                                                       |
| ---------------------------------------------------------- | ------------------------------------------------------------------------ |
| `FILTER_DLL`                                               | `0x1009ecb0`(配列の [36] 番目)、`flag = 0x20`(オブジェクトのフィルタ効果) |
| `func_proc`                                                | `0x10007a80`                                                             |
| `func_init` / `func_exit` / `func_update` / `func_WndProc` | **すべて NULL**                                                          |
| `FILTER+0x58`                                              | **NULL**(設定ウィンドウ更新エントリすら無い)                            |
| `ex_data`                                                  | **0バイト**。`ex_data_def` も `+0x70` フィールド表も NULL                |
| `+0x74`                                                    | `0x1009ec9c`。表示スケール `{1, 100, 10}` 以外は**3スロットとも NULL**   |
| 入力バッファ                                               | `*(fpip+0xAC)`。**読み取り専用**。近傍から読むのは**アルファだけ**       |
| 出力バッファ                                               | `*(fpip+0xB0)`。全画素を書いたあとポインタを入れ替える                   |

このエフェクト固有のコードは `0x10007a80`〜`0x10007dcd` の連続した
**846バイト・261命令・2関数**だけで、**本リポジトリで解析した中で最小**である
(これまで最小だった `ルミナンスキー` の 959バイトを下回る)。直前の
`0x10007a70` は `直前オブジェクト` の5命令の `func_proc`、直後の `0x10007dd0` は
共有の `mov eax,1 ; ret` スタブで、どちらも無関係(`verify_registration.py` §2)。

**チェックボックスもコンボボックスもボタンも `ex_data` も無い**ので、
`ルミナンスキー` のように「UI は全部共有コード」ですらなく、**UI に関わる
コードが存在しない**。トラックバー3本の数値表示は AviUtl 本体の汎用描画が
`+0x74` の表示スケールだけを見て行う
([`param_scaling.md` §1](../common/param_scaling.md))。

登録構造体を全100件見ると、トラックバーだけで `ex_data` もチェックボックスも
コールバックも持たない登録は20件ある(`座標`、`透明度`、`シャープ`、
`斜めクリッピング` ほか)。解析済みのうち `ぼかし` と `拡散光` もここに顔を出すが、
それは**フレーム版が `サイズ固定` を落とした結果**であって、オブジェクト版は
チェックボックスを持つ。**オブジェクト効果としてこの形なのは解析済みで
`凸エッジ` が初めて**である(`verify_registration.py` §1)。

### 呼び出す先も、触る場所も少ない

- **直接呼び出しは CRT `_ftol`(`0x10091ad8`)の1本だけ。** 間接呼び出しも
  `exfunc->exec_multi_thread_func`(`fp->exfunc + 0xCC`)の1本だけ。
- **`table[0x44]` / `table[0x48]`(矩形転送 / 矩形クリア)を呼ばない。**
  したがってキャンバス拡張の4方式([`canvas_growth.md`](../common/canvas_growth.md))の
  どれにも当てはまらない ―― `凸エッジ` は外接矩形を変えない(§7)。
- **`0x10624dd3`(共有の `/1000` マジック除算)が1つも無い。**
  `クロマキー`/`カラーキー`/`ルミナンスキー` と同じ性質
  ([`param_scaling.md` §2](../common/param_scaling.md))。
- 触る `FILTER_PROC_INFO` のフィールドは `+0x00`(flag)/ `+0xAC` / `+0xB0` /
  `+0xB4` / `+0xB8` / `+0xEC` の6つだけ。**`+0xF0`(確保行数)も
  `+0xD4`/`+0xD8`(中心補正)も `+0x1C`(フレーム番号)も読まない**ので、
  出力は入力に対して完全に決定的である。

グローバルは4個で、参照はすべて846バイトの中に閉じている(`tools.xrefs` の
バイト走査):

| アドレス     | 中身                                        |
| ------------ | ------------------------------------------- |
| `0x100d7588` | `scale = 高さ_raw / (200 * steps)` (double) |
| `0x100d7590` | `steps`(実際にサンプルする回数)            |
| `0x100d7594` | `dy = trunc( cos(角度) * 65536)`            |
| `0x100d7598` | `dx = trunc(-sin(角度) * 65536)`            |

## 2. パラメータ ―― トラックバー3本だけ

| トラックバー | 生値の範囲  | 初期値   | 表示スケール | 表示範囲      | 内部での使われ方                          |
| ------------ | ----------- | -------- | ------------ | ------------- | ----------------------------------------- |
| `幅`         | 0〜100      | **4**    | 1            | 0〜100        | サンプル回数 = 効果が届く画素数           |
| `高さ`       | 0〜300      | **100**  | 100          | 0.00〜3.00    | 輝度の振れ幅。上限は `±2048 * 高さ`       |
| `角度`       | -3600〜3600 | **-450** | 10           | -360.0〜360.0 | 方向ベクトル。`0.0` = 真下、正で時計回り  |

**ドラッグ範囲(`+0x74` のスロット2/3)が無い**ので、スライダーは生値の範囲
いっぱいを動く。グループ化マーカーも無いので3本は独立扱い。

早期リターンは `幅 == 0` の1本だけ(`0x10007a8f`)。`高さ = 0.00` でも `角度` が
何でもパイプラインは最後まで走る ―― `高さ = 0` は**`w*h*幅` 回のサンプリングを
全部やってから完全な複製を書く**、いちばん高価な恒等写像である
(`verify_shading.py` §6)。

### `幅` のクランプ ―― オブジェクトの寸法に対してだけ

```
幅 = min(幅, trunc(w/2), trunc(h/2))          // 0x10007a99〜0x10007ab9
```

`ライト` の `trunc(寸法/2) - 2` や `発光` の `寸法/2 - 1` と同型だが、
**確保済みバッファ(`fpip+0xEC` / `+0xF0`)に対するクランプが無い**のが違う。
必要が無いからで、ワーカーは全サンプルをオブジェクト矩形に対して範囲判定して
から読む(§4)。クランプ後に `幅 <= 0` になったら(= 幅か高さが 2px 未満)
`0x10007b2b` でやはり `return 1` する ―― **どちらの早期リターンもバッファを
入れ替えない**ので、オブジェクトは完全に無傷で残る。

## 3. `角度` → Q16 方向ベクトル(共有の定型)

```
t  = 角度_raw * (-pi/1800)          // 0x1009a3f8。角度は 1/10 度単位
dx = trunc(sin(t) * 65536)         // = trunc(-sin(角度) * 65536)
dy = trunc(cos(t) * 65536)         // = trunc( cos(角度) * 65536)
```

`_ftol` は0方向切り捨て。得られる2値は **Q16(`65536` = 1画素)** で、以降は
整数演算しか出てこない。

この形は `凸エッジ` 固有ではなく、`方向ブラー`・`フレームバッファ`・
`斜めクリッピング`・`グラデーション` が同じ命令列を持つ ―― 詳細と符号の2系統は
[`angle_vector.md`](../common/angle_vector.md) にまとめた。`凸エッジ` は
**負の定数 `0x1009a3f8` を使うイメージ内唯一の参照元**だが、これは `fld st(0)` で
角度を1回しか読まないための綴りの違いにすぎず、`方向ブラー` の
`sin(t) * (-65536)` と**全 7201 通りでビット単位に一致する**
(`verify_direction.py` §2)。

| `角度`        | `(dx, dy)`       | 単位ベクトル       | 画面上の向き | 明るくなる縁 |
| ------------- | ---------------- | ------------------ | ------------ | ------------ |
| `0.0`         | `(0, 65536)`     | `(0, +1)`          | 下           | 上辺         |
| `-45.0`(既定) | `(46340, 46340)` | `(+0.707, +0.707)` | 右下         | 左上         |
| `-90.0`       | `(65536, 0)`     | `(+1, 0)`          | 右           | 左辺         |
| `+90.0`       | `(-65536, 0)`    | `(-1, 0)`          | 左           | 右辺         |
| `180.0`       | `(0, -65536)`    | `(0, -1)`          | 上           | 下辺         |

## 4. サンプリング ―― 点対称な有限差分

ワーカー(`0x10007b90`)は `exec_multi_thread_func` から**行単位**で起動され、
画素ごとに次を回す:

```
acc = (0, 0) ;  sum = 0
for k = 1 .. steps:
    acc += (dx, dy)                       // int32 の単純加算
    o    = (acc.x >> 16, acc.y >> 16)     // sar = floor
    if (x+o.x, y+o.y) がオブジェクト矩形の中:  sum += a(x+o.x, y+o.y)
    if (x-o.x, y-o.y) がオブジェクト矩形の中:  sum -= a(x-o.x, y-o.y)
```

要点が4つある。

**(a) オフセットは `floor(k*dx/65536)` そのもの。** 累積は整数加算なので誤差が
溜まらず、`sar` が floor なので `k*dx` が `2^31` を超えなければ厳密に一致する
―― `幅 ≤ 100` かつ `|dx| ≤ 65536` なので最大 6,553,600、溢れる余地は無い
(`verify_direction.py` §3)。

**(b) 後ろ側のサンプルは `-(o)` であって `floor(-k*dx/65536)` ではない。**
2度目の floor を掛けないので**サンプル対は画素を中心に厳密に点対称**になり、
和は素直な符号付き微分になる。`dx = 46340`・`k = 1` では前者が `0`、後者なら
`-1` で、両者は `k*dx` が `65536` の倍数でない限り常に食い違う。

**(c) 4本の範囲判定は内側ループの中にある。** 枠外のサンプルは「透明として
数える」のではなく**何も足さない**(前後どちらの項も独立に判定される)。
したがって [`box_blur.md` §4](../common/box_blur.md) が集めているスライディング
ウィンドウの枠外読み・枠外書きは `凸エッジ` には**構造的に存在しない**。
`縁取り` が事前パディングで塞いだ穴を、こちらは素朴な `if` で塞いでいる ――
3フェーズ分割による高速化を最初から諦めた形である。

**(d) 到達距離は `幅` 画素(ユークリッド)。** 各成分の絶対値は `k` を超えず、
斜め方向でも長さは `幅 ± √2` に収まる。**成分ごとの上界は `幅` で厳密**
(`verify_direction.py` §4)。

### `k = 1` が丸ごと死ぬ象限がある

`-90.0 < 角度 < 0.0` では `dx` も `dy` も開区間 `(0, 65536)` に入るので、`k = 1`
のオフセットが `(0, 0)` になり、その項は `a(p) - a(p) = 0` になる。
**7201通りの生値のうち 1798通りがこれに当たり、既定値 `-45.0` はその真ん中**
である(`verify_direction.py` §5)。

他の3象限では少なくとも片方の成分が負で、floor が `-1` へ落とすので必ず実在の
隣接画素を指す ―― `sar` が floor である副作用がそのまま「第4象限だけ1サンプル
損をする」という非対称になっている
([`angle_vector.md` §4](../common/angle_vector.md))。

損は `幅` 分の1で、既定の `幅 = 4` なら 25%。ふつうは「45度の面取りが44度の
それよりわずかに柔らかい」程度だが、**`幅 = 1` と組み合わせると唯一のサンプルが
死んで完全な恒等写像になる**(§8)。

### 対角では同じ画素を2回数える

ステップのユークリッド長が1画素なので、45度方向では各成分が1ステップあたり
`0.707` しか進まない。`幅 = 8` なら8個のオフセットのうち最大2個が重複する
(軸方向では0個)。重複した項は2回足されるので**方向によってわずかに重み付けが
変わる**が、和を `steps` で正規化しているので振れ幅は変わらない(§5)。

## 5. 出力エンコード ―― 暗側は乗算、明側は加算

```
d = trunc(sum * scale)                       // scale = 高さ_raw / (200*steps)

if d >= 0 || y <= 0:                         // 0x10007d0d / 0x10007d11
    out = (y + d, cb, cr, a)                 // クランプ無し
else:
    ny = max(0, y + d)                       // 0x10007d15 の jns、唯一のクランプ
    k  = trunc(4096 * ny / y)                // idiv
    out = (ny, (cb*k)>>12, (cr*k)>>12, a)    // sar なので色差は floor
```

命令上は4分岐だが、`ny < 0` の枝(`ny = 0, k = 0`)は `max(0, y+d)` と
`trunc(4096*0/y)` が返すものと同じで、**除算を避けるための近道であって特別扱い
ではない**。上の閉じた式との一致は、表現可能な `y` 全4097通り × `d` の到達域
(-10240〜4096)を走った 4097×2049 通りと、負の `y` を含む追加の走査で確認済み
(`verify_shading.py` §2)。

### 暗側が乗算であることの意味

`Y` も `Cb` も `Cr` も同じ係数 `ny/y` で縮むので、BT.601 の逆変換
([`rgb_ycbcr.md` §3](../common/rgb_ycbcr.md))を通すと **R・G・B が揃って同じ
係数倍**になる ―― 色相も彩度も保ったまま黒へ向かう、物理的な「陰」の形。

明側は `Y` に足すだけで色差はそのままなので、R・G・B に**同じ絶対量**が乗る
―― 白飛びに向かって彩度が落ちる、物理的な「ハイライト」の形。

| `d`   | 経路 | 出力 `(Y, Cb, Cr)`   | RGB(概算)           | 元との比             |
| ----- | ---- | -------------------- | -------------------- | -------------------- |
| -1024 | 暗   | `(1024, -450, 750)`  | `(2076, 643, 227)`   | `(0.50, 0.50, 0.50)` |
| -1536 | 暗   | `(512, -225, 375)`   | `(1038, 322, 113)`   | `(0.25, 0.25, 0.25)` |
| +512  | 明   | `(2560, -900, 1500)` | `(4663, 1799, 965)`  | `(1.12, 1.40, 2.13)` |
| +1024 | 明   | `(3072, -900, 1500)` | `(5175, 2311, 1477)` | `(1.25, 1.80, 3.26)` |

(元画素 `Y=2048, Cb=-900, Cr=1500` = RGB 概算 `(4151, 1287, 453)`)

**「色を掛ける側」と「色を足す側」が1つのエフェクトの中に同居しているのは
解析済みで `凸エッジ` だけ**である。`ライト` の陰影パスは
`out.c += (光色C * m) >> 12` で明暗どちらも加算、`発光`/`グロー` はどちらも
乗算である([`rgb_ycbcr.md` §4](../common/rgb_ycbcr.md))。

### クランプは1箇所しか無い

`jns`(`0x10007d15`)による「暗側の下限0」だけ。上限は無いので `y + d` は 4096 を
超える(`高さ = 3.00` なら最大 10240 = 250%)。`y ≤ 0` の画素が暗側に振られると
加算経路に落ちるので、**真っ黒な画素は負の輝度になり、色差はそのまま残る**。
16bit へ格納するが、表現可能域の入力から `int16` を溢れることは無い
(`verify_shading.py` §4)。満輝度超過の行き先は `aviutl.exe` のクリップ次第で、
全エフェクト共通の未確定事項である。

### `d` の振れ幅は `幅` に依らない

```
|sum| ≤ steps * 4096
     →  |d| ≤ steps * 4096 * 高さ_raw / (200*steps) = 20.48 * 高さ_raw
```

**`steps` が約分される。** だから `幅` は面取りの**広さ**だけを決め、`高さ` が
**深さ**だけを決める ―― 描画品質フラグ(§6)がサンプル数を間引いても見た目の
強さが変わらないのはこの性質のおかげである。

| `高さ` 表示   | `高さ` raw | `|d|` 上限 | 意味                                     |
| ------------- | ---------- | ---------- | ---------------------------------------- |
| 0.00          | 0          | 0          | 完全な複製(ただし全走査はする)          |
| 1.00(既定)   | 100        | 2048       | 硬い縁で輝度が満輝度の半分動く           |
| 2.00          | 200        | 4096       | 硬い縁で 0〜4096 の全域を動ける          |
| 3.00          | 300        | 6144       | 150% 超過。上側はクリップ、下側は0止まり |

唯一の丸め誤差はここにある ―― `scale` が x87 の double 除算1回を通るので、
`(高さ, steps)` の 30100 通りのうち **22通りで振れ幅が 1 だけ小さくなる**
(`verify_shading.py` §1)。エフェクト中で丸めが結果を変えうるのはこの1除算と
`_ftol` 3本だけである。

### 段差に対する応答

`角度 = -90.0`(方向 = 右)、`幅 = 8`、`高さ = 1.00`、`u = 0` がオブジェクトの
最初の不透明画素、元の輝度 2048:

| `u` | α    | `sum` |  `d` | 出力 Y | 見える |
| --- | ---- | ----: | ---: | -----: | ------ |
| -8  | 0    |  4096 |  256 |   2304 | ―      |
| -4  | 0    | 20480 | 1280 |   3328 | ―      |
| -1  | 0    | 32768 | 2048 |   4096 | ―      |
| 0   | 4096 | 32768 | 2048 |   4096 | ○      |
| 2   | 4096 | 24576 | 1536 |   3584 | ○      |
| 4   | 4096 | 16384 | 1024 |   3072 | ○      |
| 7   | 4096 |  4096 |  256 |   2304 | ○      |
| 8   | 4096 |     0 |    0 |   2048 | ○      |

**帯の幅は `2*幅` 画素で、`u = -1` と `u = 0` の2画素が同時にピーク**を取る。
ところが外側の半分はアルファ 0 の上に乗っているので見えない ――
**アルファを素通りさせる**設計の結果、見える面取りはちょうど `幅` 画素になり、
そこから線形に 0 へ落ちる(`verify_shading.py` §5)。

## 6. 描画品質フラグ `fpip->flag & 0x200`

```
if (fpip->flag & 0x200) && 幅 > 16:            // 0x10007af2 / 0x10007af7
    dx    = c_div(dx * 幅, 16)
    dy    = c_div(dy * 幅, 16)
    steps = 16
```

**ステップを `幅/16` 倍に伸ばして本数を16に減らす**ので、到達距離も
(`scale` が `steps` を含むので)振れ幅も保たれる。実測でも最遠サンプルのずれは
1画素以内(`verify_direction.py` §6)。判定は `幅 > 16` の**真の不等号**なので、
`幅 = 16` は間引かれない。

ワーカー自身はフラグを読まない ―― `func_proc` が結論をグローバルへ焼き込むだけ
である。`閃光`/`放射ブラー`/`方向ブラー` が同じフラグでサンプル数を 50 で頭打ちに
するのに対し、`凸エッジ` は 16
([`filter_registration.md` §3](../common/filter_registration.md))。

## 7. キャンバスを動かさない

`凸エッジ` は `table[0x44]` も `table[0x48]` も呼ばず、`fpip+0xB4`/`+0xB8`
(幅・高さ)も `fpip+0xD4`/`+0xD8`(中心補正)も**書かない**。効果がシルエットの
外へ出ないので広げる必要が無く、`サイズ固定` に相当するチェックボックスも
存在しない(`verify_registration.py` §4)。

キャンバスを動かさないエフェクトは他にもある(`境界ぼかし`・`モザイク`・
`クロマキー`/`カラーキー` の `境界補正`)が、**理由が違う**。それらは
「結果がオブジェクトの外へはみ出さない」から広げないのに対し、`凸エッジ` は
**アルファを1ビットも書き換えない**から広げようが無い ―― 出力の Y/Cb/Cr が
どれだけ振れてもシルエットは入力そのままで、外接矩形が動く余地が原理的に無い。
**近傍を読みながら色だけを書き、アルファに触れないのは解析済みでこれだけ**
である(`縁取り`/`シャドー` はアルファを作る側、`境界ぼかし`/抜き系は
アルファを削る側)。

`*(fpip+0xB0)` は全画素が無条件に書かれるので事前クリアも要らない。最後に
ポインタを入れ替えるだけ(`0x10007b77`)。

## 8. 参照テーブル

`幅`(既定 4):

| raw | サンプル数 | 見える面取りの幅 | `角度 = -45.0` での実効オフセット (x,y) |
| --- | ---------- | ---------------- | --------------------------------------- |
| 1   | 1          | ―                | `(0,0)` ―― **完全に何も起きない**       |
| 4   | 4          | 4 px             | `(0,0),(1,1),(2,2),(2,2)`               |
| 8   | 8          | 8 px             | 上に加え `(3,3),(4,4),(4,4),(5,5)`      |
| 100 | 100        | 100 px           | 幅・高さの半分でクランプされる          |

> **`幅 = 1` かつ `-90.0 < 角度 < 0.0` は完全な恒等写像になる。** 唯一の
> サンプルが `k = 1` の死んだ枝に当たるので `sum` が常に 0 になるためで、
> 既定の `角度` を動かさずに `幅` だけを 1 にすると「エフェクトが効かない」。
> `角度 = 0.0` などに変えれば `幅 = 1` でも効く。

`角度`(既定 -45.0):

| raw   | 表示   | 明るくなる縁 | `k=1` が死ぬか |
| ----- | ------ | ------------ | -------------- |
| -900  | -90.0  | 左           | いいえ         |
| -450  | -45.0  | 左上         | **はい**(既定) |
| -1    | -0.1   | ほぼ上       | **はい**       |
| 0     | 0.0    | 上           | いいえ         |
| 900   | 90.0   | 右           | いいえ         |
| 1800  | 180.0  | 下           | いいえ         |

既定値 `幅 = 4, 高さ = 1.00, 角度 = -45.0` を 28×28 の平坦な `Y = 2048` の
オブジェクトに掛けると、左上の縁が `3584`、右下の縁が `512`、内部は `2048` の
まま(`simulate_convex_edge_reference.py`)。

## 10. 未確定事項

- **x87 の `fsin`/`fcos` と libm の食い違い。** `sin(角度)*65536` が整数のすぐ
  近くに落ちる (角度, 成分) の組が **34個**あり、すべて 30度の倍数である。
  そこでは Q16 成分が 1 ずれうる ―― `32768`(= 0.5)か `32767` かで
  `floor(2*d/65536)` が `1` か `0` に分かれるので、サンプル1個が1画素動く。
  実機がどちらを返すかは確認していない
  ([`angle_vector.md` §5](../common/angle_vector.md))。
- **x87 の精度制御(53bit か 64bit か)。** `scale` の除算が §5 のとおり
  30100通り中22通りで境界に落ちる。`シャドー`(5.41%)や `縁取り`(50601通り中
  5通り)と同じ未確定事項で、差はどれも1単位。
- **`fpip->flag & 0x200` を exedit 側がいつ立てるか。** 全エフェクト共通。
  `凸エッジ` の読みは「サンプル数を16で頭打ちにしてよい」で一貫している。
- **`高さ` の表示スケールが 100 なのに内部の除数が 200 である理由。**
  `fmul 0.5`(`0x1009a3b0`)を挟むのは「`高さ = 2.00` で満輝度」を意図した設計に
  見えるが、コード上の根拠はその定数そのものしかない。
- **他の4エフェクト(`方向ブラー` / `フレームバッファ` / `斜めクリッピング` /
  `グラデーション`)の軸の割り当て。** Q16 の2値を同じ命令列で作るところまでは
  確認したが、`sin` 側を x に使っているかはワーカーを読んでいない
  ([`angle_vector.md` §6](../common/angle_vector.md))。
- **`fpip+0xEC`(確保行幅)の実際の値。** ワーカーの行の刻みに使うだけで、
  クランプには一切使わない ―― 使わないこと自体は確認済みだが、値そのものは
  他エフェクトと同じく追っていない。

以下は全エフェクト共通の未確定事項:

- 最終的な YCbCr→RGB 変換とそのクリップは `aviutl.exe` 側にあるため、満輝度
  超過(`高さ ≥ 2.00`)や負の輝度が画面上でどう出るかは推定にとどまる
  ([`rgb_ycbcr.md` §3](../common/rgb_ycbcr.md))。
- BT.601 の**逆**変換係数は順変換からの推定であり、§5 の「暗側は R・G・B が
  同じ係数倍」という主張はその推定に乗っている。ただし「3成分に同じ係数」と
  「3成分に同じ加算」という**形**の対比は、輝度を無彩色軸に持つ任意の線形変換で
  成り立つ。
