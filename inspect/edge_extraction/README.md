# エッジ抽出 (edge extraction) フィルタ リバースエンジニアリング解析

対象: `data/exedit.auf`(AviUtl 拡張編集の標準フィルタプラグイン)、32bit PE、
`ImageBase = 0x10000000`。以下のアドレスはすべて VA(`RVA = VA - 0x10000000`)。

## 再現方法

すべてのスクリプトは本プロジェクトの `main.py` を踏み台にして実行する。
`main.py` はコマンドラインで指定されたスクリプトに対して、DLLパス
(デフォルト `data/exedit.auf`)とヘッダー一覧(デフォルト `data/filter.h`)を
渡す役割を持つ。

```
uv run main.py inspect/edge_extraction/<script>.py
uv run main.py tools.<tool>            # エフェクト非依存の共通ツール。一覧はリポジトリ直下の README
```

| スクリプト                                | 確認していること                                                                                                                                       |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tools.filter_table --name エッジ抽出`    | `FILTER_DLL` 配列(先頭 `0x100a3e28`)をたどり、登録エントリ・トラックバー・チェックボックスを抽出。登録は**1個だけ**(オブジェクト効果のみ)          |
| `decompile_edge_extraction.py`            | `0x10022d60`〜`0x10023c73` に絞った `CFGFast` + angr デコンパイル。`func_proc` に画素ループが無いこと、3ワーカーが互いに独立していることが分かる          |
| `disasm_params.py`                        | `func_proc` の全命令に注釈。2本のトラックバー変換、光色の分解、3分岐、バッファ入れ替え                                                                 |
| `verify_param_scaling.py`                 | `強さ` は `/1000`、`しきい値` は **`/10000`** の別マジック。全 raw 値(10001通り / 20001通り)で `trunc(raw*4096/d)` と一致。飽和する `強さ` の水準も算出 |
| `verify_dispatch.py`                      | チェックボックス2個 → 3ワーカーの対応、`func_WndProc` が2つを**排他**にしていること、exedit のコントロールID `0x1e19`〜`0x1e1c` の意味と受け手の一覧    |
| `verify_prewitt_taps.py`                  | **本命**。線形形式の抽象解釈でワーカーの命令列を実行し、8近傍のタップ位置と2つの勾配の係数行列を**導出**する。3ワーカーとも Prewitt に一致              |
| `verify_alpha_weight.py`                  | 各近傍が**自分のアルファでプリマルチプライ**されてから畳み込まれること(3分岐が1つの式であること)、`透明度エッジ` にはその分岐が無いこと                |
| `verify_output_encoding.py`               | `sqrt` → `-しきい値` → `×強さ` → `[0,4096]` クランプ → 光色＋`src.a×e` の出力。`色エッジ` が**平方根を3回**取って足すこと                            |
| `verify_border.py`                        | 外周1画素が必ず「光色＋アルファ0」で潰されること、行のスレッド分割と `h < thread_num` での重複書き込み                                                 |
| `verify_ex_data.py`                       | `ex_data` に `no_color` フィールドが**無い**こと。色ダイアログのフラグ `2` / `0x102` が全呼び出し元で `no_color` の有無と一致すること                  |
| `simulate_edge_extraction_reference.py`   | 上記すべてを織り込んだ整数忠実リファレンス実装と、モードごとの見え方のデモ                                                                             |

## 1. 一言でいうと

**Prewitt オペレータでエッジの強さを求め、それを「光色1色の画像のアルファ」に
する**フィルタ。出力の y/cb/cr は `色の設定` の値そのもので、元画像の色は
1画素も残らない ―― 合成もブレンドも一切せず、オブジェクトを**置き換える**。
元画像の上に線画を重ねたければ、オブジェクトを複製してどちらか一方にだけ
掛ける必要がある。

```
Gx = [[-1, 0, +1],      Gy = [[-1, -1, -1],
      [-1, 0, +1],            [ 0,  0,  0],
      [-1, 0, +1]]            [+1, +1, +1]]

mag   = trunc(sqrt(Gx² + Gy²))                 // 対象チャンネルごとに1回
e     = clamp(((Σmag - しきい値) * 強さ) >> 12, 0, 4096)
out   = (光色Y, 光色Cb, 光色Cr, (src.a * e) >> 12)
```

Sobel ではなく Prewitt(中央タップの重み2が無い)であることは
`verify_prewitt_taps.py` が命令列から係数行列を導出して確認している。

## 2. 登録エントリ

登録は**1個だけ**で、`flag = 0x20`(オブジェクトのフィルタ効果)。フレーム
フィルタ版は構造体ごと存在しないので、`fp->flag & 0x20` の分岐も6バイト画素の
経路も**コード上に無い**([`filter_registration.md` §2](../common/filter_registration.md))。

|                  | 値                                                                    |
| ---------------- | --------------------------------------------------------------------- |
| `FILTER_DLL`     | `0x100a2bb0`、`flag = 0x20`                                           |
| `func_proc`      | `0x10022d60`                                                          |
| `func_WndProc`   | `0x10023af0`                                                          |
| `FILTER+0x58`    | `0x10023c60`(設定ウィンドウ更新エントリ)                             |
| `ex_data`        | 4バイト、既定 `0x00ffffff`。`+0x70` フィールド表は `0x100a2b4c`       |
| `+0x74` 拡張ブロック | `0x100a2b84`。表示スケールだけを持ち、ドラッグ範囲は **NULL**     |
| 入力画像         | `*(fpip+0xAC)`、8バイト/画素 PIXEL_YCA(y, cb, cr, a)                 |
| 出力             | `*(fpip+0xB0)`。`func_proc` 末尾で `0xAC` と**入れ替える**            |
| 幅・高さ・行幅   | `*(fpip+0xB4)` / `*(fpip+0xB8)` / `*(fpip+0xEC)` [画素]               |

`func_proc` は 0xc9 バイトしかなく、画素に一切触らない。やることは
「2つのグローバルにパラメータを書く / 光色を YCbCr に分解する /
`exec_multi_thread_func` を1回呼ぶ / バッファを入れ替える」だけ。

**早期 return が1つも無い**。`強さ = 0` でも全画素を走査して完全な透明画像を
書く(`ぼかし` / `閃光` / `拡散光` / `グロー` は早期 return する ―
[`param_scaling.md` §3](../common/param_scaling.md))。

**キャンバス拡張も `サイズ固定` も無い**。出力は入力矩形の内側に収まることが
構造上保証されており([`canvas_growth.md`](../common/canvas_growth.md) の4方式は
どれも当てはまらない)、代わりに外周1画素が捨てられる(手順6)。

## 3. パラメータ変換(`func_proc` 内、フレームごとに1回)

トラックバーは `強さ`(初期値1000、範囲0〜10000)、`しきい値`(0、-10000〜10000)。

| トラックバー | 表示スケール | UI表示範囲     | スライダーで届く範囲 | 生値→内部                    |
| ------------ | ------------ | -------------- | -------------------- | ----------------------------- |
| `強さ`       | 10           | 0.0〜1000.0    | UI表示範囲と同じ     | `trunc(raw * 4096 / 1000)`    |
| `しきい値`   | 100          | -100.00〜100.00 | UI表示範囲と同じ     | `trunc(raw * 4096 / 10000)`   |

**本プロジェクトで初めて、2本のトラックバーが別々の定数除算を使うエフェクト**で
ある。`0x10624dd3 + sar 6`(= /1000、全エフェクト共通)に加えて
`0x68db8bad + sar 12`(= /10000)が出てくる。後者はイメージ全体で4箇所しか
現れない([`param_scaling.md` §2](../common/param_scaling.md))。除数が10倍違うのは
表示スケールが10倍違うからで、意味はどちらも「UI の 100 % = Q12 の 1.0」。
どちらも四捨五入ではなく0方向への切り捨て、クランプ無し
(`verify_param_scaling.py` が全 raw 値で検算)。

`+0x74` 拡張ブロックはスロット `[0]`(表示スケール)だけを持ち、
**ドラッグ範囲のポインタは NULL**(グループ化マーカーも NULL)。ブロックごと
NULL のときと同じくトラックバーの範囲全体がスライダーで届くと読める ――
つまり `強さ` は**スライダーだけで 1000.0(=×10)まで上げられる**。
`tools.track_scale` で全登録を並べると、トラックバーを持つ90エントリのうち
ドラッグ範囲を持たないものが18ある(`凸エッジ`・`縁取り`・`単色化` など)ので、
これ自体は珍しい形ではない。

## 4. 3つのモード ― チェックボックスは実質ラジオボタン

`func_proc` の分岐は `fp->check[]` の2個だけを見る:

| `輝度エッジを抽出` | `透明度エッジを抽出` | ワーカー     | 勾配を取る対象           | 平方根 |
| ------------------ | -------------------- | ------------ | ------------------------ | ------ |
| ON(既定)          | (無視される)         | `0x100234c0` | `y * a`                  | 1回    |
| OFF               | ON                   | `0x10023880` | `a`                      | 1回    |
| OFF               | OFF                  | `0x10022e30` | `y*a`, `cb*a`, `cr*a`    | **3回** |

**両方 ON は4つ目のモードではなく、`check[0]` が勝つだけ**。UI からその状態に
なることはない ―― `func_WndProc`(`0x10023af0`)が「両方1になったら、いま
押していない方を0に戻す」処理を持っているからである。`.exo` を手で書けば
両方1にできるが、そのときは `透明度エッジを抽出` が無視される。

その `func_WndProc` の解読から、exedit の設定ウィンドウのコントロールIDが
確定した(`verify_dispatch.py`):

| ID       | 意味                             | 組み立て場所 | 他に処理しているフィルタ |
| -------- | -------------------------------- | ------------ | ------------------------ |
| `0x1e19` | トラックバーが動いた(位置からの推定) | `0x10041358` | `パーティクル出力`       |
| `0x1e1a` | チェックボックスが変わった       | `0x100413d7` | `パーティクル出力` のみ  |
| `0x1e1b` | ボタンが押された                 | `0x10041456` | 13フィルタ               |
| `0x1e1c` | コンボボックスの選択が変わった   | `0x10041500` | 5フィルタ                |

いずれも `wParam = (コントロールの通し番号 << 16) | ID`、`message = 0x702`。
`0x1e1b` は既知だった([`filter_registration.md` §7](../common/filter_registration.md))。
`0x1e1a` が**チェックボックス**だと分かるのはエッジ抽出のおかげで、
その通し番号(高位ワード)で `fp->check[0]` / `fp->check[1]` を選び分けている。
チェックボックスの通知を処理しているフィルタは、イメージ全体でも
エッジ抽出と `パーティクル出力` の2つだけである。

「どちらもOFF」が一番重い色エッジになるのは UI からは読み取れない。
グレースケール画像では cb = cr = 0 なので `色エッジ` と `輝度エッジ` の出力は
**完全に一致する**(手順5)。差が出るのは彩度が動いているときだけ。

## 5. ワーカーの中身

3ワーカーとも構造は同じで、違うのは「どのチャンネルに対して勾配を取るか」
だけ。互いに1回も `call` し合わず、共通ヘルパーも持たない(唯一の呼び出しは
CRT の `_ftol` `0x10091ad8`)。

### 5.1 タップとカーネル

`verify_prewitt_taps.py` は、レジスタとスタックスロットを
`C`(入力バッファ)・`S`(行幅)・`R`(行オフセット)・各タップのシンボルの
**線形結合**として保持する抽象解釈器でワーカーを実行し、`movsx` の実効アドレスを
すべて `(dy, dx, フィールド)` に還元する。結果:

- 読むのは**8近傍だけ**。中央画素の色は勾配に一切入らない。
- 2つの累算器の係数はそのまま Prewitt の `Gx` / `Gy`。3ワーカー・全チャンネルで
  一致(色エッジは `y`/`cb`/`cr` の3組)。
- Sobel の `±2` はどこにも無い。

`色エッジ` の `Gx` は3チャンネルともスタックスロット
(`[esp+0x10]`/`[esp+0x40]`/`[esp+0x3c]`)、`Gy` はレジスタ(`ebx`/`ebp`/`eax`)に
乗っており、更新のたびにスタックを往復する。手で追うと取り違えやすい箇所で、
この解釈器を書いた理由でもある。

### 5.2 アルファによるプリマルチプライ

`色エッジ` と `輝度エッジ` は、各近傍の色に**その近傍自身のアルファ**を掛けてから
畳み込む(`verify_alpha_weight.py`):

```
a >= 4096      -> v = c                 // そのまま
0 < a < 4096   -> v = (c * a) >> 12     // sar なので floor
a <= 0         -> そのタップは加算されない(= 0)
```

3分岐は `v = c * clamp(a, 0, 4096) / 4096` という1つの式で、両端を分岐で
特別扱いして掛け算を省いているだけ(全数検算済み)。

これの帰結が大きい。**平坦な単色オブジェクトでも、シルエットそのものが
エッジになる** ―― アルファが 4096 → 0 に落ちるところで `y*a` も一緒に落ちる
からである。`輝度エッジを抽出` が既定なのはこのためで、輪郭抽出器と
シルエット抽出器を兼ねている。逆に「オブジェクト内部の模様だけ無視して
外形だけ取りたい」なら `透明度エッジを抽出` を使う。

`>> 12` は `sar`(floor)なので、符号付きの cb/cr では C の `/`(0方向切り捨て)と
食い違う。リファレンス実装を書くときの定番の落とし穴
([`integer_semantics.md`](../common/integer_semantics.md))。

`透明度エッジ` にはこの分岐が無い ―― そこではアルファ自身がサンプルなので、
掛けるものが無い。

### 5.3 出力

```
mag = trunc(sqrt(Gx² + Gy²))          // fild / fsqrt / _ftol。引数は非負なので floor
e   = (Σmag - しきい値) * 強さ >> 12
e   = clamp(e, 0, 4096)
out.y, out.cb, out.cr = 光色           // 無条件。エッジが無い画素にも書く
out.a = (src.a * e) >> 12              // 中央画素が登場する唯一の場所
```

- **中央画素はアルファとしてだけ1回登場する**。完全に透明な領域の中で
  検出されたエッジは捨てられ、結果が元のシルエットの外へ出ることはない。
- `色エッジ` は**チャンネルごとに平方根を取ってから足す**。
  `√a + √b + √c ≥ √(a+b+c)` なので、まとめて1回取るより早く飽和する。
- `しきい値` はゲートではなく**引き算**。負にすると全体が底上げされ、
  勾配が0の平坦部にもアルファが乗る。
- 1チャンネルが到達しうる最大の `mag` は `√10 × 4096 = 12952`
  (`verify_param_scaling.py` が8タップを総当たりして算出)。4096 の3倍以上なので、
  **`強さ` が 33 を超えると全コントラストのエッジはすべて飽和して**しまい、
  それ以上は弱いエッジにしか効かない。既定の 100.0 は完全に飽和側にいる。
  柔らかい輪郭が欲しければ `強さ` を30以下にする。
- 桁溢れは起きない。`色エッジ` の最大和 38856 × `強さ` 40960 = 1.6e9 < 2^31。

## 6. 外周1画素は必ず消える

3×3 の近傍が取れない外周は、クランプもミラーもせず
**「光色＋アルファ0」で塗り潰される**(`verify_border.py`):

| 対象       | 誰が書くか                          |
| ---------- | ----------------------------------- |
| 0行目      | 自分の担当先頭行が0のスレッド       |
| `h-1` 行目 | 自分の担当末尾が `h` のスレッド     |
| 0列目      | 各行ループの先頭                    |
| `w-1` 列目 | 各行ループの末尾                    |

つまり**オブジェクトは必ず外周1画素を失う**。外接矩形いっぱいに広がっている
オブジェクト(`図形` の矩形、`フレームバッファ`、画像ファイルなど)では、
その辺の輪郭が丸ごと出ない。先に `領域拡張` などで余白を作っておくのが対処法。
`w ≤ 2` なら行全体が、`h ≤ 2` なら画像全体が外周になる。

行のスレッド分割は `y0 = h*tid/n`, `y1 = h*(tid+1)/n` で、外周の判定は
**スレッド番号ではなく行番号**に対して行われる。`h < thread_num` のときは
`y0 == 0` のスレッドが複数できて全員が0行目を塗るが、書く値が同じ定数なので
実害は無い(`モザイク` の同種の重複と同じ形 ―
[`モザイク` §4](../mozaic/README.md))。

## 7. `色の設定` ―― 「指定なし」が無いボタン

`check_default = -1` のボタンで、状態は4バイトの `ex_data`(既定 `0x00ffffff`=白)に
入る。ここが `発光` / `閃光` / `グロー` と決定的に違う:

|                        | `発光` / `閃光` / `グロー` / `グラデーション` | `エッジ抽出`      |
| ---------------------- | --------------------------------------------- | ----------------- |
| `+0x70` の4バイト目    | `no_color`(= bit24)                          | **名前無しパディング** |
| 色ダイアログのフラグ   | `0x102`                                       | **`2`**           |
| ラベル生成             | bit24 を見て `指定無し (元画像の色)` に分岐   | 常に `RGB ( %d , %d , %d )` |

色ダイアログは共通の `[fp+0x64]+0x6c` で開く。イメージ内の全呼び出し元を
並べると、**フラグの bit `0x100` が立っているのは `no_color` フィールドを
持つエフェクトだけ**で、例外が無い(`verify_ex_data.py`)。したがって
`0x100` = 「指定なしボタンを出す」と読める。

出力の y/cb/cr が光色そのものである以上、「各画素自身の色」に相当するものが
存在しないので、この選択肢が無いのは仕様として整合している。

**光色の暗さが効果の強さに影響しない**のもこのフィルタの特徴。`発光` や
`グロー` では光色の Y が輝度やアルファに掛かるため暗い色を選ぶと効果自体が
弱まるが([`rgb_ycbcr.md` §4](../common/rgb_ycbcr.md))、エッジ抽出では光色は
どこにも掛からず、そのまま書かれるだけである。

保存形式・変換ルーチン(`sub_1006fed0` → `sub_1006f520`)・BT.601 係数は
他エフェクトと共有なので [`rgb_ycbcr.md`](../common/rgb_ycbcr.md) 参照。

| 25.0    | 250   | 1024  | ×0.25 |
| 100.0   | 1000  | 4096  | ×1.0  |
| 400.0   | 4000  | 16384 | ×4.0  |
| 1000.0  | 10000 | 40960 | ×10.0 |

`しきい値` (`fixed = trunc(raw*4096/10000)`): UI -100.00 → -4096、
0.00 → 0、25.00 → 1024、100.00 → 4096。

| 状況                                 | `mag` | 飽和する `強さ` |
| ------------------------------------ | ----- | --------------- |
| 全コントラストの軸方向ステップ       | 12288 | 33.4            |
| 最大(`√10 × 4096`)                | 12952 | 31.7            |
| 1/4 コントラストのステップ           | 3072  | 133.4           |
