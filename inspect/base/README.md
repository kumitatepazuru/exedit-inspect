# 座標・拡大率・透明度・回転・領域拡張・リサイズ・ローテーション・反転 リバースエンジニアリング解析

対象: `data/exedit.auf`(AviUtl 拡張編集の標準フィルタプラグイン)、32bit PE、
`ImageBase = 0x10000000`。以下のアドレスはすべて VA(`RVA = VA - 0x10000000`)。

この8つは AviUtl の「フィルタ効果の追加」メニューで**オブジェクトに個別に
足せる**、サイズ・座標変更カテゴリの基本エフェクト群。`標準描画`/`拡張描画`
オブジェクトが最初から持っている X/Y/Z 座標・拡大率・透明度・回転の
トラックバーと**名前も見た目もそっくり**で、実装がどこまで同じでどこから
違うのかを1本のドキュメントにまとめる。

## 再現方法

すべてのスクリプトは本プロジェクトの `main.py` を踏み台にして実行する。

```
uv run main.py inspect/base/<script>.py
uv run main.py tools.<tool>            # エフェクト非依存の共通ツール。一覧はリポジトリ直下の README
```

| スクリプト                          | 確認していること                                                                                                                     |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `tools.filter_table --name 座標 --name 拡大率 --name 透明度 --name 回転 --name 領域拡張 --name リサイズ --name ローテーション --name 反転` | 8エフェクトの登録エントリ・トラックバー・チェックボックスを一括デコード |
| `verify_deferred_params.py`         | `座標`/`回転`/`透明度` ―― fpip への Q12/Q16 加算・合成式。回転の `cmp 余り,36000` が原理的に到達不能なことをブルートフォースで確認     |
| `verify_scale_ratio.py`             | `拡大率` ―― `fpip+0xE0`/`+0xE4` に残る「大きい方の候補 + 相対差分(Q16)」という不変条件。angr の分岐形と突き合わせ                     |

## 1. 何をするエフェクト群か

`tools.get_func_address` で見ると、この8つ(`反転` はオブジェクト/フレームの
2登録)は登録テーブルの中で**ひとまとまりに並んでいる**:

```
[51] struct=0x1009e550 flag=0x00008020 func_proc=0x10007150 name=座標
[52] struct=0x1009e9f0 flag=0x00008020 func_proc=0x100078c0 name=拡大率
[53] struct=0x1009e228 flag=0x00008020 func_proc=0x10007040 name=透明度
[54] struct=0x1009e3b0 flag=0x00008020 func_proc=0x10007090 name=回転
[55] struct=0x1009e0b8 flag=0x00008020 func_proc=0x10006c20 name=領域拡張
[56] struct=0x1009e6d8 flag=0x00008020 func_proc=0x100071c0 name=リサイズ
[57] struct=0x1009e858 flag=0x00008020 func_proc=0x100075b0 name=ローテーション
[58] struct=0x100adf10 flag=0x00008020 func_proc=0x100804b0 name=振動        (今回は対象外)
[60] struct=0x100ae4a8 flag=0x00008020 func_proc=0x10082260 name=反転
[61] struct=0x100ae5d0 flag=0x00000000 func_proc=0x10082260 name=反転(フレーム版)
```

`ぼかし`/`発光` のような「オブジェクト版・フレーム版の2登録」を持つのは
`反転` だけで、残り7つは**オブジェクト版1個のみ**(`透明度`/`座標`/`回転`と
同じ理由 ―― アルファや座標のような「フレームには無い概念」を触るため)。

**新しい発見**: 7つすべて(と対象外の `振動`、`反転` のオブジェクト版)の
`flag` が `0x00008020` ―― 通常の「オブジェクト効果」ビット `0x20` に加えて
`0x8000` が立っている。`filter_registration.md` にまだ無いビットで、
登録テーブル全100件中この9件だけが持つ(`ミラー`/`ラスター`/`波紋`/
`画像ループ`/`極座標変換` など見た目が近い他のエフェクトは立っていない)。
正確な意味は未追跡だが、**「オブジェクトの基本的な形状パラメータを
直接動かすフィルタ」という括りの目印**である可能性が高い。

## 2. 2つの系統 ―― fpip を更新するだけ / その場でピクセルを書き換える

8つは実装のうえで完全に2グループに分かれる。

| 系統               | エフェクト                             | することは                                                                 |
| ------------------ | --------------------------------------- | ---------------------------------------------------------------------------- |
| **遅延蓄積系**     | `座標` `回転` `透明度` `拡大率`         | `exec_multi_thread_func` を1回も呼ばない。`*(fpip+0xAC)` の画素には一切触れず、fpip の専用フィールドに値を足し込む(または掛け込む)だけ |
| **即時ピクセル系** | `領域拡張` `リサイズ` `ローテーション` `反転` | ワーカーを起動して対バッファ(`*(fpip+0xB0)`)へ実際に書き込み、`*(fpip+0xAC)`/`+0xB0` を swap する(`box_blur.md` などで既出の ping-pong) |

この区別は**実行順序が結果に影響するかどうか**を直接左右する:

- 遅延蓄積系は基本的に**可換**(§3〜§4)。`座標` を2回・`回転` を先に/後に
  置いても最終的な蓄積値は同じになる(`透明度` だけは加算ではなく
  「残っている見え方」同士の掛け算だが、これも可換)。
- 即時ピクセル系はふつうの画素フィルタと同じで、**リストの順序がそのまま
  効く**。たとえば `ローテーション` の後に `領域拡張` を置くのと、
  `領域拡張` の後に `ローテーション` を置くのとでは、マージンが回転に
  巻き込まれるかどうかが変わる(前者は回転後の形にマージンが付き、
  後者は回転前のキャンバスにマージンが付いてから回転される)。

## 3. 座標・回転・透明度 ―― 遅延蓄積系の素の3つ

3関数とも191バイト以下で、`fp->track` を読んで fpip に書き込むだけの
直線的なコード(分岐は「加算するかどうか」の1つも無い)。検算は
[`verify_deferred_params.py`](verify_deferred_params.py)。

| エフェクト | `func_proc`   | サイズ | 書き込み先                          | 式                                                                 |
| ---------- | ------------- | ------ | ------------------------------------ | -------------------------------------------------------------------- |
| `座標`     | `0x10007150`  | 105B   | `fpip+0xBC`/`+0xC0`/`+0xC4` (X/Y/Z) | `+= c_div(raw<<12, 10)` ―― Q12画素、raw は 1/10画素単位(scale=10)  |
| `回転`     | `0x10007090`  | 191B   | `fpip+0xC8`/`+0xCC`/`+0xD0` (X/Y/Z軸)| `+= trunc((raw mod 36000) * 65536/36000)` ―― Q16(65536=1回転)、raw はセンチ度(scale=100) |
| `透明度`   | `0x10007040`  | 78B    | `fpip+0xE8`                          | `:= 4096 - msvc_div((4096-old)*(1000-raw), 1000)`(合成、加算ではない) |

- `座標`/`回転` はトラックバー3本(X/Y/Z)とも**全く同じコードが3回並ぶ**
  だけ(コピペそのもの)。`回転` の `idiv 36000; cmp 余り,36000; je …` は
  余りが除数と一致することが原理的に無い(`|余り| < |除数|`)ため**死んだ
  分岐** ―― `フェード` の `>= 4096` 未到達ガード(`fade/README.md` §4)と
  同じ形の安全網。
- `透明度` の `fpip+0xE8` は「透明度」そのもの(0=不透明、4096=完全透明)。
  raw==0 なら即 `return 1`(早期リターンが1本だけ、`フェード` の3出口より
  シンプル)。2つの `透明度` フィルタを直列に置くと、効果は
  `(1-raw1/1000)*(1-raw2/1000)` という不透明度の**掛け算**で重なる。
- 3つとも exec_multi_thread_func を呼ばないので、**キャンバスも対バッファも
  スレッド分割も一切登場しない** ―― この8つの中で最も小さいコード。

## 4. 拡大率 ―― `fpip+0xE0`/`+0xE4` という分数エンコーディング

`0x100078c0`(420バイト)。`拡大率`/`X`/`Y` の3本はそれぞれ
`raw==10000`(100.00%)なら**その軸の計算を丸ごとスキップ**する
高速経路を持つ(`透明度` の raw==0 と同じ発想)。

関数の**末尾**(`0x100079de`-`0x10007a63`)は disasm・angr 両方で確認できる
明確な不変条件を作る:

```
if edi == esi:      field_e0, field_e4 = edi, 0
elif edi >= esi:     field_e0, field_e4 = edi, round0(65536*(esi-edi)/edi)   # <= 0
else:                 field_e0, field_e4 = esi, round0(65536*(edi-esi)/esi)   # <= 0
```

`field_e0` は常に**2候補のうち大きい方**、`field_e4` は**小さい方が
大きい方に対してどれだけ欠けているか**を Q16 の符号付きで持つ
(`field_e4 == 0` ⇔ 前回から変化なし ⇔ 関数冒頭の `test eax,eax` 分岐に直結)。

**前段**(2つの候補 `edi`/`esi` を、前回の `+0xE4` の符号で分岐しながら
`拡大率`/`X`/`Y` で掛け込んでいく部分)は x87 と ESP 相対アドレッシングが
入り組んでいて、本プロジェクトのツール(angr は x87 を lift できず、
unicorn も未導入)だけでは1回のパスで断定できなかった。disasm の生ログと
angr の分岐構造(`decompile_base.py --only 拡大率`)は一致することを
確認済みで、`verify_scale_ratio.py` の「未確定事項」として扱っている。

## 5. 領域拡張 ―― キャンバス拡張の「方式E」

`0x10006c20`(1047バイト、この8つの中で最大)。
[`inspect/common/canvas_growth.md`](../common/canvas_growth.md) にある
方式A(ワーカーが枠外に書く)/B(table で事前拡張)/C(オフスクリーン)/
D(`func_proc` が矩形を計算)のどれとも違う、**4本の独立したマージンを
`table[0x44]` 1回で反映する**方式E(検算: [`verify_canvas_extend.py`](verify_canvas_extend.py))。

1. 上下左右のトラックバー値を**キャンバス最大サイズでクランプ**する。
   ここに非対称な優先順位がある ―― **左が右より先、上が下より先**に
   クランプされる(左だけで枠を使い切ると右は0になる)。`シャドー` の
   「オフセットが先に食う」(`canvas_growth.md` §2 末尾)と同じ発想。
2. `table[0x44](B, 左, 上, A, 0, 0, w, h, 0, 0x13000003)` で元画像を
   新しい位置へ転送し、`*(fpip+0xAC)`/`+0xB0` を swap。
3. `塗りつぶし`(check[0])で分岐:
   - **ON**: 新しい上下左右のマージンに**端の行/列を複製**して埋める。
   - **OFF(既定)**: `table[0x48]`(矩形クリア、mode=2)を4本のマージン帯
     それぞれに呼んで**透明にクリア**する。「クリアしない」のではなく
     「塗る色が違う」だけで、どちらの場合も新しい余白は必ず何かで
     埋まる。
4. `*(fpip+0xB4)`/`+0xB8` を新サイズに更新し、`*(fpip+0xD4)`/`+0xD8`
   (オブジェクト中心のずれ)に `(左-右)<<11` / `(上-下)<<11` を加算する。
   これは `(左-右)/2` 画素・`(上-下)/2` 画素を Q12(1/4096画素)で
   表したもので、`閃光`/`シャドー` に次いでこの単位を裏付ける3例目
   ([`canvas_growth.md` §8](../common/canvas_growth.md))。

## 6. リサイズ ―― 唯一 fpip+0xE0/+0xE4 を経由しない「拡大率」

`0x100071c0`(765バイト)。名前もトラックバー(`拡大率`/`X`/`Y`)も §4 の
`拡大率` と同じだが、**遅延蓄積系ではない** ―― その場で
`*(fpip+0xB4)`/`+0xB8` を書き換え、実際にピクセルをリサンプルする
(検算: [`verify_resize.py`](verify_resize.py))。

- **比率モード(既定)**: `拡大率`/`X`/`Y` は現在のサイズに掛かる百分率。
  3本とも100%ならスキップ。掛けるたびに `+0.5` してから `_ftol`
  (四捨五入寄り ―― `拡大率` フィルタの0方向切り捨てと丸め方が違う)。
- **`ドット数でサイズ指定`(check[1])**: `X`/`Y` が百分率ではなく**その
  まま目標ピクセル数**になる。ただし raw は scale=100 のトラックバーなので、
  使う前に新しいマジック定数 **`0x51eb851f`(シフト5、`/100`)** で割る ――
  `param_scaling.md` 既出の `/1000`(`0x10624dd3`)/`/250` とは別口。
- **最大キャンバスへのクランプはモードで挙動が違う**: 比率モードは
  `max_h*旧w` と `max_w*旧h` を比べて先に頭打ちになる軸を決め、
  **もう一方を新しい目標アスペクト比で再計算する**(アスペクト比を保つ)。
  ドット数モードは新しい幅・高さを**それぞれ独立に** `max_w`/`max_h` へ
  クランプする(アスペクト比は保たれない)。
- 新サイズが現在と同じなら何もせず `return 1`。新しい幅・高さの**どちらかが
  0以下**になったら `return 0`(`フェード` と同じ「このオブジェクトは
  この回描画しない」終了)。
- `補間なし`(check[0])が立っているときだけ **exedit 自前のワーカー**
  (`0x100074c0`、`src = x*旧サイズ/新サイズ` の最近傍サンプリング)を
  `exec_multi_thread_func` で走らせる。既定(補間あり)は代わりに
  `fp->exfunc` 経由で **AviUtl 本体の関数を2つ**(`+0x48`/`+0x58`)呼ぶ ――
  補間アルゴリズムの中身は `exedit.auf` の外なので、`rgb_ycbcr.md` §3 の
  YCbCr→RGB 変換と同じ扱いで範囲外とする。

## 7. ローテーション ―― mod4 のジャンプテーブル

`0x100075b0`(175バイト、ワーカー3本 `0x10007680`/`0x10007740`/`0x10007810`
は別途)。`90度回転` は raw -4..4 の9値だが、ジャンプテーブル
(`0x10007660`、`int[7]`)は `raw+3` を添字にした7エントリしか無い
(検算: [`verify_rotation_flip.py`](verify_rotation_flip.py))。

```
raw:    -4    -3    -2    -1     0    +1    +2    +3    +4
mod4:  (0)     1     2     3     0     1     2     3   (0)
表:  範囲外  ハンドラA ハンドラB ハンドラC  無回転  ハンドラA ハンドラB ハンドラC  範囲外
```

90°刻みの回転は4種で一巡するので本質は `raw mod 4` だが、テーブルは
`-3`/`+1`・`-2`/`+2`・`-1`/`+3` をそれぞれ同じハンドラへ飛ばす形で
剰余類を共有している。`raw = ±4`(mod4=0)はテーブルの範囲外に落ちて
`ja` で素通りする ―― これは無回転(0°)に帰着するはずの値なので、
**バグではなくたまたま正しい**(`フェード` の死んだガードと同種の
「実害の無い到達境界」)。

- `raw ≡ 2 (mod 4)`(180°)のハンドラだけは、呼び出し前に
  `*(fpip+0xB4)`/`+0xB8` の**入れ替えをしない**。
- 残り2つ(`raw ≡ 1`/`raw ≡ 3`)は呼ぶ前に幅高さを入れ替え、**入れ替えた
  新しい軸をそれぞれのキャンバス最大値でクランプ**してから書き込む
  (`canvas_growth.md` §1 のグローバルを再利用)。
- 3ワーカーとも `exec_multi_thread_func` で**元画像の高さ**を行分割し
  (`thread_split.md` と同型のガードあり)、対バッファへ転置コピーして
  から `*(fpip+0xAC)`/`+0xB0` を swap する。

**未確定**: どのハンドラが時計回り/反時計回りのどちらに対応するかは、
`func_proc` 側で先に更新される `*(fpip+0xB4)`/`+0xB8`/`+0xEC` にワーカーの
アドレス計算が依存するため、静的解析(capstone/angr、エミュレータなし)
だけでは1回のパスで確証を持てなかった。mod4 の対応表とクランプ・
スワップの有無は確定事項として掲載し、回転方向の同定は今後の課題とする。

## 8. 反転 ―― 1関数・2登録・8種のワーカー

`0x10082260`(365バイト)。`fp->flag & 0x20` の分岐は**関数の先頭1回だけ**
で、以降はオブジェクト効果(check 5個)/フレームフィルタ(check 4個)で
完全に別のチェック配列・別のワーカー列を順に呼ぶ
(検算: [`verify_rotation_flip.py`](verify_rotation_flip.py))。
`filter_registration.md` §2 にある「2登録が `func_proc` を共有」
「`func_proc` ごと2本」に次ぐ、**3つ目のバリエーション**(1関数が内部で
完全に枝分かれし、ワーカーのアドレスも2系統で別々)。

| チェックボックス | オブジェクト版ワーカー | フレーム版ワーカー | 式                                      |
| ----------------- | ---------------------- | -------------------- | ------------------------------------------ |
| 上下反転           | `0x10082640`            | `0x100823d0`           | 行を逆順にコピーして swap                    |
| 左右反転           | `0x10082700`            | `0x100824a0`           | 列を逆順にコピーして swap                    |
| 輝度反転           | `0x100827b0`            | `0x10082550`           | `y' = 0x1000 - y`(in-place、swapなし)      |
| 色相反転           | `0x10082830`            | `0x100825c0`           | `cb' = -cb`, `cr' = -cr`(in-place)         |
| 透明度反転         | `0x100828c0`            | ―(存在しない)        | `a' = 0x1000 - a`                           |

`輝度反転`/`透明度反転`は**同じ `0x1000 - x` という式**を y と a それぞれに
適用しているだけで、`色相反転` だけが加減算ではなく符号反転という質的に
違う式になっている(Cb-Cr平面での180°回転)。

## 9. `標準描画`/`拡張描画` との関係 ―― 何が同じで何が違うか

`標準描画`(`0x1008a020`)/`拡張描画`(`0x10023c80`)は自分自身も X/Y/Z座標・
拡大率・透明度・回転のトラックバーを持つ。この8フィルタと**同じ名前の
機能を二重に持っている**ように見えるが、確認できた事実は次の通り。

### 9.1 直接呼び出してはいない ―― コードは共有していない

`標準描画`/`拡張描画` の関数本体(それぞれ最大 `0x14000` バイトの窓で
走査)は、この8つの `func_proc` アドレスを**1つも `call` していない**
(`verify_base_drawing_link.py` の前段で `tools.decompile.call_targets`
を使って確認)。つまり**コードは共有されていない** ―― 同じロジックが
両方に**別々に書かれている**か、あるいは更に別の共有サブルーチンを
経由している(本プロジェクトでは特定していない)。

### 9.2 しかし同じ fpip フィールドへ収束する ―― 状態は共有している

一方で、`grep`(`verify_base_drawing_link.py`)によれば `標準描画`/
`拡張描画` はこの8フィルタが書き込むのと**同じ fpip オフセット**
(`+0xBC`〜`+0xE8`)を関数全域で繰り返し参照している:

```
 offset |     標準描画 |     拡張描画  意味
---------------------------------
  +0xBC |        2 |        4  座標 X
  +0xC0 |        7 |        9  座標 Y
  +0xC4 |        6 |        0  座標 Z
  +0xC8 |        1 |        2  回転 X軸
  +0xCC |        1 |        6  回転 Y軸
  +0xD0 |        4 |        4  回転 Z軸
  +0xD4 |        3 |        3  中心オフセット X (Q12)
  +0xD8 |        2 |        5  中心オフセット Y (Q12)
  +0xE0 |        0 |        1  拡大率 の大きい方の候補
  +0xE4 |       48 |       83  拡大率 の相対差分(Q16)
  +0xE8 |        2 |       10  透明度
```

`座標`/`回転`/`透明度`/`拡大率` フィルタは fpip の状態を「書くだけ」で
自分では一切描画しないので、この状態を**最終的に読んで実際の変形・
合成をする**のは `標準描画`/`拡張描画`(またはそれらが呼ぶ描画ルーチン)
という他ない。したがって:

- **`座標`/`回転`/`透明度`/`拡大率` フィルタを足すことと、`標準描画`/
  `拡張描画` 自身の同名トラックバーを動かすことは、コード上は別経路だが
  最終的に同じ状態(fpip の同じフィールド)へ加算・合成される。** 両者を
  併用すると効果が**重なる**(例: オブジェクト自身の X 座標が100、
  `座標` フィルタの X が50なら、合計150画素ぶん動く)。
- 遅延蓄積系の式は§3〜§4で見た通り**すべて可換**(加算 or 大小比較+
  差分保持)なので、`標準描画`/`拡張描画` 自身のトラックバーと `座標`/
  `回転`/`拡大率`/`透明度` フィルタを**どちらを先に評価しても最終結果は
  変わらない**はずである(exedit のエフェクト列は `標準描画`/`拡張描画`
  が常に先頭なので、実際にこの順序が入れ替わることは無いが、可換性
  そのものは処理順序への依存が無いことを意味する)。

### 9.3 UI 上の制約は base 側にしか無い ―― フィルタで迂回できる

[`filter_registration.md` §5](../common/filter_registration.md) の
`+0x78` 表によれば、`標準描画` 自身のトラックバーが埋める枠は
**X, Y, Z, Z軸回転, 拡大率, 透明度の6枠だけ**(X軸回転・Y軸回転・
中心X/Y/Z・縦横比の6枠は埋まらない)。一方 `拡張描画` は12枠**すべて**
埋める。

つまり `標準描画` オブジェクトは**自分のトラックバーだけでは** X軸/Y軸
回転や回転中心・縦横比を変えられない。しかし §3 で確認した通り、`回転`
フィルタが書き込む `fpip+0xC8`/`+0xCC`(X軸/Y軸回転)は `+0x78` の枠の
**有無に関係なく**動く ―― `回転` フィルタを足すだけで `標準描画`
オブジェクトでも X軸/Y軸回転が使える。**base 側の制約は UI(トラックバー
の有無)だけにあり、実行時の状態(fpip)には無い**、というのがこの節の
結論。

### 9.4 `リサイズ`/`領域拡張`/`ローテーション`/`反転` は base 側に無い

`+0x78` の12枠は位置・回転・拡大率・透明度に対応する数値ぶんしか無く、
「ドット数でサイズ指定」「塗りつぶし」「90度回転」「上下/左右反転」の
ような**離散的な**振る舞いを表現する枠は無い。したがって即時ピクセル系
4つは `標準描画`/`拡張描画` 自身には**対応する機能が無く**、この4つに
限っては「フィルタとして足すことでしか使えない」機能だと言える
(§2 で見た「その場でピクセルを書き換える」という実装上の違いは、この
UI 上の違いとも対応している)。
