# ライト (Light) フィルタ リバースエンジニアリング解析

対象: `data/exedit.auf`(AviUtl 拡張編集の標準フィルタプラグイン)、32bit PE、
`ImageBase = 0x10000000`。以下のアドレスはすべて VA(`RVA = VA - 0x10000000`)。

## 再現方法

すべてのスクリプトは本プロジェクトの `main.py` を踏み台にして実行する。
`main.py` はコマンドラインで指定されたスクリプトに対して、DLLパス
(デフォルト `data/exedit.auf`)とヘッダー一覧(デフォルト `data/filter.h`)を
渡す役割を持つ。

```
uv run main.py inspect/light/<script>.py
uv run main.py tools.<tool>            # フィルタ非依存の共通ツール。一覧はリポジトリ直下の README
```

| スクリプト                        | 確認していること                                                                                                                                                             |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tools.filter_table --name ライト` | `FILTER_DLL` 配列(先頭 `0x100a3e28`)の登録エントリ `0x100a72b0` を抽出。**オブジェクト効果1個のみ**、トラックバー3本・チェックボックス1個・ボタン1個、`ex_data` 4バイト        |
| `tools.track_scale --name ライト`  | `+0x74` 拡張ブロック `0x100a7290`。`拡散` だけスライダー範囲(0〜100)が表示範囲(0〜500)より狭い。3本ともグループ化マーカーは0                                                 |
| `decompile_light.py`               | `func_proc` と6ワーカー、`func_WndProc` とその補助2つの angr デコンパイル。整数演算主体で `/* unsupported instruction */` はほぼ出ない                                       |
| `disasm_params.py`                 | `func_proc` 全域と、6ワーカーの末尾(ピクセル書き込み部分)の注釈付き生逆アセンブル。decompile が丸めてしまう `add` と `mov` の違い、書き込み先が `+0xAC` か `+0xB0` かはここで確定させている |
| `verify_params.py`                 | 2つのマジックナンバー除算(`/1000`、`/11`)の裏付け、`比率` が `強さ` を2つの係数 A・B に分ける式の全数検算、`拡散` の2段クランプ                                              |
| `verify_shading.py`                | 陰影パスの式の検算。`逆光` オフが**内側ほど明るく**、オンが**縁ほど明るい**こと、`強さ` の超過分光色以上にはならないこと                                                      |
| `verify_halo.py`                   | 後光パスの式の検算。2Dボックス平均が `[0,4096]` を出ないこと、3フェーズのスライディングウィンドウが実際に `w×h` を `(w+2r)×(h+2r)` へ広げること、**暗い光色が後光の不透明度に上限を作る**こと、`比率` の両極端で何が起きるか |
| `simulate_light_reference.py`      | 上記すべてを積んだ整数忠実リファレンス実装。円形オブジェクトのASCIIアート描画と、`逆光` オン/オフの断面(走査線)比較                                                          |

共通ツール(他の `inspect/` からも使う):

| ツール                   | 役割                                                                                    |
| ------------------------ | --------------------------------------------------------------------------------------- |
| `tools.get_func_address` | `FILTER_DLL` 配列を1行/エフェクトでダンプ                                                |
| `tools.filter_table`     | 登録構造体の完全デコード(トラックバー、チェックボックス、`ex_data_def`、`+0x74` 拡張ブロック) |
| `tools.track_scale`      | `+0x74` の表示スケール / スライダー範囲 / トラックバーのグループ化マーカー              |
| `tools.disasm`           | capstone 逆アセンブル + 絶対メモリオペランドの定数解決                                  |
| `tools.decompile`        | angr による範囲限定デコンパイル、`--calls` で呼び出し先列挙                             |
| `tools.xrefs`            | 任意の VA への参照を全画像から検索し、どのエフェクトのコードかを特定                    |
| `tools.pe_image` / `tools.cints` | (単体実行不可のライブラリ)PE の VA 読み出し / C・x86 の整数意味論(`c_div`、`sar`、マジック除算) |

## 1. 登録エントリ ―― 1つだけ、コード全域は約4.2KB

`閃光`・`境界ぼかし`・抜き系3エフェクトと同じく、`ライト` は `FILTER_DLL` 配列に
**1回しか登録されていない**(`fp->flag & 0x20` による分岐は存在しない)。

| 項目           | 値                                                                        |
| -------------- | ------------------------------------------------------------------------- |
| `FILTER_DLL`   | `0x100a72b0`(配列の [33] 番目)、`flag = 0x20`(オブジェクトのフィルタ効果) |
| `func_proc`    | `0x1005ba30`                                                              |
| `func_WndProc` | `0x1005c9c0`                                                              |
| `FILTER+0x58`  | `0x1005ca90`                                                              |
| `ex_data`      | 4バイト、`ex_data_def` = `ff ff ff ff`、`+0x70` フィールド表 `0x100a722c` |
| `+0x74`        | `0x100a7290`。表示スケール `{10,1,10}` / ドラッグ範囲(下記)                |
| 入力バッファ   | `*(fpip+0xAC)`。**陰影パスがここへ直接書き戻す(イン・プレース)**          |
| 対バッファ     | `*(fpip+0xB0)`。**後光パス専用**の別キャンバス                            |

このエフェクト固有のコードは `0x1005ba30`〜`0x1005caa4` の連続した**約4.2KB**
(直後の `0x1005cab0` は `斜めクリッピング` の `func_proc` で、無関係)。
6本のワーカーは陰影用3組・後光用2組に分かれ、後述する。

### トラックバーとチェックボックス

`tools.filter_table --name ライト` の生出力:

| トラックバー | raw 既定 | raw 範囲     | 表示スケール | 表示範囲       | スライダー範囲 |
| ------------ | -------: | ------------ | -----------: | -------------- | -------------- |
| `強さ`       |     1000 | 0〜3000      |           10 | 0.0〜300.0     | 0.0〜300.0     |
| `拡散`       |       25 | 0〜500       |            1 | 0〜500         | **0〜100**     |
| `比率`       |        0 | -1000〜1000  |           10 | -100.0〜100.0  | -100.0〜100.0  |

| チェック    | 既定           | 種別                          |
| ----------- | -------------- | ----------------------------- |
| `check[0]`  | `逆光`(0)     | チェックボックス               |
| `check[1]`  | `色の設定`(-1) | ボタン(色選択ダイアログ)      |

`拡散` だけスライダーで届く範囲(0〜100)が表示範囲(0〜500)より狭く、それ以上は
数値入力でしか指定できない(`ぼかし` の `範囲` などと同じ性質、
[`param_scaling.md`](../common/param_scaling.md))。3本ともグループ化マーカー
(スロット[1])は0 ―― `比率` は見た目こそ `X`/`Y` のような対のパラメータだが、
複数トラックバーの一体グループではなく単独のトラックバーである。

### `ex_data` ―― 色が1つだけ、「指定なし」は無い

`+0x70` フィールド表(`0x100a722c`)を直接読むと、宣言されているのは1つだけ:

```
[0] kind=3 size=3 name="color"      -- R, G, B (Win32 COLORREF と同じバイト順)
[1] kind=0 size=1 name=(なし)       -- 未使用のパディング1バイト
合計 4 バイト = ex_data_size
```

`発光`・`グロー`・`閃光` は同じ4バイト構造で bit24(dword の最上位バイト)を
「色指定なし(各画素自身の色を使う)」フラグとして読むが、**`ライト` の
`func_proc` はその1バイトを一度も読まない**(`disasm_params.py` の
`0x1005bb65`〜`0x1005bb77`)。`ex_data_def` の既定値 `ff ff ff ff` は
白(`0xffffff`)+ 未使用バイト `0xff` に過ぎず、「指定なし」を意味する特別な
値ではない。**`ライト` に「各画素自身の色で光る」モードは無く、常に
`色の設定` で選んだ1色を使う。**

## 2. パラメータ変換 ―― `比率` が `強さ` を2つの係数に割る

`func_proc`(`0x1005ba30`)冒頭、`強さ = 0` なら即 `return 1`(画像にもキャンバス
にも一切触れない、`ぼかし`/`閃光`/`拡散光`と同じ早期リターン)。

```
S = trunc(強さ_raw * 4096 / 1000)          // 共通のマジックナンバー除算(0x10624dd3)
A = S                                       if 比率_raw >= 0
  = trunc(S * (1000 + 比率_raw) / 1000)     if 比率_raw <  0    // 比率<0でだけ縮む
B = S                                       if 比率_raw <= 0
  = trunc(S * (1000 - 比率_raw) / 1000)     if 比率_raw >  0    // 比率>0でだけ縮む
```

`verify_params.py` が 172,029 通りの `(強さ_raw, 比率_raw)` 組み合わせ全部で
この式と実装(`msvc_div` による逐語再現)の一致を確認している。

**A は後述の後光パスの係数、B は陰影パスの係数**で、`比率 = 0` ならどちらも
`S` に等しい。`比率` を動かすと片方だけが線形に縮み、もう片方は無傷のまま
残る ―― `比率` は「陰影と後光のどちらを強めるか」の**ミックス**であって、
両方を一緒に弱める「強さ」の役目ではない。

| `比率`(表示) | A(後光) | B(陰影) | 意味                         |
| ------------: | ------: | ------: | ---------------------------- |
|        -100.0 |  **0**  |    4096 | 後光ゼロ、陰影は満額         |
|         -50.0 |    2048 |    4096 |                              |
|           0.0 |    4096 |    4096 | 既定。両方満額               |
|          50.0 |    4096 |    2048 |                              |
|         100.0 |    4096 |  **0**  | 陰影ゼロ、後光は満額         |

`A` と `B` はそれぞれ `比率` の片側の極値でのみ厳密に0になり
(`verify_params.py` §4)、`比率 = -100.0`/`100.0` が
「陰影だけ」/「後光だけ」になる境界そのものである(§5 で詳述)。

`拡散`(raw)は他エフェクトの `強さ`/`しきい値` と違い**`/1000` 変換を一切受けず、
そのまま半径 `r` として使われる**(`グロー` の `拡散` と同じ流儀)。半径は
2段階でクランプされる:

```
クランプ#1(陰影パスが使う r。0x1005bab9-0x1005bb47):
    r = trunc(w/2) - 2     if 2r+1 >= w
    r = trunc(h/2) - 2     if 2r+1 >= h
    r = 0                  if r < 0
    r = trunc((max_w-w)/2) if w+2r > max_w    // 共通の最大キャンバス幅 0x10196748
    r = trunc((max_h-h)/2) if h+2r > max_h    // 同・高さ 0x101920e0

クランプ#2(後光パスが使う r。クランプ#1の後、A>0 判定の直後に上書き。0x1005bbef-0x1005bc31):
    r = trunc((stride-w)/2)  if 2r > stride-w   // fpip+0xEC: 確保済みバッファの行幅
    r = trunc((rows-h)/2)    if 2r > rows-h     // fpip+0xF0: 同・確保済み行数
```

クランプ#1は「オブジェクトの寸法に収まるか」と「共通の最大キャンバスに
収まるか」、クランプ#2は「**すでに確保済みのバッファに収まるか**」で、
別の上限を見ている(`verify_params.py` §5/§6)。後光パスは常にクランプ#2の
`r` を使うので、陰影パスより半径が小さくなることがある(狭い余白しか
確保されていない場合)。

`ex_data` の色は毎フレーム無条件で `0x1006fed0`(`発光`/`グロー`/`閃光` と共有の
RGB→YCbCr、Q14 の BT.601 フルレンジ、[`rgb_ycbcr.md`](../common/rgb_ycbcr.md))
に渡され、`光色 Y`/`Cb`/`Cr` としてグローバルに保存される。

## 3. 陰影パス ―― オブジェクト自身の画素に色を「足す」

`B > 0` のとき起動。**`fpip+0xAC`(オブジェクト自身の画素バッファ)を
イン・プレースで書き換える** ―― 別バッファへの合成ではなく、加算そのもの。
`逆光`(`check[0]`)で使うワーカーの組が変わる:

| `逆光` | 垂直(ボックス平均→スクラッチ) | 水平+加算(スクラッチ→`+0xAC`) |
| ------ | ------------------------------ | -------------------------------- |
| オフ(既定) | `0x1005c080`(素のアルファ) | `0x1005c250`(**+4096バイアスあり**) |
| オン      | `0x1005c520`(**反転アルファ** `4096-a`) | `0x1005c700`(バイアスなし)      |

どちらも、半径 `r`(クランプ#1)のボックス平均を**キャンバスを広げずに**
計算する ―― 除数は常にカーネル幅 `2r+1`(端では実サンプル数より少ない値を
同じ数で割るので自然にフェードする、[`box_blur.md` §3](../common/box_blur.md)
の「常にカーネル幅で割る」変種)。

```
逆光オフ:  avg = box_average(alpha, r)                 // 素のアルファ、0..4096
           m   = trunc((avg + 4096) * Bs / 4096)        // Bs = trunc(B*2/11)
逆光オン:  avg = box_average(4096 - alpha, r)           // 反転アルファ
           m   = trunc(avg * B / 4096)                  // Bのスケーリングなし

m <= 0      : 何もしない
m >= 4096   : 各画素の Y/Cb/Cr に光色をそのまま加算(スケールなし)
それ以外    : 各画素の Y/Cb/Cr に 光色*m/4096 を加算(sar、切り捨て)
```

**アルファ(`+6`)には一切触れない。** 触るのは Y/Cb/Cr の3チャンネルだけで、
書き込みは `add word ptr [...], dx`(既存の値への加算)であって上書きではない
―― これは decompile の疑似コードだと「同じ形の代入」に見えてしまう箇所で、
`add` か `mov` かは `disasm_params.py` で実際のオペコードを確認している。

**逆光オフは「+4096」バイアスがあるので `m` が0にならない**
(`Bs <= m <= 2*Bs`)。つまり既定の陰影は**完全に消えることはなく**、内側ほど
強くなる。**逆光オンはバイアスが無いので `m` は反転アルファに正比例**し、
オブジェクトの奥深く(アルファが常に満額な領域)では0まで落ちる。

`verify_shading.py` の1次元シミュレーション(半径3、12画素幅の円形断面)より:

```
   x  alpha  box avg  逆光off倍率  逆光off加算  逆光on倍率  逆光on加算
   6   1365     1755         258          258         571         571
   8   4096     2925         310          310         285         285
  15   4096     4096         362          362           0           0   <- 中心
```

**逆光オフは中心が最も明るく、逆光オンは縁が最も明るく中心でゼロになる** ――
「正面から当たる光」と「背後からの光(リムライト)」の違いがこの1点(反転の
有無とバイアスの有無)だけで作られている。

`強さ` のオーバードライブ(表示 100%超、raw 1000超)は `m >= 4096` の分岐が
早く来るだけで、**光色そのものより明るくなることはない**
(`verify_shading.py` §3。加算されるのは常にたかだか光色1回分)。

`B <= 0`(`比率 = +100.0%`)ではこのパス自体が丸ごとスキップされ、オブジェクトの
画素は一切変更されない。

## 4. 後光パス ―― 別キャンバスに塗った光を下に敷く

`A > 0` のとき、`B` の判定とは無関係に**常に**起動。`0x1005bcd0`(垂直)→
`0x1005be50`(水平+エンコード)の組は逆光の有無で変わらない、常に同じ2本。
陰影パスとの決定的な違いは**キャンバスを実際に広げる**こと:

```
垂直(0x1005bcd0): h 行の入力から (h+2r) 行を出力       // 3フェーズ・スライディングウィンドウ
水平(0x1005be50): w 列の入力から (w+2r) 列を出力、同時に画素をエンコード
```

3フェーズは「立ち上がり(**カーネル幅**回、毎回1サンプル追加+出力)→ 定常
(`寸法-カーネル幅`回、スライド)→ 立ち下がり(`カーネル幅-1`回、排出のみ)」で、
出力本数は `カーネル幅+(寸法-カーネル幅)+(カーネル幅-1) = 寸法+2r` にちょうど
一致する(`verify_halo.py` §3)。陰影パスは同じ3フェーズ構造でも**違う数を
使う** ―― 立ち上がりの前に `r` サンプル分の**無出力の先読み**を挟んだ上で
`r+1` 回だけ出力し、立ち下がりも `カーネル幅-1` ではなく `r` 回しか回さない
(`verify_shading.py` §6)。結果、陰影パスの出力本数は(無出力の先読み `r` 回を除いて)
`(r+1)+(寸法-カーネル幅)+r = 寸法` のまま変わらず、後光パスだけが広がる。

各出力画素(`avg2D` は素のアルファの2次元ボックス平均、`0..4096` の範囲に
必ず収まる、`verify_halo.py` §1):

```
scale = min(4096, trunc(avg2D * A / 4096))     // このエフェクトで唯一のハードクランプ
出力   = { Y = 4096, Cb = 光色Cb, Cr = 光色Cr, a = trunc(光色Y * scale / 4096) }
```

`Y` を基準白(4096)に固定し、明るさを丸ごと `a` に載せる ―― `閃光` の
出力エンコード([`glint/README.md` §5](../glint/README.md))と**まったく同じ
アンプリマルチプライの型**である。合成時に `out_c = dst_c*a_d*(1-a_s)/out_a`
という通常合成の式を通ると、`dst_c=4096` と `a_d=scale` の積が効くことで
「光色 × scale/4096」相当の寄与になる。

### 暗い光色は後光が出ない

アルファに載るのが `光色Y * scale / 4096` である以上、**`scale` が上限の 4096 に
飽和しても、後光の不透明度は光色の Y を超えられない**。`強さ` をいくら上げても
同じで、`verify_halo.py` §4 が `強さ` の全域(raw 0〜3000、`A` は 0〜12288)を
走査して確認している:

| 光色      | 色の Y | 後光アルファの上限 | 最大不透明度 |
| --------- | -----: | -----------------: | -----------: |
| `#ffffff` |   4095 |               4095 |       100.0% |
| `#ff0000` |   1224 |               1224 |        29.9% |
| `#0000ff` |    466 |                466 |        11.4% |
| `#000080` |    234 |                234 |         5.7% |

これは `発光`/`閃光`/`グロー` が持つ「暗い光色は効果が消える」落とし穴
([`rgb_ycbcr.md` §4](../common/rgb_ycbcr.md))と同じ現象だが、**到達経路が違う**
―― あちらはしきい値や指数の肩に光色の Y が乗るのに対し、こちらは
アンプリマルチプライのエンコードで**光色の Y がそのまま格納されるアルファ**に
なっている。**陰影パスはこの影響を受けない**(加算であってアルファを触らない)
ので、暗い光色では「陰影は付くのに後光だけがほとんど見えない」という
非対称な見え方になる。

## 5. 最終合成・入れ替え・リサイズ ―― `比率` の両極端で起きること

`A > 0` の続きとして、`func_proc` は最後に:

```
table[0x44](dst=fpip+0xB0, r, r, src=fpip+0xAC, 0, 0, w, h, 0, mode=3)
    // mode=3 = 通常合成(src over dst)、8バイト/画素 (blend_modes.md §3)
swap fpip+0xAC <-> fpip+0xB0
fpip+0xB4 = w + 2r ;  fpip+0xB8 = h + 2r
```

つまり**(陰影パスで着色済みの)オブジェクトを、後光の上に元の位置(中央)へ
描き戻す**。`サイズ固定` に相当するチェックボックスはこのエフェクトに
**存在しない**ので、`拡散 > 0` である限りキャンバスは必ず両軸とも
`2r` 広がる ―― `グロー` と同じ「常時にじむ」性質([`canvas_growth.md`
§6](../common/canvas_growth.md))。

`func_proc` の実際の分岐順序は「`B>0` なら陰影パス実行 → `A<=0` なら即
`return`」なので、**`比率` の両極端は対称ではない**:

| `比率` | 陰影パス | 後光パス・キャンバス拡張・最終合成・入れ替え | 見え方                                                     |
| -----: | :------: | :-------------------------------------------- | ------------------------------------------------------------ |
| -100.0 | 実行(B=S) | **すべてスキップ**(A=0 で即 `return`)          | オブジェクトは着色されるが後光は無く、外接矩形も変わらない  |
| +100.0 | スキップ(B=0) | 実行(A=S)                                     | オブジェクトは無着色のまま、後光だけが付き、キャンバスも広がる |

`比率 = -100.0` では、陰影パスが `fpip+0xAC` を直接書き換えた**直後に**
関数が返るので、その変更は(入れ替えが起きなくても)そのまま表示に使われる
―― 「早期リターンだから何も起きない」わけではなく、**副作用はすでに確定
済み**という非対称さが `verify_halo.py` §5/§6 の要点である。

`simulate_light_reference.py` の走査線比較(半径20の円、中心 `y=n/2`)が
これを end-to-end で裏付ける ―― オブジェクトが不透明(`a_s=4096`)な領域では
通常合成の式が後光の寄与を完全に打ち消す(`out_a=4096` なら `out_c=src_c`)
ので、その領域の `Y` は陰影パスだけを反映した値になる:

```
   x  逆光off:Y  逆光on:Y
  12        3479       3831
  24        3630       3000   <- 中心。逆光onは無着色のまま(3000=元の値)
  36        3630       3000
  48        3479       3831
```

## 6. `色の設定` ボタンと UI

`func_WndProc`(`0x1005c9c0`)は `WM_COMMAND`(`0x702`)+ コントロールID
`0x1e1b`(ボタン押下)だけを処理する:

```c
if (message == 0x702 && LOWORD(wParam) == 0x1e1b) {
    table[0x80](fp+0xE4, 0);                  // 0x1004dac0。用途未確定(§8)
    if (!table[0x6c](fp, fp->ex_data_ptr, 2))  // 0x1004d2a0。色選択ダイアログを開く。キャンセルで0
        return 0;
    sub_1004a7e0(fp+0xE4, "color");            // ex_data の "color" フィールドへ通知
    sub_1005ca30(fp, fp->ex_data_ptr);         // ボタンラベルを "RGB ( r , g , b )" に書き換え
    return 1;
}
```

**`table[0x6c]`(`0x1004d2a0`)は本解析で新たに同定した関数**(共有の描画テーブル
`fp+0x64` の `+0x6c` オフセット)。デコンパイルすると、フラグ引数の bit9
(`0x200`)で「`ex_data` を4バイト整数3本として読むか、バイト列として読むか」を
切り替えたあと、文字列 `"GET_COLOR"` を添えて `sub_10020800` を呼ぶ ―― これは
AviUtl 内部の色選択ダイアログの起動口だと読める。戻り値はユーザーが
決定したか(1)キャンセルしたか(それ以外)。

この形は `発光`(`0x10054c90`)・`グロー`(`0x10058ea0`)の `光色の設定` ボタンと
**完全に同一のパターン**であり、フラグ引数だけが違う:

| エフェクト | `table[0x6c]` 第3引数(フラグ) | `0x1004a7e0` の呼び出し                 | 理由                                             |
| ---------- | ------------------------------ | ---------------------------------------- | -------------------------------------------------- |
| `ライト`   | `2`(`0b010`)                    | `"color"` 1回                            | `ex_data` に `no_color` 相当のフィールドが無い     |
| `発光`     | `0x102`(`0b1_0000_0010`)        | `"color"`、`"no_color"` の2回            | ダイアログに「各画素自身の色」トグルがある        |
| `グロー`   | `0x102`                         | `"color"`、`"no_color"` の2回            | 同上                                                |

`table[0x6c]` のデコンパイル結果を読むと、フラグの **bit8(`0x100`)だけ**が
`ライト`(`2`)と `発光`/`グロー`(`0x102`)で異なり(bit1 の `0x2` はどちらにも
立っている)、その値がそのままグローバル `g_1011f078` に保存されて
`sub_10020800` へ渡っている ―― ダイアログ側に渡る「もう1つのトグルを
出すかどうか」のフラグだと考えて矛盾がない。**推測を「らしい」で止めず、
実際に3引数中どのビットが3エフェクト間で違うかまでデコンパイルで確認した**、
という位置づけである。

`table[0x80]`(`0x1004dac0`)も3エフェクトすべてが UI ハンドラの先頭で無条件に
呼ぶ(`グロー` は `形状` コンボ変更時にも同じ形で呼ぶ)。中身を見ると
`sub_1008d150()` を呼んだあと、第1引数を `(arg & 0xffff) - 1` に変換して
`sub_1008d290` へ**末尾呼び出し**するだけの小さな中継関数で、戻り値は
どのエフェクトでも捨てられている。`sub_1008d150`/`sub_1008d290` 自体は
本解析の範囲外(§8)。

`FILTER+0x58`(`0x1005ca90`)は `sub_1005ca30` を呼ぶだけの1行で、設定ウィンドウ
再構築時にボタンラベルを最新の色へ同期する。

## 8. 未確定事項

- **`table[0x6c]`(`0x1004d2a0`)の完全な引数仕様。** bit8 が「色指定なし
  トグルの有無」らしいところまでは3エフェクトのデコンパイル比較で確認したが、
  bit1・bit9・bit10 の意味、`"GET_COLOR"` を受け取る `sub_10020800` 自体の実装
  (`aviutl.exe` 側のダイアログコードと思われる)までは追っていない。
- **`table[0x80]`(`0x1004dac0`)が中継する `sub_1008d150`/`sub_1008d290` の中身。**
  `table[0x80]` 自体は `sub_1008d150()` を呼んでから第1引数を `-1` して
  `sub_1008d290` へ末尾呼び出しするだけの中継だと確認したが、その先の2関数は
  本解析の範囲外。3エフェクトとも戻り値を捨てているので効果への実害は
  無さそうだが未確認([`filter_registration.md`](../common/filter_registration.md)
  の既存の未確定事項を、具体的なアドレスと中継の形まで前進させたもの)。
- **`0x1004a7e0` の中身。** `(fp+0xE4, フィールド名文字列)` を引数に取る
  ―― ex_data のどのフィールドが変わったかを exedit 側(アンドゥ履歴?
  プロジェクトの dirty フラグ?)へ知らせる関数だと推測しているが、本解析では
  呼び出し元(3エフェクト)からの観測に留まる。
- **確保済みバッファの実際の余白(`fpip+0xEC`/`+0xF0`)。** クランプ#2が
  参照する「すでに確保済みの行幅・行数」がどのタイミングでどれだけ
  確保されるかは、`拡散光` の同名フィールドの解析([`拡散光`
  §4](../diffusion_light/README.md))を踏襲した読みで、`ライト` 自身では
  書き込み側を追っていない。
- **`table[0x44]`(`0x10081b40`)自体の内部。** 通常合成の式は
  [`blend_modes.md`](../common/blend_modes.md) 記載のものをそのまま使っており、
  本エフェクトの解析はその式が正しいという前提の上に乗っている。

以下は全エフェクト共通の未確定事項:

- `fpip->flag & 0x200`(描画品質を落としてよいフラグ)をこのエフェクトが
  読むかどうかは未確認(`disasm_params.py` の範囲では出てこない)。
- 最終的な YCbCr→RGB 変換とそのクリップは `aviutl.exe` 側にあるため、本
  プロジェクトの解析対象外([`rgb_ycbcr.md` §3](../common/rgb_ycbcr.md))。
