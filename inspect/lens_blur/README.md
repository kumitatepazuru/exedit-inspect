# レンズブラー (lens blur) フィルタ リバースエンジニアリング解析

対象: `data/exedit.auf`(AviUtl 拡張編集の標準フィルタプラグイン)、32bit PE、
`ImageBase = 0x10000000`。以下のアドレスはすべて VA(`RVA = VA - 0x10000000`)。

## 再現方法

```
uv run main.py inspect/lens_blur/<script>.py
uv run main.py tools.<tool>            # エフェクト非依存の共通ツール。一覧はリポジトリ直下の README
```

| `decompile_lens_blur.py`              | `func_proc`・ワーカー2本・リサイズ4本を range 限定デコンパイル                                                                        |

## 1. 何をするエフェクトか

**半径 `R` の円板(disc)を一様重みのカーネルとして畳み込む**エフェクト。
`ぼかし` の箱でも `発光` のマルチスケールでもなく、**窓の形が円**である
ことがこのエフェクトの唯一かつ本質的な違いで、そのおかげで点光源が
`2R+1` 画素の円板になる ―― 実際のレンズの玉ボケと同じ形。

そこに `ぼかし` と共有の**指数/対数の輝度カーブ**(`光の強さ`)がかかるので、
暗い面に埋もれた明点が円板として浮き上がる。`範囲=6`・`光の強さ=1` では
明点の寄与が輝度 239(周囲 200)にしかならないのに対し、`光の強さ=60`
では 2798 になる(`simulate_lens_blur_reference.py` §3)。

計算量は `O(R²)` なので、そのままでは `範囲 = 1000` に耐えられない。
実装は**画像のほうを縮小してからぼかす**ことでこれを解いている(手順4)。

## 2. 登録2個 ―― こちらは普通の2登録モデル

`FILTER_DLL` に2回登録され、**`func_proc` は共有**(`0x10012420`)。分岐は
`fp->flag & 0x20` の1点だけで、[`filter_registration.md` §2](../common/filter_registration.md)
の教科書どおり。隣にいる `放射ブラー` / `方向ブラー` が例外だったのと対照的。

| 項目             | オブジェクト効果             | フレームフィルタ         |
| ---------------- | ---------------------------- | ------------------------ |
| `FILTER_DLL`     | `0x100a0b70`、`flag=0x20`    | `0x100a0c98`、`flag=0x00` |
| チェックボックス | `サイズ固定`(**既定 1 = ON**) | 無し                   |
| ワーカー         | `0x10012880`(8バイト/画素)  | `0x10012b50`(6バイト/画素) |

`func_WndProc` も `ex_data` も `+0x74` のグループ化マーカーも `+0x78` も無い。
エフェクト固有コードは `0x10012420`-`0x10012dbf` の **2464 バイト・3関数**で、
外へ出る直接呼び出しは**カーブ4本 + リサイズ4本 + `_ftol`** の9本
(`verify_registration.py`)。

**`サイズ固定` の既定が ON なのは exedit 全体でこのエフェクトだけ**である
(`ぼかし` / `発光` / `拡散光` / `放射ブラー` / `方向ブラー` はすべて既定 OFF)。

## 3. パラメータ

| トラックバー | 生値の範囲 | 既定 | ドラッグ範囲 | 意味                              |
| ------------ | ---------- | ---- | ------------ | --------------------------------- |
| `範囲`       | 0~1000     | 5    | **0~200**    | 元画像でのぼかし半径[画素]        |
| `光の強さ`   | 0~60       | 32   | 0~60         | 指数/対数カーブの底(`ぼかし` と同じ) |

どちらも表示スケールは 1(生値がそのまま UI の数値)。`範囲` は
**スライダーでは 200 までしか動かせず**、それ以上は数値入力が要る
([`param_scaling.md` §1](../common/param_scaling.md))。

`範囲 = 0` は `func_proc` の先頭で `return 1`(何もしない)。

## 4. 7工程

```
(1) サイズ固定 OFF なら キャンバスを 範囲 画素ずつ広げる       0x1001246f
(2) 輝度カーブ 順変換                                        0x100125d3 / 0x100125e7
(3) 範囲 -> 内部半径 R(0〜45)へ圧縮                        0x100125ec
(4) 画像を R/範囲 倍に縮小(カーブ空間のまま)                0x100126a6 / 0x100126e8
(5) 半径 R の円板で平均                                      0x1001275c / 0x10012781
(6) 輝度カーブ 逆変換                                        0x100127be / 0x100127d6
(7) 元のサイズへ拡大(線形空間)                              0x10012809 / 0x10012852
```

### (3) `範囲` → 内部半径 `R`

```
R = 範囲
if (R > 8)  { R = R/2 + 4
if (R > 16) { R = R/4 + 12
if (R > 32) { R = R/8 + 28
if (R > 45) { R = 45 }}}}
```

3段の折れ線で、区分の境目(`8 → 8`、`24 → 16`、`152 → 32`)がちょうど
つながる。**生値 984 以上で `R = 45` に張り付く**
(`verify_pipeline.py` §1)。

| `範囲` | 1 | 5 | 8 | 9 | 16 | 32 | 64 | 128 | 200 | 400 | 1000 |
| ------ | - | - | - | - | -- | -- | -- | --- | --- | --- | ---- |
| `R`    | 1 | 5 | 8 | 8 | 12 | 17 | 21 | 29  | 32  | 35  | 45   |

### (4) 縮小 ―― `範囲` は半径ではなく縮小率

```
new_w = (R·w + 範囲/2) / 範囲          // 四捨五入
new_h = (R·h + 範囲/2) / 範囲
```

**縮小率 `R/範囲` は「ぼかし半径 / 画像の縮尺」を一定に保つように選ばれて
いる** ―― 縮小画像で半径 `R` は、元画像に戻すとちょうど `範囲` 画素に
なる(`verify_pipeline.py` §2)。

| `範囲` | `R` | 640x480 が | 縮小率 | 元画像でのぼかし半径 |
| ------ | --- | ---------- | ------ | -------------------- |
| 8      | 8   | 640x480    | 1/1.0  | 8                    |
| 16     | 12  | 480x360    | 1/1.3  | 16                   |
| 64     | 21  | 210x158    | 1/3.0  | 64                   |
| 200    | 32  | 102x77     | 1/6.2  | 200                  |
| 1000   | 45  | 29x22      | 1/22.2 | 1000                 |

`範囲 <= 8` では `R = 範囲` なので縮小が起きない。9 以上では必ず縮む。
円板が `O(R²)`、画像が `O((R/範囲)²)` なので、**`範囲` を上げるほど総計算量は
むしろ下がる** ―― 「重い設定ほど速い」という珍しい性質になっている。
代償は**解像度**で、`範囲 = 1000` では 640x480 の画像が 29x22 まで潰されて
から拡大し直される。

### (2)/(6) 輝度カーブ ―― `ぼかし` と共有、ただし無条件

順変換 `0x10070220`(8B)/ `0x10070550`(6B)、逆変換 `0x100703f0` /
`0x10070700` は `ぼかし` の `光の強さ`、`発光` の `拡散速度` と同じヘルパー
([`exp_log_curve.md`](../common/exp_log_curve.md))。`レンズブラー` は
円板の平均をこのカーブ空間で行うので、`ぼかし` と同じ**べき平均**になり、
輝度が 4096 を超えることはない。

**`ぼかし` が `光の強さ > 0` のときだけ呼ぶのに対し、`レンズブラー` は
無条件に呼ぶ**(`verify_registration.py` §4)。ヘルパー側が値を `[1, 100]`
にクランプするので `光の強さ = 0` でも `base = 1.001` のカーブを1往復する。
帰結として:

- **色差が常に 1/16 に量子化される。** `(c+8)>>4` → `<<4` で 4097 段階が
  256 段階に落ち、`+2048` は `+2032` に切られる
  ([`exp_log_curve.md` §5](../common/exp_log_curve.md))。
  `光の強さ = 0` にしてもこれは避けられない。
- 往復の変換パスが2つ余分に走る(`ぼかし` なら 0 のときは走らない)。

### (4)/(7) リサイズ ―― 縮小と拡大で画素形式が違う

工程の順番が `順変換 → 縮小 → ぼかし → 逆変換 → 拡大` なので、
**縮小はカーブ空間、拡大は線形空間**で行われる。これがヘルパーが4本ある
理由で、実際に読む画素形式が違う(`verify_pipeline.py` §5):

| ヘルパー     | 向き | 画素形式                                     |
| ------------ | ---- | -------------------------------------------- |
| `0x10071420` | 縮小 | `{float y; int8 cb; int8 cr; int16 a}`(カーブ空間) |
| `0x100709a0` | 拡大 | `PIXEL_YCA`(int16 ×4)                       |
| `0x10072870` / `0x10072000` | 縮小 / 拡大 | 同・6バイト画素版           |

どれも x 軸 → y 軸の2段分離型で、倍率は Q16 の `(src<<16)/dst`。
縮小のワーカー(`0x10071580` ほか)は**アルファ加重の面積平均**
(部分被覆の端を Q16 の被覆率で重み付けし、色は `(c·wa)>>12` で累積する)
だった。4本とも `レンズブラー` からしか呼ばれない。

## 5. 円板カーネル

`func_proc` が1回だけ作る3つの値:

```
外² = trunc((R + 0.5)²) = R² + R          // g_1011ec60
内² = trunc((R - 0.5)²) = R² - R          // g_1011ec68
除数 = 外² - 内² = 2R                      // g_1011ec64
```

`.25` が両方とも切り捨てられるので、除数はちょうど `2R` になる
(`R = 1..45` の全部で確認、`verify_disc_kernel.py` §1)。ワーカーは
`[-R, +R]²` の正方形を走査して:

```
d² >= 外²  -> 読まない
d² <= 内²  -> 重み 4096
それ以外   -> 重み = ((外² - d²) << 12) / 2R
```

`d²` は `d² += 2·dx + 1` で差分更新されるので、**内側のループに掛け算が
1つも無い**。

- **円の内側は完全に一様**(重み 4096)。ガウシアンでも三角形でもない ――
  [`box_blur.md` §2](../common/box_blur.md) の「一様重みしか無い」がここでも
  成り立ち、違うのは窓の形だけである。
- **境界は1画素幅の線形ランプ**で、`d = R` ちょうどが 2048(半分)。
- 重みの総和 / 4096 が `πR²` に一致する(`R = 45` で 6361.5 対 6361.7)。

### 累積と正規化

```
wa = (a·重み) >> 12                       // 重み 4096 の内側は wa = a
sum_y  += y_float · wa                     // カーブ空間なので float
sum_cb += cb_byte · wa ;  sum_cr += cr_byte · wa
sum_a  += wa ;  sum_w += 重み

out.y  = sum_y / sum_a                                  // float 除算
out.cb = (sum_cb + sum_a/2) / sum_a                     // idiv、四捨五入項つき
out.a  = trunc(sum_a · 4096.0 / sum_w + 0.5)            // 四捨五入
```

アルファを**実際に覆えた面積 `sum_w` で割る**ので、窓が画像の端で
切られてもアルファは薄まらない ―― [`box_blur.md` §3](../common/box_blur.md)
の2つ目の変種で、**`サイズ固定` の ON/OFF はこの除数を変えない**
(`方向ブラー` とはここが違う)。平坦な不透明画像は端でもアルファ 4096 の
ままである。

色差の `+sum_a/2` は 0方向切り捨てと組み合わさるので、**四捨五入になるのは
正の側だけ**。`-1000/7` は厳密には `-142.857` だが実装は `-142` を返す
(`simulate_lens_blur_reference.py` §6)。同じ式の中に float 除算・
`idiv`・`_ftol` の3種類の丸めが同居している例
([`integer_semantics.md`](../common/integer_semantics.md))。

## 6. キャンバス拡張 ―― 4本の帯だけを塗る

`サイズ固定` OFF のとき(既定は ON なので明示的に外したとき)だけ、
**縮小の前に**キャンバスを `範囲` 画素ずつ広げる:

```
rx = 範囲 ;  if (w + 2*範囲 > 最大キャンバス幅) rx = (最大幅 - w)/2
ry = 範囲 ;  if (h + 2*範囲 > 最大キャンバス高) ry = (最大高 - h)/2
table[0x48](対バッファ, 左の帯)     // (0,0,0,0) = 完全な透明で塗る
table[0x48](対バッファ, 右の帯)
table[0x48](対バッファ, 上の帯)
table[0x48](対バッファ, 下の帯)
table[0x44](対バッファ, rx, ry, 元画像, 0, 0, w, h, 0, 0x13000003)   // 中央へ単純コピー
swap ;  w += 2*rx ;  h += 2*ry
```

[`canvas_growth.md` §3](../common/canvas_growth.md) の方式B(事前拡張)と
同じ2関数を使うが、目的が違う ―― 方式Bは「スライディングウィンドウの中段
ループを負にしないため」の足場で `縁取り` はあとで削り戻すのに対し、
**`レンズブラー` の拡張は出力そのものの置き場所**であり最後まで残る。
また**全面クリアではなく上下左右4本の帯だけ**を塗る点も他に例が無い
(中央は直後の矩形転送が埋めるので塗り直す必要がない)。

広げる量が `範囲` 画素なのは、円板の半径が元画像で `範囲` 画素だから
ちょうど過不足がない。上限は最大キャンバスサイズだけで、
確保済みバッファの余白(`fpip+0xEC`/`+0xF0`)は見ていない。

## 7. スレッド分割

[`thread_split.md`](../common/thread_split.md) の (B) だけ(行分割、
`寸法 = h`)。ガード (A) が無いので `シャープ` のような穴も無い。
1〜32スレッドで出力が完全に一致することを再実装で確認済み
(`simulate_lens_blur_reference.py` §5)。

リサイズのヘルパーは自前のディスパッチャ `0x1006c650` で
「`寸法 >= 64` ならマルチスレッド、そうでなければ直接呼ぶ」を選ぶ
(`0x1007144b` の `cmp esi, 0x40; setge`)。

## 10. 未確定事項

- **リサイズのワーカーを読み切っていない。** 縮小側(`0x10071580` ほか)が
  Q16 の被覆率によるアルファ加重の面積平均であることは確認したが、
  拡大側(`0x10070b00` ほか)の補間(最近傍か線形か)と、`0x10070840`
  (拡大の直前に呼ばれる準備ルーチン)の中身は追っていない。
  `simulate_lens_blur_reference.py` が `範囲 <= 8`(縮小が起きない範囲)
  に限っているのはこのためである。
- **`0x1006c650`(リサイズのマルチスレッド ディスパッチャ)の中身**。
  `寸法 >= 64` でフラグを立てて呼ぶところまでしか見ていない。
- **拡大で戻したあとの解像度感**。`範囲 = 1000` では 640x480 が 29x22 まで
  潰されるので、円板の縁が拡大時の補間でどこまでなまるかは実機での確認が
  要る。
- **UI 上どう体感されるかは実機で確認していない。**

以下は全エフェクト共通の未確定事項:

- 最終的な YCbCr→RGB 変換とそのクリップは `aviutl.exe` 側にある ――
  [`rgb_ycbcr.md` §3](../common/rgb_ycbcr.md)
- 輝度カーブヘルパーが使う行幅グローバル `0x10135c68` / `0x10149840` の
  書き込み側 ―― [`exp_log_curve.md` §7](../common/exp_log_curve.md)
