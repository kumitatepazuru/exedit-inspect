# フェード (fade) フィルタ リバースエンジニアリング解析

対象: `data/exedit.auf`(AviUtl 拡張編集の標準フィルタプラグイン)、32bit PE、
`ImageBase = 0x10000000`。以下のアドレスはすべて VA(`RVA = VA - 0x10000000`)。

## 再現方法

すべてのスクリプトは本プロジェクトの `main.py` を踏み台にして実行する。
`main.py` はコマンドラインで指定されたスクリプトに対して、DLLパス
(デフォルト `data/exedit.auf`)とヘッダー一覧(デフォルト `data/filter.h`)を
渡す役割を持つ。

```
uv run main.py inspect/fade/<script>.py
uv run main.py tools.<tool>            # エフェクト非依存の共通ツール。一覧はリポジトリ直下の README
```

| スクリプト                       | 確認していること                                                                                                                                 |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tools.filter_table --name フェード` | 登録エントリが1個(`0x100a5698`、`flag=0x20`)であること、トラックバー2本・チェックボックス0個・`ex_data` 無し・コールバック全 NULL           |
| `decompile_fade.py`              | `0x1004dd40` / `0x1004de20` / `0x1004dea0` を範囲限定 `CFGFast` + angr でデコンパイル。`fp` と `fpip` の取り違えが無いことの独立した裏付けになる |
| `disasm_params.py`               | `func_proc` とワーカーの全命令に注釈。x87 スタックの流れと3つの出口                                                                             |
| `verify_seconds_to_frames.py`    | `イン`/`アウト` の秒→フレーム変換。`fmul st(2)`/`fdiv st(1)` の**宛先レジスタをオペコードバイトで確定**し、全生値・全フレームレートで再現       |
| `verify_timeline.py`             | `fp+0x118`/`fp+0x11C`/`fpip+0xA8`/`fpip+0x118` の同定。exedit 側の充填ルーチン2本と、`fpip->frame` との恒等式                                     |
| `verify_alpha_curve.py`          | ランプが両端に触れないこと、フェードイン側の `< 4096` ガードが死んでいること、`return 0` が `fpip+0x118` 無しでは到達不能なこと                 |
| `verify_worker.py`               | ワーカーが**アルファ(`+6`)しか触らない**こと、対バッファもスクラッチも使わないこと、スレッド分割が安全な形であること                            |
| `verify_audio_twin.py`           | `音量フェード`(`0x1004dea0`)との命令単位の差分。変換部は**オペコード完全一致**、違うのは3点だけ                                                 |
| `simulate_fade_reference.py`     | 上記すべてを織り込んだ整数忠実リファレンス実装。オブジェクト1個分のアルファ推移を描画                                                           |

## 1. 何をするエフェクトか

**オブジェクトの画素のアルファに定数を掛けるだけ**である。掛ける値は
`イン`/`アウト` と「オブジェクトのどのフレームにいるか」だけから決まり、画素の
内容には一切依存しない。`y`/`cb`/`cr` は読まれもしない。

登録は `0x100a5698` の1個だけ(`flag = 0x20` = オブジェクト効果)。フレーム
フィルタ版は存在しない ―― フレーム側の画素は 6バイトの `PIXEL_YC` でアルファを
持たないので、アルファしか触らないエフェクトには置きようがない。**アルファだけを
読み書きするエフェクトが「オブジェクトのみ」登録になる**のは
`境界ぼかし` と同じ理由である。

- チェックボックス **0個**、`ex_data_size = 0`、`func_init`/`func_exit`/
  `func_update`/`func_WndProc` **すべて NULL**。UI コードは1バイトも無い。
- グローバルは `0x101a5390` **1個**だけ(Q12 のアルファ)。
- キャンバス拡張なし、対バッファ(`fpip+0xB0`)なし、スクラッチなし。
  オブジェクト画像 `*(fpip+0xAC)` を**その場で**書き換える。

エフェクト固有コードは `0x1004dd40`〜`0x1004de95` の **342バイト・2関数**
(`func_proc` 211バイト・74命令 / ワーカー 118バイト・45命令、間に nop 13バイト)。
`凸エッジ` の846バイト、`ルミナンスキー` の959バイトを下回り、**解析済みで最小**。

## 2. パラメータ

トラックバーは `fp->track[]` の順に `イン`(初期値50、範囲0~1000)、
`アウト`(50、0~1000)。`+0x74` 拡張ブロック(`0x100a5688`)は4スロットのうち
**表示スケール `{100, 100}` だけが非 NULL** で、グループ化マーカーもドラッグ範囲も
持たない([`param_scaling.md` §1](../common/param_scaling.md))。

| トラックバー | 表示スケール | UI表示範囲 | スライダーで届く範囲 |
| ------------ | ------------ | ---------- | -------------------- |
| `イン`       | 100          | 0.00~10.00 | 0.00~10.00(全域)   |
| `アウト`     | 100          | 0.00~10.00 | 0.00~10.00(全域)   |

つまり**生値は 1/100 秒単位**で、初期値 50 は 0.50 秒にあたる。

`func_proc` はこれをフレーム数に直す。全エフェクト共通の `/1000` マジック除算
(`0x10624dd3`)は**1箇所も無く**、x87 と `_ftol` だけを使う
([`object_time.md` §4](../common/object_time.md)):

```
in_frames  = trunc(イン   * rate / (scale * 100))     // _ftol = 0方向切り捨て
out_frames = trunc(アウト * rate / (scale * 100))
```

`rate` / `scale` は `*(fpip+0xFC)` / `*(fpip+0x100)` にあるフレームレートの
分子・分母。**四捨五入ではないので、29.97fps では既定の `0.50` 秒が14フレーム
(30fps なら15フレーム)になる**。1フレームに満たない指定(30fps で 0.03 秒
以下)は 0 フレームに落ち、そのままフェードが消える。

| 生値 | UI     | 24fps | 23.976 | 29.97 | 30fps | 59.94 | 60fps |
| ---- | ------ | ----- | ------ | ----- | ----- | ----- | ----- |
| 3    | 0.03 s | 0     | 0      | 0     | 0     | 1     | 1     |
| 50   | 0.50 s | 12    | 11     | 14    | 15    | 29    | 30    |
| 100  | 1.00 s | 24    | 23     | 29    | 30    | 59    | 60    |
| 1000 | 10.00s | 240   | 239    | 299   | 300   | 599   | 600   |

x87 スタックの使い方には1つ注意点がある。除数 `rate` と `scale*100` は
**1回目の `_ftol` を跨いでスタックに残され**、2本目の変換で再利用される
(`fmul st(2)` / `fdiv st(1)` はどちらも `ST(0)` を宛先にする `D8` 形式で、
capstone の1オペランド表記からは読み取れない ――
`verify_seconds_to_frames.py` §1 がオペコードバイトで確定している)。

## 3. どのフレーム番号を読むか

これが本エフェクトで一番重い部分で、共通ドキュメント
[`inspect/common/object_time.md`](../common/object_time.md) に切り出してある。
要点だけ:

```
t = *(fpip+0xA8) - fp[0x118] - *(fpip+0x118)      // フェードイン用
u = fp[0x11C]    - *(fpip+0xA8)                   // フェードアウト用
```

- `fpip+0xA8` = **現在のフレーム(タイムライン絶対)**。`時間制御` 適用後の値。
- `fp+0x118` / `fp+0x11C` = **オブジェクト全体**の開始・終了フレーム。
  **中間点で分割されていてもチェーン全体**を指す(exedit の充填ルーチン
  `0x10047fc7` がチェーンをたどって先頭の開始と末尾の終了を入れる)。
  区間ごとの `fp+0xEC` / `fp+0xF0` は読まない ―― **中間点を打ってもフェードは
  オブジェクト全体で1回**である。
- `fpip+0x118` = そのサブオブジェクト固有の遅延[フレーム]。イメージ中でこれを
  変える書き込みは `テキスト` の1文字描画コールバック(`0x1008b2f2`)だけで、
  `表示速度` から作られる。

同じ充填ルーチンが `fpip->frame` と `fpip->frame_n`(SDK のフィールド)を
**いま入れたばかりの `fp+0x118`/`fp+0x11C` から**作っているので、

```
fpip->frame   == *(fpip+0xA8) - fp[0x118]
fpip->frame_n == fp[0x11C] - fp[0x118] + 1
```

が恒等式として成り立つ。つまり `フェード` は SDK の2フィールドで書けたはずの
ことを分解した形で書いている(`+0x1C`/`+0x20` への参照は0件)。

## 4. アルファのランプ

```
g = 4096
if (t < in_frames)  { a = ((t+1) << 12) / (in_frames  + 1);  if (a < 4096) g = a; }
if (u < out_frames) { a = ((u+1) << 12) / (out_frames + 1);  if (g > a)    g = a; }
```

分子・分母の**両方に `+1` が付く**のがこの式の性格を決めている
(`verify_alpha_curve.py`):

- フェードインの最初のフレームは `4096/(N+1)` で、**0 にはならない**。
  完全に透明なフレームは1枚も無い。
- 最後のランプ値は `N*4096/(N+1)` で **4096 に届かない**。満不透明は
  「分岐に入らなかった」ときにしか出ない。したがって長さ N のフェードは
  **ちょうど N フレーム**を占め、N+1 フレーム目から不透明になる。
- フェードイン側の `if (a < 4096)` は**到達しない死んだガード**である
  (`t <= in_frames-1` なので商は必ず 4096 未満)。フェードアウト側は
  `if (g > a)` という本物の min で、こちらは働く。

2本の min なので、**`イン + アウト` がオブジェクトの長さ以上だと最大不透明度が
1 未満に頭打ちになる**。既定値(0.50 + 0.50 秒)は30fpsで30フレームぶんなので、
**1秒ちょうどのオブジェクトは既定設定では最大 3840/4096 = 93.8% までしか
不透明にならない**。しかも2本とも「オブジェクト全体」から計算されるので、
この頭打ち値はフレームによらずオブジェクトの長さだけで決まる。

| N(フレーム) | 1枚目 | 2枚目 | ... | N枚目 | N+1枚目 |
| ------------ | ----- | ----- | --- | ----- | -------- |
| 1            | 2048  | ―    |     | 2048  | 4096     |
| 12           | 315   | 630   |     | 3780  | 4096     |
| 15           | 256   | 512   |     | 3840  | 4096     |
| 30           | 132   | 264   |     | 3963  | 4096     |

## 5. 3つの出口 ―― `return 0` を返す珍しいエフェクト

```
if (g >= 4096) return 1;      // 何もせずに帰る。ワーカーすら起動しない
if (g <= 0)    return 0;      // ★
                              // それ以外: exec_multi_thread_func 1回、return 1
```

`func_proc` が **0 を返す**のは解析済み81個の `func_proc` のうち20個だけで、
`フェード`/`音量フェード`/`ワイプ`/`グロー` などが持つ。exedit のディスパッチ
(`0x1004993e` / `0x10049fab`)は戻り値を `1` と比較し、違えばそのオブジェクトの
エフェクト列ループを抜ける。前者はそのまま関数ごと `return` するので、
**そのオブジェクトは以降まったく描画されない**。

ただし `t = *(fpip+0xA8) - fp[0x118]` と `u = fp[0x11C] - *(fpip+0xA8)` は、
exedit がそのオブジェクトを描くフレームでは必ず 0 以上である(§3 の恒等式:
`t == fpip->frame`)。**したがって `return 0` は `fpip+0x118` が無ければ
到達不能**で、`イン` をオブジェクトより長くしても落ちはしない(最後まで
薄いままになるだけ)。この出口が存在するのは `テキスト` の
`文字毎に個別オブジェクト` + `表示速度` のためで、**まだ出現していない文字は
`t < 0` → アルファ ≤ 0 → 描画されない**。

`(t+1) << 12` は `shl` なので負の `t` でも符号のまま流れ、`cdq`+`idiv` が
0方向へ切り捨てるため、`t <= -1` は必ず 0 以下になる。

## 6. ワーカー `0x1004de20`

```
y_begin = h * tid       / thread_num           // idiv、0方向切り捨て
y_end   = h * (tid + 1) / thread_num
if (y_begin >= y_end) return;                  // ガード (B) のみ

for (y = y_begin; y < y_end; y++) {
    p = (char*)*(fpip+0xAC) + *(fpip+0xEC) * y * 8 + 6;   // アルファ
    for (x = 0; x < *(fpip+0xB4); x++) {
        *(short*)p = (short)((*(short*)p * g_101a5390) >> 12);   // sar = floor
        p += 8;
    }
}
```

- **触るのは 8バイト画素の `+6`(アルファ)だけ**。16bit のロード1個・ストア
  1個がどちらもこのアドレスで、`y`/`cb`/`cr` のオフセット 0/2/4 は
  一度も出てこない(`verify_worker.py` §1)。アルファだけを操作する点は
  `境界ぼかし` と同じだが、あちらと違って**近傍を読まない**ので
  キャンバスも動かない。
- 使うバッファは `*(fpip+0xAC)` **1本だけ**。対バッファも共有スクラッチ
  `[0x101a5328]` も出てこないので、入れ替え(ping-pong)も無い。
  完全な in-place という点では `モザイク` と同類。
- `>> 12` は `sar`(floor)。アルファは非負なので `idiv`(0方向切り捨て)との
  差は出ない ―― ただし `音量フェード` では出る(§8)。
- `a' = floor(a * g / 4096) <= a` なので、**フェードはアルファを減らすことしか
  できない**。半透明のオブジェクトは自分の不透明度からフェードし、
  `透明度` など他のアルファ操作とは単純な掛け算で合成される。
- スレッド分割は**行**分割で、`寸法 < thread_num` のガード (A) を持たない
  安全な形([`thread_split.md` §1](../common/thread_split.md))。行ループの
  外に無条件の書き込みも無いので、§4 の重複書き込み問題も起きない。
  1画素高のオブジェクトでも正しく処理される。

## 7. `イン`/`アウト` の実効的な意味

以上をまとめると、UI の `イン = X 秒` は次のように振る舞う:

1. `N = trunc(X * fps)` フレームに丸められる(0方向)。
2. オブジェクト開始から `N` フレームぶん、アルファに
   `(k+1)/(N+1)`(`k` = 0..N-1)が掛かる。
3. `N` フレーム目以降は等倍。
4. `アウト` も同じ形で終端から数え、両者の**小さいほう**が採用される。

「フェードが終わった瞬間に不透明になる」のではなく、**最後のフェードフレームが
`N/(N+1)` で、その次のフレームで 1 に飛ぶ**という 1/(N+1) の段差がある。
`N = 1`(30fps では生値 4~6 = 0.04~0.06 秒)では 2048 → 4096 と**倍に飛ぶ**ので、
極端に短いフェードは見た目に段が出る。

## 8. 音声版 `音量フェード`(`0x1004dea0`)

配列の別エントリ(添字89、`0x100a5810`、`flag = 0x00200020`)として登録された
**別エフェクト**だが、`.text` 上で `フェード` の直後に置かれた双子である。
トラックバーの名前・範囲・初期値・表示スケールはすべて同一で、秒→フレーム
変換のブロックは**オペコード単位で完全に一致**する(`verify_audio_twin.py` §2)。

違いは3点だけ:

| | `フェード` | `音量フェード` |
| - | ---------- | -------------- |
| アルファの置き場 | グローバル `0x101a5390` | レジスタ `ebp` |
| `*(fpip+0x118)` | 引く | **引かない** |
| 適用先 | `exec_multi_thread_func` で `*(fpip+0xAC)` の α | インラインループで `*(fpip+0x104)` の PCM |

グローバルが要るのは、`exec_multi_thread_func` がパラメータを2個しか渡せない
から([`filter_registration.md` §6](../common/filter_registration.md))。
ワーカーを持たない `音量フェード` はそれが不要で、結果として
**専用グローバルを1つも持たない**(`ルミナンスキー` に次ぐ2例目)。

サンプルは `*(fpip+0x104)`(exedit 独自の 16bit PCM バッファ。SDK の
`audiop`(`+0x2C`)ではない ―― `モノラル化` `0x1006ab3d` も同じ番地を読む)を
`audio_ch * audio_n` 個ぶん、`(s * g) >> 12` で処理する。

ここで `sar` が効いてくる: **PCM サンプルは負になりうる**ので、
`sar`(floor)と `idiv`(0方向切り捨て)が実際に食い違い、負側のサンプルだけが
1LSB 下へ丸められる([`integer_semantics.md` §1](../common/integer_semantics.md))。
無音をフェードすると 0 ではなく -1 が並ぶ、という程度の影響。

## 10. 未確定事項

- 通常のオブジェクトで `*(fpip+0x118)` に何が入っているか。イメージ中の
  書き込みは `テキスト` 経由の3箇所だけで、`FILTER_PROC_INFO` がどこで最初に
  構築されるかは本プロジェクトでは追えていない。0 である前提で読んでいる
  ([`object_time.md` §5](../common/object_time.md))。
- `*(fpip+0xFC)` / `*(fpip+0x100)` の**書き込み側**。フレームレートの分子・分母
  であることは2方向の使われ方から確定しているが、どこで埋まるかは未追跡
  (`0x10135c68` と同じ形の宿題)。
- `fpip+0x12C`(`時間制御` の時刻表)を書く側。`時間制御` の `func_proc` は
  `xor eax,eax; ret` の2命令しかない([`object_time.md` §6](../common/object_time.md))。
- exedit のディスパッチが `func_proc` の戻り値 0 を受けたあと、そのオブジェクトの
  描画パイプラインのどこまでが飛ばされるか。`0x1004993e` の側は関数ごと
  `return` することまで確認したが、`0x10049fab` の側は内側ループを抜けるだけで、
  その先は追っていない。
- 最終的な YCbCr→RGB 変換とそのクリップは `aviutl.exe` 側にある ――
  [`rgb_ycbcr.md` §3](../common/rgb_ycbcr.md)
