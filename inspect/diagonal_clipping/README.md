# 斜めクリッピング (diagonal clipping) フィルタ リバースエンジニアリング解析

対象: `data/exedit.auf`(AviUtl 拡張編集の標準フィルタプラグイン)、32bit PE、
`ImageBase = 0x10000000`。以下のアドレスはすべて VA(`RVA = VA - 0x10000000`)。

## 再現方法

すべてのスクリプトは本プロジェクトの `main.py` を踏み台にして実行する。

```
uv run main.py inspect/diagonal_clipping/<script>.py
uv run main.py tools.<tool>            # エフェクト非依存の共通ツール。一覧はリポジトリ直下の README
```

| スクリプト                                | 確認していること                                                                                                                                             |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tools.filter_table --name 斜めクリッピング` | 登録が1個(`0x100a7490`、`flag=0x20`)、トラックバー5本、チェックボックス0個、`ex_data` 無し、`func_proc` 以外のコールバック全 NULL であること                 |
| `decompile_diagonal_clipping.py`          | 1016バイト全域を range 限定デコンパイル。手読みした制御フローの独立な裏付け(`幅` の符号で丸ごと2つに割れること、書くのがアルファだけであること)              |
| `disasm_params.py`                        | `func_proc` と2ワーカーの**全命令**に注釈。パラメータ→グローバル、符号付き距離の漸化式、3分岐の `m` の作り方、共通の末端                                       |
| `verify_registration.py`                  | 登録内容、1016バイトが連続していること、ワーカーが関数ポインタ経由でしか到達できないこと、グローバル6個が中に閉じていること、外に出るのが `_ftol` と共有 LUT だけであること |
| `verify_direction.py`                     | `角度` → Q16 の法線ベクトル。**`sin` 側が x、`cos` 側が y** であることを命令の対応から確定(`angle_vector.md` §6 の保留を解消)。帯幅が `\|v\|` を取り直して作られる意味 |
| `verify_edge_ramp.py`                     | `ぼかし+1`、イージング表 `0x101dcf78`、除数 `ceil(band/256)` が**添字を表からはみ出させない唯一のガード**であること、`m*16` の int32 余裕、アルファが減る一方であること |
| `verify_clip_geometry.py`                 | `幅` が選ぶ3モードの式を Python 再実装で検算。階調帯の位置(centered / 内側 / 外側)、半平面の対は足すと元に戻るが帯の対は戻らないこと、`幅 = 0` の左右の不連続 |
| `simulate_diagonal_clipping_reference.py` | 上記すべてを織り込んだ整数忠実リファレンス。マスクを ASCII で描画                                                                                             |

## 1. 何をするエフェクトか

**オブジェクトを1本の直線で切り落とす**エフェクト。直線は
`中心X`/`中心Y` が通る点を、`角度` が向きを決める。`ぼかし` は切り口の
階調幅で、`幅` は「片側を落とす(半平面)」を「直線を挟む帯を残す/消す」に
切り替える。

やっていることは**オブジェクト自身のアルファに 0〜4096 の係数を掛ける**
だけで、`y`/`cb`/`cr` は一度も読まない。キャンバスも動かさず、対バッファ
(`fpip+0xB0`)も使わず、共有ワーカーも1つも呼ばない ―― [`フェード`](../fade/README.md)
の「アルファに定数を掛ける」、[`ワイプ`](../wipe/README.md) の「アルファに
マスクを掛ける」と同じ系統で、マスクの中身が**直線からの符号付き距離**に
なったもの。アルファは減る一方なので、このエフェクトでオブジェクトが
はみ出すことはない(だからキャンバス拡張も `サイズ固定` も要らない)。

名前の似た `クリッピング`(`0x10014580`、本プロジェクト未解析)とは別実装で、
そちらはトラックバーが `上`/`下`/`左`/`右` の4本(それぞれ 0~4000)＋
チェックボックス `中心の位置を変更` 1個 ―― UI からしてこちらとは別物である。

## 2. 登録エントリ ―― 1016バイト、UI コードは1バイトも無い

登録は `0x100a7490` の1個だけ(`flag = 0x20` = オブジェクト効果)。
フレームフィルタ版は存在しない。

| 項目                | 値                                                       |
| ------------------- | -------------------------------------------------------- |
| `func_proc`         | `0x1005cab0`                                             |
| 他のコールバック    | `func_init` / `func_exit` / `func_update` / `func_WndProc` すべて NULL |
| `track_n`           | 5 (`中心X` `中心Y` `角度` `ぼかし` `幅`)                 |
| `check_n`           | **0** ―― チェックボックスもコンボもボタンも無い          |
| `ex_data_size`      | **0** ―― `ex_data_def` も `+0x70` フィールド表も無い     |
| `+0x74` 拡張ブロック | `0x100a747c`。表示スケール `{0,0,10,0,0}`(0 = 割らない)とドラッグ範囲は持つ、グループ化マーカーはポインタごと NULL |

`check_n = 0` かつ `ex_data_size = 0` かつコールバック全 NULL、つまり
[`凸エッジ`](../convex_edge/README.md) と同じ「**UI 関連のコードが1バイトも
無い**」形である。exedit の100登録のうちこの形は22個あるが、**トラックバーが
5本あるのは斜めクリッピングだけ**(次点は `画像ループ` / `極座標変換` の4本)。

エフェクト固有コードは `0x1005cab0`〜`0x1005cea7` の連続した **1016バイト・
3関数・329命令**で、間は16バイト境界合わせの `nop` 20バイトだけ。解析済みでは
`フェード`(342)/ `凸エッジ`(846)/ `ルミナンスキー`(959)に次いで4番目に小さい。
`_ftol`(`0x10091ad8`)以外の直接呼び出しは無く、外から読むのは
イージング表 `0x101dcf78` の1本だけ(`verify_registration.py`)。

グローバルは `0x101b20c4`〜`0x101b20d8` の6個で、参照は**すべて**この
1016バイトの中に閉じている。`exec_multi_thread_func` が `fp`/`fpip` 以外を
渡せない([`filter_registration.md` §6](../common/filter_registration.md))
ためのグローバルである。

## 3. パラメータ

`fp->track[]` の順に `中心X`(初期値0、範囲-2000~2000)、`中心Y`(0、-2000~2000)、
`角度`(0、-36000~36000)、`ぼかし`(**1**、0~2000)、`幅`(0、-2000~2000)。

| トラックバー | 表示スケール | UI表示範囲       | ドラッグ範囲    | 意味                                        |
| ------------ | ------------ | ---------------- | --------------- | ------------------------------------------- |
| `中心X`      | 1            | -2000~2000       | -1000~1000      | 直線が通る点の x = `w/2 + 中心X` [画素]     |
| `中心Y`      | 1            | -2000~2000       | -1000~1000      | 同・y = `h/2 + 中心Y` [画素]                |
| `角度`       | 10           | -3600.0~3600.0   | 0.0~360.0       | 法線の向き[度]。**10回転ぶん指定できる**    |
| `ぼかし`     | 1            | 0~2000           | 0~1000          | 切り口の階調幅 - 1 [画素]                   |
| `幅`         | 1            | -2000~2000       | -1000~1000      | 帯の**全幅**[画素]。符号でモードが変わる(§6) |

`+0x74` 拡張ブロックの読み方は
[`param_scaling.md`](../common/param_scaling.md) 参照。`角度` の生値範囲
`±36000` は `方向ブラー` / `色ずれ` / `グラデーション` と同じで、
`±3600`(±360.0度)の `凸エッジ` より一桁広い ―― 連続回転のアニメーションを
数値入力で書けるようにするためと読める。

**`ぼかし` の既定が 0 ではなく 1 なのは表示上の話で、実装は常に `ぼかし+1` を
使う**(§5)。

`中心X`/`中心Y` は名前も意味も対だが、`+0x74` のグループ化マーカーは
**全ゼロ**である ―― 同じ `中心X`/`中心Y` を持つ `波紋` が `{+1, -1}` で
2成分コントロールにまとめているのと対照的で、AviUtl の UI 上は独立した
スライダー2本として出る(`verify_registration.py`)。

## 4. 直線の表し方 ―― `角度` から Q16 の法線ベクトルへ

`func_proc` は5本のトラックバーをグローバル6個に畳むだけで、画素には一切
触らない:

```
g_101b20c8 = w/2 + 中心X                       // 直線が通る点 cx [画素]
g_101b20cc = h/2 + 中心Y                       // 同 cy
g_101b20d8 = ぼかし + 1
θ          = 角度 * pi/1800                    // 表示スケール10 = 1/10度単位
g_101b20d0 = vx = trunc(sin(θ) *  65536.0)    // _ftol は0方向切り捨て
g_101b20d4 = vy = trunc(cos(θ) * -65536.0)
g_101b20c4 = hw = 幅 << 15                     // Q16 での 幅/2 = 「半値幅」
```

`fsin`/`fcos` → Q16 という定型そのもので、`+sinθ` / `-cosθ` の符号の付け方は
`グラデーション` と同じ列に入る([`angle_vector.md` §2](../common/angle_vector.md))。

ワーカーは各画素について

```
s(x, y) = vx*(x - cx) + vy*(y - cy)            // Q16 の符号付き距離
```

を作る。実装は乗算をせず、行ごとに `vy*y + base` を組んでから列を進めるたびに
`s += vx` するだけなので、**丸めが一度も入らず誤差が溜まらない**。
`|v| = 65536` が1画素なので `s/65536` がそのまま「直線からの符号付き距離
[画素]」になる。

### 軸の割り当て ―― `sin` 側が x

[`angle_vector.md` §6](../common/angle_vector.md) が「Q16 の2値を作るところ
までは同じだが、どちらを x に使うかはワーカーを読んでいない」として保留して
いた点は、本エフェクトについては命令の対応で確定する
(`verify_direction.py` §2):

| 命令                                     | 言っていること           |
| ---------------------------------------- | ------------------------ |
| `0x1005cc19  imul edx, eax` (`edx=中心X`, `eax=g_d0`) | `中心X` と組むのは `sin` 側 |
| `0x1005cbe9  imul ecx, [0x101b20d4]` (`ecx=中心Y`)    | `中心Y` と組むのは `cos` 側 |
| `0x1005cc41  imul ecx, edi` (`ecx=g_d4`, `edi=行番号`) | y に掛かるのは `cos` 側    |
| `0x1005cc85  add ecx, eax` (列を1つ進めるたび、`eax=g_d0`) | x に掛かるのは `sin` 側 |

したがって画面座標(y は下向き)では:

| `角度` | `(vx, vy)` 単位 | 法線の向き | `幅 = 0` で残る側 |
| ------ | --------------- | ---------- | ----------------- |
| `0.0`  | `(0, -1)`       | 上         | 直線より**上**    |
| `45.0` | `(+0.707, -0.707)` | 右上    | 直線より右上      |
| `90.0` | `(+1, 0)`       | 右         | 直線より右        |
| `180.0`| `(0, +1)`       | 下         | 直線より下        |
| `270.0`| `(-1, 0)`       | 左         | 直線より左        |

**`角度 = 0` は法線が上を向き、正の角度で画面上を時計回りに回る。** 既定値
(`中心` も `幅` も 0)では、オブジェクトの上半分が残って下半分が消える。
`凸エッジ` の `(-sinθ, +cosθ)` はこれのちょうど逆向きで、同じ `角度 = 0` が
向こうでは「下」になる ―― 符号の2系統が実際に逆を向くことの確認でもある。

なお実機で見比べたわけではなく、命令列とその Python 再実装からの帰結である。

## 5. 階調帯 ―― `ぼかし+1` とイージング表

帯幅はワーカーの先頭で1回だけ作られる:

```
band = trunc( sqrt(vx² + vy²) * (ぼかし+1) )    // fild/fmul/faddp/fsqrt/fimul/_ftol
div  = (band + 255) / 256                       // = ceil(band/256)
```

`65536` を決め打ちせず、**`_ftol` 済みの成分から長さを取り直している**のが
効いていて、`s` と `band` の単位が必ず一致する。おかげで階調帯の幅は
`band/|v| = ぼかし+1` 画素ちょうどになり、**角度によらない**(全72001角度で
誤差 2e-5 画素以内、`verify_direction.py` §4)。

3つの分岐は末端の十数命令が完全に共通で、`m`(下記 §6)が決まったあとは:

```
m >= band  -> アルファを触らない
m <= 0     -> アルファ = 0
それ以外   -> alpha = (alpha * table[ m*16 / div ]) >> 12
```

`table` は共有の 1-cos イージング表 `0x101dcf78`
([`lut_tables.md`](../common/lut_tables.md)、`table[i] = trunc(2048*(1-cos(i*pi/4096)))`)。
`table[i] <= 4096` と `sar 12`(floor)から `alpha' <= alpha` が常に成り立ち、
**アルファは減ることしかできない**。

### `ぼかし = 0` でもハードエッジにはならない

`func_proc` の `inc eax`(`0x1005caf0`)で `ぼかし` は必ず +1 される。生値 0 でも
階調帯は 1 画素残るので、**このエフェクトでジャギーのある切り口は作れない**。
斜めの直線を扱う以上そうでないと困る、という設計と読める ―― `ぼかし = 0` が
ハードエッジになる [`ワイプ`](../wipe/README.md) との違い。

| `d`(法線方向の距離[画素]) | `ぼかし=0` | `ぼかし=1` | `ぼかし=4` |
| ------------------------- | ---------- | ---------- | ---------- |
| `-1.00`                   | 0.0000     | 0.0000     | 0.2058     |
| `-0.25`                   | 0.1462     | 0.3086     | 0.4216     |
| `0.00`                    | 0.4998     | 0.4998     | 0.4998     |
| `+0.25`                   | 0.8535     | 0.6912     | 0.5779     |
| `+1.00`                   | 1.0000     | 1.0000     | 0.7937     |

### `ceil` が唯一の範囲ガード

添字は `m*16 / div` で、`m < band` なので `m*4096/band` の切り下げ側、
つまり必ず `4095` 以下に収まる。**これが成り立つのは除数が `ceil(band/256)`
だから**で、`floor(band/256)` だったら `band mod 256 >= 2` のときに添字が
4096 を超える。`band` が 256 の倍数にならない角度は普通にある(45.0度・
`ぼかし=0` で `band = 65534`、添字は最大 4111 まで伸びる)ので、これは
机上の話ではない。はみ出す先は表の直後3ワードのパディングと、その次に
置かれた sin テーブル `0x101def80` ―― 落ちはせず、境界の階調が壊れる
(`verify_edge_ramp.py` §4)。

`m*16` の側は `ぼかし = 2000`(生値の上限)で `2098200560` = `INT32_MAX` の
97.7%。`ぼかし` の上限が 2048 だったらここは溢れていた。

## 6. `幅` が選ぶ3つのモード

`func_proc` は `shl edx, 0xf` の ZF だけを見てワーカーを選び、`幅 != 0` 側は
さらに符号で2変種に割れる。3つの違いは `s` から `m` を作るところに凝縮
されている:

| `幅`  | ワーカー     | `m`            | 残る領域(`d = s/65536` [画素]) |
| ----- | ------------ | -------------- | ------------------------------ |
| `= 0` | `0x1005cb70` | `s + band/2`   | `d >= +(ぼかし+1)/2` が不透明、`d <= -(ぼかし+1)/2` が透明。**階調帯は直線の上に centered** |
| `> 0` | `0x1005ccb0` | `hw - \|s\|`     | `\|d\| <= 幅/2` が可視で、`\|d\| <= 幅/2 - (ぼかし+1)` が不透明。**帯を残す** |
| `< 0` | `0x1005ccb0` | `\|s\| + hw`     | `\|d\| <= \|幅\|/2` が透明で、`\|d\| >= \|幅\|/2 + (ぼかし+1)` が不透明。**帯を消す** |

`hw = 幅 << 15` は Q16 での `幅/2`、つまり **`幅` は帯の全幅**である。

### 階調帯の位置が3つで違う

半平面版だけが `base` に足した `band/2` をそのまま使い、帯版は行ごとに
`sub ecx, band/2` で引き戻している(2つのワーカーが同じ prologue を共有した
結果の非対称)。実際の効き方は:

* `幅 = 0` ―― 階調は直線を**またいで**乗る。`d = 0` でちょうど 0.4998。
* `幅 > 0` ―― アルファ 0 の境目が `|d| = 幅/2` **ちょうど**で、階調は帯の
  内側へ `ぼかし+1` 画素伸びる。
* `幅 < 0` ―― アルファ 0 の境目はやはり `|d| = |幅|/2` ちょうどで、階調は
  帯の**外側**へ伸びる。

### 対にしても元に戻るのは半平面だけ

`table[i] + table[4096-i]` は実数では 4096 ちょうど(切り捨てで 4095、
`i = 2048` の1点だけ 4094)なので、**`角度 = θ` と `角度 = θ+180` の
半平面2枚は足すとアルファが元に戻る**(実測で誤差 2/4096 以内)。
オブジェクトを斜めに2分割してから別々に動かす、という使い方が破綻しないのは
このおかげである。

**ところが `幅 = +W` と `幅 = -W` の対は戻らない。** `|d| = W/2` では
`m = hw - |s|` も `m = |s| - hw` も 0 なので、境目で両方とも透明になり、
`2(ぼかし+1)` 画素ぶんの切れ目が残る(`verify_clip_geometry.py` §5)。

### `幅 = 0` の左右で挙動が飛ぶ

24x24・`ぼかし=1` での可視画素数(`verify_clip_geometry.py` §6):

| `幅`  | 可視 | 完全不透明 | 意味               |
| ----- | ---- | ---------- | ------------------ |
| `-4`  | 456  | 408        | 4px幅の帯を消す    |
| `-1`  | 552  | 456        | 1px幅の帯を消す    |
| `0`   | 312  | 288        | **上半分を残す**   |
| `+1`  | 24   | 0          | 1px幅の帯を残す    |
| `+4`  | 72   | 24         | 4px幅の帯を残す    |

生値を1つ動かしただけで可視画素が 96% ⇄ 4% に飛ぶ。**`幅` は 0 をまたいで
連続なパラメータではなく、3つのモードのセレクタである。** `幅` を 0 から
アニメーションさせると、途中でどちらの側へ動いても不連続な切り替わりが
起きることになる(実機での見え方は未確認)。

もう1つの帰結として、**`幅 > 0` かつ `幅 < 2(ぼかし+1)` では完全不透明な画素が
1つも残らない**。帯が階調帯より細いので、中心線ですら `table[hw*4096/band]`
倍にしかならない。しきい値はちょうど `幅 = 2(ぼかし+1)`。

## 7. 適用先とスレッド分割

ワーカーは `*(fpip+0xAC)`(オブジェクトの画像、8バイト/画素 PIXEL_YCA)の
`+6`(アルファ)だけを in-place で読み書きする。行幅は `*(fpip+0xEC)` [画素]、
寸法は `*(fpip+0xB4)` / `*(fpip+0xB8)`。**`fp`(param1)は一度も参照されず、
その引数スロットは `band` や `w` の置き場として潰されている**
(`0x1005cbfa` / `0x1005cb8a`)―― パラメータは全部グローバルに入っているので、
ワーカーが必要とするのは `fpip` だけである。

分割は [`thread_split.md`](../common/thread_split.md) の (B) だけの形:

```
y0 = h*tid / thread_num;  y1 = h*(tid+1) / thread_num
if (y0 >= y1) return;
```

`寸法 < thread_num` でも担当が空のスレッドが増えるだけで、どの行も必ず
どれか1つのスレッドが処理する。行ループの外に書き込みが無いので
[`thread_split.md` §4](../common/thread_split.md) の重複書き込みも起きない
―― 1〜32スレッドで結果が完全に一致することを確認済み
(`verify_clip_geometry.py` §8)。

## 9. 参照テーブル

`角度` → Q16 法線ベクトル(`trunc` は0方向切り捨て):

| `角度` | `vx` | `vy` | `\|v\|` | `ぼかし=1` の `band` |
| ------ | ---- | ---- | ----- | -------------------- |
| `0.0`   | 0      | -65536 | 65536.000 | 131072 |
| `30.0`  | 32768  | -56755 | 65535.272 | 131070 |
| `45.0`  | 46340  | -46340 | 65534.656 | 131069 |
| `60.0`  | 56755  | -32767 | 65534.772 | 131069 |
| `90.0`  | 65536  | 0      | 65536.000 | 131072 |

`幅` の効き方(`ぼかし = b`、`d` は直線からの符号付き距離[画素]):

| `幅`   | 完全不透明          | 階調                              | 完全透明        |
| ------ | ------------------- | --------------------------------- | --------------- |
| `0`    | `d >= (b+1)/2`      | `-(b+1)/2 < d < (b+1)/2`          | `d <= -(b+1)/2` |
| `+W`   | `\|d\| <= W/2 - (b+1)` | `W/2 - (b+1) < \|d\| < W/2`        | `\|d\| >= W/2`    |
| `-W`   | `\|d\| >= W/2 + (b+1)` | `W/2 < \|d\| < W/2 + (b+1)`        | `\|d\| <= W/2`    |

## 10. 未確定事項

- **UI 上どう体感されるかは実機で確認していない。** §4 の「`角度 = 0` で
  上半分が残る」も、§6 の「`幅 = 0` の左右で飛ぶ」も、命令列とその Python
  再実装からの帰結である。オブジェクトバッファの行 0 が画面の上端に対応する
  という前提も、他エフェクトと共通の読みをそのまま引き継いでいる。
- **`角度` の生値範囲が ±3600.0 度(10回転)である理由。** `方向ブラー` /
  `色ずれ` / `グラデーション` と同じ値なので、このエフェクト固有の意味が
  あるわけではなさそうだが、なぜ 10 回転なのかは分からない。
- `幅` が `<< 15`(`/2` を Q16 化)であることは式から確定しているが、
  UI の「幅」が帯の全幅を指すという読み方自体は、その式からの解釈である。
