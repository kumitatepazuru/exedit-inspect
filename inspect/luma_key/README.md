# ルミナンスキー (Luminance Key) フィルタ リバースエンジニアリング解析

対象: `data/exedit.auf`(AviUtl 拡張編集の標準フィルタプラグイン)、32bit PE、
`ImageBase = 0x10000000`。以下のアドレスはすべて VA(`RVA = VA - 0x10000000`)。

## 再現方法

すべてのスクリプトは本プロジェクトの `main.py` を踏み台にして実行する。
`main.py` はコマンドラインで指定されたスクリプトに対して、DLLパス
(デフォルト `data/exedit.auf`)とヘッダー一覧(デフォルト `data/filter.h`)を
渡す役割を持つ。

```
uv run main.py inspect/luma_key/<script>.py
uv run main.py tools.<tool>            # エフェクト非依存の共通ツール。一覧はリポジトリ直下の README
```

| スクリプト                                 | 確認していること                                                                                                                                                                                                 |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tools.filter_table --name ルミナンスキー` | `FILTER_DLL` 配列(先頭 `0x100a3e28`)から登録エントリ `0x100a7d60` を抽出。**オブジェクト効果1個のみ**、トラックバー2本・コンボボックス1個、`ex_data` 4バイト                                                     |
| `tools.track_scale --name ルミナンスキー`  | `+0x74` 拡張ブロック `0x100a7d48`。表示スケールは2本とも1、ドラッグ範囲は 0〜4096 で、`基準輝度` の負側は**数値入力でしか届かない**                                                                              |
| `decompile_luma_key.py`                    | `0x10064e00`〜`0x100652a0` に絞った `CFGFast` + angr デコンパイル。**`/* unsupported instruction */` が1つも出ない**唯一のエフェクト(4箇所だけ読み替えに注意)                                                   |
| `disasm_params.py`                         | `func_proc` 全域(25命令)と4ワーカー全域、`FILTER+0x58` と共有 `func_WndProc` の注釈付きダンプ。4分岐・共通プロローグ・1命令だけの差分                                                                            |
| `verify_dispatch.py`                       | 4ディスパッチとコンボ4項目の対応、各ワーカーの被参照が**画像全体で1件ずつ**であること、**グローバルが0個**であること、書き込みが `+6`(アルファ)だけであること、命令語彙23種の全列挙                              |
| `verify_ex_data.py`                        | `+0x70` フィールド表による `ex_data` レイアウト、コンボ4項目の文字列、`func_WndProc` が**5登録で共有される汎用ハンドラ**であること、`table[0x4c]` の第2引数が **5=ボタン / 6=コンボ / 7=静的テキスト** であること |
| `verify_alpha_curve.py`                    | 4本のアルファカーブ。分岐 mnemonic の照合、分岐チェーンと閉じた式の**180万通り全数一致**、`ぼかし=0` でゼロ除算に到達しないこと、切り捨ての向き、退化する領域                                                    |
| `simulate_luma_key_reference.py`           | 上記すべてを織り込んだ整数忠実リファレンス実装。14項目の自己検証つき                                                                                                                                             |

## 1. 登録エントリ ―― 959バイトで全部

`ルミナンスキー` の登録は `0x100a7d60` の1個だけで、`クロマキー` / `カラーキー`
と同じく**フレーム(映像)フィルタ版が存在しない**。`fp->flag & 0x20` の分岐は
コード上に無く、画素は常に 8バイト/画素 PIXEL_YCA である。

| 項目           | 値                                                                        |
| -------------- | ------------------------------------------------------------------------- |
| `FILTER_DLL`   | `0x100a7d60`(配列の [32] 番目)、`flag = 0x20`(オブジェクトのフィルタ効果) |
| `func_proc`    | `0x10064ee0`                                                              |
| `func_WndProc` | `0x10018080` ―― **5つの登録で共有される汎用ハンドラ**(手順7)              |
| `FILTER+0x58`  | `0x10065270` ―― `インターレース解除` と共有(手順7)                        |
| `ex_data`      | 4バイト、`ex_data_def = 0x101bacdc`(全ゼロ)、`+0x70` 表 `0x100a7d10`      |
| `+0x74`        | `0x100a7d48`。表示スケール `{1,1}` / ドラッグ範囲 `0..4096` ×2            |
| 入力バッファ   | `*(fpip+0xAC)`。**完全にイン・プレース**                                  |
| 作業バッファ   | **使わない**。`*(fpip+0xB0)` はコード全域に1度も現れない                  |

このエフェクト固有のコードは `0x10064ee0`〜`0x1006529e` の連続した **959バイト**
だけで、本リポジトリで解析した中で最小である(次に小さい `カラーキー` の
1,844バイトの半分強)。直前の関数は `0x10064ed1` の `ret` で終わっており、
前後で最も近い登録済み関数は下が `斜めクリッピング` の `func_proc`
(`0x1005cab0`)、上が `マスク` の `func_proc`(`0x10069870`)である。

**このエフェクトには浮動小数点も、グローバル変数も、共有ルーチンの呼び出しも
1つも無い。** 全域に現れる命令は23種(`add`, `call`, `cdq`, `cmp`, `dec`,
`idiv`, `imul`, `jge`, `jle`, `jmp`, `jne`, `jns`, `lea`, `mov`, `movsx`,
`nop`, `pop`, `push`, `ret`, `shl`, `sub`, `test`, `xor`)だけで、絶対アドレスの
メモリオペランドは `SendMessageA` のインポートサンク1件に尽きる
(`verify_dispatch.py`)。

> **グローバルが0個**なのはこのエフェクトだけである。`exec_multi_thread_func`
> の引数が足りないという制約([`filter_registration.md` §6](../common/filter_registration.md))
> のせいで他のエフェクトは必ず専用グローバルを用意するが、ここは
> **ワーカーが自分で `fp->track[]` を読み、必要な派生値は `sub` / `add` 1命令で
> 作れる**ので、渡すものが何も無い。

## 2. `ex_data` ―― コンボボックスの添字1個

exedit 自身の `+0x70` フィールド表(`0x100a7d10`、
[`filter_registration.md` §5](../common/filter_registration.md))が宣言する
フィールドは1つだけで、宣言サイズの合計が `ex_data_size` と一致する:

| offset | size | kind | name   | 意味                     |
| ------ | ---- | ---- | ------ | ------------------------ |
| 0      | 4    | 1    | `type` | コンボボックスの選択添字 |

```c
struct { int type; };   // 4 bytes
```

`type` という名前は exedit の中で汎用で、同じ文字列 `0x1009d6c4` を**18個の
フィールド表が共有**している。`ex_data_def`(`0x101bacdc`)は全ゼロなので、
追加直後は `type = 0` = `暗い部分を透過` から始まる。

`クロマキー` / `カラーキー` が 12バイトの `ex_data`(`PIXEL_YC` のキー色 +
スポイトの状態)を持つのに対し、**`ルミナンスキー` はキーにする値が最初から
画素の中にある**ので、拾ってくる色が要らない。スポイトも色選択ダイアログも
存在しない。

### コンボボックスの4項目

`check_default[0] = -2` は exedit のコンボボックス印
([`filter_registration.md` §5](../common/filter_registration.md))で、項目名は
`check_name[0]` から始まる連続した cp932 文字列である:

| `type` | 文字列 VA    | 項目名                       | ワーカー     |
| ------ | ------------ | ---------------------------- | ------------ |
| 0      | `0x100a7e98` | `暗い部分を透過`             | `0x10064f60` |
| 1      | `0x100a7ea7` | `明るい部分を透過`           | `0x10065020` |
| 2      | `0x100a7eb8` | `明暗部分を透過`             | `0x100650e0` |
| 3      | `0x100a7ec7` | `明暗部分を透過(ぼかし無し)` | `0x100651b0` |

4項目の直後(NUL パディング3バイトを挟んで)に `基準輝度` = `track_name[0]` が
続くので、この4本でちょうど項目リストである(`verify_ex_data.py`)。

`func_proc` の分岐は `0 / 1 / 2 / else` なので、**`type` が 3 以外の想定外の値
でもワーカー3が走る**。コンボボックスからは 0〜3 しか来ないが、`ex_data` を
直接書き換えた場合の落ち先はここになる。

## 3. パラメータ

| トラックバー | 生値の範囲  | 初期値   | 表示スケール | ドラッグ範囲 | 内部での使われ方                   |
| ------------ | ----------- | -------- | ------------ | ------------ | ---------------------------------- |
| `基準輝度`   | -4096〜8192 | **2048** | 1            | 0〜4096      | 帯の中心。`PIXEL_YC.y` と同じ単位  |
| `ぼかし`     | 0〜4096     | **512**  | 1            | 0〜4096      | 帯の半幅であり、ランプの幅でもある |

| コンボボックス   | 初期値 | 役割         |
| ---------------- | ------ | ------------ |
| `暗い部分を透過` | 0      | 4項目。手順2 |

表示スケールが2本とも1なので、**UI に出ている数字がそのまま PIXEL_YC の輝度値**
である(4096 = 満輝度)。`/1000` のマジックナンバー除算はエフェクト全域に0件で、
この性質は `クロマキー` / `カラーキー` と共通である
([`param_scaling.md` §2](../common/param_scaling.md))。

**トラックバーはワーカーが自分で `fp->track[]` から読む**。`func_proc` は
トラックバーを1度も参照しないので、`ぼかし = 0` でも `基準輝度` がどれだけ
外れていても**早期 return は無く、必ず全画素を1回走査する**。第1トラックバーが
0 のときに即 return する `ぼかし` / `閃光` / `拡散光` / `グロー` とは対照的である
([`param_scaling.md` §3](../common/param_scaling.md))。

### `基準輝度` のドラッグ範囲が生値の範囲より狭い

生値の範囲は -4096〜8192 だが、`+0x74` のドラッグ範囲は 0〜4096 しかない。
つまり**スライダーで届く範囲は PIXEL_YC の表現可能域そのもの**で、その外側は
数値入力でしか指定できない。そして外側はどちらもほぼ退化している(手順6)ので、
実質的にスライダーの範囲が有効範囲だと考えてよい。

## 4. 4つのモード ―― 全部「1つの `t` と3分岐」

4つのワーカーは**同じプロローグ**を持ち、`fp->track[]` から `基準輝度`(base)と
`ぼかし`(blur)を読んで1個の値にまとめてから画素ループに入る。ループの中で
起きることは、符号付き整数 `t` を作って3回分岐するだけである:

```
type 0  暗い部分を透過                t = y - base + blur
type 1  明るい部分を透過              t = base + blur - y
type 2  明暗部分を透過                t = blur - |y - base|
type 3  明暗部分を透過(ぼかし無し)    t = blur - |y - base|

t < 0        ->  a = 0
t >= blur    ->  a はそのまま
それ以外     ->  a = a * t / blur          (type 3 にはこの枝が無い)
```

- **見るのは `y` だけ。** 色差 `cb` / `cr` は読みもしない。名前のとおり
  輝度だけのキーである。
- **書くのは `a` だけ。** 4ワーカーの16bit書き込みは全部 `[reg+6]` で、
  `y` / `cb` / `cr` は素通りする(`verify_dispatch.py`)。
- **境界は「残す側」が閉じている。** 1つ目は `jns`(`t = 0` は残す側へ)、
  2つ目は `jge`(`t = blur` はそのまま)で、`jg` ではない。これが
  `ぼかし = 0` をゼロ除算ではなくきれいなハードステップにしている。
- **`type 2` / `type 3` の `|・|` は `abs` ではなく2命令の折り返し**である ――
  `t > blur` なら `t = 2*blur - t`。折り返し後は必ず `t <= blur` になる。
- **`type 0` と `type 1` の違いは1命令**。プロローグの
  `sub`(`0x10064f9e`)と `add`(`0x1006505e`)、それとループ内の減算の向きだけで、
  分岐は完全に同じである。
- **`type 3` には `imul` も `idiv` も無い。** ワーカー内の `idiv` はスレッド
  分割用の2個だけで、他の3つは3個ある(`verify_alpha_curve.py`)。

分岐チェーンの逐語再現と上の閉じた式は、**`基準輝度` 10通り × `ぼかし` 11通り ×
`y` の表現可能域 4097通り × 4モード = 180万通りで全数一致**する
(`verify_alpha_curve.py` §2)。

### 既定値でのカーブ

`基準輝度 = 2048`、`ぼかし = 512`、入力アルファ 4096:

| `y`  | type 0 | type 1 | type 2 | type 3 |
| ---- | ------ | ------ | ------ | ------ |
| 0    | 0      | 4096   | 0      | 0      |
| 1535 | 0      | 4096   | 0      | 0      |
| 1536 | 0      | 4096   | 0      | 4096   |
| 1537 | 8      | 4096   | 8      | 4096   |
| 1792 | 2048   | 4096   | 2048   | 4096   |
| 2047 | 4088   | 4096   | 4088   | 4096   |
| 2048 | 4096   | 4096   | 4096   | 4096   |
| 2049 | 4096   | 4088   | 4088   | 4096   |
| 2304 | 4096   | 2048   | 2048   | 4096   |
| 2560 | 4096   | 0      | 0      | 4096   |
| 2561 | 4096   | 0      | 0      | 0      |
| 4096 | 4096   | 0      | 0      | 0      |

**`type 0` のランプは `基準輝度` の下側にしか無い。** `[base-blur, base]` で
0 から 1 まで上がり、`base` より上は素通りである。`type 1` はその鏡像。

### 割り算は切り捨て

ランプは `imul` / `cdq` / `idiv` なので C の `/` と同じ**0方向への切り捨て**で、
アルファも `t` も非負だから常に切り下げになる。誤差は必ず1未満で、
`a * blur / blur == a` は厳密に成り立つ ―― だから「そのまま」の枝とランプの枝は
境界 `t = blur` で連続する。既定の `ぼかし = 512` は2のべき乗なので誤差0で、
この切り捨ては**既定値では観測できない**
([`integer_semantics.md`](../common/integer_semantics.md))。

## 5. `明暗部分を透過` と `(ぼかし無し)` の違いは「帯の全部がランプかどうか」

`type 2` と `type 3` は `t` の作り方が**命令単位で同一**で、違うのは
`t >= blur` を外れたあとの処理だけである。ところが折り返しのせいで、
**`t >= blur` は `t == blur`、つまり `y == base` 1点でしか成立しない**。

|                              | 満アルファで残る `y` の個数 | 半透明になる `y` の個数 |
| ---------------------------- | --------------------------: | ----------------------: |
| `明暗部分を透過`             |      **1**(`y = 2048` のみ) |                    1022 |
| `明暗部分を透過(ぼかし無し)` | **1025**(`y = 1536..2560`) |                       0 |

(`基準輝度 = 2048`、`ぼかし = 512`)

つまり `明暗部分を透過` のアルファは、帯の中心で 1、両端で 0 の**三角形**である。
名前は「ぼかしを外した版」と読めるが、実際に外れているのは
**帯の全域を覆っていたランプ**で、`ぼかし` はどちらのモードでも帯の半幅として
効き続ける。同じ `ぼかし` 値で見比べると、`(ぼかし無し)` のほうが残る面積が
圧倒的に広い。

`type 0` / `type 1` ではランプ幅(`blur`)と通過域(片側全部)が別物なので、
この現象は起きない。

## 6. 退化するパラメータ領域

PIXEL_YC の輝度は 0〜4096 だが `基準輝度` は -4096〜8192 まで指定できる。
帯が表現可能域の外へ出ると、エフェクトは「何もしない」か「全部消す」の
どちらかになる(`verify_alpha_curve.py` §5、入力は全画素不透明):

| `type` | `基準輝度`    | `ぼかし` | 結果                       |
| ------ | ------------- | -------- | -------------------------- |
| 0      | -4096         | 0        | 何もしない                 |
| 0      | 8192          | 0        | オブジェクトが丸ごと消える |
| 1      | -4096         | 0        | オブジェクトが丸ごと消える |
| 1      | 8192          | 0        | 何もしない                 |
| 2      | -4096 / 8192  | 4096     | オブジェクトが丸ごと消える |
| 3      | 2048          | 4096     | 何もしない(帯が全域を覆う) |

**クランプはエフェクト内に1つも無い。** `基準輝度` も `ぼかし` も生値のまま
使われるので、スライダーで届かない領域が「何もしない」と「全部消す」に
分かれているのは、単に算術の結果である。

`ぼかし = 0` も退化の一種で、4モードすべてがハードステップになる。特に
`type 2` / `type 3` は**`y == 基準輝度` の画素だけを残す**という、ほぼ使い道の
無い状態になる。ゼロ除算にはならない(手順4の境界の話)。

## 7. 近傍を一切見ない ―― `カラーキー` との対比

`ルミナンスキー` の出力アルファは**その画素自身の `y` と `a` だけ**の関数である。
ボックス平均も `境界補正` も無く、隣の画素を読む命令が1つも無い。結果として:

- 一様に半透明なオブジェクトは、帯の外なら**そのまま通る**。`カラーキー` の
  `境界補正` が一様な 50% アルファを `r=1` で 512 に、`r>=2` で 0 に潰してしまう
  のとは対照的である([`border_correction.md`](../common/border_correction.md))。
- 端の減衰も無い。ゼロ埋めのボックス平均を持たないので、上下左右が痩せない。
- そのかわり**アンチエイリアスされた境界は救えない**。ソフトエッジは
  `ぼかし` の輝度ランプからしか出てこないので、輝度が帯の中に収まっている限り
  ジャギーはそのまま残る。

`t >= blur` と `t < 0` の2枝は冪等だが、ランプの枝は**既にあるアルファに
掛け算する**ので、同じ設定で2回重ねると係数が2乗される
(`simulate_luma_key_reference.py`)。

## 8. UI は全部共有コード

このエフェクトは**自分専用の UI コードを1バイトも持っていない**。

### `func_WndProc` `0x10018080` ―― 5登録で共有

| 登録                 | `ex_data` | `+0x58`      |
| -------------------- | --------- | ------------ |
| `ルミナンスキー`     | 4         | `0x10065270` |
| `ミラー`             | 4         | `0x1006aa70` |
| `色ずれ`(2登録)      | 4         | `0x100180d0` |
| `インターレース解除` | 4         | `0x10065270` |

いずれも `check_name[0]` がコンボボックスで `ex_data` が4バイト。ハンドラは
`0x702`(`WM_FILTER_COMMAND`)の**コントロール ID `0x1e1c` だけ**を見て、
`table[0x80](fp+0xE4, 0)` を呼んでから `ex_data[0] = lParam` を書いて `TRUE` を
返す。それで全部で、`fp->track[]` は一切参照しない。ボタンの `0x1e1b`
(`クロマキー` / `カラーキー` の `キー色の取得`)の次の ID である。

### `FILTER+0x58` `0x10065270` ―― `インターレース解除` と共有

設定ウィンドウが作り直されたときに `ex_data.type` をコンボへ押し戻すだけ:

```
SendMessageA(table[0x4c](fp+0xE4, 6, 0), CB_SETCURSEL, ex_data.type, 0)
```

`SendMessageA` の引数を先に積んでおいて `table[0x4c]` の3引数分だけ
`add esp, 0xc` する、という書き方をしている(push が6本、cleanup が1回)。

### `table[0x4c]` の第2引数が判明した

`クロマキー` / `カラーキー` の解析時点では「第2引数の `5` が何のコントロール
種別を指すかは未追跡」だった。呼び出し側を全部並べると決まる:

| 第2引数 | 意味                      | 根拠                                                                          |
| ------- | ------------------------- | ----------------------------------------------------------------------------- |
| 5       | チェックボックス / ボタン | `クロマキー`(`0x100144d9`、添字2)、`カラーキー`(`0x10016959`、添字0)          |
| 6       | コンボボックス            | `ルミナンスキー`(`0x1006528f`)、`グロー`(`0x10059002`)、`色ずれ`(`0x100180f0`) |
| 7       | 静的テキスト              | `グロー` の `形状`(`0x10059022`)                                              |

決め手は `グロー` で、**同じ関数の4命令違いで 6 と 7 を使い分け、前者に
`SendMessageA`(`CB_SETCURSEL`)、後者に `SetWindowTextA` を投げている**。
第3引数がその種別の中での添字であることは、`クロマキー`(2)と `カラーキー`(0)の
差から既に確定していた通りである(`verify_ex_data.py` §5)。0〜4 は exedit の
ダイアログコードで使われているが、解析済みエフェクトには出てこない。
まとめは [`filter_registration.md` §7](../common/filter_registration.md)。

## 9. 関数マップ

| アドレス     | 役割                                                                                   |
| ------------ | -------------------------------------------------------------------------------------- |
| `0x10064ee0` | `func_proc` ―― `ex_data.type` の4分岐だけ。25命令。**画素にもトラックバーにも触らない** |
| `0x10064f60` | ワーカー `type 0` `暗い部分を透過`。`t = y - base + blur`                               |
| `0x10065020` | ワーカー `type 1` `明るい部分を透過`。`t = base + blur - y`                             |
| `0x100650e0` | ワーカー `type 2` `明暗部分を透過`。折り返し + 帯全域のランプ                           |
| `0x100651b0` | ワーカー `type 3` `明暗部分を透過(ぼかし無し)`。折り返しのみ。**乗除算なし**            |
| `0x10065270` | `FILTER+0x58`(設定ウィンドウ更新)。**`インターレース解除` と共有**                     |
| `0x10018080` | `func_WndProc`。**5登録で共有される汎用コンボボックスハンドラ**                         |

4ワーカーはいずれも**画像全体で1回ずつしか参照されない**(`tools.xrefs` の
バイト走査。`カラーキー` のキーワーカーが2回 push されるのとは違う)。
スレッド分割は4つとも行単位で、`w` / `h` / 行幅は `*(fpip+0xB4)` /
`*(fpip+0xB8)` / `*(fpip+0xEC)` から取る。

## 10. 未確定事項

- **`table[0x4c]` の第2引数 0〜4**。5/6/7 は確定したが、残りが選ぶコントロール
  種別は未追跡。exedit のダイアログコード(`0x10002000` 付近など)には出てくる。
- **`table[0x80]`**。共有 `func_WndProc` がコンボの変更時に呼ぶが、戻り値は
  捨てられており、何をしているかは追っていない。
- **`fp+0xE4`** の中身。`クロマキー` / `カラーキー` と共通の未確定事項。
- **表現可能域外の `y`**。ワーカーは `y` を `movsx` で読むだけでクランプしない
  ので、0〜4096 を外れた輝度が入ってきた場合も式どおりに扱われるはずだが、
  そのような画素が実際に来るかは exedit 側の問題であり未確認。
- **`インターレース解除`(`0x1005b050`)** は `+0x58` を共有し、`ex_data` も
  コンボ1個で同型だが、本リポジトリでは未解析。共有を確認したのは UI 側だけで、
  画素処理は見ていない。`ミラー`(`0x1006a140`)と `色ずれ`(`0x100170a0`)も同様。
- `rand()` や `fpip->frame`(`+0x1C`)を読む箇所は無い(`verify_dispatch.py` の
  フィールド一覧に `+0x1C` が出てこない)ので、同じ入力に対する出力は完全に
  決定的である。

[`rgb_ycbcr.md` §3](../common/rgb_ycbcr.md) 参照:

- 最終的な YCbCr→RGB 変換とそのクリップは `aviutl.exe` 側にあるため、
  本プロジェクトの解析対象外。
