# 方向ブラー (directional blur) フィルタ リバースエンジニアリング解析

対象: `data/exedit.auf`(AviUtl 拡張編集の標準フィルタプラグイン)、32bit PE、
`ImageBase = 0x10000000`。以下のアドレスはすべて VA(`RVA = VA - 0x10000000`)。

## 再現方法

```
uv run main.py inspect/directional_blur/<script>.py
uv run main.py tools.<tool>            # エフェクト非依存の共通ツール。一覧はリポジトリ直下の README
```

| スクリプト                                | 確認していること                                                                                                                     |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `tools.filter_table --name 方向ブラー`    | 登録2個(`0x100a0070` / `0x100a0198`)、トラックバー2本、`サイズ固定` はオブジェクト側のみ                                            |
| `decompile_directional_blur.py`           | 5関数を range 限定デコンパイル。2つのワーカーが最後の除数以外は同形であることの独立な裏付け                                         |
| `disasm_params.py`                        | `func_proc` 2本とワーカー3本の**全命令**に注釈                                                                                       |
| `verify_registration.py`                  | `func_proc` を共有しない2登録モデル、`+0x74` まで共有(`放射ブラー` との差)、`fp+0x78` の枠5 = `Z軸回転`、2816バイト・5関数、**フレーム版が共有描画ルーチンを呼ばない**こと |
| `verify_direction.py`                     | `角度` → Q16 ベクトルの定型、**`sin` 側が x**([`angle_vector.md` §6](../common/angle_vector.md) の保留を解消)、`角度` と `角度+180` が完全に同じ絵になること、x87 と libm が食い違いうる322角度 |
| `verify_sample_schedule.py`               | 4分岐の付け替えで**到達距離が常に `範囲` 画素**になること、サンプル密度が 4/2/1/1未満と変わること、`N <= 1` の早期 return が到達不能であること、キャンバスが角度に依存しないこと |
| `simulate_directional_blur_reference.py`  | 整数忠実リファレンス。`サイズ固定` が端の除数を変えること、180度対称、1〜32スレッド一致、フレーム版                                 |

## 1. 何をするエフェクトか

**`角度` の向きに `±範囲` 画素の線分を取り、その上を等間隔にサンプルして
平均する**。窓は出力画素を中心に**対称**なので、被写体は伸びるだけで
ずれない ―― カメラを平行移動させたときのブレ。

`放射ブラー` と兄弟で(コードも隣り合っている)、違うのは**窓の向きが画素に
よらず一定**という1点だけ。にもかかわらず分離型ボックス平均にはなっておらず、
`放射ブラー` と同じ「毎画素サンプルを取り直す」形をしている。斜め方向では
窓が行に沿って平行移動しないので差分更新できない、という
[`box_blur.md` §3](../common/box_blur.md)(`凸エッジ`)と同じ事情である ――
ただし `角度 = 0` / `90.0` のときですら特別扱いは無い。

## 2. 登録2個 ―― `放射ブラー` と同じ例外、細部は違う

|                    | オブジェクトのフィルタ効果 | フレーム(映像)フィルタ            |
| ------------------ | -------------------------- | --------------------------------- |
| `FILTER_DLL`       | `0x100a0070`、`flag=0x20`  | `0x100a0198`、`flag=0x40000000`   |
| `func_proc`        | `0x1000c200`               | `0x1000c9b0`                      |
| `func_WndProc`     | `0x1001b550`(`放射ブラー` と共有) | 同左                       |
| トラックバー定義   | 完全に同一(`+0x74` 拡張ブロックまで共有) | 同左              |
| チェックボックス   | `サイズ固定`               | 無し                              |
| ワーカー           | **2本**(`サイズ固定` で切替) | 1本                            |

`func_proc` が2本ある形は exedit の100登録中 `放射ブラー` / `方向ブラー` /
`ラスター` / `画像ループ` だけ([`filter_registration.md` §2](../common/filter_registration.md)
の2登録モデルの例外)。`放射ブラー` は `範囲` の上限が 750 と 1000 で
食い違い `+0x74` も別々だったのに対し、`方向ブラー` は**2登録で完全に同じ
UI 定義**である。

### `fp+0x78` は枠5(`Z軸回転`)

登録構造体の `+0x78`(描画パラメータ枠 → トラックバー添字の `int[12]`。
初出とデコードは [`放射ブラー` §2](../emission_blur/README.md))は
`方向ブラー` では**枠5 = `Z軸回転` に `track[1]`(`角度`)を割り当てている**。
`放射ブラー` が枠0/枠1(位置)を使うのと対照的で、**プレビュー上の操作が
「回転」として扱われる**ことを意味する、と読める。

**ただしフレーム版は共有描画ルーチン `0x10019160` を呼ばない。**
`放射ブラー` のフレーム版は同じ `+0x78` を持ちながらこれを呼ぶので、
「`+0x78` があるから呼ぶ」ではない ―― 何が違うのかは未確定(手順8)。

エフェクト固有コードは `0x1000c200`-`0x1000ccff` の **2816 バイト・5関数**、
グローバル7個(`0x100d75cc`-`0x100d75e4`)の参照はその中に閉じており、
外への直接呼び出しは `_ftol` 1本だけ(`verify_registration.py`)。

## 3. パラメータ

`fp->track[]` の順に `範囲`(初期値20、0~500)、`角度`(500、-36000~36000)。

| トラックバー | 表示スケール | UI表示範囲     | ドラッグ範囲    | 意味                                |
| ------------ | ------------ | -------------- | --------------- | ----------------------------------- |
| `範囲`       | 1            | 0~500          | 0~500           | **片側の到達距離[画素]**(支持長は `2·範囲+1`) |
| `角度`       | 10           | -3600.0~3600.0 | -360.0~360.0    | ブレの向き[度]。**10回転ぶん指定できる**    |

`角度` の生値範囲 `±36000` は `斜めクリッピング` / `色ずれ` /
`グラデーション` と同じ([`angle_vector.md` §3](../common/angle_vector.md))。

`範囲 = 0` は `func_proc` の先頭で `return 1`(何もしない)。

## 4. `角度` → Q16 方向ベクトル

[`angle_vector.md` §1](../common/angle_vector.md) の定型そのままで、符号は
`(-sinθ, +cosθ)` 系(`凸エッジ` / `フレームバッファ` と同じ列):

```
θ  = 角度 * pi/1800
vx = trunc(sin(θ) * -65536.0)      -> g_100d75cc
vy = trunc(cos(θ) *  65536.0)      -> g_100d75d0
```

### `sin` 側が x ―― `angle_vector.md` §6 の保留を解消

`angle_vector.md` は「`方向ブラー` / `フレームバッファ` / `グラデーション` に
ついては Q16 の2値を作るところまでしか確認していない」としていた。
`方向ブラー` については**3本のワーカーすべて**で確定する
(`verify_direction.py` §2):

| 命令                                          | 言っていること                              |
| --------------------------------------------- | ------------------------------------------- |
| `0x1000c5d9  cmp ecx, [esp+0x40]`(= `*(fpip+0xB4)` = 幅) | `vx` 側のアキュムレータが x   |
| `0x1000c5df  cmp eax, [esp+0x44]`(= `*(fpip+0xB8)` = 高さ) | `vy` 側が y                 |
| `0x1000c85d` / `0x1000c863`                   | `サイズ固定` ON のワーカーも同じ対応        |
| `0x1000cc26` / `0x1000cc2c`                   | フレーム版ワーカーも同じ対応                |

したがって画面座標(y は下向き)では:

| `角度` | `(vx, vy)` 単位 | ブレの向き            |
| ------ | --------------- | --------------------- |
| `0.0`  | `(0, +1)`       | 縦(上下)             |
| `45.0` | `(-0.707, +0.707)` | 左下 ⇔ 右上 の対角線 |
| `90.0` | `(-1, 0)`       | 横(左右)             |
| `180.0`| `(0, -1)`       | 縦(上下)             |

### 向きの符号は絵に出ない

窓は `k = -N .. +N` の `k·v` なので、`v → -v` は `k → -k` の置き換えに
すぎない ―― **`角度` と `角度+180` は完全に同じ出力になる**
(`verify_direction.py` §3 でサンプル集合が一致することを確認)。
`凸エッジ` では `(-sinθ, cosθ)` と `(sinθ, -cosθ)` の違いが「どちらが
明るくなるか」を分けたが、`方向ブラー` では**符号の系統がどちらでも
見た目が変わらない**。

## 5. サンプル数と歩幅 ―― 4分岐

`func_proc` は `範囲` の生値を見て `v` と片側サンプル数 `N` を付け替える:

| 生値 `範囲`   | `v`             | `N`      | カーネル幅 `2N+1` | サンプル密度 |
| ------------- | --------------- | -------- | ----------------- | ------------ |
| `< 16`        | `v/4`           | `範囲·4` | 9 〜 121          | 4 /画素      |
| `16..31`      | `v/2`           | `範囲·2` | 65 〜 125         | 2 /画素      |
| `32..128`     | そのまま        | `範囲`   | 65 〜 257         | 1 /画素      |
| `> 128`       | `v·範囲/128`    | `128`    | **257 で固定**    | **1未満**    |

**どの枝でも `N·|v| = 範囲·65536`**、つまり片側の到達距離はちょうど `範囲`
画素で一定である(全角度・全生値で誤差 0.02 画素以内、
`verify_sample_schedule.py` §1)。変わるのは密度だけ。

**`範囲` が 128 を超えると1画素あたり1サンプルを割り込む。**
`範囲 = 500` なら歩幅 3.91 画素 ―― 元画像の画素を飛ばしながらサンプルする
ので、細かい模様では 128 本の櫛が見える可能性がある(実機未確認)。

`fpip->flag & 0x200`(描画品質を落としてよい)が立つと
`N` は 50 に落ち、`v` は `v·N/50` に引き伸ばされる ―― **到達距離は変わらず、
粗くなるだけ**。50 という値は `閃光` / `放射ブラー` と共通
([`filter_registration.md` §3](../common/filter_registration.md))。

### 到達不能な早期 return

`func_proc` は `N <= 1` で何もせず返る分岐を持つが、生値 0 は関数の先頭で
弾かれ、生値 1 でも `N = 4` になるので**この分岐に落ちる入力が存在しない**
(`verify_sample_schedule.py` §5)。

## 6. 累積と `サイズ固定` ―― 除数が変わる

サンプルの足し方は全オブジェクト効果に共通のアルファ加重(プリマルチプライ)
累積([`box_blur.md` §1](../common/box_blur.md))で、**2つのワーカーの差は
アルファの除数1点だけ**:

| ワーカー     | `サイズ固定` | アルファの除数           | 端の見え方                     |
| ------------ | ------------ | ------------------------ | ------------------------------ |
| `0x1000c4a0` | OFF          | **カーネル幅 `2N+1`**    | 枠外を透明として数える → フェードする |
| `0x1000c720` | ON           | **枠内サンプルの本数**   | 端で正規化し直す → 減衰しない  |

[`box_blur.md` §3](../common/box_blur.md) の1つ目と2つ目の変種がそのまま
1つのエフェクトの中に並んでいる形で、`ぼかし` と同じ設計である。
平坦な不透明画像(32x32、`範囲=10`、`角度=90.0`)の x=0 の列で:

| `x`     | 0    | 2    | 4    | 6    | 8    | 10   |
| ------- | ---- | ---- | ---- | ---- | ---- | ---- |
| OFF の `a` | 2174 | 2578 | 2983 | 3388 | 3792 | 4096 |
| ON の `a`  | 4096 | 4096 | 4096 | 4096 | 4096 | 4096 |

色(`y`/`cb`/`cr`)はどちらも `sum_a` で割る ―― ここは共通なので、
**`サイズ固定` は色を変えずアルファだけを変える**。

フレーム版(6バイト/画素)は3チャンネルとも**生存サンプル数**で割り、
**生存が 0 のときは書き込みそのものをしない**(対バッファの古い内容が残る)。

## 7. キャンバス拡張 ―― 角度を見ない

```
x0 = -範囲 ;  x1 = w + 範囲
y0 = -範囲 ;  y1 = h + 範囲
```

**`角度` はこの式に出てこない。** `角度 = 90.0`(真横にしかぶれない)でも
上下に `範囲` 画素の完全に透明な帯が付く ―― `グロー` と同じ無駄
([`canvas_growth.md` §6](../common/canvas_growth.md))。方式としては
[`canvas_growth.md` §5](../common/canvas_growth.md) の「`func_proc` が矩形を
計算して置き直す」型。

上限(最大キャンバス幅 `0x10196748` / 高さ `0x101920e0`)を超える間は
**左右(上下)対称に1画素ずつ**削る。`放射ブラー` の「はみ出しが大きい側から」
とは違うが、中心という概念が無いので当然ではある。

`サイズ固定` ON では矩形が `(0,0,w,h)` に戻り、同時にワーカーも
生存サンプル数で割るほうに切り替わる(手順6)。

## 8. スレッド分割

[`thread_split.md`](../common/thread_split.md) の (B) だけ。ガード (A) も
`thread_num = 1` の差し替えも無いので、`シャープ` のような「パスが丸ごと
走らない」問題は起きない。1〜32スレッドで出力が完全に一致することを
再実装で確認済み(`simulate_directional_blur_reference.py` §4)。

## 11. 未確定事項

- **フレーム版が `0x10019160` を呼ばない理由。** `放射ブラー` のフレーム版は
  同じ `flag` bit30 と同じ `fp+0x78` を持ちながら呼ぶ。差は `+0x78` の
  中身(位置枠 か 回転枠 か)だけに見えるが、`0x10019160` の中身を読んで
  いないので断定できない。
- **`0x1001b550`(共有 `func_WndProc`)の中身**。`fp+0x78` の枠を読むところ
  までしか確認していない ―― [`放射ブラー` §10](../emission_blur/README.md)
  と同じ宿題。
- **`範囲 > 128` の櫛が実機でどう見えるか。** 歩幅が1画素を超えることは
  式から確定しているが、実際の映像でモアレになるかは確認していない。
- **UI 上どう体感されるかは実機で確認していない。** §4 の「`角度 = 0` で
  縦にぶれる」も命令列とその Python 再実装からの帰結である。

以下は全エフェクト共通の未確定事項:

- x87 の `fsin`/`fcos` が libm と 1 ulp 違いうる角度が 322 組ある(すべて
  30度の倍数)。影響はサンプル位置が 1/65536 画素動くだけ ――
  [`angle_vector.md` §5](../common/angle_vector.md)
- 最終的な YCbCr→RGB 変換とそのクリップは `aviutl.exe` 側にある ――
  [`rgb_ycbcr.md` §3](../common/rgb_ycbcr.md)
