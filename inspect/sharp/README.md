# シャープ (sharp) フィルタ リバースエンジニアリング解析

対象: `data/exedit.auf`(AviUtl 拡張編集の標準フィルタプラグイン)、32bit PE、
`ImageBase = 0x10000000`。以下のアドレスはすべて VA(`RVA = VA - 0x10000000`)。

## 再現方法

すべてのスクリプトは本プロジェクトの `main.py` を踏み台にして実行する。
`main.py` はコマンドラインで指定されたスクリプトに対して、DLLパス
(デフォルト `data/exedit.auf`)とヘッダー一覧(デフォルト `data/filter.h`)を
渡す役割を持つ。

```
uv run main.py inspect/sharp/<script>.py
uv run main.py tools.<tool>            # エフェクト非依存の共通ツール。一覧はリポジトリ直下の README
```

| スクリプト                     | 確認していること                                                                                                                                 |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tools.filter_table --name シャープ` | `FILTER_DLL` 配列(先頭 `0x100a3e28`)をたどって登録エントリを抽出。登録は**1個だけ**、トラックバー2本、チェックボックスも `ex_data` も**0**   |
| `decompile_sharp.py`           | `0x10089030`〜`0x10089d99` に絞った `CFGFast` + angr デコンパイル。`func_proc` に画素ループが無いこと、4パス+合成の構成が読める                    |
| `disasm_params.py`             | `func_proc` と合成ワーカーの全命令に注釈。早期 return 2本、スクラッチへの複製、半径の2分割、5回のディスパッチ、アンシャープの2経路                |
| `verify_param_scaling.py`      | `強さ` は `trunc(raw*4096/1000)`(全8001通り)。**`/1000` がワーカー側にある**唯一の例。`+0x74` の表示スケールとドラッグ範囲                       |
| `verify_blur_chain.py`         | `範囲` → 2半径 → 三角形カーネル、除数は**生存サンプル数**、半径クランプが1つも無いこと。そして2ワーカーが **`ぼかし` の `サイズ固定` オン版と命令単位で同一**であること |
| `verify_unsharp.py`            | **本命**。合成ワーカーの2経路。高速路に入るのは両アルファ 4096 のときだけ、一般路は半透明で差分を `4096/a` 倍する、`imul` に桁溢れの歯止めが無い |
| `verify_thread_split.py`       | **オブジェクトがスレッド数より小さいとパスが丸ごと走らない**こと。`ぼかし` の `サイズ固定` **オフ**版が持つ `thread_num = 1` の差し替えが、ここにも `サイズ固定` オン版にも無い |
| `verify_luma_undershoot.py`    | 負の輝度の後始末(色差を薄めてから黒へ)。同じ定型が `色調補正` と減算合成にもあること                                                            |
| `simulate_sharp_reference.py`  | 上記すべてを織り込んだ整数忠実リファレンス実装と、パラメータごとの見え方のデモ                                                                   |

## 1. 一言でいうと

**アンシャープマスク**。元画像を丸ごとスクラッチバッファに退避し、`ぼかし` と
同じ4パスのボックス平均でぼかしてから、退避しておいた元画像との差を `強さ` 倍して
足し戻す。

```
S     = trunc(強さ * 4096 / 1000)              // UI 100.0 = 4096 = ×1.0
blur  = 分離型ボックス平均(半径 範囲、軸あたり2パス)
out.c = orig.c + S * (orig.c - blur.c) / 4096  // 両方不透明なときの式
out.a = orig.a                                 // アルファは絶対に変えない
```

半透明の画素では式が変わり、差分が `4096/アルファ` 倍に増幅される(手順5)。
**平坦な部分は完全な不動点**(ボックス平均が定数を返すので差が0)なので、
`強さ` はどれだけ上げても輪郭にしか効かない。

## 2. 登録エントリ

登録は**1個だけ**で、`flag = 0x20`(オブジェクトのフィルタ効果)。フレーム
フィルタ版は構造体ごと存在しないので、`fp->flag & 0x20` の分岐も6バイト画素の
経路も**コード上に無い**([`filter_registration.md` §2](../common/filter_registration.md))。

|                      | 値                                                                |
| -------------------- | ----------------------------------------------------------------- |
| `FILTER_DLL`         | `0x100b86f8`、`flag = 0x20`                                       |
| `func_proc`          | `0x10089030`                                                      |
| `func_init` / `exit` / `update` / `WndProc` | **すべて NULL**                            |
| `ex_data`            | `ex_data_size = 0`。`ex_data_def` も `+0x70` フィールド表も NULL  |
| `+0x74` 拡張ブロック | `0x100b86e8`。表示スケール `{10, 1}` とドラッグ範囲を持つ         |
| 入力画像             | `*(fpip+0xAC)`、8バイト/画素 PIXEL_YCA(y, cb, cr, a)             |
| 対バッファ           | `*(fpip+0xB0)`。ぼかしパスごとに `0xAC` と**入れ替える**          |
| 元画像の退避先       | 共有スクラッチ `[0x101a5328]`                                     |
| 幅・高さ・行幅       | `*(fpip+0xB4)` / `*(fpip+0xB8)` / `*(fpip+0xEC)` [画素]           |

**UI コードが1バイトも無い**。チェックボックスも `ex_data` も無く、色の設定も
ファイル選択も無いので、`func_WndProc` も `FILTER+0x58` も要らない ――
`凸エッジ`(846バイト)・`ルミナンスキー`(959バイト)と同じ性質で、
エフェクト固有コードは `0x10089030`〜`0x10089d99` の **3,434バイト・4関数**が
全部である。

`func_proc` は画素に一切触れない。やることは

1. `強さ == 0` か `範囲 == 0` なら即 `return 1`(**独立した早期 return が2本**)、
2. `table[0x44]`(モード語 `0x13000003` = 単純コピー、src/dst とも8バイト画素)で
   オブジェクト画像を丸ごとスクラッチへ複製、
3. `範囲` を2つの半径に割って V→H→V→H の4パスを起動、そのつどバッファを入れ替え、
4. 合成ワーカーを1回起動 ―― **こちらは入れ替えない**、

の4つだけ。

**元画像を丸ごと `[0x101a5328]` に複製するのは解析済みでシャープだけ**である。
このスクラッチを借りているエフェクトは他に6つあるが、`発光`/`グロー`/`ライト` は
ぼかしの中間バッファ、`シャドー`/`縁取り` は16bitのアルファ専用プレーン、
`クロマキー` はマット用で、**8バイト画素の入力そのものを置くのはここだけ**
(4パスの ping-pong で元画像が消えるので、退避しないと引き算する相手が無い)。

**キャンバス拡張も `サイズ固定` も無い。** 出力サイズは常に入力と同じで、
[`canvas_growth.md`](../common/canvas_growth.md) の4方式はどれも当てはまらない。

## 3. パラメータ

トラックバーは `強さ`(初期値 raw 500 = UI 50.0、範囲 0〜8000)、
`範囲`(初期値5、0〜100)の2本だけ。

| トラックバー | 表示スケール | UI表示範囲 | スライダーで届く範囲 | 生値→内部                  |
| ------------ | ------------ | ---------- | -------------------- | --------------------------- |
| `強さ`       | 10           | 0.0〜800.0 | **0.0〜100.0**       | `S = trunc(raw*4096/1000)`  |
| `範囲`       | 1            | 0〜100     | 0〜100               | そのまま画素半径            |

`強さ` の UI 表示範囲(800.0)に対してスライダーは 100.0 で止まる。その先は
数値入力でしか指定できない(`グロー` の `強さ`、`ライト` の `拡散` と同じ形 ――
[`param_scaling.md` §1](../common/param_scaling.md))。

**この変換が `func_proc` ではなくワーカーの中にある**のが本エフェクトの特徴で、
解析済みで唯一の例である。`0x10624dd3`(`/1000` のマジック)はエフェクト全域で
1個だけ、それが合成ワーカー `0x10089bac` にある。したがって

- `func_proc` は `fp->track[]` を**0と比べるためだけ**に読む、
- 変換はスレッドごとに毎回やり直される、
- グローバルは半径・カーネル幅の4本だけで、`強さ` 用のグローバルが**無い**

という並びになる。`範囲` のほうは除算を一度も通らず、生値がそのまま画素半径。

## 4. ぼかし ―― `ぼかし` の `サイズ固定` オン版**そのもの**

まず結論から。垂直・水平の2ワーカーは `ぼかし` の `サイズ固定` **オン**版
(`0x1000f310` / `0x1000f7e0`)と**命令単位で同一**である。

| 比較                            | 命令数    | 完全一致 | 相対変位が同じ分岐 | グローバルの差し替え | それ以外   |
| ------------------------------- | --------- | -------- | ------------------ | -------------------- | ---------- |
| `0x1000f310` vs `0x100891c0`(V) | 368 / 368 | 325      | 31                 | 12                   | **0**      |
| `0x1000f7e0` vs `0x10089690`(H) | 367 / 367 | 324      | 31                 | 12                   | **0**      |

差し替えられているのは `0x1011ec34/38/3c/40`(`ぼかし` の半径・カーネル幅)→
`0x102320bc/c0/c4/c8`(シャープのそれ)の4本だけ。**説明のつかない差が1つも無い**
ので、以下の性質はシャープの設計判断ではなく、この共有コードの性質である ――
除数が生存サンプル数であることも、半径クランプが無いことも、手順7の
スレッド分割の穴も。

`範囲` は `r_hi = 範囲 - 範囲/2`(= `ceil`)と `r_lo = 範囲/2`(= `floor`)に
割られ、`V(r_hi) → H(r_hi) → V(r_lo) → H(r_lo)` の順に走る。軸ごとの合成
カーネルは `box(2*r_hi+1) ⊛ box(2*r_lo+1)`、つまり支持長ちょうど `±範囲` の
三角形(`範囲` が奇数なら上底3の台形)。`範囲 = 1` だけは `r_lo = 0` なので
3・4パス目が丸ごと飛び、幅3の平らな箱になる。

| グローバル   | 中身                     |
| ------------ | ------------------------ |
| `0x102320bc` | 垂直パスの半径           |
| `0x102320c0` | 水平パスの半径           |
| `0x102320c4` | 垂直パスのカーネル幅 `2r+1` |
| `0x102320c8` | 水平パスのカーネル幅     |

2つのワーカーは**互いの半径を1度も読まない**(`verify_blur_chain.py` が機械的に
数える)。これが「どちらが垂直でどちらが水平か」の根拠で、両者とも同じ
`(fp, fpip)` しか渡されない以上、他に区別する材料が無い。

集計は全オブジェクト版共通のアルファ加重平均で、色は `sum_a` で割り、アルファは
別の除数で割る([`box_blur.md` §1](../common/box_blur.md))。その除数は
**窓に残っている実サンプル数**(`r+i+1` → `2r+1` → `2r-i`)で、カーネル幅
固定ではない ―― `ぼかし` の `サイズ固定` **オン**と同じ変種である。

その帰結として、**オブジェクトの縁でぼかしが減衰しない**。ぼかしと元画像が
縁でも一致するので、外周に不要な差分(= 縁だけ光る)が出ない。キャンバスを
広げる必要が無いのもこれと表裏である。

### 半径クランプが1つも無い

`func_proc` は `fpip+0xEC` / `+0xF0`(確保済みバッファの余白)を1度も読まず、
半径を `w`/`h` と比べもしない。したがって `2*r_hi+1 > 寸法` になると
スライディングウィンドウの中段が負回数になり、パスは長さによらず `2r+1` 本
書き、先行ポインタは末尾より先を読む
([`box_blur.md` §4](../common/box_blur.md) の1つ目の穴そのまま)。

| `範囲` | `r_hi` | カーネル幅 | これ未満の寸法で破綻 |
| ------ | ------ | ---------- | -------------------- |
| 5      | 3      | 7          | 7                    |
| 10     | 5      | 11         | 11                   |
| 50     | 25     | 51         | 51                   |
| 100    | 50     | 101        | 101                  |

`ぼかし` は事前拡張(`サイズ固定` オフ)か利用者の選択(オン)でこの状態に
辿り着くのに対し、**シャープには逃げ道が無い**。書き込み先は最大キャンバス
サイズで確保された対バッファなので落ちはしないが、末尾付近の除数は「無かった
サンプル」を数えており、`simulate_sharp_reference.py` の手順6が
「全行が同じ画像なのに高さで結果が変わる」形で実測している。

## 5. 合成ワーカー `0x10089b60` ―― ここが本体

```
p = (blur.a * orig.a) >> 12

p == 4096 : c' = orig.c + (S * (orig.c - blur.c)) >> 12
p >  0    : c' = orig.c + (S * trunc((orig.c*orig.a - blur.c*blur.a) / p)) >> 12
p <= 0    : c' = orig.c                                    // ぼかしを捨てる

out.a = orig.a                                             // 無条件
```

`p == 4096` は `orig.a == blur.a == 4096` のときだけ成立する(全アルファ組を
総当たりで確認)。そこでは割り算が割り切れるので、一般路は高速路に**代数的に
一致する** ―― 別々の式ではなく、同じ式の特別扱いである。

### 5.1 半透明では差分が増幅される

一般路の商は `4096 * (orig.c/blur.a - blur.c/orig.a)` で、平坦な半透明部
(`orig.a == blur.a == a`)では `4096 * (orig.c - blur.c) / a` になる。つまり

| アルファ | 差分の倍率 |
| -------- | ---------- |
| 4096     | ×1         |
| 2048     | ×2         |
| 1024     | ×4         |
| 512      | ×8         |

**同じ `強さ` でも、不透明度が下がるほどシャープが強く効く。** 教科書的な
アンシャープマスクとの一番大きな違いがここで、丸め誤差ではなく式の形である。
アンチエイリアスされたシルエットの縁では `orig.a` と `blur.a` が食い違うので、
そこも自動的に一般路に落ちて強めに効く。

### 5.2 桁溢れの歯止めが無い

`idiv` は `imul eax, S` の**前**にあるので、商がそのまま32bit の掛け算に入る。
`p == 1` まで落ちると商は最大 16,781,312 に達し、既定の `S = 2048` でも
`|商| ≥ 1,048,576` で `imul` が32bit を溢れる(クランプもサチュレーションも
無い)。

ただし到達性は別問題で、`blur.a` は自分自身のアルファを必ず含む窓の平均なので
1パスあたり `orig.a / カーネル幅` を下回れない。`blur.a` を 1 近くまで落として
なお `orig.a = 4096` を保つには、大きな `範囲` と数画素のオブジェクトが要る。
**実出力での再現は未確認**で、確定しているのは「割り算と掛け算の間に何の歯止めも
無い」ことだけである。

### 5.3 アルファは絶対に変わらない

出力アルファは常にスクラッチ側(= 元画像)の値。4パスのぼかしがアルファを
どう変えていようが、最後にそれごと捨てられる。**シャープはシルエットを変えない。**

`p <= 0` の画素は元画像がそのまま書き戻される。これは「どちらかのアルファが 0」
だけでなく `orig.a * blur.a < 4096` 全体、つまり**2つのアルファの相乗平均が
64/4096 = 1.6 % を下回るところ全部**である(両方 1.5 % なら `63*63 = 3969 < 4096`
で切り捨て)。ほとんど透明な領域はシャープが一切効かず、代わりに元画像が
そのまま出る ―― ぼかしの残骸が透明領域に残ることも無い。合成ワーカーは
`w × h` を全画素書くので、手順4の枠外書き込みが可視領域に漏れることもない。

### 5.4 上には青天井

輝度に上限クランプは1つも無く、色差にはどちら側のクランプも無い。オーバー
シュートは `aviutl.exe` の最終的な YCbCr→RGB まで生き残る
([`rgb_ycbcr.md` §3](../common/rgb_ycbcr.md))。下側だけは手順6の処理がある。

## 6. 負の輝度の後始末 ―― クランプではなく彩度を落とす

アンシャープマスクは暗い側でアンダーシュートする。exedit はそれを 0 で
クランプせず、

```
y' >= 0          -> そのまま(上限なし)
-1024 < y' < 0   -> cb *= (y'+1024)/1024 ; cr *= (y'+1024)/1024 ; y' = 0
y' <= -1024      -> y' = cb = cr = 0
```

とする。単にクランプすると「輝度0なのに彩度は満タン」の画素が残って色の縁に
見えるが、この形なら沈み込むほど色が抜け、-25 % まで行くと純粋な黒に着地する。

同じ命令列(`-1024` のしきい値、`+0x400` してから `sar 10`)が
**`色調補正` と減算合成 `0x100081e0`(ブレンド関数テーブル `0x1009fbb0` の添字
`0x02`)にもある**(`verify_luma_undershoot.py` が全8箇所を列挙)。
`色調補正` 版はさらに `0x2000` の上限クランプが続くが、シャープには無い。
明暗が非対称なのはこのためで、**光る側のハローのほうが目立つ**。

## 7. オブジェクトがスレッド数より小さいと、パスが丸ごと走らない

3ワーカーとも先頭は同じ形をしている。

```
lo = 寸法 * tid       / thread_num
hi = 寸法 * (tid + 1) / thread_num
if (寸法 < thread_num && tid != 0) return;     // (A)
if (lo >= hi) return;                          // (B)
```

(B) だけなら害は無い ―― 範囲は隣接して積み上がるので、`寸法 < thread_num` でも
全行がどれかのスレッドに属する(`シャドー`/`エッジ抽出`/`ライト` はこの形)。
問題は (A) で、tid 0 以外を黙らせたうえで、その tid 0 の担当範囲が
`[0, 寸法/thread_num)` = **空**になる。結果、**パスが1画素も走らない**。

`ぼかし` の整数・`サイズ固定` **オフ**の2ワーカー(`0x1000eae0`/`0x1000eef0`)は
同じ (A) を持つが破綻しない。飛ばされるスロットに `thread_num = 1` を書き、
`lo`/`hi` を**その後で**計算するからである。シャープは `lo`/`hi` を先に計算して
いて差し替えも無い ―― 手順4のとおり2ワーカーは `ぼかし` の `サイズ固定`
**オン**版そのものなので、これも**そちらから受け継いだ**ものである
(`verify_thread_split.py` が両者を並べて出す)。`ぼかし` を `サイズ固定` オンに
したときに何が見えるかは、パス構成が違うので**別途追う必要がある**。

`func_proc` はパスが何か書いたかに関係なくバッファを入れ替えるので、結果は
入れ替えの帳尻まで追う必要がある(`verify_thread_split.py` §4 が実際に回す)。

| 条件 | `*(fpip+0xAC)` の中身 | 最終出力 |
| ---- | --------------------- | -------- |
| `w >= N`, `h >= N` | 4回ぼかした結果 | 正常 |
| `w < N`, `h >= N`  | `ぼかし(対バッファの古い内容)` ―― 垂直パスが何も書かないのに入れ替えるので、水平パスが古い内容を「1パス目の出力」として読む | `元画像 + S*(元画像 - それ)`。**引き算の相手が別物になる** |
| `w >= N`, `h < N`  | **元画像**。垂直パスの結果は次の(走らない)パスの入れ替えでそのつど取り消され、合成も走らない | **完全な無操作**(縦ぼかしが残るわけではない) |
| `w < N`, `h < N`   | **元画像**。何も走らない | **完全な無操作** |

合成ワーカー `0x10089b60` は `ぼかし` からの流用ではなくシャープ固有のコードだが、
プロローグだけは同じ形をそのまま持っている ―― つまりこの穴は3ワーカーすべてに
あり、うち1つは書き写しではなく新しく書かれたものである。

`N` は AviUtl のスレッド数設定(通常はコア数)。細い線や小さな文字でしか
起きないが、落ちるわけではなく、静かにシャープでなくなる。
**未確定**: 対バッファの古い内容が何かは、本プロジェクトでは一度も追えていない
([`box_blur.md` §4](../common/box_blur.md) と同じ留保)。

## 10. 未確定事項

- 手順7の「`w < N` で対バッファの古い内容がぼかしとして読まれる」ケースで、

- `table[0x44]` がスクラッチへ書くときの行幅は `[0x101539c0]`(8バイト画素用の
  グローバル)で、合成ワーカーがスクラッチを読むときの行幅は `*(fpip+0xEC)`。
  同じ複製で転送元にも `[0x101539c0]` が使われている以上この2つは一致するはず
  だが、`[0x101539c0]` の**書き込み側**は追っていない

- スクラッチ `0x101a5328` の確保サイズ。8バイト画素で `w × h` 分を置ける前提で
  読んでいる。

- 最終的な YCbCr→RGB 変換とそのクリップは `aviutl.exe` 側にある ――
