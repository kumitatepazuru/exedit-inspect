# エフェクト登録構造体とディスパッチ

対象: `data/exedit.auf`、32bit PE、`ImageBase = 0x10000000`。アドレスはすべて VA。

解析済みの全エフェクトが**例外なく**共有している骨組み。個別 README の
「1. 登録エントリとモードの違い」に当たる部分の共通項をここにまとめる。

## 1. `FILTER_DLL` 配列 `0x100a3e28`

exedit は自分が持つ標準エフェクトを `FILTER_DLL*` の配列として `0x100a3e28` から
並べている。**この配列のエントリは AviUtl には登録されない** ―― exedit 自身が
オブジェクトに紐付けて呼び出す内部テーブルである。

```
uv run main.py tools.get_func_address        # 1行/エフェクトでダンプ
uv run main.py tools.filter_table --name <名前>   # 1エフェクト分の完全デコード
```

構造体そのものは `data/filter.h` の `FILTER` レイアウトに一致するが、exedit は
末尾の2フィールドを**別の用途に流用**している(手順4・5)。

## 2. 2登録モデル ―― `fp->flag & 0x20`

多くのエフェクトは**同じ `func_proc` を共有する登録構造体を2個**持つ。
実行時の分岐は `fp->flag & 0x20` の1点だけで、そこから先は画素フォーマットから
違う。

| `flag` | 種別                       | 画素                                         | 入力                    | 対バッファ              |
| ------ | -------------------------- | -------------------------------------------- | ----------------------- | ----------------------- |
| `0x20` | オブジェクトのフィルタ効果 | **8バイト/画素 PIXEL_YCA**(y, cb, cr, **a**) | `*(fpip+0xAC)`          | `*(fpip+0xB0)`          |
| `0x00` | フレーム(映像)フィルタ     | 6バイト/画素 PIXEL_YC(アルファなし)          | `fpip->ycp_edit` (`+4`) | `fpip->ycp_temp` (`+8`) |

登録の数はエフェクトによって違う:

| エフェクト                                 | 登録数 | オブジェクト側 | フレーム側     | 備考                                                                                              |
| ------------------------------------------ | ------ | -------------- | -------------- | ------------------------------------------------------------------------------------------------- |
| [`ぼかし`](../blur/README.md)              | 2      | `0x100a0720`   | `0x100a0848`   | フレーム版は `サイズ固定` を落とす                                                                |
| [`境界ぼかし`](../boundary_blur/README.md) | 1      | `0x100a09e0`   | ―              | フレーム版そのものが存在しない                                                                    |
| [`発光`](../luminous/README.md)            | 2      | `0x100a6218`   | `0x100a6340`   | フレーム版は `サイズ固定` を落とす                                                                |
| [`モザイク`](../mozaic/README.md)          | 2      | `0x100a8858`   | `0x100a8980`   | 両者のUI定義は完全に同一                                                                          |
| [`閃光`](../glint/README.md)               | 1      | `0x100a59f8`   | (`0x100a5b20`) | フレーム版の構造体は .data に**あるが配列から到達できない**。`func_proc` は `0x1004f260` のスタブ |
| [`拡散光`](../diffusion_light/README.md)   | 2      | `0x100a21d0`   | `0x100a22f8`   | `+0x74` 拡張ブロックまで共有                                                                      |
| [`グロー`](../glow/README.md)              | 2      | `0x100a6528`   | `0x100a6650`   | フレーム版は `光成分のみ` を落とす。**フレーム版も `*(fpip+0xB0)` を作業用に使う**                |
| [`クロマキー`](../chroma_key/README.md)    | 1      | `0x100a0e28`   | ―             | フレーム版そのものが存在しない。`+0x74` も NULL                                                    |
| [`カラーキー`](../color_key/README.md)     | 1      | `0x100a16d8`   | ―             | 同上。`ex_data` のレイアウトも `クロマキー` と同一                                                |
| [`ルミナンスキー`](../luma_key/README.md)  | 1      | `0x100a7d60`   | ―             | 同上。ただし `+0x74` は持つ。抜き系3エフェクトはどれもフレーム版が無い                            |
| [`ライト`](../light/README.md)             | 1      | `0x100a72b0`   | ―             | フレーム版そのものが存在しない。`サイズ固定` に相当するチェックボックスも無い                     |
| [`シャドー`](../shadow/README.md)          | 1      | `0x100b8560`   | ―             | 同上。`flag = 0x40000020` で bit30 が立つ(意味は未追跡)。名前の似た `シャドー(カメラ制御)`(`0x100a31b0`)は別実装 |
| [`縁取り`](../border/README.md)            | 1      | `0x100a5cf8`   | ―             | 同上、`flag = 0x40000020`。`ex_data` レイアウトも UI の作りも `シャドー` と揃っているが、**チェックボックスは1個も無い**(ボタン2個だけ) |
| [`凸エッジ`](../convex_edge/README.md)     | 1      | `0x1009ecb0`   | ―             | フレーム版なし。**`check_n = 0` かつ `ex_data_size = 0` かつコールバック全 NULL** で、UI 関連のコードが1バイトも無い |
| [`エッジ抽出`](../edge_extraction/README.md) | 1    | `0x100a2bb0`   | ―             | フレーム版そのものが存在しない。`func_WndProc` がチェックボックスを排他にする                     |
| [`斜めクリッピング`](../diagonal_clipping/README.md) | 1 | `0x100a7490` | ―          | フレーム版なし。`凸エッジ` と同じ **`check_n = 0` かつ `ex_data_size = 0` かつコールバック全 NULL**。exedit の100登録中この形は22個あるが、**トラックバー5本はこれだけ** |

フレーム版がチェックボックスを1個落とすときは、**オブジェクト版の
`check_name` / `check_default` 配列の途中を指す**という手が使われている
(`発光` の `サイズ固定`、`閃光` の残骸版がこれ)。

## 3. `FILTER_PROC_INFO` のオフセット

SDK 定義(`data/filter.h`)の範囲:

| offset            | フィールド              | 備考                              |
| ----------------- | ----------------------- | --------------------------------- |
| `+0x00`           | `flag`                  | exedit 独自ビットあり(下記)       |
| `+0x04` / `+0x08` | `ycp_edit` / `ycp_temp` | フレーム版の入出力                |
| `+0x0C` / `+0x10` | `w` / `h`               | フレーム版のサイズ                |
| `+0x14` / `+0x18` | `max_w` / `max_h`       | 画像領域のサイズ                  |
| `+0x1C`           | `frame`                 | 現在のフレーム番号                |
| `+0x40` / `+0x44` | `yc_size` / `line_size` | **exedit はどちらも読んでいない** |

フレーム版のワーカーは1行のバイト数を `max_w`(`+0x14`)×6 で自前計算しており、
バイト数として文書化されている `line_size`(`+0x44`)を使わない。

SDK に定義が無い、exedit 独自の領域:

| offset            | 意味                                                                                                                           | 出典                                        |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------- |
| `+0xAC`           | オブジェクトの画像バッファ(8バイト/画素)                                                                                       | 全エフェクト共通                            |
| `+0xB0`           | 対バッファ(同上)                                                                                                               | 全エフェクト共通                            |
| `+0xB4` / `+0xB8` | オブジェクトの幅 / 高さ [画素]                                                                                                 | 全エフェクト共通                            |
| `+0xD4` / `+0xD8` | 新キャンバスに対するオブジェクト中心のずれ。単位 **1/4096画素(推定)**                                                          | [`閃光` §3](../glint/README.md)             |
| `+0xEC`           | オブジェクトバッファの行幅 [画素]                                                                                              | 全エフェクト共通                            |
| `+0xF0`           | 同・確保されている行数                                                                                                         | [`拡散光` §4](../diffusion_light/README.md) |
| `+0xA8` / `+0x114` | 現在のフレーム(タイムライン絶対、`時間制御` 適用後)/ その 1/100 フレーム端数                                                 | [`object_time.md` §1](object_time.md)       |
| `+0xFC` / `+0x100` | フレームレートの分子 / 分母。`fps = 分子/分母`                                                                                | [`object_time.md` §4](object_time.md)       |
| `+0x104`          | 音声バッファ(16bit PCM)。SDK の `audiop`(`+0x2C`)は exedit では使われない                                                   | [`object_time.md` §1](object_time.md)       |
| `+0x118`          | サブオブジェクト固有の遅延[フレーム]。`テキスト` の `文字毎に個別オブジェクト` だけが書く                                     | [`object_time.md` §5](object_time.md)       |
| `+0x12C`          | `時間制御` の時刻表(無ければ NULL)                                                                                            | [`object_time.md` §6](object_time.md)       |
| `flag & 0x200`    | **描画品質を落としてよい**。`閃光`/`放射ブラー`/`方向ブラー` はサンプル数を50、`凸エッジ` は16で頭打ちにする。立てる側は未追跡 | [`閃光` §2](../glint/README.md) / [`凸エッジ` §6](../convex_edge/README.md) |

`モザイク` は `fpip->frame`(`+0x1C`)を一切読まない ―― `func_proc` 全域
(`0x1006b090`〜`0x1006bd26`)を逆アセンブルし、`fpip` レジスタへの `+0x18`/`+0x1C`
アクセスが無いことを確認済み([`モザイク` §1](../mozaic/README.md))。同じ入力に
対する出力は完全に決定的で、フレームをまたぐ揺らぎは無い。

## 4. `fp+0x60` / `fp+0x64` の差し替え

exedit は起動時の初期化ループ(`0x10031570` 付近、書き込みは `0x100315a4`)で、
全エフェクト構造体の末尾2フィールドを**AviUtl SDK とは別の意味で**埋める。

| offset  | SDK での意味     | exedit が入れるもの                             |
| ------- | ---------------- | ----------------------------------------------- |
| `+0x60` | `dll_hinst` 相当 | exedit 自身の `fp->exfunc`(AviUtl の `EXFUNC*`) |
| `+0x64` | `hwnd`           | **exedit 内部の関数テーブル `0x100a41e0`**      |

したがって系統が2つあり、混同しやすい:

- **マルチスレッド起動** ―― `[fp+0x60]+0xCC` = `EXFUNC::exec_multi_thread_func`。
  引数は `(worker, param1, param2)` の3つだけで、ワーカーは
  `(tid, thread_num, param1, param2)` を受け取る。**パラメータを4個より多く
  渡せない**ため、半径などは必ずグローバル経由になる(手順6)。
- **矩形転送 / 矩形クリア** ―― `[fp+0x64]+0x44` / `+0x48`。実体は
  `0x10081b40` / `0x10081f90`。詳細は [`blend_modes.md`](blend_modes.md)。

### 登録構造体は**オブジェクトごとに書き換えられる**

`FILTER_DLL` 配列の指す構造体は静的な .data の1個きりだが、exedit は
`func_proc` を呼ぶ直前に、いま処理しているオブジェクトの状態を**そこへ
毎回書き込む**(`0x10047be0` / `0x10047e30` のほぼ同一な2ルーチン)。

| offset            | 入るもの                                                          |
| ----------------- | ----------------------------------------------------------------- |
| `+0x44` / `+0x48` | `track` / `check` ―― オブジェクトのデータ領域を指す               |
| `+0x4C`           | `ex_data_ptr`(`+0x104` にも同じ値が入る)                         |
| `+0xE0`           | オブジェクト構造体(1個 `0x5C8` バイト)                           |
| `+0xE4`           | `(通し番号 << 16) \| 添字+1` ―― UI ヘルパーに渡す値(§7)         |
| `+0xEC` / `+0xF0` | この区間の開始・終了フレーム                                     |
| `+0x118` / `+0x11C` | オブジェクト全体の開始・終了フレーム(中間点を跨ぐ)             |
| `+0x120` / `+0x124` | `obj+0x5C0` / `obj+0x5C4` の写し                                |

`fp->track` が SDK 通り「AviUtl 側で設定される」のと同じ仕組みだが、時間の
2組(`+0xEC`/`+0xF0` と `+0x118`/`+0x11C`)は exedit 独自で、`フェード` /
`ワイプ` / `テキスト` / `パーティクル出力` が読む。詳細は
[`object_time.md`](object_time.md)。

## 5. `+0x70` (`ex_data_def`) と `+0x74`

exedit は AviUtl の `FILTER` の後半も流用している。

- **`+0x70`** ―― `{u16 kind; u16 size; char *name}` の配列。`ex_data` の中身を
  フィールド単位で宣言する。`ex_data` を持つ**全49フィルタで合計サイズが
  `ex_data_size` と一致する**ことを確認済み
  ([`閃光` §7](../glint/README.md) / `verify_ex_data_layout.py`)。
- **`+0x74`** ―― 表示スケール / スライダーのドラッグ範囲 / 多成分コントロールの
  グループ化マーカー。SDK では `func_is_saveframe` の位置。詳細は
  [`param_scaling.md`](param_scaling.md)。

`ex_data` の実例:

| エフェクト | サイズ | レイアウト                                       |
| ---------- | ------ | ------------------------------------------------ |
| `発光`     | 4      | `dword[0]` の下位24bit = RGB、bit24 = 色指定なし |
| `閃光`     | 8      | `color`(3) + `no_color`(1) + `mode`(4)           |
| `グロー`   | 8      | `color`(3) + `no_color`(1) + `type`(4)           |
| `クロマキー` | 12   | `color_yc`(6、`PIXEL_YC`) + パディング(2) + `status`(4) |
| `カラーキー` | 12   | 同上(フィールド表は `0x100a16a0` と別物だが宣言内容は同一) |
| `ルミナンスキー` | 4 | `type`(4) のみ。フィールド表は `0x100a7d10`               |
| `シャドー` | **260** | `color`(3) + パディング(1) + **`file`(256)**。フィールド表は `0x100b84b0` |
| `縁取り`   | **260** | 同上。フィールド表は `0x100a5ca8` ―― **別テーブルだが宣言内容も名前文字列のポインタも `シャドー` と完全に一致する** |
| `エッジ抽出` | 4    | `color`(3) + **名前無しパディング**(1)。`no_color` が無い |

`kind` の値は `0` = 無名パディング、`1` = int、`2` = 固定長文字列、`3` = 色
(`size` が 3 なら RGB バイト列、6 なら `PIXEL_YC`)。`2` は
`シャドー` の `file`(パターン画像のパス)が初出で、`ex_data_size = 260` も
解析済みで最大である([`シャドー` §1](../shadow/README.md))。`縁取り` が同じ
260バイトを持つのは偶然ではなく、**パターン画像を持つ2エフェクトが同じ
レイアウトを共有している**([`縁取り` §1](../border/README.md))。

フィールド名の文字列も共有されている ―― `type` (`0x1009d6c4`) は**18個の
フィールド表**が指しており、「コンボボックスの選択値が入る dword」の総称に
なっている。

`ex_data` の色まわりは [`rgb_ycbcr.md`](rgb_ycbcr.md) にまとめてある。

### `check_default` が負のチェックボックス

`data/filter.h` の言うとおり負の初期値はボタンを意味するが、exedit は値で
種類を分けている。`-1` は**ボタン**(色選択ダイアログを開く)、`-2` は
**コンボボックス**で、選択値は `ex_data` の dword に入る。

| エフェクト | `check_default` が負のもの           | 実体                             |
| ---------- | ------------------------------------ | -------------------------------- |
| `発光`     | `光色の設定` = -1                    | ボタンのみ                       |
| `閃光`     | `光色の設定` = -1、`前方に合成` = -2 | 3項目のコンボ(`ex_data.mode`)   |
| `グロー`   | `光色の設定` = -1、`通常` = -2       | 6項目のコンボ(`ex_data.type`)   |
| `クロマキー` | `キー色の取得` = -1                | ボタンのみ(スポイトを起動)      |
| `カラーキー` | `キー色の取得` = -1                | 同上。**文字列そのものを共有**(`0x100a0f5c`) |
| `ルミナンスキー` | `暗い部分を透過` = -2          | 4項目のコンボ(`ex_data.type`)。**負のチェックボックスがこれ1個だけ**のエフェクト |
| `シャドー` | `影色の設定` = -1、`パターン画像ファイル` = -1 | **ボタン2個**。どちらも `-1` で、片方はファイル選択ダイアログを開く |
| `縁取り`   | `縁色の設定` = -1、`パターン画像ファイル` = -1 | 同上。**`check[]` が全部ボタン**で、真のチェックボックスも `-2` のコンボも持たない。`ボタン2個だけ` は `特定色域変換` と2例のみ |
| `エッジ抽出` | `色の設定` = -1                    | ボタンのみ(色ダイアログ。「指定なし」抜き ―― [`rgb_ycbcr.md` §1](rgb_ycbcr.md)) |

コンボボックスの項目名は `check_name[i]` が指す位置から始まる**連続した cp932
文字列**で、先頭要素がそのまま `check_name` になっている(`閃光` は
`0x100a5c5c` から3個、`グロー` は `0x100a6790` から6個、`ルミナンスキー` は
`0x100a7e98` から4個)。コントロールの静的テキストは別に持つ(`グロー` は
`0x100a67d4` の `形状`)。

## 6. パラメータはグローバルで渡る

`exec_multi_thread_func` の引数が足りないので、`func_proc` が計算した値は
**専用グローバルに書いてからワーカーが読む**。エフェクトごとに別の番地を使って
おり、`tools.xrefs` で検索すると参照が当該エフェクト内に閉じることを確認できる。

| エフェクト | グローバル                                 | 中身                                             |
| ---------- | ------------------------------------------ | ------------------------------------------------ |
| `ぼかし`   | `0x1011ec34` / `0x1011ec38`                | 垂直 / 水平パスの半径                            |
|            | `0x1011ec3c` / `0x1011ec40`                | 同・カーネル幅 (`半径*2+1`)                      |
| `拡散光`   | `0x1011efdc`                               | `強さ` から作った Q12 の不透明度                 |
|            | `0x1011efe4` / `0x1011efe0`                | 現ラウンドの半径 / カーネル幅                    |
| `モザイク` | `0x101bad24` / `0x101bad28` / `0x101bad2c` | `size` / `offset_x` / `offset_y`                 |
| `カラーキー` | `0x1011ed38` / `0x1011ed34`              | `境界補正` の半径 `r` / カーネル幅 `2r+1`。**これで全部**(キー色もトラックバーもワーカーが自分で読む) |
| `閃光`     | `0x101a6b7c`〜`0x101a6bac`                 | 毎フレーム状態ブロック(中心座標・しきい値・光色) |
| `発光`     | `0x101a5328`                               | ぼかしの中間スクラッチバッファ                   |
| `グロー`   | `0x101b2010`〜`0x101b203c`                 | 毎フレーム状態ブロック(w/h・強さ・半径3種・光色・バッファ2本・しきい値)。スクラッチは `発光` と同じ `0x101a5328` を借りる |
| `ルミナンスキー` | **無し**                             | **グローバルを1つも持たない2つのうちの1つ**。ワーカーが `fp->track[]` を直接読み、派生値(`基準輝度 ± ぼかし`)は `sub` / `add` 1命令で作る |
| `フェード` | `0x101a5390`                               | Q12 のアルファ**1個だけ**。時間の計算は全部 `func_proc` にあり、ワーカーに渡すものがこれしか無い |
| `音量フェード` | **無し**                               | 同じ計算をして**ワーカーを起動しない**(音声はインラインループ)ので、アルファはレジスタ `ebp` に留まる |
| `ライト`   | `0x101b20ac`〜`0x101b20c0`                 | 半径・カーネル幅・現在実行中のパスの係数(A または B)・光色。スクラッチは `発光`/`グロー` と同じ `0x101a5328` を借りる |
| `シャドー` | `0x10231f90`〜`0x10231fa8`、`0x102320b4`〜`0x102320b8` | スクラッチ2プレーン(`0x101a5328` を16bitアルファ用に2分割)・カーネル幅2本・`density`・影の箱の原点・影色。**半径 `r` そのものはグローバルに置かれず**、各ワーカーが `w`/`h` とカーネル幅から寸法を再計算する |
| `凸エッジ` | `0x100d7588`〜`0x100d7598`                 | スケール(double)・サンプル回数・Q16 方向ベクトル2本。**作業バッファを1つも借りない**(スクラッチ `0x101a5328` を使わない数少ない例)ので、グローバルはパラメータ4個で全部 |
| `ワイプ`   | `0x1024df80`/`0x1024e0b0`                  | 進捗(Q12)・反転フラグ。全パターンワーカー共通                                                            |
|            | `0x1024e098`/`0x1024df88`/`0x1024e0a0`/`0x1024e0a4` | ぼかしの2軸ぶんの半径・カーネル幅。スクラッチは `発光` 等と同じ `[0x101a5328]` を借りる               |
|            | `0x1024e094`/`0x1024e09c`/`0x1024df84`/`0x1024e0a8`/`0x1024e0ac` | カスタムPNGパターン専用: しきい値の帯幅・位置・書き込み先/読み込み元ポインタ3本 |

グローバルが要るのは「`func_proc` でしか計算できない値」がある場合だけで、
`ルミナンスキー` はそれが無い ―― トラックバー2本をワーカーがそのまま読み、
1命令で足し引きするだけなので、渡すものが残らない
([`ルミナンスキー` §1](../luma_key/README.md))。`カラーキー` が2個で済むのも
同じ理屈の途中まで(キー色とトラックバーはワーカーが読み、`境界補正` の半径
だけが `func_proc` 由来)である。`音量フェード` はもう一方の抜け道で、
**ワーカーを起動しなければグローバルは要らない** ―― 同じ計算をする
`フェード` がちょうど1個持っているのと対になる
([`フェード` §8](../fade/README.md))。

## 7. UI 用コードはほぼ存在しない

`func_init` / `func_exit` / `func_update` / `func_WndProc` は、`ぼかし`・
`境界ぼかし`・`モザイク`・`拡散光`・`凸エッジ` では**すべて NULL**。
`凸エッジ` はさらに `FILTER+0x58` も `ex_data` もチェックボックスも持たない
ので、**UI に相当するものがトラックバー3本しか無い**(全100登録のうち、
トラックバーだけで `ex_data` もチェックボックスもコールバックも持たないのは
20登録。解析済みではこれが唯一 ―― [`凸エッジ` §1](../convex_edge/README.md))。
`func_WndProc` を持つのは
`発光`(`0x10054c90`)・`閃光`(`0x1004f3f0`)・`グロー`(`0x10058ea0`)・
`ライト`(`0x1005c9c0`)・`クロマキー`(`0x100143d0`)・`カラーキー`(`0x10016850`)・
`ルミナンスキー`(`0x10018080`)・`シャドー`(`0x10088da0`)・
`エッジ抽出`(`0x10023af0`)だけで、やっているのは主に
`光色の設定` / `キー色の取得` ボタンのラベル書き換えと、コンボボックスや
スポイトの結果を `ex_data` へ書き戻すことである。唯一 `シャドー` だけは
画像ファイルの読み込み可否まで見て、駄目なら `MessageBoxA` を出す
([`シャドー` §8](../shadow/README.md))。`エッジ抽出` だけはチェックボックスの
変更通知も処理し、2つのチェックボックスを排他にする(後述)。それ以外は
`fp->track[]` を一切参照しない。

### コントロールID(メッセージ `0x702` の `wParam`)

`wParam = (そのコントロールの添字 << 16) | ID` で、ボタンの場合は送信側
`0x10041453` が `shl eax, 0x10 ; or eax, 0x1e1b` で組み立てている。添字は下の
`table[0x4c](fp+0xE4, 種別, 添字)` に渡すものと同じで、ボタン/チェックボックス
なら `check_name[]` の添字にあたる。ID ごとのディスパッチ側の組み立て/分岐
アドレスまで確認できているもの(`inspect/edge_extraction/verify_dispatch.py`)
を含めてまとめる:

| ID       | 意味                                                | 受け取るエフェクト                                                                                                                    | やること                                             |
| -------- | --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| `0x1e16` | ファイル名の到着                                    | `シャドー` / `縁取り` の `パターン画像ファイル`                                                                                          | `lParam` が指すパスを `ex_data+4` へ                   |
| `0x1e19` | トラックバーが動いた(**推定**、組み立て `0x10041358`) | `パーティクル出力` のみ                                                                                                              | ―                                                       |
| `0x1e1a` | チェックボックスが変わった(組み立て `0x100413d7`)   | `エッジ抽出` / `パーティクル出力` の2つだけ                                                                                              | 高位ワードで `fp->check[0]`/`[1]` を選び、排他にする   |
| `0x1e1b` | ボタン押下(分岐 `0x10041456`)                       | `閃光` / `グロー` / `ライト` の `光色の設定`(`ライト` は `色の設定`)、`クロマキー` / `カラーキー` の `キー色の取得`、`シャドー` / `縁取り` の**2つのボタン**、`エッジ抽出` ほか | 色選択 / ファイル選択ダイアログ / スポイトを起動       |
| `0x1e1c` | コンボの選択変更(組み立て `0x10041500`)             | `ルミナンスキー` ほか(下記の共有ハンドラ)、`グロー` の `形状` など                                                                       | `ex_data[0] = lParam`(`CB_GETCURSEL` の戻り値そのもの) |
| `0x1e1d` | スポイトの結果到着                                  | `クロマキー` / `カラーキー`                                                                                                              | `lParam` が指す `PIXEL_YC` を `ex_data` へコピー       |

`0x1e1a` が「チェックボックス」だと言えるのは `エッジ抽出` の受け側からで、
高位ワードを添字として `fp->check[0]` / `fp->check[1]` を選び分けている ――
`輝度エッジを抽出` と `透明度エッジを抽出` を排他にするための処理である
([`エッジ抽出` §4](../edge_extraction/README.md))。`0x1e19` は同じディスパッチで
直前に組み立てられる ID で、コントロールの種類の並び順からトラックバーと
**推定**しているだけ。**チェックボックスの通知を処理するエフェクトはほとんど
無い**(他はみな `fp->check[]` を `func_proc` で読むだけ)。`クロマキー` は続きの
`0x1e1d` を「スポイトの結果が届いた」通知として受ける
([`クロマキー` §2](../chroma_key/README.md))。

### `wParam` の上位16bit ―― どのコントロールか

解析済みエフェクトのうち**ボタンを2個持つのは `シャドー` と `縁取り`** で、
真の意味で `HIWORD` を添字として使い分けるのもこの2つである(`エッジ抽出` の
チェックボックス排他判定は `check[]` の2値切り替えなので性質が異なる)。
**添字は同じ規約でエフェクトごとに違う**のが要点:

| エフェクト | 色ボタン       | パターンボタン | 分岐                              |
| ---------- | -------------- | -------------- | --------------------------------- |
| `シャドー` | `check[1]`     | `check[2]`     | `cmp eax, 1` の一致側が色         |
| `縁取り`   | `check[0]`     | `check[1]`     | `shr eax,0x10 ; jne` の0側が色    |

差は「前に真のチェックボックス(`影を別オブジェクトで描画`)があるかどうか」
だけである([`シャドー` §8](../shadow/README.md) /
[`縁取り` §7](../border/README.md))。他のエフェクトは `LOWORD` しか見ないが、
これは「上位が無い」のではなく「見なくても一意に決まる」だけである。

`FILTER+0x58`(SDK では `func_save_start`)も exedit の流用で、設定ウィンドウの
更新エントリが入る ―― `閃光` の `0x1004f560`、`クロマキー` の `0x10014560`、
`カラーキー` の `0x100169e0`、`ルミナンスキー` の `0x10065270`。

### コンボボックス1個だけのエフェクトは `func_WndProc` を共有する

`0x10018080` は**エフェクト非依存の汎用ハンドラ**で、5つの登録構造体が
同じアドレスを指している([`ルミナンスキー` §8](../luma_key/README.md)):

| 登録                 | `func_proc`  | `+0x58`      |
| -------------------- | ------------ | ------------ |
| `ルミナンスキー`     | `0x10064ee0` | `0x10065270` |
| `ミラー`             | `0x1006a140` | `0x1006aa70` |
| `色ずれ`(2登録)      | `0x100170a0` | `0x100180d0` |
| `インターレース解除` | `0x1005b050` | `0x10065270` |

いずれも `ex_data_size = 4` で `check_name[0]` がコンボボックス。中身は
`message == 0x702 && LOWORD(wParam) == 0x1e1c` を確認して
`table[0x80](fp+0xE4, 0)` を呼び、`ex_data[0] = lParam` を書いて `TRUE` を
返すだけ、全部で67バイトである。**自分がどのエフェクトか知らないまま動く**ので、
`ルミナンスキー` の `func_WndProc` は `func_proc` から300KB離れた場所にある。

`FILTER+0x58` の側も同様に共有される。`0x10065270` は `ルミナンスキー` と
`インターレース解除` の両方が使い、
`SendMessageA(table[0x4c](fp+0xE4, 6, 0), CB_SETCURSEL, ex_data[0], 0)` の
1行しかない。

### コントロールの `HWND` を取る `table[0x4c](fp+0xE4, kind, index)`

**第2引数はコントロールの種別**である。呼び出し側を全部並べると3つ決まる:

| `kind` | 種別                      | 根拠                                                                          |
| ------ | ------------------------- | ----------------------------------------------------------------------------- |
| 5      | チェックボックス / ボタン | `クロマキー`(`0x100144d9`)、`カラーキー`(`0x10016959`)                        |
| 6      | コンボボックス            | `ルミナンスキー`(`0x1006528f`)、`グロー`(`0x10059002`)、`色ずれ`(`0x100180f0`) |
| 7      | 静的テキスト              | `グロー` の `形状`(`0x10059022`)                                              |

決め手は `グロー` の設定ウィンドウ更新(`0x10058fe0`)で、**同じ関数の中で
`kind = 6` の結果に `SendMessageA(CB_SETCURSEL)` を、`kind = 7` の結果に
`SetWindowTextA` を投げている**。`0`〜`4` も exedit のダイアログコードには
現れるが、解析済みエフェクトはどれも使っていない。

**第3引数はその種別の中での添字**で、5 と 6 では `check_name[]` の添字と一致する
―― `クロマキー` は `2`、`カラーキー` は `0`(どちらもボタン)、`ルミナンスキー` /
`グロー` は `0`(コンボ)。実際に UI 上のコントロール位置と対応している。

**トラックバーの数値表示は AviUtl 本体側の汎用描画が担っており、その表示スケールは
`+0x74` の拡張ブロックで決まる**([`param_scaling.md`](param_scaling.md))。

### 色選択ボタンの共通実装 ―― `table[0x6c]` と `table[0x80]`

`光色の設定`/`色の設定` ボタン(`0x1e1b`)を持つ `発光`・`グロー`・`ライト` の
`func_WndProc` は、**3つとも命令レベルで同一のパターン**を実行する
([`ライト` §6](../light/README.md)、`0x1005c9c0` のデコンパイルが出どころ):

```
table[0x80](fp+0xE4, 0);                     // 0x1004dac0。用途未確定
if (!table[0x6c](fp, fp->ex_data_ptr, flag))  // 0x1004d2a0。色選択ダイアログ。1以外はキャンセル扱い
    return 0;
ex_data の各フィールド名について 0x1004a7e0(fp+0xE4, フィールド名) を呼ぶ
ボタンラベルを再構築
```

`table[0x6c]`(`0x1004d2a0`)をデコンパイルすると、内部で `"GET_COLOR"` という
文字列を添えて `sub_10020800` を呼んでいる ―― AviUtl 本体側の色選択ダイアログの
起動口だと読める。`flag`(第3引数)の **bit8(`0x100`)だけ**が `ライト`(`2`)と
`発光`/`グロー`(`0x102`)で異なり、その値はそのままダイアログ側へ渡る
グローバルに保存される。`発光`/`グロー` は `0x1004a7e0` を `"color"`/
`"no_color"` の2回、`ライト` は `"color"` の1回しか呼ばない(`ライト` の
`ex_data` に `no_color` に相当するフィールドが無いため)ことと合わせると、
**bit8 がダイアログに「各画素自身の色を使う」トグルを出すかどうかの
スイッチ**だと考えて矛盾がない。

`table[0x80]`(`0x1004dac0`)は3エフェクトとも無条件に呼ぶが、戻り値は
どこでも捨てられる。中身は `sub_1008d150()` を呼んだあと第1引数を
`(arg & 0xffff) - 1` に変換して `sub_1008d290` へ末尾呼び出しするだけの
中継で、その先の2関数は未解析([`README.md` §5](README.md)の一覧参照)。
