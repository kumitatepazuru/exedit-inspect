# C / x86 の整数意味論と CRT ヘルパー

リファレンス実装が「グレースケールでは一致するのに色が付いた瞬間ずれる」ときは、
だいたいここが原因。実装は `tools.cints`(ライブラリ、`main.py` からは実行不可)。

## 1. 3種類の丸めが同じ式に同居する

| 演算 | x86 | 丸め | Python での等価 |
|---|---|---|---|
| C の `/`(整数除算) | `idiv` | **0方向への切り捨て** | `tools.cints.c_div` |
| 固定小数のスケーリング | `sar` | **floor**(負値は下へ) | `tools.cints.sar` / `>>` |
| double → int | `fistp`(RC=truncate) | **0方向への切り捨て** | `math.trunc` |

Python の `//` は floor なので、**負の被除数で C の `/` と食い違う**。exedit は
固定小数のスケーリングに `sar` を、平均に `idiv` を、**隣り合った行で使い分けて
いる**。

```
sum_c += (c * a) >> 12          // sar  : floor
avg_a  = sum_a / count          // idiv : truncate
avg_c  = trunc(sum_c * 4096.0 / sum_a)   // x87 + fistp : truncate
```

影響が出るのは**符号付きの値だけ**。輝度 `y` とアルファ `a` は負にならないので
どちらの丸めでも同じ結果になり、**色差 Cb/Cr でだけ差が出る**。だから
グレースケールのテスト画像では一致してしまう。

具体例:

* `モザイク` の `タイル風`: `>> 2` は `sar` なので `0 <= v <= 3` は変化なしだが、
  `-1 >> 2 == -1` なので `v = -1` でも BRIGHT が `-2`、DARK が `0` になる
  ([`モザイク` §6](../mozaic/README.md))。
* フレームフィルタ版のボックス平均は素の `idiv` 3本なので、符号付きの Cb/Cr で
  Python の `//` とズレる([`拡散光` §6](../diffusion_light/README.md))。
* `フェード` と `音量フェード` は**同じ `(v * g) >> 12` を書いていて片方だけ
  ズレる**という分かりやすい対比になっている。`フェード` が掛けるのはアルファ
  (非負)なので `sar` と `idiv` が一致するが、`音量フェード` が掛けるのは 16bit
  PCM サンプルで、負側だけ 1LSB 下へ丸められる
  ([`フェード` §8](../fade/README.md))。

## 2. マジックナンバー除算

MSVC の符号あり整数定数除算の定型。`0x10624dd3` を掛けて上位32bitを取り、
`sar 6`(実質 `>>38`)し、符号補正を足す ―― 意味は `/1000` で、**四捨五入では
なく0方向への切り捨て**。使用箇所と検算は [`param_scaling.md` §2](param_scaling.md)。

`tools.cints` はこの命令列を逐語再現しているので、リファレンス実装は
`raw * 4096 // 1000` ではなくこちらを通すのが安全(正の入力では一致する)。

## 3. CRT ヘルパー

| アドレス | 役割 |
|---|---|
| `0x10091ad8` | `double` → `int` の切り捨て変換(`_ftol` 定型)。x87 制御ワードの丸めを `or ah, 0xc` で 11(0方向切り捨て)にしてから `fistp` する |
| `0x10091c70` → `0x10091c92` | `pow(double, double)` ラッパー |

`0x10091ad8` は解析済み6エフェクトすべてに出てくる ―― x87 を経由する計算の出口は
例外なくここ。`フェード` / `音量フェード` では**これが唯一の直接呼び出し**で、
秒→フレームの2回の変換にしか使われない([`object_time.md` §4](object_time.md))。

## 4. x87 の double 除算

色の正規化 `trunc(sum_c * 4096.0 / sum_a)` は整数除算ではなく **x87 の double
除算**を通る(定数 `4096.0` は `0x1009a3a0`)。

`sum * 4096` は最大43bitなので double に**厳密に**載る。したがって丸めが入るのは
除算1回だけで、結果は厳密有理数の切り捨てと一致する ―― `モザイク` で400,000通りの
乱数を突き合わせて確認済み(`verify_alpha_average.py`)。

### 除算を先に丸めてから掛ける形は一致しない

`シャドー` のエンコーダは順序が逆で、**スレッドごとに1回
`scale = density / (カーネル幅 * 4096)` を作り、それを各画素の窓和に掛ける**。
除算の丸めが先に確定してしまうので、厳密には整数になる組み合わせでも結果が
1 小さくなることがある ―― `拡散`×`濃さ` の全 501,501 通りのうち 27,109 通り
(5.41%)で、完全不透明な内側が `濃さ` ではなく `濃さ - 1` になる
([`シャドー` §5](../shadow/README.md))。

「`sum * 定数 / 除数`」と「`sum * (定数 / 除数)`」は**同じ式ではない**、という
だけの話だが、リファレンス実装を `sum * density // (k * 4096)` と書くと
静かにずれるので注意が要る。なおこの見積りは x87 の精度制御が 53bit
(MSVC の既定)であることを前提にしており、**AviUtl 本体が制御ワードをどう
残しているかは未確認**である(§6)。

## 5. `>> 12` と `a >= 4096` の分岐

`(c * a) >> 12` は Q12 の乗算だが、`a >= 4096` のときは掛け算を飛ばして `c` を
そのまま足す近道が入る。これは単なる最適化ではない ―― `data/filter.h` が明記して
いるとおり画素値は範囲外に出ることがあり、**`a > 4096` では色側が `a = 4096`
相当で頭打ちになる一方 `sum_a` は生の `a` を積む**。`モザイク` ではそのブロック
だけが暗くなる形で結果に出る。

## 6. 未確定事項

* **x87 の精度制御(PC)が 53bit か 64bit か**。MSVC の CRT は 53bit を既定に
  するが、exedit は DLL なので制御ワードを残すのはホストの `aviutl.exe` である。
  §4 の「除算を先に丸める」形の誤差評価だけがこれに依存する。
* **最終的な YCbCr→RGB 変換とそのクリップは `aviutl.exe` 側**にあるため、
  満輝度超過(`モザイク` の `タイル風` ハイライト、`発光` の LogSumExp、
  `閃光` の超白)や色差の16bit折り返しが画面上でどう出るかは、どのエフェクトでも
  推定にとどまる。
