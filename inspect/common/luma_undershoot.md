# 負の輝度の後始末 ―― クランプではなく彩度を落とす

画素の輝度が 0 を下回りうるエフェクトは、それを 0 でクランプする代わりに
**最後の 1/4 レンジで色差を線形に抜く**同じ定型を使う。

解析の出どころは [`シャープ` §6](../sharp/README.md)。

## 1. 式

```
y >= 0          -> そのまま(この定型に上限は無い)
-1024 < y < 0   -> cb = (cb * (y + 1024)) >> 10
                   cr = (cr * (y + 1024)) >> 10
                   y  = 0
y <= -1024      -> y = cb = cr = 0
```

`1024 = 4096/4`、つまり満輝度の 25 %。`>> 10` は `sar` なので符号付きの
Cb/Cr では floor で、C の `/` とは負側で食い違う
([`integer_semantics.md`](integer_semantics.md))。

| `y`     | 出力 `y` | 色差の倍率 |
| ------- | -------- | ---------- |
| 0 以上  | そのまま | 1          |
| -256    | 0        | 0.750      |
| -512    | 0        | 0.500      |
| -1023   | 0        | 0.001      |
| -1024以下 | 0      | 0          |

**単にクランプすると「輝度0なのに彩度は満タン」の画素が残る。** YCbCr の
`y = 0, cb ≠ 0` は RGB に直すとどこかのチャンネルが負になる組み合わせで、
最終変換のクリップ次第で色の付いた縁に見える。この形なら沈み込むほど色が抜け、
-25 % まで行くと純粋な黒に着地する。

## 2. 命令列

```
0x10089c76: test ecx, ecx            ; y
0x10089c78: jge  <write>             ; y >= 0 -> 何もしない
0x10089c7e: cmp  ecx, 0xfffffc00     ; -1024
0x10089c84: jle  <all zero>
0x10089c86: add  ecx, 0x400
0x10089c8c: imul ebp, ecx            ; cb *= (y + 1024)
0x10089c8f: imul ebx, ecx            ; cr *= (y + 1024)
0x10089c92: sar  ebp, 0xa
0x10089c95: sar  ebx, 0xa
0x10089c98: xor  ecx, ecx            ; y = 0
```

`cmp` は2つの符号化(`0x81 /7` の汎用形と `0x3d` の eax 短縮形)で現れるので、
バイト検索するときは両方を見る必要がある。

## 3. 使っているところ

`uv run main.py inspect/sharp/verify_luma_undershoot.py` が全8箇所を列挙する。

| 場所                                | 用途                                     | 上限クランプ |
| ----------------------------------- | ---------------------------------------- | ------------ |
| `0x10089c7e` / `0x10089d1e`         | `シャープ` のアンシャープ合成、2経路      | **無し**     |
| `0x10014f1d` ほか計4箇所            | `色調補正`                                | あり(`0x2000` = 8192) |
| `0x10008219` / `0x10008382`         | ブレンド関数テーブル `0x1009fbb0` の添字 `0x02`(減算合成、[`blend_modes.md` §3](blend_modes.md)) | ― (未読) |

3つとも「引き算で 0 を割りうる」処理である点が共通している ―― アンシャープの
アンダーシュート、明るさ・コントラストの引き下げ、減算合成。

**`シャープ` にだけ上限が無い**のが違いで、そのためオーバーシュートは
`aviutl.exe` の最終的な YCbCr→RGB まで生き残る
([`rgb_ycbcr.md` §3](rgb_ycbcr.md))。明暗が非対称になり、光る側のハローの
ほうが目立つ。

**未確定**: 減算合成 `0x100081e0` の本体は読んでいない ―― この定型が2箇所ある
ことだけを確認している。
