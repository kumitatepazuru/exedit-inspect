# アルファ加重平均と分離型ボックス平均

`ぼかし`・`発光`・`境界ぼかし`・`拡散光`・`モザイク`・`閃光`・`グロー`・
`クロマキー`・`カラーキー`・`ライト`・`シャドー`・`縁取り`・`シャープ` が、名前も見た目も違うのに**同じ2つの型**で書かれている部分。個別 README を読み直す前にここを
見れば、そのエフェクト固有なのは「除数」と「パス構成」だけだと分かる。

極端な例が `シャープ` で、2つのワーカーは `ぼかし` の `サイズ固定` オン版と
**命令単位で同一**(差は分岐先とグローバル4本だけ)。この型は「似ている」の
ではなく、実際に同じコードが複製されていることがある
([`シャープ` §4](../sharp/README.md))。

## 1. アルファ加重(プリマルチプライ)累積 ―― 全オブジェクト版の共通形

オブジェクト効果版(8バイト/画素 PIXEL_YCA)の集計は、**例外なく**この形。

```
for each sample:
    a == 0     -> 何もしない(色にもアルファ和にも寄与しない)
    a >= 4096  -> sum_y += y;  sum_cb += cb;  sum_cr += cr        // (c*4096)>>12 == c の近道
    それ以外   -> sum_y  += (y  * a) >> 12
                  sum_cb += (cb * a) >> 12
                  sum_cr += (cr * a) >> 12
    sum_a += a                                                     // a != 0 のときだけ

sum_a != 0 -> out.c = trunc(sum_c * 4096.0 / sum_a)   // 色は「アルファの和」で割る
sum_a == 0 -> 色は書き込まない(書き込み先の古い内容が残る)
out.a = sum_a / 除数                                   // アルファは別の数で割る
```

**色をアルファの和で割る**のがこの形の意味で、透明画素が色を黒へ引っ張らない。
だからぼかされたオブジェクトのふちは灰色にならず、色味を保ったまま透明度だけが
落ちる。もし色も画素数で割っていたら、縁は不透明なまま暗く濁っていた。

`sum_a == 0` のときに色を書かないのは一見危険だが、その画素のアルファは必ず 0 に
なる(`0/除数`)ので、以降のパスでも合成でも読まれない
(**未確認**: 後段がアルファを無視して色を読む経路があれば古い値が漏れうる。
[`拡散光` §9](../diffusion_light/README.md))。

### 正規化の分母 ―― 色とアルファで違う

| エフェクト                               | 色 (`y`,`cb`,`cr`) の分母 | アルファの分母                         |
| ---------------------------------------- | ------------------------- | -------------------------------------- |
| [`ぼかし`](../blur/README.md)            | `sum_a`                   | カーネル幅 or 生存サンプル数(下表)     |
| [`拡散光`](../diffusion_light/README.md) | `sum_a`                   | 同上                                   |
| [`モザイク`](../mozaic/README.md)        | `sum_a`                   | **ブロックの画素数**(透明画素も数える) |
| [`閃光`](../glint/README.md)             | `length`(サンプル数)※     | ― (輝度がそのままアルファになる)       |

※ `閃光` だけは `sum_a` で割らない。範囲外・アルファ0のサンプルは読み飛ばすが
**割る数は常に `length`** なので、はみ出した分は黒として平均されるのと同じに
なる。これは被覆率を測るための意図的な設計で、出力は
`(y=4096, cb, cr, a=out)` というアンプリマルチプライ形になる
([`閃光` §5](../glint/README.md))。

`発光` の明部抽出だけは向きが逆で、**輝度にアルファを掛けてから**しきい値と
比較し(`y_eff = (src.y * src.a) >> 12`)、色差には掛けない。この非対称は
[`発光` §3](../luminous/README.md) 参照。

### フレームフィルタ版

アルファが無いので素の整数平均になる。3チャンネルとも `idiv`(0方向切り捨て)
1本で、x87 は使われない。**符号付きの Cb/Cr で Python の `//` とズレる**のは
ここ([`integer_semantics.md`](integer_semantics.md))。

## 2. ボックス平均 ―― 一様重みしかない

**全エフェクト・全ワーカーを通して、ガウシアン核も重みテーブルも存在しない。**
1パスは常に「窓内の単純和 ÷ 除数」、カーネル幅は `2*半径 + 1`。
`発光` の縮小精度版、`拡散光` の3変種、`ぼかし` の12ワーカーすべてで確認済み。

### 例外1 ―― `縁取り` は割らずに飽和させる

`縁取り` の2パスは窓の和をカーネル幅で割らず、`(sum * gain) >> 10` を
**4096 で飽和**させて書く([`縁取り` §4](../border/README.md))。両ワーカーとも
`idiv` はスレッド範囲の計算に2つあるだけで、**画素ループに除算が1命令も無い**。

平均なら完全被覆の窓は 4096 に戻るだけだが、和なら 4096 を大きく超えて飽和側に
張り付く ―― この1点で、同じスライディングウィンドウが**ぼかしではなく膨張
(dilation)**になる。`ぼかし = 0` のとき `gain = 1024` で `>> 10` と打ち消し
合い、二値のシルエットに対しては一辺 `2*サイズ+1` の正方形による厳密な膨張。
`ぼかし` は飽和に必要な被覆率を上げる利得で、**パス1とパス2の両方に掛かる**。

`グロー`(下記)が「割らずに足す」のに対し、`縁取り` は「割らずに飽和させる」。
どちらも正規化がコードのどこにも書かれていない点は同じである。

### 例外2 ―― `グロー` は割らない

`グロー` の水平パスとストリークワーカーは、和をカーネル幅で割る代わりに
`(sum >> 4) * 強さ >> 10` を蓄積バッファへ**足す**([`グロー` §4](../glow/README.md))。
形は同じスライディングウィンドウだが平均ではないので、**1パスの利得が窓幅に
比例する** ―― `拡散` を上げると広がるだけでなく明るくなる。正規化を担っているのは
`func_proc` が各パスへ渡す `強さ` のスケジュールのほうで、コードのどこにも
「平均」は書かれていない。垂直パスと `ぼかし` 用の水平パスだけは普通に
カーネル幅で割る。

滑らかさは重みではなく**パスの重ね方**で作られている:

| エフェクト      | パス構成                                                                                                      | 合成カーネル                                                                                    |
| --------------- | ------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `ぼかし`        | 固定4パス `V(ry_hi) → H(rx_hi) → V(ry_lo) → H(rx_lo)`。半径は `r_hi = ceil(r/2)`, `r_lo = floor(r/2)` に2分割 | 軸ごとに box⊛box = **三角形**(r が奇数なら上底3の台形)。台の広がりは `r_hi + r_lo = r` ちょうど |
| `発光`          | 固定6パス、半径は `2.0` から等比数列(`k = pow(拡散*0.5, 0.2)`)。各パスの結果を**蓄積バッファへ足し込む**      | マルチスケール。連鎖でもあり和でもある                                                          |
| `グロー` `通常` | 固定4パス、半径は `拡散/8, /6, /4, /2`。**垂直パスが蓄積バッファ自身を読む**ので、パス N+1 はそれまでの合計をさらにぼかす | 完全なカスケード。パスごとの重みは `強さ` を毎回半分にして与える                               |
| `グロー` ライン/クロス | 1方向につき3スケール(半径 `r, r/2, r/4`、`強さ` は `1, 2, 4` 倍)。カスケードせず、どれも抽出結果を読む | **3スケールの利得が等しい**ので、細く明るい芯 + 広い暈になる                                    |
| `拡散光`        | 2ラウンド、半径は `r2 = trunc(拡散/2.236)`, `r1 = 拡散 - r2`。**各ラウンドの水平パスの中で合成まで済ませる**  | 「diffuse → merge」の直列。`発光` の蓄積とは別物                                                |
| `境界ぼかし` ON | 2パス(V→H)、半径分割なし                                                                                      | 素の分離型ボックス。ただし対象は**αチャンネルだけ**                                             |
| `クロマキー` `境界補正` | 2パス(V→H)、半径分割なし。対象は画素ではなく**16bit のマット**                                        | 素の分離型ボックス。ただし出口で元マットとの積とコントラスト伸張が付く([`border_correction.md`](border_correction.md)) |
| `カラーキー` `境界補正` | 同上。ただしマットを作らず**画素のアルファ本体**をぼかす                                              | 同上。掛ける相手もアルファなので**平坦な半透明部が `a³/4096²` に潰れる**([`border_correction.md` §4](border_correction.md)) |
| `ライト` 陰影パス | 2パス(V→H)、半径分割なし。**画素そのものではなくアルファ(素または `4096-a` 反転)をスカラーとしてぼかす**。除数は常にカーネル幅で、キャンバスは広げない | 素の分離型ボックス。出口でオブジェクト自身の Y/Cb/Cr へ加算(合成ではない) |
| `ライト` 後光パス | 2パス(V→H)、半径分割なし。対象は`陰影パス`と同じくアルファのみ(反転なし) | 同上だが**キャンバスを `w×h` から `(w+2r)×(h+2r)` へ広げる**唯一の「アルファだけをぼかす」パス([`ライト` §3/§4](../light/README.md)) |
| `シャドー`      | 固定4パス `V(kB) → H(kB) → V(kA) → H(kA)`。半径は `ぼかし` と同じ2分割(`kA = 2*floor(拡散/2)+1`, `kB = 2*ceil(拡散/2)+1`) | 軸ごとに box⊛box = **三角形**(`拡散` が奇数なら上底3の台形)。支持長は `2*拡散+1` ちょうど。対象は**アルファだけ**で、中間は16bitのアルファ専用プレーン2枚([`シャドー` §4](../shadow/README.md)) |
| `シャープ`      | 固定4パス `V(r_hi) → H(r_hi) → V(r_lo) → H(r_lo)`、`ぼかし` と同じ2分割。**ワーカーは `ぼかし` の `サイズ固定` オン版と命令単位で同一** | 軸ごとに三角形。ただし使い道が逆で、この結果は元画像から**引かれる**(アンシャープマスク) |
| `縁取り`        | 2パス(V→H)、半径分割なし。カーネル幅は `2*サイズ+1`。対象は**アルファだけ**で、中間は16bitプレーン1枚 | **平らな箱**(畳み込みが起きないので三角形にならない)。振幅1のインパルスは値1のまま `(2*サイズ+1)²` 画素へ広がる。ただし各パスの出口に飽和があるので、実効的な形は被覆率次第([`縁取り` §4](../border/README.md)) |
| `レンズブラー`  | 1パス。窓は正方形ではなく**半径 `R` の円板**で、境界だけ1画素幅の線形ランプ。`R` は 0〜45 に圧縮され、画像のほうを `R/範囲` 倍に縮小してから走る | **一様重みの円板**。1画素の明点が `2R+1` 画素の円になる = 玉ボケ。累積は輝度カーブ空間([`レンズブラー` §5](../lens_blur/README.md)) |

半径がグローバル経由でワーカーに渡る理由は
[`filter_registration.md` §6](filter_registration.md)。

### ping-pong

`ぼかし` は「現画像を読む → 対バッファへ書く」を1パスとし、`func_proc` が直後に
ポインタを入れ替える。**半径0のパスは丸ごとスキップされ、入れ替えも飛ぶ**ので
連鎖は壊れない。`発光` のステップ2は `ycp_temp` に書き戻すので、次のパスの
ステップ1が読む場所そのものになる(= 連鎖)。

## 3. 除数の違いが、端の扱いのすべて

集計の式は共通なので、**画像の外をどう数えるかは「アルファを割る除数」1箇所に
しか現れない**。ここが3変種ある。

| 除数                                                       | 意味                                              | 採用しているワーカー                                                                                    |
| ---------------------------------------------------------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| **常にカーネル幅** `2r+1`                                  | 画像外を**透明として数える** → ふちがフェードする | `ぼかし` オブジェクト・`サイズ固定` オフ / `拡散光` 成長版 / `境界ぼかし` ON(ゼロ埋め) / `クロマキー`・`カラーキー` の `境界補正`(ゼロ埋め) / `ライト`(陰影・後光の両パス。`サイズ固定` に相当するチェックボックス自体が無く、**この変種しか存在しない**) / `シャドー`(4パスとも。影が輪郭でフェードするのはこれ) / `方向ブラー` オブジェクト・`サイズ固定` オフ / `放射ブラー` オブジェクト(**`サイズ固定` の有無によらず常にこちら**) |
| **窓に残っている実サンプル数** (`r+i+1` → `2r+1` → `2r-i`) | 端で**正規化し直す** → ふちの不透明度が保たれる   | `ぼかし` オブジェクト・`サイズ固定` オン / `ぼかし` フレーム / `拡散光` `サイズ固定`版・フレーム版 / `シャープ`(**`ぼかし` の `サイズ固定` オン版ワーカーそのもの** ― [`シャープ` §4](../sharp/README.md)) / `方向ブラー` オブジェクト・`サイズ固定` オン、およびフレーム版 / `レンズブラー`(**`サイズ固定` の有無によらず常にこちら**。除数は「覆えた円板の面積」`sum_w`) |
| **除算しない**(和に利得を掛けて飽和)                     | 画像外は透明として数えるが、**割らない**ので端の減衰は「窓に入る不透明サンプル数」がそのままランプになる | `縁取り` の2パス([`縁取り` §4](../border/README.md))。ふちがフェードするかどうかは `ぼかし` = 利得次第 |
| ―                                                          | 端の扱い**未確認**                                | `発光`(スライディングウィンドウの前後処理ループを読み切っていない。[`発光` §10](../luminous/README.md)) |

**`サイズ固定` は「大きさが変わらない」だけでなく、端の明るさの扱いまで変える。**
成長版にとって画像の外は本当に何も無い場所なので、カーネル幅で割ることが
そのまま「透明として扱う」になり、拡張した縁へ自然にフェードする。固定版は
実サンプル数で割るため、**端でも拡散光やぼかしが減衰しない**。

## 4. スライディングウィンドウの3フェーズと既知の overrun

1本のパスは「立ち上がり(窓が育つ) → 中段(定常) → 立ち下がり(窓が縮む)」の
3フェーズで書かれ、中段のループ回数が `長さ - カーネル幅` になっている。

**この回数は `カーネル幅 > 長さ` で負になり、そのとき破綻する。**
各エフェクトはそれぞれ別の方法で回避している:

| エフェクト   | 回避策                                                                                                                                       |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `ぼかし`     | いずれかの半径が寸法の半分以上なら**事前拡張経路**へ([`canvas_growth.md`](canvas_growth.md))。フレーム側は各半径を独立に `寸法/2` でクランプ |
| `拡散光`     | `2*r >= w or h` なら先にキャンバスを広げ、以後 `サイズ固定` 扱い                                                                             |
| `境界ぼかし` | `rx = min(rx, w//2)`, `ry = min(ry, h//2)` の独立クランプのみ                                                                                |
| `発光`       | 半径を `h/2-1`(垂直)/ `w/2-1`(水平)でクランプ                                                                                                |
| `グロー`     | `2*拡散+1 > 寸法` なら事前拡張(オブジェクト)/ 半径を `c_div(寸法-1,2)` にクランプ(フレーム)。加えて各ワーカーが自前でもクランプする ―― ただし `通常` の水平ワーカー `0x10055ed0` **だけはしない**(呼び出し経路では安全) |
| `ライト`     | `発光` と同型のクランプ(`trunc(寸法/2)-2`、`発光` の `-1` よりわずかに保守的)を1段目に、**確保済みバッファの余白**(`fpip+0xEC`/`+0xF0`)に対する2段目のクランプを追加([`ライト` §2](../light/README.md))。1段目は陰影パスの半径、2段目は後光パスの半径に使われ、両者が食い違うことがある |

| `クロマキー` / `カラーキー` | **何もしない**。`境界補正` は最大5なのでカーネル幅は高々11で、そこまで小さいオブジェクトは想定外という扱い |
| `シャドー`   | **寸法に対しては何もしない**。半径は「確保済みバッファの余白」に対してだけクランプされ(`ライト` のクランプ#2に相当)、`w`/`h` とは一度も比較されない。破綻するのは各軸**1本目**のパスだけで、2本目は入力長が `寸法 + kB - 1` あるので `kA ≤ kB` より必ず足りる([`シャドー` §2](../shadow/README.md)) |
| `シャープ`   | **何もしない。** `func_proc` は `fpip+0xEC`/`+0xF0` を読まず、半径を `w`/`h` と比べもしない。`ぼかし` の `サイズ固定` オン版ワーカーをそのまま使いながら、`サイズ固定` に相当するチェックボックスも事前拡張も持たないので、**下の1つ目の穴に逃げ道無しで嵌まる**([`シャープ` §4](../sharp/README.md)) |
| `縁取り`     | **半径を縮めるのではなく、オブジェクトを先に太らせる。** `2*サイズ >= w or h` なら透明なパディングを付けて `w`/`h` を `2*サイズ+1` 以上にしてから走らせ、終わったら同じ量を削り戻す。半径クランプは確保済みバッファの余白に対するものだけ([`縁取り` §3](../border/README.md)) |

回避しきれていないケースが3つ、実測で見つかっている:

- **`ぼかし` の `サイズ固定` オン + `範囲` が寸法の半分以上**。クランプも事前拡張も
  されないので、画像外の読み出しと**書き込まれない帯**が生じる。最大サイズで
  確保されたバッファ内なのでクラッシュはしないが、出力は確保時の内容次第
  ([`ぼかし` §9](../blur/README.md))。**`シャープ` は同じワーカーを使いながら
  `サイズ固定` を選ばずに常にこの状態にいる**ので、`範囲` が寸法を超えれば必ず
  嵌まる([`シャープ` §4](../sharp/README.md))。
- **`境界ぼかし` OFF の偶数サイズ + 半径 = サイズ/2**。`k = length+1 > length` で
  中段が0回になり、書き込みポインタが連続加算のまま立ち下がりフェーズを回るので
  **1行(列)分バッファ外へ溢れ、上下(左右)非対称のフェード**になる
  ([`境界ぼかし` §3.2](../boundary_blur/README.md))。
- **`シャドー` の高さ(幅)がカーネル幅未満**。中段が0回になるので1本目のパスが
  `2*カーネル幅-1` 本出力し、立ち上がりフェーズがオブジェクトの外の行(列)から
  アルファを読む。スクラッチ プレーン1をはみ出すのは**高さ1〜2画素かつ `拡散` が
  奇数のとき、最大2行**だけで(総当たりで確認)、はみ出し先は次のパスが
  上書きするプレーン2の領域。実害があるのは読み出しのほう
  ([`シャドー` §2](../shadow/README.md))。
- **`クロマキー` / `カラーキー` の `境界補正` + 幅か高さが `2r+1` 未満**。
  立ち上がりフェーズが `r+1` 回、立ち下がりが `r` 回を無条件に回すので、長さに
  よらず必ず `2r+1` 個書く。`クロマキー` は垂直パスの溢れが map A から map B の
  領域へ、`カラーキー` は対バッファの `h` 行目より後ろへ落ち、どちらも水平パスの
  溢れは画素バッファ内へ落ちる。先行・後行ポインタのどちらにも上限が無いので
  **読み出しも枠外へ出る**([`border_correction.md` §5](border_correction.md))。

**未確定**: いずれも「バッファは最大キャンバスサイズで確保されているので
クラッシュしない」という前提で止めており、溢れた分の着地先は追っていない。

**`縁取り` だけがこの穴を構造的に塞いでいる。** 半径を寸法に合わせて縮めるので
はなく、寸法のほうをカーネル幅以上に太らせてから走らせ、終わってから削り戻す
([`縁取り` §3](../border/README.md))。半径クランプが「見た目を変えない代わりに
効きを削る」のに対し、こちらは**効きを保ったまま前提を満たす**。上の5行の
どれにも当てはまらない唯一のエフェクトである。

### 3フェーズを使わない選択肢 ―― `凸エッジ`

近傍を読むエフェクトがすべてスライディングウィンドウで書かれているわけではない。
`凸エッジ` は各画素で `2*幅` 個のサンプルを取り直し、**1サンプルごとに4本の
範囲判定を通してから読む**([`凸エッジ` §4](../convex_edge/README.md))。
和を差分更新しないので `O(w*h*幅)` になる代わりに、立ち上がり / 中段 /
立ち下がりの区別そのものが無く、この節の穴はどれも成立しない ―― 枠外の
サンプルは「透明として数える」でもなく**そもそも足されない**。

窓は画素ごとに形が同じなので、走査方向と `角度` が揃っていれば差分更新に
できるが、任意の角度では窓が行に沿って平行移動しないので一般には効かない
―― `幅` の上限が 100 と小さいことと引き換えに、全角度で同じ素直なコードに
してある、と読める。

### 同じ選択をしている3つのブラー

`放射ブラー` / `方向ブラー` / `レンズブラー` も、近傍を舐めるのに
スライディングウィンドウを使わない。理由はそれぞれ違う:

| エフェクト     | 窓の形                   | 差分更新できない理由                             | 計算量の抑え方                     |
| -------------- | ------------------------ | ------------------------------------------------ | ---------------------------------- |
| `放射ブラー`   | 画素ごとに向きも長さも違う線分 | 窓が画素ごとに別物                          | サンプル数を `範囲·R'/1000` で頭打ちにする([`放射ブラー` §4](../emission_blur/README.md)) |
| `方向ブラー`   | 向きが一定の線分         | 斜めだと行に沿って平行移動しない(`凸エッジ` と同じ) | サンプル数を 4〜257 に押し込める([`方向ブラー` §5](../directional_blur/README.md)) |
| `レンズブラー` | 円板                     | 円は行ごとに幅が変わるので和の差分更新が2次元で要る | **画像を縮小してから**半径 45 でぼかす([`レンズブラー` §4](../lens_blur/README.md)) |

3つとも「窓の中を毎回舐め直す」`O(w·h·窓)` のループで、`凸エッジ` と同じく
**§4 の3フェーズの穴はどれも成立しない**(枠外のサンプルは足されないだけ)。

## 5. 丸め

- `(c * a) >> 12` は `sar` = floor。プリマルチプライの往復で半透明部の色が
  わずかにずれる。`ぼかし` で `範囲=2`・`cb=-1000, cr=2000` のスプライトを
  4パス通すと `cb ∈ [-1030, -1000]`、`cr ∈ [1980, 1998]`(1%未満)。
- 色の除算は整数ではなく **x87 の double 除算**を通る。`sum * 4096` は最大43bitで
  double に厳密に載るため、丸めが入るのは除算1回だけ。`モザイク` で400,000通りの
  乱数を厳密有理数の切り捨てと突き合わせて一致を確認済み。
- **同じ式の中に `sar`(floor)と `idiv`/`fistp`(0方向切り捨て)が同居する。**
  符号付きの色差ではこの2つが食い違う ―― [`integer_semantics.md`](integer_semantics.md)。
