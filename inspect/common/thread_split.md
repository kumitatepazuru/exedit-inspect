# ワーカーのスレッド分割と、2つのガード

`exec_multi_thread_func`(`[fp+0x60]+0xCC`、[`filter_registration.md` §4](filter_registration.md))が
起動するワーカーは `(tid, thread_num, param1, param2)` を受け取り、自分の担当
範囲を先頭で計算する。**その計算の形が2通りあり、片方はオブジェクトが
スレッド数より小さいときにパスを丸ごと落とす。**

解析の出どころは [`シャープ` §7](../sharp/README.md)。

## 1. 共通の形

```
lo = 寸法 * tid       / thread_num        // idiv、0方向切り捨て
hi = 寸法 * (tid + 1) / thread_num
...
if (lo >= hi) return;                     // (B)
for (i = lo; i < hi; i++) { ... }
```

`寸法` は分割の軸で決まる。

| ワーカーの種類     | 分割する軸 | `寸法` |
| ------------------ | ---------- | ------ |
| 垂直ボックス平均   | **列**     | `w`    |
| 水平ボックス平均   | 行         | `h`    |
| 画素ごとの処理     | 行         | `h`    |

垂直パスだけ列分割なのは、1本のスライディングウィンドウが1列を上から下へ
走るからで、`クロマキー`/`カラーキー` の `境界補正`
([`border_correction.md`](border_correction.md))も同じ理由で同じ形になる。

(B) だけの形は `寸法 < thread_num` でも安全である。`lo`/`hi` は隣接して
積み上がる(`Σ (hi - lo) == 寸法`)ので、担当が空になるスレッドが増えるだけで
**どの行も必ずどれか1つのスレッドが処理する**。`シャドー`・`エッジ抽出`・
`ライト`・`グロー` などはこの形。

## 2. ガード (A) ―― 付けると壊れることがある

一部のワーカーは (B) の前にもう1本持っている。

```
if (寸法 < thread_num && tid != 0) return;     // (A)
```

意図は「小さいオブジェクトは1スレッドでやる」で、そのままでは足りない ――
tid 0 の担当も `[0, 寸法/thread_num) = [0, 0)` で**空**だからである。
成立させるには `thread_num` を 1 に差し替えたうえで `lo`/`hi` を**その後で**
計算する必要がある。

```
                            差し替えあり                    差し替えなし
  cmp   寸法, thread_num      cmp ecx, esi                   idiv esi        ; lo
  jge   skip                  jge  skip                      idiv esi        ; hi
  test  tid, tid              test edi, edi                  cmp  ecx, esi
  jne   return                jne  return                    jge  skip
  mov   thread_num, 1         mov  esi, 1     <-- これ       test edi, edi
skip:                       skip:                            jne  return
  lo = ... / thread_num       lo/hi をここで計算            skip:
```

**差し替えを持つのは少数派**である。イメージ全域を走査すると、
`jge / test r,r / jne` の形のガードは40箇所以上あるのに対し、飛ばされる
スロットに `mov r32, 1` があるのは数箇所しかない
(`uv run main.py inspect/sharp/verify_thread_split.py` §3)。

`ぼかし` の中ですら分かれている:

| ワーカー                                | 形            |
| --------------------------------------- | ------------- |
| 整数・`サイズ固定` オフ(`0x1000eae0` / `0x1000eef0`) | (A) + 差し替え |
| 整数・`サイズ固定` オン(`0x1000f310` / `0x1000f7e0`) | (A) のみ ―― `シャープ` が流用しているのはこの2本 |
| カーブ版(`0x10010190` ほか)            | (A) のみ      |

## 3. 壊れたときに何が起きるか

`シャープ` で確認した3つのケース。分割の軸が違うワーカーが混ざっている
エフェクトでは、幅と高さで別々に効く。

| 条件                | 結果                                                                                                   |
| ------------------- | -------------------------------------------------------------------------------------------------------- |
| `w < N`(垂直パス)  | 垂直パスが1画素も書かない。`func_proc` は**それでもバッファを入れ替える**ので、次の水平パスは対バッファの古い内容を「前のパスの出力」として読む |
| `h < N`(水平パス・画素パス) | 同様に何も書かない。`シャープ` の4パス構成では垂直パスの結果が次の(走らない)パスの入れ替えでそのつど取り消され、**完全な無操作**になる |
| 両方                | 何も走らず、やはり無操作                                                                                |

**入れ替えの帳尻まで追わないと結論が逆になる。** 「片方の軸だけぼけた絵が出る」
と読みたくなるが、実際には ping-pong が元に戻すので何も起きない ――
`シャープ` では `verify_thread_split.py` §4 が4パス分の入れ替えを実際に回して
確認している。

`N` は AviUtl のスレッド数設定(通常はコア数)。**落ちはしない** ―― バッファは
最大キャンバスサイズで確保されており、読み書きの範囲も変わらない。静かに
効果が消えるか、引き算の相手が別物になるだけである。

**未確認**: `ぼかし` の `サイズ固定` オン版も同じ形なので同じことが起きるはずだが、
そちらのパス構成と入れ替えの帳尻は追っていない。

**未確定**: 対バッファの古い内容が何か。本プロジェクトはどのエフェクトでも
そこを追えていない([`box_blur.md` §4](box_blur.md) と同じ留保)。
また、差し替えを持たない40箇所すべてについて (B) が本体全体を覆っているかは
確認していない ―― `シャープ` の3ワーカーについてだけ確定している。

## 4. 重複書き込みのほう

(A) を持たない形にも副作用がある。`寸法 < thread_num` では `lo == hi == 0` の
スレッドが複数できるので、**行ループの外に無条件の書き込みがあるワーカーでは
それが重複する**。`エッジ抽出` の外周1画素([`エッジ抽出` §6](../edge_extraction/README.md))と
`モザイク` の同種の重複([`モザイク` §4](../mozaic/README.md))がこれで、
どちらも書く値が同じ定数なので実害は無い。
