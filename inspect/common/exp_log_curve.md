# 指数/対数空間の輝度カーブ(`光の強さ` / `拡散速度`)

`ぼかし` の `光の強さ`、`発光` の `拡散速度`、`レンズブラー` の `光の強さ` は、
**まったく同じヘルパー**を呼んでいる。範囲がどれも 0~60 なのもそのためである。違うのは
「カーブ空間で平均するか、加算するか」の1点だけで、そこから帰結が大きく分かれる。

## 1. ヘルパー4本

ぼかし・発光の6パスループの**前後に1回ずつ**、全画面の往復変換として走る。
`レンズブラー` は円板カーネルの前後に1回ずつ。

| アドレス                    | 役割                     | 使うのは                     |
| --------------------------- | ------------------------ | ---------------------------- |
| `0x10070220` → `0x10070290` | 順変換(**8バイト/画素**) | `ぼかし` オブジェクト版 / `レンズブラー`   |
| `0x100703f0` → `0x10070470` | 逆変換(8バイト/画素)     | 同上                         |
| `0x10070550` → `0x100705c0` | 順変換(**6バイト/画素**) | `ぼかし` フレーム版 / `発光` / `レンズブラー` |
| `0x10070700` → `0x10070780` | 逆変換(6バイト/画素)     | 同上                         |

矢印は「エントリ → 画素ループ本体」。

### 呼ぶ側のガードは共通ではない

**`ぼかし` は値が 0 のとき呼び出しごとスキップする**(`0x1000e539` の
`test eax,eax; jle`)ので、`光の強さ = 0` なら往復変換そのものが走らない。
**`レンズブラー` は無条件に呼ぶ** ―― ヘルパー側が値を `[1, 100]` に
クランプするので、`光の強さ = 0` でも `base = 1.001` のカーブを必ず1往復する。
帰結として **`レンズブラー` では色差が常に 1/16 に量子化される**(§5)。
`発光` の `拡散速度` は `> 0` のときだけカーブ経路そのものへ入る。

関連グローバル(`ぼかし` で同定):

| アドレス                                   | 中身                                                  |
| ------------------------------------------ | ----------------------------------------------------- |
| `0x101e4318` / `0x101e4310`                | `base` / `1/ln(base)`                                 |
| `0x101e42f4` / `0x101e4300` / `0x101e4304` | ヘルパーへの引数(画像 / w / h)                        |
| `0x10135c68` / `0x10149840`                | ヘルパーが使う行幅[画素](オブジェクト8B / フレーム6B) |

## 2. 底

```
base = 1.0 + clamp(値, 1, 100) * 0.001        // UI の 1~60 では 1.001 ~ 1.06
```

`ぼかし` の `光の強さ` も `発光` の `拡散速度` も同じ式。UI の上限が60なので
`1.06` までしか届かないが、コード上は100までクランプされる。

## 3. 順変換 / 逆変換

**順変換**(8バイト版。画素を `{float y; int8 cb; int8 cr; int16 a;}` へ組み替える):

```
a <= 0     -> y = 0.0f, cb = 0, cr = 0            (アルファ自体は不変)
それ以外   -> y  = (float) pow(base, clamp(y, 0, 4096) / 16) - 1
              cb = clamp((cb + 8) >> 4, -128, 127)
              cr = clamp((cr + 8) >> 4, -128, 127)
```

6バイト版はアルファが無いぶんクランプ分岐が無く、`y_in = clamp(src.y, 0, 4096)`
から同じ式。**pow の前にクランプするので指数は最大256**。

**逆変換**:

```
y  = round(ln(y + 1) * 16 / ln(base))     // クランプなしで16bit書き戻し
cb = cb_byte << 4;   cr = cr_byte << 4
```

`pow` は `0x10091c70` のラッパー経由、float→int は `0x10091ad8`
([`integer_semantics.md`](integer_semantics.md))。

## 4. 平均するか、加算するか ―― 決定的な違い

|                    | `ぼかし` の `光の強さ`                                                      | `発光` の `拡散速度`                         |
| ------------------ | --------------------------------------------------------------------------- | -------------------------------------------- |
| カーブ空間での操作 | 4パスの**平均**                                                             | 6パスの**加算**(蓄積バッファへ)              |
| 結果の式           | `out = 16 * log_base( mean_i( base^(y_i/16) ) )` = **べき平均**             | `log(sum(exp(x_i)))` に近い **LogSumExp**    |
| 上界               | 平均は入力の min/max の間に必ず収まるので、**4096を超えることはあり得ない** | **平気で 4096 を超える**                     |
| 逆変換のクランプ   | 無い(が、上記の理由で不要)                                                  | 無い(こちらは実害あり)                       |
| 帰結               | 「ぼかしても明るい所が明るいまま広がる」                                    | 「6パスのうち最も明るい1パスの寄与が支配的」 |

`ぼかし` 側は750通りの窓で 4096 超えが起きないことを確認済み
(`verify_light_curve.py`)。したがって **`発光` で問題になる「満輝度超過 →
チャンネルごとのクリップ → 色相のずれ」は `ぼかし` では起きない。**

`レンズブラー` は `ぼかし` と同じ**平均**側なので、こちらも 4096 を超えない。
違うのは窓の形(円板)と、`ぼかし` のように 0 でスキップしない点だけである
([`レンズブラー` §4](../lens_blur/README.md))。

`発光` 側で重要なのは順序である。`log_base(a+b) ≠ log_base(a) + log_base(b)` なので、
**6個の値を指数空間で足してから1回だけ対数を取る**のと、各パスを個別に往復させて
から線形空間で足すのとは数学的に別物になる。また指数の肩に乗るのは明部抽出の
出力なので、`拡散速度` は単独の強さを持たない ―― `強さ`/`しきい値`/`光色のY` が
その場所に与えた輝度が大きいほど桁違いに増幅される。

### `光の強さ` の実測(窓 `[0,0,0,0,4096]` のぼかし後輝度)

| 光の強さ | base               | 出力 | 最大値に対する比 |
| -------- | ------------------ | ---- | ---------------- |
| 0        | (カーブを通らない) | 819  | 0.200            |
| 1        | 1.001              | 907  | 0.221            |
| 5        | 1.005              | 1337 | 0.326            |
| 10       | 1.010              | 1946 | 0.475            |
| 20       | 1.020              | 2816 | 0.688            |
| 30       | 1.030              | 3226 | 0.788            |
| 60       | 1.060              | 3654 | 0.892            |

`base` が1に近いほど算術平均に、大きいほど窓内で最も明るいサンプルが支配的に
なる。**何かを足したり掛けたりしているわけではない。**

## 5. 代償

- 全画面の往復変換が2パス増える(AviUtl の説明の「処理が重くなる」/
  「若干処理が重くなります」に対応)。
- **色差がカーブ空間の間ずっと 1/16 に量子化される。** `(c+8)>>4` → `<<4` なので
  16単位のグリッドに乗り、-2048~2048 の 4097 段階が **256 段階**になる。
  さらに符号付きバイトの範囲が非対称なため、`+2048` は `+2032` に切られるが
  `-2048` はそのまま通る。
  **`レンズブラー` はこれを避けられない** ―― `光の強さ = 0` にしても
  ヘルパーが 1 にクランプするだけでカーブは走るので、色差は常に 256 段階になる。
- `発光` の縮小精度ワーカーでは、色差が**毎パス [-128,127] にクランプ**される
  (輝度側は無クランプの float 加算)。
