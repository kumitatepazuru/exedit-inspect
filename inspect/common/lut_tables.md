# 共有ルックアップテーブル `0x1006c680`

実行時に生成される三角関数テーブル3本。`境界ぼかし` の角丸め侵食で発見・導出
したものだが、**`境界ぼかし` 以外の複数のフィルタからも参照されている**。

**生成ルーチン `0x1006c680` の正体は `ノイズ` の `func_init` である**
(`FILTER_DLL` 配列の [70] 番、`0x100a8ee0`)。呼ぶのは AviUtl ではなく
**exedit 自身の初期化ループ**で、`+0x60`/`+0x64` を埋めるのと同じ周回の中で
各エントリの `func_init` を呼んでいる:

```
0x100315de: mov  eax, [esi + 0x34]     ; fp->func_init
0x100315e1: test eax, eax
0x100315e3: je   0x100315eb
0x100315e5: push esi
0x100315e6: call eax
```

`FILTER_DLL` 配列は AviUtl には登録されない
([`filter_registration.md` §1](filter_registration.md))ので、AviUtl 側が
呼んでくれるわけではない ―― それでも exedit が起動時に全エントリを1周する
ため、`ノイズ` を一度も使わなくても表は埋まる。`境界ぼかし` の `func_init` が
NULL でも困らないのはそのため
(`uv run main.py inspect/diagonal_clipping/verify_registration.py` §5)。

出典: [`境界ぼかし` §3.1](../boundary_blur/README.md) / `verify_ease_table.py`、
[`斜めクリッピング`](../diagonal_clipping/README.md) / `verify_edge_ramp.py`

## 1. 3本のテーブル

`0x1006c680` が cos / sin / 1-cos で生成する。各 4097 要素の `int16` 配列
(`i = 0..4096`)。

| 先頭アドレス | 生成式 | 確認状況 |
|---|---|---|
| `0x101daf68` | cos 系 | 生成ルーチン内での分類のみ。**式は未検算** |
| `0x101dcf78` | `table[i] = trunc(2048 * (1 - cos(i * pi/4096)))` | `.rdata` の実定数から導出・検算済み |
| `0x101def80` | sin 系 | **式は未検算** |

## 2. `0x101dcf78` ―― イージングテーブル

0からなだらかに立ち上がり4096で頭打ちになる「持ち上げコサイン」型のイーズイン
カーブで、直線でも真円弧でもない。

| i | 0 | 1024 | 2048 | 3072 | 4096 |
|---|---|---|---|---|---|
| `table[i]` | 0 | 599 | **2047** | 3496 | 4096 |

中間点は理論値 2048 ちょうどのはずが、`cos(pi/2)` の浮動小数点誤差で **2047** に
なる(実測、実害なし)。

### 引き方は2通りあるが、配列は1本

```
順方向:  table[v]                    // v はそのまま 0~4096 の値
逆方向:  *(0x101def78 - 2*t)         // t は 0~4096 の比
```

`0x101dcf78 + 4096*2 == 0x101def78` が成り立つので、**逆方向参照は同じ配列の
`table[4096 - t]`(= 左右反転)に過ぎない**。アドレス演算だけで確認できる。

`0x101def78` はテーブル2の**末尾要素**(`table[4096]`)であって、テーブル3の先頭
`0x101def80` とは別物 ―― 8バイト手前にある。見間違えやすい。

## 3. 使われ方(`境界ぼかし` OFF パス)

縦横それぞれの「軸ランプ」(位置だけで決まる 0~4096 の直線)をテーブルに通し、
**ユークリッド和**を取る:

```
v = table[縦ランプ値]
h = table[横ランプ値]                             // 逆引きテーブル参照で実装
dist   = trunc(sqrt(v*v + h*h))                   // fild/fsqrt/切り捨て
alpha' = max(元のalpha - 2*dist, 0)
```

角では両軸の寄与が重なってより深く侵食され、辺の中央は片方の軸しか効かない ――
これが「辺は緩やかに、角は丸く縮む」角丸め侵食の正体。

## 4. 使われ方(`斜めクリッピング`)

[`斜めクリッピング`](../diagonal_clipping/README.md) は同じ表を、直線からの
符号付き距離を階調に変えるのに使う:

```
alpha' = (alpha * table[ m*16 / ceil(band/256) ]) >> 12
```

`m` は 0..band の範囲に入っているので、`m*16 / ceil(band/256)` は
`m*4096/band` の切り下げ側になり、**添字は必ず 4095 以下**に収まる。
`floor(band/256)` で割っていたら `band mod 256 >= 2` のとき添字が 4096 を
超え、表の直後3ワードのパディングを踏み越えて sin テーブル `0x101def80` を
読み始める ―― `band` が 256 の倍数にならない角度は普通にあるので
(45.0度・`ぼかし=0` で `band = 65534`、添字は最大 4111)、この切り上げは
実際に効いているガードである(`verify_edge_ramp.py` §4)。

`table[i] + table[4096-i]` は実数では 4096 ちょうどで、切り捨てぶんを除けば
成り立つ(`4094`〜`4096`。`4094` になるのは `i = 2048` の1点だけ)。
`斜めクリッピング` の半平面を `角度 = θ` と `θ+180` の2枚に分けても
アルファが元に戻るのは、この相補性による。

## 5. 参照元

`tools.xrefs` で3アドレスを引いた結果:

| テーブル     | 書く側                | 読む側                                                |
| ------------ | --------------------- | ----------------------------------------------------- |
| `0x101daf68` | `ノイズ.func_init` のみ | **絶対 dword としての参照は無い**(別の基点から索いている可能性は残る) |
| `0x101dcf78` | 同上                  | `境界ぼかし`(5箇所)/ `グラデーション`(4箇所)/ `斜めクリッピング`(3箇所) |
| `0x101def78` | ―(表2の末尾要素)     | `境界ぼかし`(2箇所、逆引きの基点)                    |
| `0x101def80` | `ノイズ.func_init` のみ | 同じく参照無し                                        |

## 6. 未確定事項

* **`0x101daf68` / `0x101def80` の正確な生成式と参照元**。cos / sin と分類しては
  いるが、`0x101dcf78` のように `.rdata` の実定数から導出したわけではない。
  §5 の「参照無し」も**絶対 dword のバイト走査での話**で、`0x101daf6a` のような
  ずれた基点で索いていれば引っかからない。
