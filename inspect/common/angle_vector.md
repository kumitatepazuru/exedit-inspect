# 角度トラックバー → Q16 方向ベクトル

`角度` を持つエフェクトが共有している「度 → 方向ベクトル」の変換。
`クロマキー` の**色相**が使う `atan2` + 16bit2進角([`chroma_key`](../chroma_key/README.md))とは
別系統で、こちらは **x87 の `fsin`/`fcos` → Q16 固定小数点**である。

アドレスはすべて VA(`RVA = VA - 0x10000000`)。

## 1. 定型命令列

```
fild dword [track + 4*i]        ; 角度の生値。表示スケールは常に 10(= 1/10 度単位)
fmul qword [0x1009a410]         ; +pi/1800  (= (pi/180)/10)
fld  st(0)                      ; ← 凸エッジだけ。角度を1回しか読まない書き方
fsin
fmul qword [0x1009a3e8 or 0x1009a408]   ; ±65536.0
call 0x10091ad8                 ; _ftol(0方向切り捨て)
fcos
fmul qword [0x1009a3e8 or 0x1009a408]
call 0x10091ad8
```

結果は **Q16 の整数2本**で、`65536 = 1 画素`。以降は整数だけで扱われる ――
`acc += d` を繰り返して `sar 16` すれば `floor(k * d / 65536)` になる、という
形が典型([`凸エッジ` §4](../convex_edge/README.md))。

| アドレス     | 値                | 用途                                                        |
| ------------ | ----------------- | ----------------------------------------------------------- |
| `0x1009a410` | `+pi/1800`        | 度(1/10単位)→ ラジアン。**7エフェクトが共有**              |
| `0x1009a3f8` | `-pi/1800`        | 同上、符号反転版。**`凸エッジ` の1箇所だけ**               |
| `0x1009a3e8` | `65536.0`         | Q16 スケール。角度以外の用途にも広く使われる(119箇所)      |
| `0x1009a408` | `-65536.0`        | 同上、符号反転版(10箇所)                                   |

`0x1009a3f8` と `0x1009a410`、`0x1009a3e8` と `0x1009a408` はどちらも
**符号ビットだけが違う同じ double** で、コンパイラが定数畳み込みでどちらに
寄せたかの違いにすぎない。`凸エッジ` は `fld st(0)` で角度を使い回すために
`fsin` の前に符号を済ませておく必要があり、そのために負の定数側が要る
(`verify_direction.py` §1 が2つの綴りの結果が全 7201 通りで一致することを
確認している)。

## 2. 符号の付け方は2通りある

`±65536` の掛け分けで、得られるベクトルは互いに**ちょうど逆向き**の2種類になる。

| ベクトル             | `fsin` に掛ける値 | `fcos` に掛ける値 | 使っているエフェクト                                 |
| -------------------- | ----------------- | ----------------- | ---------------------------------------------------- |
| `(-sinθ, +cosθ)`   | `-65536`(※)     | `+65536`          | `凸エッジ`(`0x10007ac8`)/ `方向ブラー`(`0x1000c229`)/ `フレームバッファ`(`0x100526a9`) |
| `(+sinθ, -cosθ)`   | `+65536`          | `-65536`          | `斜めクリッピング`(`0x1005cb00`)/ `グラデーション`(`0x100591a0`) |

※ `凸エッジ` は `fmul -pi/1800` で角度側の符号を反転してから `+65536` を
掛けるので命令の見た目は違うが、`sin(-θ)·65536 = sin(θ)·(-65536)` なので
結果は同じ列に入る。

`色ずれ`(`0x100170b1`)は同じ `+pi/1800` を使うが、`65536` ではなく
トラックバー由来の振幅を掛けて `±0.5` の丸め補正を足す別の形。
`極座標変換`(`0x1007494b`)は `+3.5π`(`0x1009a7f8` = `10.995574287564276`)を
足して double のまま保存しており、ベクトルにしていない。どちらもこの表の
「方向ベクトル」系ではない。

## 3. 軸の割り当てと画面上の向き

**`sin` 側が x、`cos` 側が y** ―― これを実際の座標まで追い切っているのは、
本リポジトリでは `凸エッジ`([`凸エッジ` §4](../convex_edge/README.md)、
`verify_direction.py` §2/§3)と `斜めクリッピング`
([`斜めクリッピング` §4](../diagonal_clipping/README.md)、同名の
`verify_direction.py` §2)の2つである。**符号の系統が互いに逆の2エフェクトで
軸の割り当てだけは一致した**ので、この対応は符号の付け方とは独立だと読める。
残る `方向ブラー` / `フレームバッファ` / `グラデーション` については、
「同じ命令列で Q16 の2値を作る」ところまでしか確認していない。

`斜めクリッピング` 側の根拠は、ベクトルを画素オフセットに落とすのではなく
**距離の漸化式に使う**ので `凸エッジ` とは形が違う ―― `中心X` と組む積が
`sin` 側(`0x1005cc19`)、`中心Y` と組む積が `cos` 側(`0x1005cbe9`)、行の項が
`cos` 側 × 行番号(`0x1005cc41`)、列を1つ進めるたびに足すのが `sin` 側
(`0x1005cc85`)。

`凸エッジ` の `(-sinθ, cosθ)` を画面座標(y は下向き)で読むと:

| `角度` | ベクトル (Q16)  | 単位ベクトル       | 画面上の向き |
| ------ | --------------- | ------------------ | ------------ |
| `0.0`  | `(0, 65536)`    | `(0, +1)`          | 下           |
| `-45.0`(既定) | `(46340, 46340)` | `(+0.707, +0.707)` | 右下  |
| `-90.0` | `(65536, 0)`   | `(+1, 0)`          | 右           |
| `+90.0` | `(-65536, 0)`  | `(-1, 0)`          | 左           |
| `180.0` | `(0, -65536)`  | `(0, -1)`          | 上           |

つまり **`角度 = 0` は真下、正の角度で画面上を時計回り**。`±360.0` まで
指定できるので同じ向きが2回ずつ出てくる。

`斜めクリッピング` の `(+sinθ, -cosθ)` はこれのちょうど逆で、`角度 = 0` が
**真上**、以降やはり時計回りになる。回る向き(時計回り)は2系統で共通で、
違うのは「どちらを向いて始まるか」だけである。

| `角度` | ベクトル (Q16)   | 単位ベクトル       | 画面上の向き |
| ------ | ---------------- | ------------------ | ------------ |
| `0.0`  | `(0, -65536)`    | `(0, -1)`          | 上           |
| `45.0` | `(46340, -46340)` | `(+0.707, -0.707)` | 右上        |
| `90.0` | `(65536, 0)`     | `(+1, 0)`          | 右           |
| `180.0`| `(0, 65536)`     | `(0, +1)`          | 下           |
| `270.0`| `(-65536, 0)`    | `(-1, 0)`          | 左           |

`角度` の生値範囲は一様ではない ―― `凸エッジ` だけが `±3600`(±360.0度)で、
`方向ブラー` / `色ずれ` / `グラデーション` / `斜めクリッピング` は
**`±36000`(±3600.0度 = 10回転)**である。表示スケールはどれも 10。

## 4. 丸めの癖 ―― `_ftol` は0方向、`sar` は floor

Q16 成分そのものは `_ftol`(0方向切り捨て)で作られるが、そこから画素オフセットを
取り出すのは `sar 16`(floor)である。**符号によって挙動が変わる**のはこの
組み合わせのせい:

- 成分が正なら `floor` は原点側へ縮む
- 成分が負なら `floor` は原点から1画素遠ざかる

`凸エッジ` ではこれが「第4象限(`-90.0 < 角度 < 0.0`)で `k=1` のオフセットが
`(0,0)` になり、その1サンプルが丸ごと無駄になる」という形で表に出る ――
**既定値の `-45.0` はその真ん中**である([`凸エッジ` §4](../convex_edge/README.md))。

## 5. x87 と libm の食い違いが出うる角度

`fsin`/`fcos` の精度は約1 ulp とされているので、`sin(θ)·65536` が整数のすぐ
近くに落ちる角度では Q16 成分が 1 ずれうる。そういう (角度, 成分) の組は
**すべて 30 度の倍数**である(`sin`/`cos` が厳密に `0`, `±0.5`, `±1` に
なる点)。それ以外の角度は最も際どいところでも整数まで `7.4e-4` の余裕があり、
double の ulp(`65536` のところで `1.5e-11`)よりはるかに大きい。

| 生値の範囲              | 該当する組 | 出典                                                   |
| ----------------------- | ---------- | ------------------------------------------------------ |
| `±3600`(`凸エッジ`)    | 34         | [`凸エッジ`](../convex_edge/README.md) `verify_direction.py` §7 |
| `±36000`(他の4つ)      | 322        | [`斜めクリッピング`](../diagonal_clipping/README.md) `verify_direction.py` §6 |

**実機の x87 がどちらを返すかは未確認。** 本リポジトリのリファレンス実装は
ホストの libm を使っている。影響の出方は使い方で変わる:

- **画素オフセットに落とす側**(`凸エッジ`)では「成分が `32768` か `32767` か」
  が `floor(2·32768/65536) = 1` と `floor(2·32767/65536) = 0` の差になり、
  **サンプルが1つ丸ごと別の画素を指す**。
- **Q16 のまま距離の比較に使う側**(`斜めクリッピング`)では境界が
  `1/65536` 画素動くだけで、絵には出ない。

## 6. 未確定事項

- **`方向ブラー` / `フレームバッファ` / `グラデーション` の軸の割り当て**。
  Q16 の2値を作るところまでは同じ命令列だが、`sin` 側を x に使っているか
  どうかはワーカーを読んでいない(`凸エッジ` と `斜めクリッピング` については
  §3 で確定済み)。
- **2つの符号系の意味の違い。** 「進む向き」と「来る向き」の使い分けに見えるが、
  ワーカーまで読めた2本は**ベクトルの役割自体が違う**(`凸エッジ` は
  サンプルを進める向き、`斜めクリッピング` は残る側を指す法線)ので、
  符号の系統がどちらの役割に対応するのかは相変わらず言えない。
- **`0x1009a7f8`(`3.5π`)を足す `極座標変換` の形。** 角度の基準を回している
  ように見えるが未追跡。
