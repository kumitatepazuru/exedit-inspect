# オブジェクトの時間軸 ―― フレーム番号とフレームレート

`ぼかし` 系のエフェクトが画素しか見ないのに対し、**入力が時間であるエフェクト**が
いくつかある(`フェード` / `ワイプ` / `音量フェード` / `ラスター` / `波紋` /
`テキスト` の `表示速度` / `パーティクル出力` の `生存時間` など)。それらが読む
フレーム番号とフレームレートは AviUtl SDK には1つも定義が無く、すべて exedit が
`FILTER` / `FILTER_PROC_INFO` の後ろに足した独自フィールドである。

出どころは [`フェード`](../fade/README.md)。検算は
`uv run main.py inspect/fade/verify_timeline.py`。

## 1. フィールド一覧

| offset          | 中身                                                        |
| --------------- | ----------------------------------------------------------- |
| `fp+0xE0`       | オブジェクト構造体へのポインタ(1個 `0x5C8` バイト)          |
| `fp+0xEC`       | **この区間**の開始フレーム(絶対、`obj+8` の写し)           |
| `fp+0xF0`       | 同・終了フレーム(`obj+0xC` の写し)                          |
| `fp+0x118`      | **オブジェクト全体**の開始フレーム(中間点で分割されていても) |
| `fp+0x11C`      | 同・終了フレーム                                            |
| `fpip+0x1C`     | `fpip->frame`(SDK)= `*(fpip+0xA8) - fp[0x118]`             |
| `fpip+0x20`     | `fpip->frame_n`(SDK)= `fp[0x11C] - fp[0x118] + 1`          |
| `fpip+0xA8`     | **現在のフレーム(絶対)**。`時間制御` 適用後                 |
| `fpip+0x114`    | 同・1/100フレーム単位の端数                                  |
| `fpip+0x118`    | そのサブオブジェクト固有の遅延、フレーム単位(§5)            |
| `fpip+0x12C`    | `時間制御` の時刻表(無ければ NULL、§6)                      |
| `fpip+0xFC`     | フレームレートの**分子**(`rate`)                            |
| `fpip+0x100`    | 同・**分母**(`scale`)。`fps = rate / scale`                 |
| `fpip+0x104`    | 音声バッファ(16bit PCM、インターリーブ)。SDK の `audiop`(`+0x2C`)ではない |

`fp` 側と `fpip` 側で **`+0x118` / `+0x11C` / `+0x120` / `+0x124` が別々に存在
する**ことに注意。`0x1008b010`(`テキスト` の1文字描画コールバック)は同じ基本
ブロックの中で両方の `+0x118` を読んでいるので、偶然オフセットが一致している
別の構造体だと確定できる。

## 2. 誰が埋めるか

exedit はオブジェクト1個の処理に入る直前に、ほぼ同一の2つのルーチン
(`0x10047be0` / `0x10047e30`)で `fp` と `fpip` を同時に埋める。どちらも
`obj+0x50`(中間点チェーンの先頭オブジェクト添字、単独なら負)で分岐する:

```
if (obj[+0x50] < 0) {                     // 中間点で分割されていない
    fp[0x118] = fp[0xEC] = obj[+8]
    fp[0x11C] = fp[0xF0] = obj[+0xC]
} else {                                  // 分割されている
    first     = obj[+0x50]
    fp[0x118] = obj[first][+8]            // 最初の区間の開始
    last      = 0x101592d8 のチェーンを while(next >= 0) でたどった終端
    fp[0x11C] = obj[last][+0xC]           // 最後の区間の終了
    if (fp[0xF0] != fp[0x11C]) fp[0xF0]++ // 最終区間以外は1フレーム伸ばす
}
```

**したがって時間ベースのエフェクトは、中間点で区切られていてもオブジェクト
全体を1つの時間軸として扱う。** 区間ごとの `fp+0xEC` / `fp+0xF0` を読んで
いるエフェクトは解析済みの中に無い。

## 3. `fpip->frame` との関係

同じルーチンが、いま格納したばかりの2つの値を使って SDK のフィールドも作る:

```
fpip->frame   (+0x1C) = *(fpip+0xA8) - fp[0x118]
fpip->frame_n (+0x20) = fp[0x11C] - fp[0x118] + 1
```

つまり `fp+0x118` / `fp+0x11C` / `fpip+0xA8` は **`fpip->frame` と
`fpip->frame_n` を分解したもの**であり、`フェード` の2つのカウンタは

```
t = fpip->frame - *(fpip+0x118)
u = fpip->frame_n - 1 - fpip->frame
```

と書き直せる。にもかかわらず `フェード` も `ワイプ` も SDK 側の2本を読まない
(`+0x1C` / `+0x20` への参照が1つも無い)。**帰結として、exedit がオブジェクトを
描画するフレームでは常に `t >= 0` かつ `u >= 0`** ―― `フェード` の
「アルファ≤0で `return 0`」が `fpip+0x118` 抜きでは到達不能なのはこのため
([`フェード` §5](../fade/README.md))。

## 4. 秒 ⇄ フレームの定型

トラックバーの生値は 1/100 秒単位(表示スケール100)で、フレームへの変換は
全エフェクトで同じ形をしている。`/1000` のマジック除算
([`param_scaling.md` §2](param_scaling.md))とは別系統で、**x87 と `_ftol`
だけ**を使う:

```
fild [fpip+0xFC]            ; rate
fild [fpip+0x100]           ; scale
fmul qword [0x1009a538]     ; * 100.0     <- 26箇所が共有する定数
fild [track]                ; 生値 [1/100 s]
fmul st(2)                  ; * rate
fdiv st(1)                  ; / (scale*100)
call 0x10091ad8             ; _ftol = 0方向切り捨て
```

逆方向(フレーム → 秒)は同じ2フィールドを入れ替えるだけで、`ラスター`
(`0x10080af9`)と `波紋`(`0x10082e67`)が `fpip->frame * scale / rate` を
計算している。**この2方向が同居していることが `+0xFC` = 分子 / `+0x100` =
分母の根拠**である(片方だけでは fps か 1/fps か決まらない)。

丸めは四捨五入ではなく**0方向への切り捨て**なので、29.97fps では既定の
`0.50` 秒が **14フレーム**(30fps なら15)になる。1フレーム未満の指定は
まるごと0になり、そのエフェクトは何もしなくなる。

| 生値 | UI     | 24fps | 23.976 | 29.97 | 30fps | 59.94 | 60fps |
| ---- | ------ | ----- | ------ | ----- | ----- | ----- | ----- |
| 3    | 0.03 s | 0     | 0      | 0     | 0     | 1     | 1     |
| 50   | 0.50 s | 12    | 11     | 14    | 15    | 29    | 30    |
| 100  | 1.00 s | 24    | 23     | 29    | 30    | 59    | 60    |
| 1000 | 10.00s | 240   | 239    | 299   | 300   | 599   | 600   |

## 5. `fpip+0x118` ―― サブオブジェクトの遅延

`テキスト` の `文字毎に個別オブジェクト` は、1文字ごとに描画コールバック
`0x1008b010` を呼ぶ。その中で `表示速度`(`track[1]`)から1文字あたりの遅延を
出し、**フレーム単位に直して `fpip+0x118` に足す**(`0x1008b2f2`):

```
delay_frames = _ftol(delay * rate / (scale * 1000)) + 呼び出し時の値
```

`*1000` と `rate/scale = fps` から、掛けられている `delay` の単位は
ミリ秒だと読める。イメージ中で `fpip+0x118` を**変える**書き込みはここ1箇所
だけで、残る2箇所(`0x1008b388` / `0x1008b6fb`)は入口で退避した値を戻して
いるだけである。

`フェード` はこれをフェードイン側だけから引く。結果として、文字ごとに個別
オブジェクト＋表示速度＋フェードを組み合わせると**各文字が自分の出現時刻から
フェードインする**。まだ出現していない文字は `t < 0` → アルファ ≤ 0 →
`func_proc` が `return 0` で、そもそも描画されない。

`ワイプ` は同じ `fp+0x118` / `fp+0x11C` を読むのに `fpip+0x118` を引かない。
フェードアウト側も引いていない。

**未確定**: 通常のオブジェクトで `fpip+0x118` に何が入っているか。イメージ中に
他の書き込みが無く、`FILTER_PROC_INFO` がどこで最初に構築されるかは本プロジェクト
では追えていない([`README.md` §5](README.md) の `0x10135c68` と同じ宿題)。
読み手はいずれも 0 である前提で書かれている。

## 6. `時間制御` と `fpip+0xA8`

`fpip+0x12C` が非 NULL のとき、`fpip+0xA8` は素の再生位置ではなく
**`table[obj+0x5C0]` から引き直した時刻**になる(§2 の2ルーチンの前半)。値は
1/100 フレーム単位で、`obj+8` / `obj+0xC` を100倍したものでクランプしてから
100で割り、余りが `fpip+0x114` に入る。

`時間制御` の `func_proc`(`0x10007de0`)は `xor eax,eax; ret` の2命令しか
なく、実体を持たない ―― この表の書き手が exedit のコア側にいるという読みと
整合する。`0x1004b200`(別オブジェクトとして描画)の前後で `fpip+0x12C` が
退避・**0クリア**・復帰される(`0x1004b273` / `0x1004b287` / `0x1004b2f3`)。

**未確定**: 表を書く側。`時間制御` の `位置` / `繰り返し` / `コマ落ち` が
どうこの表になるかは追っていない。

## 7. 時間を読むエフェクト

| エフェクト     | 読むもの                                 | 用途                             |
| -------------- | ---------------------------------------- | -------------------------------- |
| `フェード`     | `fp+0x118`/`+0x11C`, `fpip+0xA8`/`+0x118`, `fpip+0xFC`/`+0x100` | アルファのランプ2本 |
| `音量フェード` | 同上(`fpip+0x118` を除く)               | PCM サンプルのランプ2本          |
| `ワイプ`       | 同上(`fpip+0x118` を除く)               | 遷移の進行度                     |
| `ラスター`     | `fpip+0x1C`, `fpip+0xFC`/`+0x100`        | `周期` の位相                    |
| `波紋`         | 同上                                     | 同上                             |
| `テキスト`     | `fp+0x118`/`+0x11C`, `fpip+0x1C`/`+0x114`, `fpip+0xFC`/`+0x100` | `表示速度` / `自動スクロール` |
| `パーティクル出力` | `fp+0x118`/`+0x11C`, `fpip+0xFC`     | `生存時間` / 出力頻度            |
| `モーションブラー` | `fpip+0x1C`/`+0xA8`/`+0x114` を**書き換える** | 過去の時刻で描き直す(下記) |
| `音声波形表示` | `fpip+0x1C`, `fpip+0xFC`/`+0x100`        | 表示窓の長さ                     |

`モザイク` が `fpip->frame` を1度も読まないこと
([`filter_registration.md` §3](filter_registration.md))と対になる表である
―― 画素エフェクトは時間を読まず、時間エフェクトは画素をほとんど読まない。

### 時計を巻き戻す唯一のエフェクト

`モーションブラー`(`0x1006bfa0`〜`0x1006c01a`)は3本を**同時に**巻き戻し、
そのつど `0x1004b200`(別オブジェクトとして描画)を呼び、終わったら戻す:

```
fpip[0x114] += 端数;  fpip[0x1C]--;  fpip[0xA8]--     // 1サンプル前へ
    call 0x1004b200(..., fpip, ...)                   // その時刻で描画
fpip[0x114] -= 端数;  fpip[0x1C]++;  fpip[0xA8]++     // 戻す
```

3つが1つの時計の別表現であることの直接の裏付けで、同時に「サブオブジェクトの
時刻をずらして描き直す」という `fpip+0x118`(§5)と同系統の仕掛けでもある。
`0x1004b200` の中身自体は未読([`README.md` §1](README.md))。
