# `境界補正` ―― 抜き系エフェクトが共有するマット後処理

対象: `data/exedit.auf`、32bit PE、`ImageBase = 0x10000000`。アドレスはすべて VA。

`境界補正` という名前のトラックバーを持つエフェクトは3つあり、いずれも
**「被覆率マップを分離型ボックス平均でぼかし、元のマップと掛けて、
コントラスト伸張して適用する」**という同じ2段パイプラインを持つ。
コードは複製だが式は同一なので、個別 README を読み直さずに済むよう
ここにまとめる。

| エフェクト                                    | `境界補正` | 初期値 | 伸張定数の計算 | ぼかす対象                  | 状態       |
| --------------------------------------------- | ---------- | ------ | -------------- | --------------------------- | ---------- |
| [`クロマキー`](../chroma_key/README.md)       | 0〜5       | 1      | `0x100138f9`   | 16bit マット `min(d, 4096)` | 解析済み   |
| `特定色域変換`                                | 0〜8       | 2      | `0x10015b49`   | 16bit マット(未確認)        | **未解析** |
| [`カラーキー`](../color_key/README.md)        | 0〜5       | 0      | `0x10016602`   | **画素のアルファ本体**      | 解析済み   |

この3つで打ち止めであることは、**両側から別々に数え上げて**確認している
(`inspect/color_key/verify_border_chain.py` §6):

- `mov eax, 0x1000; cdq; idiv r32` に続いて `A`/`B` を作る形は、850KB の
  画像全体でこの3箇所にしか現れない(バイト走査)。
- `境界補正` という名前のトラックバーを持つ登録エントリも、この3つだけ
  (`0x100a3e28` の配列を全走査)。

## 1. パイプライン

```
pass V   マップを垂直にボックス平均               (スレッド分割は「列」)
pass H   その結果を水平にボックス平均し、
         v = (blur * 元マップ) >> 12
         t = (v - A) * r + B
         v == 0 || t <= 0 ?  a = 0  :  a = (a * t) >> 12
```

- 垂直パスだけ**列でスレッド分割**する。水平パスとキー判定は行分割なので、
  パスごとに別の `exec_multi_thread_func` になる(その境界がバリアを兼ねる)。
- ボックス平均は [`box_blur.md` §4](box_blur.md) の3フェーズそのままで、
  **除数は常にカーネル幅 `2r+1`**。画像の外はゼロ、つまり「被覆率0 =
  キー色」として平均される。
- 掛けているのは**ぼかす前のマップ**であって、ブレンドではない。単純に
  ぼかしただけでは前景側へにじむが、元マップとの積を取ることでキー側は 0 の
  まま保たれる。結果として `境界補正` は**フェザーではなく、柔らかい肩を持つ
  収縮(erosion)**になる。

## 2. 伸張定数

```
A = 4096 - 4096/r              // C の整数除算(0方向切り捨て)
B = 4096 - (4096/r)*r          // = 4096 mod r
t(v) = (v - A) * r + B
```

| `r` | カーネル | `A`  | `B` | `t(0)`  | `t(2048)` | `t(4096)` | 生存下限 `v` |
| --- | -------- | ---- | --- | ------- | --------- | --------- | ------------ |
| 1   | 3        | 0    | 0   | 0       | 2048      | 4096      | 1(恒等)      |
| 2   | 5        | 2048 | 0   | -4096   | 0         | 4096      | 2049(50%)    |
| 3   | 7        | 2731 | 1   | -8192   | -2048     | 4096      | 2731(67%)    |
| 4   | 9        | 3072 | 0   | -12288  | -4096     | 4096      | 3073(75%)    |
| 5   | 11       | 3277 | 1   | -16384  | -6144     | 4096      | 3277(80%)    |
| 8※ | 17       | 3584 | 0   | -28672  | -12288    | 4096      | 3585(87.5%)  |

- **`t(4096) == 4096` が全 `r` で厳密に成り立つ。** `B` が `4096 mod r` に
  なっているのはそのためで、完全に埋まった内部は不透明のまま残る。
- **`r = 1` は恒等の伸張**(`A = B = 0`、傾き1)。このときパイプラインは
  「ぼかして元と掛ける」だけになる。
- `r` を上げると `A` 未満がすべてアルファ0に落ちる。傾きも `r` になるので、
  境界の帯はどんどん細く硬くなる。

※ `r = 8` は `特定色域変換` でしか選べない。この行について確認できているのは
**`A`/`B` を作る命令列が他の2つと同一である**ことまでで、後段が同じ形で使って
いるかは未検証(冒頭の表のとおり `特定色域変換` 自体が未解析)。

## 3. 端が必ず減衰する

除数がカーネル幅固定でゼロ埋めなので、**キー色が1画素も無い画像でも
上下左右 `r` 画素分のアルファが落ちる**。16行の不透明な列の先頭4行を
`カラーキー` の式で通した例:

| `r` | 行0  | 行1  | 行2  | 行3  | 内部 |
| --- | ---- | ---- | ---- | ---- | ---- |
| 1   | 2730 | 4096 | 4096 | 4096 | 4096 |
| 2   | 818  | 2456 | 4096 | 4096 | 4096 |
| 5   | 0    | 0    | 0    | 371  | 4096 |

`クロマキー` でも同じことが起きる([`クロマキー` §7](../chroma_key/README.md))。
オブジェクトが自分のバッファの端に接している限り避けられない。

## 4. 「何をぼかすか」で挙動が割れる

**式は同じでも、パイプラインに入れるマップが違うと結果の意味が変わる。**
これが2つの解析済みエフェクトの最大の差である。

| | `クロマキー` | `カラーキー` |
| --- | --- | --- |
| マップ | 別バッファの 16bit マット `min(d, 4096)` | **画素のアルファそのもの** |
| 非キー画素のマップ値 | 常に 4096(アルファに依存しない) | そのアルファ |
| 一様に不透明な内部 | 素通り | 素通り |
| 一様に**半透明**な内部 | 素通り | **`a³/4096²` になる。`r ≥ 2` では 0** |
| グローバル | 5個(マップ3本 + `r` + `2r+1`) | 2個(`r` + `2r+1`) |

`カラーキー` では `v = (blur(a) * a) >> 12` の両項がアルファなので、
平坦部でも `v = a²/4096` にしかならない。`r = 1` なら3乗、`r ≥ 2` なら
`v` が `A` を超えられず**丸ごと消える**。

生き残れる一様アルファの下限:

| `r` | `A`  | 下限アルファ | 割合  |
| --- | ---- | ------------ | ----- |
| 1   | 0    | 256          | 6.2%  |
| 2   | 2048 | 2898         | 70.8% |
| 3   | 2731 | 3346         | 81.7% |
| 4   | 3072 | 3548         | 86.6% |
| 5   | 3277 | 3665         | 89.5% |

`クロマキー` にこの副作用は無い。**共有しているのはコードであって、
セマンティクスではない。**

## 5. 既知の overrun

ボックス平均のフェーズ2は `r+1` 回、フェーズ4は `r` 回を**無条件に**回すので、
辺の長さが `2r+1` 未満でも必ず `2r+1` 個書く。先行・後行ポインタのどちらにも
上限が無いので読み出しも枠外へ出る。

| エフェクト   | 垂直パスの溢れ先           | 水平パスの溢れ先       | 発火条件      |
| ------------ | -------------------------- | ---------------------- | ------------- |
| `クロマキー` | map A から map B の領域へ  | 画素バッファ内         | 幅か高さ < 11 |
| `カラーキー` | 対バッファの `h` 行目以降  | 画素バッファの `w` 列目以降 | 幅か高さ < 11 |

**未確定**: いずれも「バッファは最大キャンバスサイズで確保されているので
クラッシュしない」という前提で止めており、溢れた分の着地先は追っていない
([`box_blur.md` §4](box_blur.md) の他2件と同じ性質)。

```
uv run main.py inspect/color_key/verify_border_chain.py    # 全6項目 + 伸張イディオムの全件走査

```
