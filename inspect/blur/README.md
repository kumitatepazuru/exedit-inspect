# ぼかし (Blur) フィルタ リバースエンジニアリング解析

対象: `data/exedit.auf`(AviUtl 拡張編集の標準フィルタプラグイン)、32bit PE、
`ImageBase = 0x10000000`。以下のアドレスはすべて VA(`RVA = VA - 0x10000000`)。

## 再現方法

すべてのスクリプトは本プロジェクトの `main.py` を踏み台にして実行する。
`main.py` はコマンドラインで指定されたスクリプトに対して、DLLパス
(デフォルト `data/exedit.auf`)とヘッダー一覧(デフォルト `data/filter.h`)を
渡す役割を持つ。

```
uv run main.py inspect/blur/<script>.py
uv run main.py tools.<tool>            # エフェクト非依存の共通ツール。一覧はリポジトリ直下の README
```

| スクリプト | 確認していること |
|---|---|
| `tools.filter_table --name ぼかし` | `FILTER_DLL` 配列(先頭 `0x100a3e28`)をたどり、`ぼかし` の2つの登録エントリを抽出。トラックバー定義は完全に同一で、差は `サイズ固定` チェックボックスの有無だけ。両方とも `func_proc = 0x1000e2f0` を共有 |
| `decompile_blur.py` | `0x1000e2f0` 周辺に絞った `CFGFast` + angr デコンパイルで `func_proc` と **12個のワーカー** 全部を復元。角度の違う確認として、浮動小数点まみれでリフトできないカーブ変換ヘルパーは capstone で生ダンプ |
| `disasm_params.py` | `範囲`/`縦横比` → 半径の変換。マジックナンバー除算を定数解決した上で、半径が2分割されて **2回のボックスパス** になることを示す |
| `verify_radius_split.py` | 除算列を Python で再実装し、`範囲`×`縦横比` の全2,002,000通りが `trunc(x/1000)` と一致することを確認。さらに2パス合成後の実効カーネルの台が**ちょうど ±範囲**であることを全 r=0..1000 で確認 |
| `verify_mode_mapping.py` | `fp->flag & 0x20` の2分岐が触る構造体フィールドを読み、**24箇所のワーカー起動を機械的に抽出**して12個のワーカー表を復元。どれがキャンバスを広げるかも命令から判定 |
| `verify_pass_chain.py` | 4パスの順序・半径の受け渡し(グローバル4個)と、12ワーカーが**片方の軸のグローバルしか読まない**ことを走査で確認(=垂直/水平の割り当て確定) |
| `verify_box_average.py` | 1パスの中身。アルファ加重(プリマルチプライ往復)であること、そして**除数の違いだけが端処理の違いのすべて**であることを、除算箇所の抽出とPython再実装の数値比較で示す |
| `verify_canvas_growth.py` | `サイズ固定` と2種類のキャンバス拡張(通常経路 / 事前拡張経路)。最終サイズをPythonで再現 |
| `disasm_light_strength.py` | `光の強さ` の順変換/逆変換ヘルパー(`発光` の `拡散速度` と同一のもの)の全浮動小数点定数 |
| `verify_light_curve.py` | カーブ自体は誤差0で往復すること、平均が**べき平均**に変わること、`ぼかし` では **4096を超えようがない**こと(`発光` との決定的な違い)、色差が1/16に量子化されること |
| `simulate_blur_reference.py` | 上記すべてを織り込んだ整数忠実リファレンス実装。小さな合成画像に対して実行して結果を表示する |

`simulate_blur_reference.py` はパラメータを受け取る:

```
uv run main.py inspect/blur/simulate_blur_reference.py --range 8 --light 30
uv run main.py inspect/blur/simulate_blur_reference.py --aspect -600 --size-fixed
uv run main.py inspect/blur/simulate_blur_reference.py --frame --range 1000
```

## 1. 2つの登録エントリとモードの違い

`ぼかし` は `FILTER_DLL` として2回登録されており、どちらも
`func_proc = 0x1000e2f0` を共有する。`func_init` / `func_exit` / `func_update` /
`func_WndProc` はすべて NULL で、**このフィルタには UI 用のコードが一切無い**。
実行時の分岐は `fp->flag & 0x20` の1点のみで、画素フォーマットからして違う。

| | オブジェクトのフィルタ効果 | フレーム(映像)フィルタ |
|---|---|---|
| `FILTER_DLL` | `0x100a0720`、`flag=0x20` | `0x100a0848`、`flag=0x00` |
| チェックボックス | `サイズ固定` | なし |
| 画像バッファ | `*(fpip+0xAC)` | `fpip->ycp_edit` (`+4`) |
| 対バッファ | `*(fpip+0xB0)` | `fpip->ycp_temp` (`+8`) |
| 画素形式 | **8バイト/画素 PIXEL_YCA**(y, cb, cr, **a**) | 6バイト/画素 PIXEL_YC(アルファなし) |
| 行幅 | `*(fpip+0xEC)` [画素] | `fpip->max_w` (`+0x14`) [画素] |
| 幅・高さ | `*(fpip+0xB4)` / `*(fpip+0xB8)` | `fpip->w` (`+0xC`) / `fpip->h` (`+0x10`) |
| 半径の上限 | キャンバス最大サイズに収まるところまで | 各半径を独立に `寸法/2` でクランプ |
| サイズ変化 | あり(`サイズ固定` 次第) | なし |

2登録モデル・`FILTER_PROC_INFO` のオフセット・`fp+0x60`/`fp+0x64` の差し替え
(マルチスレッド起動とキャンバス拡張が別系統であること)は全エフェクト共通。
詳細は [`inspect/common/filter_registration.md`](../common/filter_registration.md)。

## 2. パラメータ変換(`func_proc` 冒頭、フレームごとに1回)

トラックバーは `fp->track[]` の順に `範囲`(初期値5、範囲0~1000)、
`縦横比`(0、-1000~1000)、`光の強さ`(0、0~60)。

UI に表示される数値との対応は、登録構造体 `+0x74` にある exedit 独自の拡張
ブロック(表示スケール / スライダーのドラッグ下限・上限)で決まる。ブロックの
構造は [`inspect/common/param_scaling.md`](../common/param_scaling.md) 参照:

| トラックバー | 表示スケール | UI表示範囲 | スライダーで届く範囲 |
|---|---|---|---|
| `範囲` | 1 | 0~1000 | 0~300 |
| `縦横比` | 10 | -100.0~100.0 | -100.0~100.0 |
| `光の強さ` | 1 | 0~60 | 0~60 |

つまり `範囲` と `光の強さ` は**UIの数値がそのまま生値**、`縦横比` だけが
10で割って表示される(UI の `50.0` が生値 `500`)。`範囲` は300を超える値を
スライダーでは指定できず、数値入力が必要。

以下、`func_proc` がその生値に対して行う変換:

* **`範囲 == 0` は即 return**。画像には一切触れない。
* **半径**。`範囲` がそのまま両軸の半径になり、`縦横比` が**片方の軸だけ**を縮める:
  ```
  rx = ry = 範囲
  縦横比 > 0  ->  ry = trunc(範囲 * (1000 - 縦横比) / 1000)   // 縦が縮む = 横長のぼかし
  縦横比 < 0  ->  rx = trunc(範囲 * (1000 + 縦横比) / 1000)   // 横が縮む = 縦長のぼかし
  ```
  除算は全エフェクト共通のマジックナンバー除算 `0x10624dd3`
  ([`param_scaling.md` §2](../common/param_scaling.md))で、**四捨五入ではなく
  0方向への切り捨て**。到達しうる全2,002,000通りで `trunc(x/1000)` と一致する
  ことを確認済み(`verify_radius_split.py`)。`縦横比 = ±1000` でその軸の半径が
  0になり、完全な横ぼかし/縦ぼかしになる。
* **半径の2分割**。各軸の半径は直後に2つに割られる:
  ```
  r_hi = r - r/2 = ceil(r/2)     r_lo = r/2 = floor(r/2)
  ```
  この2つが別々のボックスパスとして走る(手順3)。

## 3. 4パスのチェーンと三角カーネル

固定で **4パス**、この順に走る(半径0のパスは丸ごとスキップされる):

```
pass 1  垂直    半径 ry_hi
pass 2  水平    半径 rx_hi
pass 3  垂直    半径 ry_lo
pass 4  水平    半径 rx_lo
```

各パスは「現画像を読む → 対バッファへ書く」で、`func_proc` が直後にポインタを
入れ替える(**ping-pong**)。スキップされたパスは入れ替えも飛ばすので連鎖は
壊れない。半径はグローバル経由でワーカーに渡る
(`MULTI_THREAD_FUNC` は引数を4個しか取れないため):

| グローバル | 中身 |
|---|---|
| `0x1011ec34` / `0x1011ec38` | 垂直 / 水平パスの半径 |
| `0x1011ec3c` / `0x1011ec40` | 垂直 / 水平パスのカーネル幅 = `半径*2+1` |

12個のワーカーがそれぞれ**片方の軸のグローバルしか読まない**ことを走査で
確認済み(`verify_pass_chain.py`)。

**1パスは一様重みのボックス平均**で、ガウシアン核はどこにも無い。ただし
同じ軸を2回通すので、合成カーネルは box(2*r_hi+1) ⊛ box(2*r_lo+1) =
**三角形(r が奇数なら上底3の台形)**になる。台の広がりは
`r_hi + r_lo = r` ちょうどで、つまり **`範囲` がそのまま実効半径**である。

| 範囲 | 2パスの半径 | 合成カーネル |
|---|---|---|
| 1 | 1, 0 | `[1,1,1]`(パス1本だけ、ただの3タップ box) |
| 2 | 1, 1 | `[1,2,3,2,1]` |
| 3 | 2, 1 | `[1,2,3,3,3,2,1]` |
| 4 | 2, 2 | `[1,2,3,4,5,4,3,2,1]` |

## 4. アルファ加重ボックス平均と、端の扱い

オブジェクト版の累積・正規化の式(プリマルチプライした加重和、`sum_a` で色を
割ること、丸め誤差)は全エフェクト共通の形。詳細は
[`inspect/common/box_blur.md`](../common/box_blur.md) 参照
(`verify_box_average.py` が本エフェクトでの検算)。

**端の扱いの違いは、アルファを割る「除数」だけに現れる**:

| ワーカー系統 | 除数 | 意味 | 出力サイズ |
|---|---|---|---|
| オブジェクト・`サイズ固定` **オフ** | 常にカーネル幅 | 画像外は**透明として数える** → ふちがフェードする | 各軸 `+2*半径` |
| オブジェクト・`サイズ固定` **オン** | キャンバス内に残っているサンプル数 | 端で**正規化し直す** → ふちの不透明度が保たれる | 変わらず |
| フレーム | フレーム内に残っているサンプル数 | 同上(アルファが無いので輝度がそのまま) | 変わらず |

`サイズ固定` オフのワーカーだけが出力を `2*半径` 行(列)分多く書き、
`func_proc` が `*(fpip+0xB8)` / `*(fpip+0xB4)` にその分を足す。同時に出力が
半径分ずれるので、オブジェクトは広がったキャンバスの中央に収まる。

## 5. `サイズ固定` とキャンバス拡張

`サイズ固定` は**2回、別の意味で**読まれる。

1. **チェックボックスそのもの**(`fp->check[0]`)。オンならキャンバス拡張も
   半径のクランプも一切行わず、そのまま手順3へ進む。
2. **その場のローカルコピー**。どのワーカーを呼ぶかを決める。事前拡張経路
   (下記)はここだけを 1 に書き換える。

オフのときは、いずれかの半径がキャンバスの半分以上
(`2*rx_hi >= w` / `2*ry_hi >= h` / `2*rx_lo >= w` / `2*ry_lo >= h` のいずれか)
だと**事前拡張経路**(`table[0x48]`/`table[0x44]` を使う方式)に入る。仕組みは
[`inspect/common/canvas_growth.md` §3](../common/canvas_growth.md) 参照。
以後は非拡張ワーカーが拡大済みバッファ上で走るので、**最終サイズはどちらの
経路でも `(w+2rx, h+2ry)` で同じ**になる。

| w | h | 範囲 | 固定 | 半径 (rx, ry) | 事前拡張 | 最終キャンバス |
|---|---|---|---|---|---|---|
| 200 | 100 | 5 | 0 | (5, 5) | いいえ | 210 x 110 |
| 200 | 100 | 5 | 1 | (5, 5) | いいえ | 200 x 100 |
| 200 | 100 | 60 | 0 | (60, 60) | いいえ | 320 x 220 |
| 32 | 32 | 100 | 0 | (100, 100) | **はい** | 232 x 232 |
| 4000 | 100 | 100 | 0 | (48, 100) | **はい** | 4096 x 300 |

オブジェクト側で `範囲` に効く唯一の上限は最大キャンバスサイズで、
`w + 2*rx > 最大幅`(`0x10196748`)なら `rx = (最大幅 - w)/2` に切り詰められる
(高さは `0x101920e0`)。上の4000幅の例がこれ。

フレーム側にはキャンバスが無いので、代わりに**4つの半径を個別に `寸法/2` で
クランプ**する。個別なので実効的な総半径は最大 `2*(寸法/2) ≈ 寸法` まで届く。

## 6. `光の強さ` ― 指数/対数空間での平均

`光の強さ > 0` のときだけ、4パスループの**前後に1回ずつ**全画面変換が入る。
使われるヘルパーは `発光` の `拡散速度` とまったく同じもので、範囲が同じ 0~60
なのもそのためである。式・底 `base` の計算・色差の量子化・代償は
[`inspect/common/exp_log_curve.md`](../common/exp_log_curve.md) にまとめてある
(`disasm_light_strength.py` / `verify_light_curve.py` が本エフェクトでの検算)。

`ぼかし` は6パス版の `発光` と違い、curved 空間で**足すのではなく平均する**。
平均は入力の最小値と最大値の間に必ず収まるので、逆変換の書き戻しにクランプが
無くても**4096を超えることはあり得ない**(750通りの窓で確認済み)。`発光` で
問題になる「満輝度超過→チャンネルごとのクリップ→色相のずれ」は `ぼかし` では
起きない ―― この対比が [`exp_log_curve.md` §4](../common/exp_log_curve.md) の主題。

## 9. 未確定事項

* フレーム側で寸法が偶数のとき、末尾位相が可視領域の1行(列)先まで書く。
  ループ境界からの導出で、`寸法/2` へのクランプ後 `カーネル幅 = 寸法+1` に
  なることによる。バッファ内なので実害は無い。

以下は本エフェクト単独の未確定事項ではなく、全エフェクト共通の未確定事項。
