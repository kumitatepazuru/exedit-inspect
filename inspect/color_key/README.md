# カラーキー (Color Key) フィルタ リバースエンジニアリング解析

対象: `data/exedit.auf`(AviUtl 拡張編集の標準フィルタプラグイン)、32bit PE、
`ImageBase = 0x10000000`。以下のアドレスはすべて VA(`RVA = VA - 0x10000000`)。

## 再現方法

すべてのスクリプトは本プロジェクトの `main.py` を踏み台にして実行する。
`main.py` はコマンドラインで指定されたスクリプトに対して、DLLパス
(デフォルト `data/exedit.auf`)とヘッダー一覧(デフォルト `data/filter.h`)を
渡す役割を持つ。

```
uv run main.py inspect/color_key/<script>.py
uv run main.py tools.<tool>            # エフェクト非依存の共通ツール。一覧はリポジトリ直下の README
```

| スクリプト                            | 確認していること                                                                                                                                              |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tools.filter_table --name カラーキー` | `FILTER_DLL` 配列(先頭 `0x100a3e28`)から登録エントリ `0x100a16d8` を抽出。**オブジェクト効果1個のみ**、トラックバー3本・ボタン1個、`ex_data` 12バイト          |
| `tools.track_scale --name カラーキー`  | `+0x74` 拡張ブロックが **NULL** ―― 3本とも表示スケール1・ドラッグ範囲指定なしで、生値がそのまま UI 表示値                                                     |
| `decompile_color_key.py`              | `0x10016000`〜`0x10016a00` に絞った `CFGFast` + angr デコンパイル。**浮動小数点が1命令も無い**ので全体がほぼそのまま読める(2箇所だけ angr の読み替えに注意)   |
| `disasm_params.py`                    | func_proc 全域(40命令)とキーワーカー全域の注釈付きダンプ。早期 return、2つのグローバル、4回のワーカー起動、6つの区間境界の作り方                              |
| `verify_ex_data.py`                   | `+0x70` フィールド表による `ex_data` レイアウトの裏取り、`status` が3値であること、スポイトの手順が `クロマキー` と**文字列レベルで共有**であること、そして**キー色の3成分すべてが使われる**こと |
| `verify_key_box.py`                   | キー判定が YCbCr の**軸並行な直方体**であること、6つの境界がすべて閉区間であること、書き込みが `alpha = 0` の1命令しか無いこと、そして**エフェクト全域の命令語彙28種を全部出す**ことで x87/SSE もマジック除算も無いと示すこと |
| `verify_dispatch.py`                  | 4回のディスパッチと**キーワーカーが2回呼ばれる**こと、グローバル2個がカラーキー専有であること、3ワーカーの入力が排他であること、**書き込みが `+6`(アルファ)だけ**であること |
| `verify_border_chain.py`              | `境界補正` の2パス。ボックス平均のフェーズ構成が閉じた式と一致すること、伸張定数 `A`/`B` が `クロマキー` と同一であること、**半透明が潰れること**、端の減衰、小さい画像での書き込み溢れ、伸張イディオムが画像全体で3箇所しか無いこと |
| `simulate_color_key_reference.py`     | 上記すべてを織り込んだ整数忠実リファレンス実装。21項目の自己検証つき                                                                                          |

## 1. 登録エントリ ―― オブジェクト効果1個だけ

`カラーキー` の登録は `0x100a16d8` の1個だけで、`クロマキー` や `境界ぼかし` と
同じく**フレーム(映像)フィルタ版が存在しない**。`fp->flag & 0x20` の分岐はコード上
に無く、画素は常に 8バイト/画素 PIXEL_YCA である。

| 項目           | 値                                                                    |
| -------------- | --------------------------------------------------------------------- |
| `FILTER_DLL`   | `0x100a16d8`、`flag = 0x20`(オブジェクトのフィルタ効果)               |
| `func_proc`    | `0x100162c0`                                                          |
| `func_WndProc` | `0x10016850`(`func_init`/`func_exit`/`func_update` は NULL)           |
| `FILTER+0x58`  | `0x100169e0`(exedit 流用の設定ウィンドウ更新エントリ)                 |
| `ex_data`      | 12バイト、`ex_data_def = 0x1011ed3c`(全ゼロ)、`+0x70` 表 `0x100a16a0` |
| `+0x74`        | **NULL** ―― 表示スケールもドラッグ範囲も持たない                      |
| 入力バッファ   | `*(fpip+0xAC)`。**完全にイン・プレース**、バッファ入れ替えもキャンバス拡張も無い |
| 作業バッファ   | `*(fpip+0xB0)`(`境界補正` のときだけ、アルファ欄のみ)                 |

コードは `0x100162c0`〜`0x100169f3` の連続した1,844バイトに収まる。前後で
いちばん近い登録済み関数は、下が `特定色域変換` の `func_WndProc`
(`0x10016020`)、上が `拡張色設定` の `func_proc`(`0x10016a00`)。

**このエフェクトには浮動小数点が1命令も無い。** 全域に現れる命令は28種
(`add`, `and`, `call`, `cdq`, `cmp`, `dec`, `idiv`, `imul`, `inc`, `je`, `jg`,
`jge`, `jl`, `jle`, `jmp`, `jne`, `lea`, `mov`, `movsx`, `nop`, `pop`, `push`,
`ret`, `sar`, `shl`, `sub`, `test`, `xor`)だけで、x87 も SSE も CRT `_ftol` も
`0x10624dd3` のマジック除算も現れない。`call` は `exec_multi_thread_func` と
UI 用の exedit テーブル・`wsprintfA`/`SetWindowTextA` だけ(`verify_key_box.py`)。
共有ルーチンを1つも呼ばない点で、本リポジトリで解析した中では最も孤立している。

## 2. `ex_data` ―― キー色とスポイトの状態

トラックバーは3本ともキーの「広さ」を決めるだけで、**キー色そのものは
`ex_data` に入っている**。レイアウトは exedit 自身の `+0x70` フィールド表
(`0x100a16a0`、[`filter_registration.md` §5](../common/filter_registration.md))が
宣言しており、宣言サイズの合計が `ex_data_size` と一致する:

| offset | size | kind | name       | 意味                                     |
| ------ | ---- | ---- | ---------- | ---------------------------------------- |
| 0      | 6    | 3    | `color_yc` | `PIXEL_YC { short y, cb, cr; }` = キー色 |
| 6      | 2    | 0    | (無名)     | アラインメント用パディング               |
| 8      | 4    | 1    | `status`   | スポイトの状態(下表)                     |

```c
struct { short y, cb, cr; short pad; int status; };   // 12 bytes
```

`クロマキー` の `0x100a0dd0` と**フィールド構成が完全に一致する**別テーブルで、
`status` の意味も同じ3値。`func_proc` の1行目(`0x100162c8`)は `status == 1`
以外をすべて弾く:

| `status` | ボタンのラベル                             | `func_proc` |
| -------- | ------------------------------------------ | ----------- |
| 0        | `< 未取得 >`                               | 即 return   |
| 1        | `YCbCr ( %d , %d , %d )`                   | **実行**    |
| 2        | `マウスをクリックして色を取得してください` | 即 return   |

### スポイトの手順は `クロマキー` と同一実装

`func_WndProc`(`0x10016850`)は `0x702`(`WM_FILTER_COMMAND`)だけを扱い、
`0x1e1b`(ボタン押下)と `0x1e1d`(スポイト結果の到着)に反応する。
`table[0x80](fp+0xE4, 0)` → `table[0x68]` で起動/解除、`table[0x4c]` で
ラベルの `HWND` を取る流れまで `クロマキー` の `0x100143d0` と同じで、
**`< 未取得 >` / `マウスをクリックして…` / `YCbCr ( %d , %d , %d )` の3文字列は
同じアドレス**(`0x100a0fbc` / `0x100a0fc8` / `0x100a0ff4`)を共有している。
`キー色の取得` と `境界補正` のラベル文字列も同じアドレスである
(`verify_ex_data.py`)。**コードは複製、データは共有**という MSVC の
文字列プーリングの結果で、2つのエフェクトが同じソースから書かれたことを示す。

`table[0x4c]` に渡す第3引数だけが違い、`カラーキー` は `0`、`クロマキー` は `2`。
これは `check_name[]` の中でのボタンの添字で、`table[0x4c](fp+0xE4, 5, i)` が
「i 番目のチェックボックス枠の `HWND`」を返すことになる。

**取得済みの状態でボタンを2回押すとキー色を失う**(`0x10016910` で `status = 0`)
のも `クロマキー` と同じ。

### キー色の輝度は使われる

`クロマキー` はキー色の `y` を設定ウィンドウのラベルにしか使わないが、
`カラーキー` のキーワーカーは `[ecx]`(y)・`[ecx+2]`(cb)・`[ecx+4]`(cr)を
すべて読む(`0x10016367` / `0x1001637c` / `0x10016380`)。**同じ 12バイトの
`ex_data` を、片方は 2/3 しか使わず、もう片方は全部使う。**

## 3. パラメータ

| トラックバー | 生値の範囲 | 初期値 | 表示スケール | 内部での使われ方                                  |
| ------------ | ---------- | ------ | ------------ | ------------------------------------------------- |
| `輝度範囲`   | 0〜4096    | **0**  | 1            | `key.y ± 輝度範囲` の閉区間                       |
| `色差範囲`   | 0〜4096    | **0**  | 1            | `key.cb ± 色差範囲` と `key.cr ± 色差範囲` の両方 |
| `境界補正`   | 0〜5       | **0**  | 1            | ボックス平均の半径 `r` そのもの                   |

| チェックボックス | 初期値 | 役割                                |
| ---------------- | ------ | ----------------------------------- |
| `キー色の取得`   | ―     | ボタン(`check_default = -1`)。手順2 |

`+0x74` 拡張ブロックが NULL なので、`/1000` のマジックナンバー除算も表示スケールも
**1つも存在しない**。この性質は `クロマキー` と共通である
([`param_scaling.md` §1](../common/param_scaling.md))。

**トラックバーはワーカーが自分で `fp->track[]` から読む**。グローバル経由で
渡されるのは `境界補正` から作った `r` と `2r+1` だけで、これも
`exec_multi_thread_func` の引数が4個しかないという共通の制約
([`filter_registration.md` §6](../common/filter_registration.md))による。

### 初期値が 0/0/0 であること

**3本とも初期値が 0**なので、スポイトでキー色を取った直後の `カラーキー` は
「キー色と完全に一致する画素だけを消す」状態から始まる。実写素材ではまず何も
起きないので、`輝度範囲` と `色差範囲` は必ず手で上げることになる。
`クロマキー` が 24 / 96 / 1 で最初から動くのとは対照的である。

### スライダーの上限が 4096 である理由

PIXEL_YC は `y ∈ [0, 4096]`、`cb, cr ∈ [-2048, 2048]`。ある軸が飽和する
(= 全画素を受理する)のは色差なら `色差範囲 ≥ 2048 + |key.c|`、輝度なら
`輝度範囲 ≥ max(key.y, 4096 - key.y)` のときで、**最悪のキー色でちょうど 4096**
になる。範囲の上限はここから決まっている。逆に中央寄りのキー色では
スライダーの上半分が効かなくなる(`verify_key_box.py` が体積で示す)。

## 4. キー判定 ―― 距離ではなく直方体

キーワーカー `0x10016340` がやることの全部:

```
ymin  = key.y  - 輝度範囲      ymax  = key.y  + 輝度範囲
cbmin = key.cb - 色差範囲      cbmax = key.cb + 色差範囲
crmin = key.cr - 色差範囲      crmax = key.cr + 色差範囲

if ymin <= y <= ymax and cbmin <= cb <= cbmax and crmin <= cr <= crmax:
    a = 0
```

- **距離を1度も計算しない。** 3軸を独立に区間判定するだけなので、受理領域は
  球でも円柱でもなく**軸並行な直方体**である。3つの半幅が等しいとき、頂点方向は
  面の中心の √3 倍(色差平面だけを見れば √2 倍)遠くまで届く。
- **6つの境界はすべて閉区間**。分岐は `jl` / `jg` の6本で、`jle` / `jge` は
  1つも無い(`verify_key_box.py` が命令の mnemonic を照合)。だから
  `範囲 = 0` でもキー色そのものは消える。
- **出力は2値**。ワーカーの中で画素バッファへ書く命令は
  `mov word ptr [ecx+6], 0` の**1つだけ**で、`imul` も `sar` も画素に触らない。
  アルファは「そのまま」か「0」かの2択で、中間値は作れない。
- **色差の2軸は1本のトラックバーを共有する**。`cb` と `cr` は同じ `色差範囲` で
  判定されるので、色差平面での受理領域は必ず正方形になる。
- **y, cb, cr は書き換えられない。** 3ワーカーの16bit書き込みはすべて画素の
  `+6`(アルファ)で、`クロマキー` の `色彩補正` に当たるスピル除去は存在しない
  (`verify_dispatch.py`)。

> `クロマキー` との対比が分かりやすい。あちらは Cb-Cr 平面の**色相角と彩度**で
> 測り、輝度を無視し、距離 `d` から連続的なアルファを作る。こちらは
> **YCbCr の3軸をそのまま**見て、輝度も使い、答えは 0 か 1 しか返さない。
> 名前のとおり「その色か、そうでないか」だけを判定するフィルタである。

### ソフトエッジは `境界補正` にしか無い

判定が2値である以上、`境界補正 = 0` の `カラーキー` はジャギーの立った
アルファしか作れない。半透明の境界を作る唯一の手段が `境界補正` で、
これは `クロマキー` の同名パラメータとは重みが違う ―― あちらでは
既定値 1 が「マットを 3×3 でぼかすだけ」の飾りだが、こちらでは
**エフェクトを使い物にするための必須パラメータ**である。

## 5. `境界補正` ―― アルファそのものをぼかす

`境界補正 = r > 0` にすると、`exec_multi_thread_func` が3回追加で走る
(ただしワーカーの実体は2つ。手順の 1. と 2. は同じアドレス)。渡される
グローバルは2つだけ:

```
g_1011ed38 = r                  半径
g_1011ed34 = 2r+1               カーネル幅
```

| 順 | アドレス     | 内容                                                              | スレッド分割 |
| -- | ------------ | ----------------------------------------------------------------- | ------------ |
| 1  | `0x10016340` | キー判定(`境界補正 = 0` のときと同じもの)                        | 行           |
| 2  | `0x10016340` | **同じワーカーをもう一度**                                        | 行           |
| 3  | `0x10016430` | アルファの**垂直**ボックス平均。`*(fpip+0xAC)` → `*(fpip+0xB0)`  | **列**       |
| 4  | `0x100165d0` | **水平**ボックス平均 → 元アルファとの積 → 伸張 → 画素へ適用     | 行           |

### 2. の重複ディスパッチ

`func_proc` は `push 0x10016340` を**2回**行う(`0x100162d8` と `0x10016303`)。
`tools.xrefs` でこのアドレスを画像全体から検索しても出てくるのはこの2つだけで、
デコンパイラの読み違いではない(`verify_dispatch.py`)。

キーワーカーの判定は `y`/`cb`/`cr` の関数で、そのどれも書き換えないから、
**2回目は1回目と同じ答えを出して同じ 0 を書く**。つまり `境界補正 > 0` は
全画素を1回余計に走査するだけで、絵は1ビットも変わらない。MSVC の
同一関数畳み込み(`/OPT:ICF`)で別々のソース関数が同じアドレスに潰れた、と
読むのが自然だが、**どちらにせよ観測できる違いは無い**。

### 3./4. のボックス平均

[`box_blur.md` §4](../common/box_blur.md) の3フェーズそのままで、
**除数は常にカーネル幅 `2r+1`**。画像の外はゼロ(=「完全に透明」)として
平均される。`verify_border_chain.py` がフェーズ構成を
`sum(src[i-r : i+r+1]) / (2r+1)` と全数照合している。

`クロマキー` は同じコードを**16bit のマット**(`min(d, 4096)`)に対して走らせるが、
`カラーキー` にマットは無い ―― **ぼかす対象も掛ける相手も画素のアルファ本体**で、
作業バッファ `*(fpip+0xB0)` はアルファ欄しか使われない(y/cb/cr は放置)。
グローバルが2個で済むのはこのためである。

### 4. の積とコントラスト伸張

```
A = 4096 - 4096/r
B = 4096 - (4096/r)*r          // = 4096 mod r

v = (水平ボックス平均(垂直ボックス平均(a)) * a) >> 12
t = (v - A) * r + B

if v == 0 || t <= 0:  a = 0
else:                 a = (a * t) >> 12
```

伸張定数は `クロマキー`(`0x100138f9`)と**同じ式・同じ命令列**で、
`t(4096) == 4096` が全 `r` で厳密に成り立つ。`r = 1` は `A = B = 0`・傾き1、
つまり恒等の伸張。

| `r` | カーネル | `A`  | `B` | `v` の生存下限     |
| --- | -------- | ---- | --- | ------------------ |
| 0   | ―       | ―   | ―  | (この経路を通らない) |
| 1   | 3        | 0    | 0   | 1(恒等)            |
| 2   | 5        | 2048 | 0   | 2049(50%)          |
| 3   | 7        | 2731 | 1   | 2731(67%)          |
| 4   | 9        | 3072 | 0   | 3073(75%)          |
| 5   | 11       | 3277 | 1   | 3277(80%)          |

## 6. `境界補正` は半透明を潰す

`カラーキー` 固有の副作用で、しかも小さくない。掛ける相手がマットではなく
アルファ本体なので、**一様に半透明な領域でも `v = a²/4096` になってしまう**。
広い平坦部(端から `r` 画素以上離れたところ)でぼかし結果は `a` に等しいから:

```
r = 1:  a' = a³ / 4096²          (伸張が恒等なので純粋な3乗)
r >= 2: a' = 0                   (v = a²/4096 が A を超えられない)
```

一様アルファの出力(`verify_border_chain.py` / リファレンス実装の自己検証):

| 入力アルファ | `r=1` | `r=2` | `r=3` | `r=4` | `r=5` |
| ------------ | ----- | ----- | ----- | ----- | ----- |
| 4096 (100%)  | 4096  | 4096  | 4096  | 4096  | 4096  |
| 3686 (90%)   | 2984  | 2283  | 1582  | 881   | 180   |
| 3072 (75%)   | 1728  | 384   | 0     | 0     | 0     |
| 2048 (50%)   | 512   | 0     | 0     | 0     | 0     |
| 1024 (25%)   | 64    | 0     | 0     | 0     | 0     |

生き残れる一様アルファの下限は `r=2` で 2898(70.8%)、`r=5` で 3665(89.5%)。
**`境界補正` を 2 以上にすると、半分だけ透けたオブジェクトはキー色が1画素も
無くても丸ごと消える。**

`クロマキー` にこの挙動は無い。あちらのマットは `min(d, 4096)` で、キー色から
遠い画素ではアルファに関係なく 4096 になるから、積が 4096 に戻って内部は
素通りする。**共有しているのはコードで、ぼかす対象が違う。**

### 端も減衰する

除数がカーネル幅固定でゼロ埋めなので、キー色が1画素も無くても
**上下左右 `r` 画素分のアルファが落ちる**。16行の不透明な列の先頭4行:

| `r` | 行0  | 行1  | 行2  | 行3  | 内部 |
| --- | ---- | ---- | ---- | ---- | ---- |
| 1   | 2730 | 4096 | 4096 | 4096 | 4096 |
| 2   | 818  | 2456 | 4096 | 4096 | 4096 |
| 5   | 0    | 0    | 0    | 371  | 4096 |

`クロマキー` の同じ性質([`クロマキー` §7](../chroma_key/README.md))と同じ原因で、
こちらは伸張が効く分だけ悪化している。

## 7. `境界補正` は3エフェクトで共有されている

`mov eax, 0x1000; cdq; idiv r32` に続く2つの減算(= `A`/`B` の計算)という命令列は、
850KB の画像全体で**ちょうど3箇所**にしか現れない
(`verify_border_chain.py` がバイト走査で全件出す):

| アドレス     | エフェクト                                | `境界補正` の範囲 | 初期値 |
| ------------ | ----------------------------------------- | ----------------- | ------ |
| `0x100138f9` | [`クロマキー`](../chroma_key/README.md)   | 0〜5              | 1      |
| `0x10015b49` | `特定色域変換`(**本リポジトリ未解析**)    | 0〜8              | 2      |
| `0x10016602` | `カラーキー`                              | 0〜5              | 0      |

**`境界補正` というトラックバーを持つエフェクトもこの3つだけ**で、両側を
登録テーブルと命令列走査から別々に数え上げて一致することを確認している
(`verify_border_chain.py` §6)。共通部分の解説は
[`border_correction.md`](../common/border_correction.md)。

## 9. 参照テーブル

キー色 `(y, cb, cr) = (2048, -600, -400)` のときに受理される直方体の体積
(表現可能な `4097³` 通りに対する割合。`verify_key_box.py`):

| `輝度範囲` | `色差範囲` | y の幅 | cb の幅 | cr の幅 | 体積比   |
| ---------- | ---------- | ------ | ------- | ------- | -------- |

| 256        | 256        | 513    | 513     | 513     | 0.001963 |

## 10. 未確定事項

- **キーワーカーが2回ディスパッチされる理由**。挙動に影響しないことは
  確認済み(冪等)だが、`/OPT:ICF` による関数畳み込みなのか、素直に同じ関数を
  2回呼んでいるのかは、この1バイナリからは区別できない。
- **`境界補正` の2パスは、幅か高さが `2r+1` より小さいと枠外へ書く**。
  フェーズ2は `r+1` 回、フェーズ4は `r` 回を無条件に回し、先行・後行ポインタの
  どちらにも上限が無い。垂直パスの溢れは対バッファの `h` 行目より後ろへ、
  水平パスの溢れは画素バッファの `w` 列目より後ろへ落ちる。`r ≤ 5` なので
  11画素未満のオブジェクトでしか起きず、確保済みバッファ内には収まるはずだが、
  **着地先は追っていない**([`box_blur.md` §4](../common/box_blur.md) の
  既知 overrun と同じ性質)。
- **`fp+0xE4`** の中身。スポイトの起動 `table[0x68]` / ラベル取得
  `table[0x4c]` に渡している値だが、exedit 側の何を指すかは追っていない
  (`クロマキー` と共通の未確定事項)。
- **`table[0x4c]` の第2引数 `5`**。第3引数がチェックボックスの添字であることは
  `クロマキー`(2)との差分から確定したが、`5` が何のコントロール種別を指すかは
  未追跡。
- **スポイトが読む画素**。`0x1e1d` で届く `PIXEL_YC` を exedit のどのバッファ
  から取っているか(合成前か後か、ズーム中の補間の有無)は本エフェクトの
  コード外にある。
- **`特定色域変換`(`0x10015480`)** は同じ伸張定数の命令列を持ち、
  `func_proc` の骨格も似ているが、本リポジトリでは未解析。§7 で確認したのは
  「同じ命令列がある」ことだけで、パイプライン全体が一致するかは未確認。
- `rand()` や `fpip->frame`(`+0x1C`)を読む箇所は無いので、同じ入力に対する
  出力は完全に決定的である。

以下は全エフェクト共通の未確定事項。詳細は
[`rgb_ycbcr.md` §3](../common/rgb_ycbcr.md) 参照:

- 最終的な YCbCr→RGB 変換とそのクリップは `aviutl.exe` 側にあるため、
  本プロジェクトの解析対象外。
