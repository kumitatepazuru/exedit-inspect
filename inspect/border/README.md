# 縁取り (border) フィルタ リバースエンジニアリング解析

対象: `data/exedit.auf`(AviUtl 拡張編集の標準フィルタプラグイン)、32bit PE、
`ImageBase = 0x10000000`。以下のアドレスはすべて VA(`RVA = VA - 0x10000000`)。

## 再現方法

すべてのスクリプトは本プロジェクトの `main.py` を踏み台にして実行する。
`main.py` はコマンドラインで指定されたスクリプトに対して、DLLパス
(デフォルト `data/exedit.auf`)とヘッダー一覧(デフォルト `data/filter.h`)を
渡す役割を持つ。

```
uv run main.py inspect/border/<script>.py
uv run main.py tools.<tool>            # エフェクト非依存の共通ツール。一覧はリポジトリ直下の README
```

| スクリプト                         | 確認していること                                                                                                                                                                |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tools.filter_table --name 縁取り` | `FILTER_DLL` 配列(先頭 `0x100a3e28`)の登録エントリ `0x100a5cf8` を抽出。**オブジェクト効果1個のみ**、トラックバー2本・ボタン2個、`ex_data` **260バイト**                       |
| `tools.track_scale --name 縁取り`  | `+0x74` 拡張ブロック `0x100a5cd8`。表示スケールの配列以外は**3スロットとも NULL**                                                                                               |
| `decompile_border.py`              | `func_proc`・3つのワーカー・`func_WndProc`・ラベル再構築の angr デコンパイル。浮動小数点は利得の計算1箇所だけなので、そこ以外はほぼそのまま読める                               |
| `disasm_params.py`                 | `func_proc` 全域(8区間)と3ワーカーの演算部の注釈付き生逆アセンブル。`esp+0x..` のスロットに名前を付けているのはここ                                                            |
| `verify_params.py`                 | `ぼかし` の `/1000` 変換結果が**イメージ全体で一度も読まれない**こと、実際に効く利得 `round(1024/(0.02*サイズ*ぼかし+1))` の性質、事前パディングがスライディングウィンドウの前提を保証すること |
| `verify_canvas.py`                 | 公開されるキャンバスが常に `(w+2*サイズ, h+2*サイズ)` であること、オブジェクトがきっかり `(サイズ, サイズ)` に載ること、4本の矩形クリアが**到達不能**であること、`fpip+0xD4`/`+0xD8` を触らないこと |
| `verify_border_chain.py`           | インパルス応答が**平らな箱**(三角形ではない)であること、画素ループに除算が1つも無いこと、利得が2回掛かること、`imul` が `サイズ≥256` かつ `ぼかし=0` でだけ32bitを溢れること |
| `verify_encode.py`                 | 縁色が**素のまま** Y/Cb/Cr に入ること(黒でも不透明度が落ちない)、`sum==0` の特例、パターン版が色を1度も書かないこと、最後の合成が通常合成であること                          |
| `verify_ex_data.py`                | 260バイトの `ex_data` が**`シャドー` と同一レイアウト**(名前文字列まで共有)であること、2つのボタンが `HIWORD(wParam)` で区別されること、色とパターンが排他であること          |
| `simulate_border_reference.py`     | 上記すべてを積んだ整数忠実リファレンス実装。ASCIIアートと走査線比較                                                                                                             |

## 1. 登録エントリ ―― 1つだけ、コード全域は約3.3KB

`シャドー`・`ライト`・`閃光`・抜き系3エフェクトと同じく、`縁取り` は
`FILTER_DLL` 配列に**1回しか登録されていない**(`fp->flag & 0x20` による
オブジェクト/フレームの分岐は存在しない)。

| 項目           | 値                                                                                    |
| -------------- | ------------------------------------------------------------------------------------- |
| `FILTER_DLL`   | `0x100a5cf8`(配列の [35] 番目)、`flag = 0x40000020`                                   |
| `func_proc`    | `0x100515d0`                                                                          |
| `func_WndProc` | `0x10052070`                                                                          |
| `FILTER+0x58`  | `0x100522d0`                                                                          |
| `ex_data`      | **260バイト**、`ex_data_def` = `0x101b1e48`(全ゼロ)、`+0x70` フィールド表 `0x100a5ca8` |
| `+0x74`        | `0x100a5cd8`。表示スケールの配列 `0x101b1f60`(全ゼロ)以外は**3スロットとも NULL**     |
| 入力バッファ   | `*(fpip+0xAC)`。**読むのはアルファだけ**                                              |
| 対バッファ     | `*(fpip+0xB0)`。縁を塗る新キャンバス                                                  |

このエフェクト固有のコードは `0x100515d0`〜`0x100522e3` の連続した**3348バイト**
(直後の `0x100522f0` は `フレームバッファ` の `func_proc` で、無関係)。

`flag` の bit30(`0x40000000`)は `シャドー` と同じく立っているが、意味は依然
未追跡(§10)。**なお `シャドー` の README が「`影を別オブジェクトで描画` を持つ
2エフェクトがどちらも `0x40000020`」と書いていたのは誤りで、`縁取り` にその
チェックボックスは無い** ―― `縁取り` はチェックボックスを1つも持たない
(2つとも `check_default = -1` のボタン)。

### トラックバーとボタン

`tools.filter_table --name 縁取り` の生出力:

| トラックバー | raw 既定 | raw 範囲 | 表示スケール | 表示範囲 | スライダー範囲 |
| ------------ | -------: | -------- | -----------: | -------- | -------------- |
| `サイズ`     |        3 | 0〜500   |          (1) | 0〜500   | 0〜500(全域)  |
| `ぼかし`     |       10 | 0〜100   |          (1) | 0〜100   | 0〜100(全域)  |

| チェック   | 既定                       | 種別                     |
| ---------- | -------------------------- | ------------------------ |
| `check[0]` | `縁色の設定`(-1)           | ボタン(色選択ダイアログ) |
| `check[1]` | `パターン画像ファイル`(-1) | ボタン(ファイル選択)     |

**`+0x74` の4スロットのうち3つが NULL** で、`シャドー` の `{0,0,10,0}` より
さらに素っ気ない。ドラッグ範囲が無いのでスライダーは raw 範囲いっぱいを動き、
グループ化マーカーも無いので `サイズ` と `ぼかし` は独立した2本として扱われる
([`param_scaling.md` §1](../common/param_scaling.md))。表示スケールの配列は
`0x101b1f60` ―― 全ゼロなので `.rdata` ではなく `.data` に置かれている
(`カラーキー` の `track_s`/`track_e` と同じ理由)。

### `ex_data` ―― `シャドー` と同一レイアウト

`+0x70` フィールド表(`0x100a5ca8`)が宣言しているのは3本:

```
[0] kind=3 size=  3 name="color"     -- R, G, B (Win32 COLORREF と同じバイト順)
[1] kind=0 size=  1 name=(なし)      -- 未使用のパディング1バイト
[2] kind=2 size=256 name="file"      -- パターン画像のパス(NUL終端)
合計 260 バイト = ex_data_size
```

**`シャドー` の表(`0x100b84b0`)と宣言内容が完全に一致し、`"color"`
(`0x1009d7c0`)と `"file"`(`0x1009d7d0`)の文字列そのものも共有している** ――
テーブルの実体だけが別、という `クロマキー`/`カラーキー` と同じ関係
(`verify_ex_data.py` §1)。

`ex_data_def` は **260バイトすべてゼロ**、つまり新規追加時は
**縁色 = RGB(0,0,0) の真っ黒、パターン画像なし**。`発光`/`閃光`/`グロー` が
持つ bit24 の「指定なし」フラグは無く、4バイト目は `ライト`/`シャドー` と同じ
単なるパディングである([`rgb_ycbcr.md` §1](../common/rgb_ycbcr.md))。

## 2. パラメータ変換 ―― `/1000` の結果は誰も読まない

`func_proc`(`0x100515d0`)冒頭、`サイズ = 0` なら即 `return 1`。**早期リターンは
これ1本だけ**で、`ぼかし = 0` でもパイプラインは最後まで走る。

その直後に、いかにも普通の Q12 パラメータに見える値が作られる:

```
g_101b1e38 = 4096 - trunc(ぼかし_raw * 4096 / 1000)      // 0x10051632
```

**この値は二度と読まれない。** 定数 `0x101b1e38` はイメージ 850KB 全体で
**この1回しか出現しない**(`verify_params.py` §1 が生バイト走査で確認)ので、
読み手が存在しようがない。エフェクト内で唯一のマジックナンバー除算
`0x10624dd3`([`param_scaling.md` §2](../common/param_scaling.md))も、この
死んだ計算のためだけに置かれている。

`ぼかし` が実際に効くのは、800バイト先で x87 が作る**利得**のほうである:

```
kernel = 2*サイズ + 1                                          // g_101b1e34
gain   = trunc(1024 / ((kernel-1) * ぼかし * 0.01 + 1) + 0.5)  // g_101b1f54
       = round(1024 / (0.02 * サイズ * ぼかし + 1))
```

`+0.5` してから `_ftol`(0方向切り捨て)なので四捨五入。オペランドは常に
非負なので単純な round-half-up になる。`ぼかし = 0` なら分母が 1 で
`gain = 1024`、これは後段の `>> 10` とちょうど打ち消し合う。

利得は 501×101 通りすべてで `1..1024` に収まり、`ぼかし` と `サイズ` の
どちらについても単調非増加(`verify_params.py` §3)。

> x87 の精度制御(53bit か 64bit か)が結果を変えうるのは **50601通り中5通り
> だけ**で、そこでも差は 1/1024 である。`シャドー` は同じ問題を入力の 5.41% で
> 抱えている([`シャドー` §5](../shadow/README.md))のに対し、`縁取り` は
> ほぼ免れている。該当する組は `verify_params.py` §3 が列挙する。

### サイズのクランプ ―― 確保済みバッファに対してだけ

```
if 2*サイズ > stride(fpip+0xEC) - w:  サイズ = trunc((stride - w) / 2)
if 2*サイズ > rows  (fpip+0xF0) - h:  サイズ = trunc((rows   - h) / 2)
```

`ライト` の `trunc(寸法/2) - 2` や `発光` の `寸法/2 - 1` に相当する
「オブジェクト自身の大きさに対するクランプ」は無い ―― その役目は §3 の
事前パディングが担う。`シャドー` と違って余白を取り合う `X`/`Y` オフセットが
無いので、`サイズ` は余白を丸ごと使える。

## 3. キャンバス ―― 先に太らせて、最後に削り戻す

`縁取り` のキャンバス操作は2段階で、**1段目は出力のためではなく、
スライディングウィンドウの前提を満たすためだけに存在する**。

### 3.1 事前パディング(`0x10051641`〜`0x1005176d`)

```
if 2*サイズ >= w || 2*サイズ >= h:                 // どちらか片方でも成立すれば
    padX = (max(2*サイズ - w, 0) + 2) / 2
    padY = (max(2*サイズ - h, 0) + 2) / 2
    (padX, padY をそれぞれ stride, rows の余白でクランプ)
    table[0x48](fpip+0xB0, 0, 0, w+2*padX, h+2*padY, 0,0,0,0, 2)      // 透明で埋め
    table[0x44](fpip+0xB0, padX, padY, fpip+0xAC, 0,0, w, h, 0, 0x13000003)
    swap fpip+0xAC <-> fpip+0xB0
    fpip+0xB4, +0xB8 = w+2*padX, h+2*padY
```

条件は「カーネル幅 `2*サイズ+1` がどちらかの軸に収まらない」であり、パディング
後の幅・高さは**必ず `2*サイズ+1` 以上**になる(偶奇によって `+1` か `+2`。
`verify_params.py` §4 が 200×200×34 通りで確認)。これは
[`box_blur.md` §4](../common/box_blur.md) が `クロマキー`/`カラーキー`/
`境界ぼかし` について、[`シャドー` §2](../shadow/README.md) が `シャドー` に
ついて挙げている「軸がカーネルより短いと中段ループ回数が負になり、立ち上がり
フェーズがオブジェクトの外を読む」という穴を、**解析済みで初めて塞いでいる
実装**である。

2つの癖:

- **軸ごとではなくエフェクトごとに発火する。** 片方の軸だけが足りない場合でも
  両軸がパディングされ、`(v+2)/2` の `+2` によって足りていた側にも 1 画素ずつ
  付く。
- **確保が窮屈だとクランプが保証を壊しうる**が、その直後の `サイズ` 再クランプ
  (§2)が同じ余白を見てカーネルを縮めるので、結果的に安全側に落ちる
  (`verify_border_chain.py` §6)。

### 3.2 縁のぶんの成長

```
w += 2*サイズ ;  h += 2*サイズ                     // 0x100517aa
```

こちらは**ワーカー自身が枠外に書く**方式A
([`canvas_growth.md` §2](../common/canvas_growth.md))で、各パスが
`n + kernel - 1` 本を出力することで実現される。

### 3.3 削り戻しと公開

```
if 2*padX <= 0 && 2*padY <= 0:
    swap fpip+0xAC <-> fpip+0xB0
else:
    w -= 2*padX ;  h -= 2*padY
    table[0x48](fpip+0xAC, 0, 0, w, h, ...)                            // 冗長
    table[0x44](fpip+0xAC, 0, 0, fpip+0xB0, padX, padY, w, h, 0, 0x13000003)
fpip+0xB4, +0xB8 = w, h
```

**公開されるサイズは事前パディングの有無によらず常に
`(w0 + 2*サイズ, h0 + 2*サイズ)`** で、オブジェクトはその中の
`(サイズ, サイズ)` にきっかり載る ―― つまり縁は上下左右に等しく `サイズ` 画素
(`verify_canvas.py` §1/§2 が 174960 通りで確認)。

**事前パディングを最後に取り消すエフェクトは解析済みで `縁取り` だけ**である。
`ぼかし`/`拡散光`/`グロー` の事前拡張は出力そのものの置き場所なので取り消さない。

削り戻し前の `table[0x48]` は、続く転送が単純コピー(`0x13`)で転送元矩形も
キャンバス内に必ず収まるため、1画素も残さず上書きされる ―― 冗長である。

`サイズ固定` に相当するチェックボックスは**存在しない**ので、`サイズ > 0` なら
外接矩形は必ず変わる(`グロー`・`ライト`・`シャドー` と同じ性質、
[`canvas_growth.md` §6](../common/canvas_growth.md))。ただし `シャドー` と違って
**塗られない透明な帯は残らない** ―― 成長が対称なので、増えた `2*サイズ` 行
(列)はすべて縁が届く範囲にある。

同じ理由で **`fpip+0xD4` / `+0xD8`(オブジェクト中心のずれ補正)を1度も触らない**
(`verify_canvas.py` §4)。`シャドー` が `(-X) << 11` を書き込むのは片側にしか
伸びないからで、`縁取り` には補正すべきずれが無い。

### 3.4 内容ボックス原点と4本の矩形クリア ―― 全部死んでいる

`func_proc` は `シャドー` の `g_X`/`g_Y`(影の箱の原点)に相当するグローバル
`0x101b1e3c` / `0x101b1e40` を持ち、パターンの敷き詰め原点・タイル走査の上限・
4本の矩形クリアがすべてこれを参照する。**どちらも冒頭で 0 が書かれるだけで、
イメージ中に他の書き手が居ない。**

その結果:

- 左・上のクリアは `g > 0` のガードで弾かれる
- 右・下のクリアは境界が `fpip->w + 2*サイズ + g` = 成長後のキャンバス幅と
  一致するので弾かれる

**4本とも到達不能**(`verify_canvas.py` §3 が 174960 通り×4本で確認)。
`シャドー` では同じ4本が本当に仕事をしている(内容ボックスが
`(max(X,0), max(Y,0))` にずれていてキャンバスより小さい)ので、コードの出どころ
は明らかである。キャンバスがクリアされないままでも困らないのは、色版ワーカーが
全画素のアルファを無条件に書くからである(§5)。

## 4. 被覆マップ ―― 2パスの「割らないボックス」

`EXFUNC::exec_multi_thread_func`(`exfunc+0xCC`)経由で2パスが順に走る。
対象は**オブジェクトのアルファだけ**で、Y/Cb/Cr は1度も読まれない
(パス1の `movsx` の変位は `+6` のみ)。

| パス | 関数                        | 向き | 入力             | 出力                      | スレッド分割 |
| ---- | --------------------------- | ---- | ---------------- | ------------------------- | ------------ |
| 1    | `0x10051ae0`                | 垂直 | `fpip+0xAC` の α | 16bit スクラッチ プレーン | 列           |
| 2    | `0x10051c80` / `0x10051ea0` | 水平 | スクラッチ       | `fpip+0xB0`(エンコード)  | 行           |

中間プレーンは `[0x101a5328]`(`発光`/`グロー`/`クロマキー`/`ライト`/`シャドー`
と同じ共有スクラッチ)を1枚だけ借りる。行の刻みはキャンバス幅ではなく
**確保幅 `fpip+0xEC`** で、これは入力バッファ側と同じ。

各パスは全エフェクト共通の3フェーズ・スライディングウィンドウだが、
**窓の和をカーネル幅で割らない**:

```
sum  = Σ (窓内のサンプル)
v    = (sum * gain) >> 10          // imul は符号付き32bit、sar は floor
out  = (v >= 4096) ? 4096 : v      // 飽和。負値はそのまま16bitで格納される
```

両ワーカーとも `idiv` は**スレッド範囲の計算に2つあるだけ**で、画素ループには
除算が1命令も無い(`verify_border_chain.py` §2)。
[`box_blur.md` §3](../common/box_blur.md) の「常にカーネル幅で割る」も
「生存サンプル数で割る」も、ここには当てはまらない。

**これがこのエフェクトの本質である。** 平均なら完全被覆の窓は 4096 に戻るだけ
だが、和なら 4096 を大きく超えて飽和側に張り付く ―― 二値のシルエットに対して
`ぼかし = 0` の `縁取り` は**厳密に「一辺 `2*サイズ+1` の正方形による膨張
(dilation)」**になる。半透明のオブジェクトでは、薄い画素でも近傍で足し合わ
されて不透明な縁になりうる。

### 合成カーネルは三角形ではなく平らな箱

軸ごとに1パスなので畳み込みが起きない。振幅1のインパルスを入れると出力は
**値1が `(2*サイズ+1)²` 画素に広がるだけ**(`verify_border_chain.py` §1)。
`ぼかし` と `シャドー` は軸ごとに2パス走らせて箱と箱を畳み込み、半幅ちょうどの
三角形を作る([`box_blur.md` §2](../common/box_blur.md))が、`縁取り` は
そもそも滑らかにしたいわけではないので分割していない。

各パスの出力本数は `n + kernel - 1 = n + 2*サイズ` で、2パスで
`(w + 2*サイズ) × (h + 2*サイズ)` ―― §3 が公開するキャンバスとちょうど一致する。

### `ぼかし` の効き方 ―― 利得は2回掛かる

`gain` はパス1(`0x10051b6d`)とパス2(`0x10051d59`)の**両方**で掛かる。
1パスぶんで見ると、窓が飽和するのに必要な不透明サンプル数は

```
1024 / gain ≒ 0.02 * サイズ * ぼかし + 1 = 1 + (カーネル幅 - 1) * ぼかし/100
```

つまり **`ぼかし` は「縁が不透明になるためにカーネルの何%が埋まっている必要が
あるか」**である。`ぼかし = 100` なら窓がまるごと埋まってようやく飽和する。

`サイズ = 8` での実測プロファイル(`verify_border_chain.py` §4。横に十分広い
水平エッジで、数字は縁の外側へ 0, 2, 4, … 画素進んだところのアルファ):

| `ぼかし` | gain |    0 |    2 |    4 |    6 |    8 |
| -------- | ---: | ---: | ---: | ---: | ---: | ---: |
| 0        | 1024 | 4096 | 4096 | 4096 | 4096 |    0 |
| 25       |  205 | 4096 | 4096 | 4096 | 4096 |    0 |
| 50       |  114 | 4096 | 4096 | 3452 | 1726 |    0 |
| 75       |   79 | 3315 | 2486 | 1657 |  828 |    0 |
| 100      |   60 | 1912 | 1434 |  956 |  478 |    0 |

**`ぼかし` は縁の外側をぼかすだけでなく、上げすぎると縁全体を半透明にする** ――
飽和した芯にも同じ利得が掛かるからである。縁の広がりそのもの(`2*サイズ`)は
`ぼかし` によらず一定。

### `imul` の32bit溢れ

`imul` は符号付き32bitで拡張されない。1パスの最悪ケースは窓が全部不透明な
場合の `カーネル幅 * 4096 * gain` で、これが `2^31` を超えると符号が反転する。

`verify_border_chain.py` §5 が 50601 通りを総当たりして、**溢れうるのは
`ぼかし = 0` かつ `サイズ ≥ 256` の 245 通りだけ**であることを確認している
(閾値は `(2*サイズ+1) * gain ≥ 524288`、`gain = 1024` なら `カーネル幅 ≥ 512`)。

```
サイズ=300, ぼかし=0, 601行すべて不透明な窓:
  sum        = 2461696
  sum * 1024 = 2520776704   (> 2^31)
  int32 として = -1774190592
  sar 10 → 負 → `>= 4096` の飽和判定を素通りし、下位16bit がそのまま格納される
```

影響を受けるのは「窓がまるごとシルエット内部にある」画素 ―― つまり縁の中でも
オブジェクトの奥で、通常はオブジェクト自身に覆われて見えない。透けている穴が
あって、かつ対象軸に 512 画素超の不透明領域がある場合にだけ表に出る。

## 5. 出力エンコード ―― 縁色は素のまま入る

### 縁色版 `0x10051c80`

```
sum == 0 : dst.a = 0                          // y/cb/cr は書かない
それ以外 : dst.y, dst.cb, dst.cr = 縁色       // そのまま格納
           dst.a = min(4096, (sum*gain)>>10)
```

**縁色は Y/Cb/Cr に素のまま入り、被覆率だけがアルファに入る。**
`ライト` の後光や `閃光` は `Y = 4096` に固定して光色の Y をアルファへ載せる
アンプリマルチプライなので「暗い光色ほど効果が消える」が
([`rgb_ycbcr.md` §4](../common/rgb_ycbcr.md))、`縁取り` は `シャドー` と同じ側で
**真っ黒な縁も真っ白な縁と同じ不透明度になる**。既定値が RGB(0,0,0) である
以上そうでなければ困る、という設計上の必然でもある(`verify_encode.py` §1)。

`濃さ` に相当するトラックバーが無いので、出力アルファを下げられるのは
`ぼかし` が被覆率を縮めるときだけ。上限は飽和判定そのもので、`シャドー` に
ある「x87 の丸めで芯が 1 足りない」ような誤差も無い ―― 割り算をしないので
当然である。

`sum == 0` で色を書かないのは、その画素のアルファが必ず 0 になるからで、
[`box_blur.md` §1](../common/box_blur.md) の `sum_a == 0` と同じ理屈である。
なお `sum != 0` でもアルファが 0 に切り捨てられる画素はあり、そちらには縁色が
書かれる ―― 透明画素が2種類あることになるが、どちらも見えない。

### パターン画像版 `0x10051ea0`

```
v = (sum*gain) >> 10
if v >= 4096:  何も書かない                   // パターンの画素をそのまま残す
else:          dst.a = (dst.a * v) >> 12      // dst.a = 敷き詰め済みパターンのα
```

**Y/Cb/Cr は1度も書かれない**(3つの縁色グローバルへの参照が関数内に0件、
`verify_encode.py` §4)。色はタイル済みのパターン画像がそのまま供給し、
`縁色の設定` はこのモードでは完全に無効になる。飽和時に**書き込みごとスキップ
する**のは `シャドー` のパターン版(乗算を必ず行う)との細かな違いだが、
`v = 4096` での乗算は恒等なので結果は同じ。

### 最後の合成 ―― オブジェクトを上に戻す

```
table[0x44](fpip+0xB0, サイズ, サイズ, fpip+0xAC, 0, 0, w, h, 0, 3)
```

モード語 `3` は下位バイト `3`(転送元・転送先とも8バイト画素)＋上位バイト `0`
= **通常合成 `0x10007df0`**([`blend_modes.md` §3](../common/blend_modes.md))。
縁の被覆マップの上に、元オブジェクトを src-over で重ねる。

膨張したシルエットの中央はオブジェクト自身に覆われるので、見えるのは
**縁の外側 `サイズ` 画素ぶんと、オブジェクトの穴・半透明部から透ける縁**だけに
なる。`シャドー` が箱ごとずらすのに対し、`縁取り` は同心のまま重ねる ―― これが
2つのエフェクトの見た目の差そのものである。

## 6. `パターン画像ファイル` ―― キャンバス全面に敷き詰める

`ex_data+4` が空文字列でないとき、ワーカーが始まる**前に**次を行う:

```
ok = table[0x38]([0x101a5328], path, &patW, &patH, 0, 0)     // 0x1004c8d0 = 画像ローダ
if ok:
    for tileY in 0, patH, 2*patH, ... < canvasH:
        for tileX in 0, patW, ... < canvasW:
            table[0x44](fpip+0xB0, tileX, tileY, [0x101a5328],
                        0, 0, patW, patH, 0, 0x13000003)      // 単純コピー、8バイト画素
```

`table[0x38]`(`0x1004c8d0`)と `table[0x3c]`(`0x1004cc40`)は `シャドー` と共有
の画像ローダ / パス解決。デコード先にスクラッチ `[0x101a5328]` を借りるが、
被覆マップのプレーンとして使い始めるのはこの後(`0x1005196a`)なので競合しない。

タイルの原点は §3.4 のとおり常に `(0, 0)` = キャンバスの左上で、`シャドー` が
影の箱の左上から敷き詰めるのとはここが違う。どちらにせよ**パターンはフレーム
ではなくオブジェクトに固定される**ので、オブジェクトが動けば模様も一緒に動く。

`patW` と `patH` の両方が非0のときだけパターン版ワーカーが選ばれる
(`0x100519de`)。パスが空でもローダが失敗しても、どちらも縁色版に落ちる。

## 7. UI ―― 2つのボタンが1つのコントロールIDを共有する

`func_WndProc`(`0x10052070`)は `WM_FILTER_COMMAND`(`0x702`)だけを見て、
`LOWORD(wParam)` が `0x1e1b`(ボタン押下)か `0x1e16`(ファイル名の通知)の
どちらかのときだけ動く。`シャドー` に続いて**ボタンを2個持つ2例目**で、
区別は `HIWORD(wParam)` にある:

```c
if (message == 0x702) {
    if (LOWORD(wParam) == 0x1e16) goto file_accepted;     // exedit がパスを lParam で渡してきた
    if (LOWORD(wParam) != 0x1e1b) return 0;
    if (HIWORD(wParam) == 0) {                            // check[0] = 縁色の設定
        table[0x80](fp+0xE4, 0);
        if (!table[0x6c](fp, ex_data, 2)) return 0;       // 色選択ダイアログ。フラグ 2 は シャドー と同じ
        ex_data[4] = '\0';                                // ★ パターンのパスを消す
        sub_1004a7e0(fp+0xE4, "color");
        sub_10052200(fp, ex_data);                        // ラベル再構築
        return 1;
    }
    /* HIWORD != 0 -> check[1] = パターン画像ファイル */
    if (sub_10020900(&localPath, table[0x3c](ex_data+4)) != 1) return 0;
file_accepted:
    table[0x80](fp+0xE4, 0);
    if (LOWORD(wParam) == 0x1e16) lstrcpyA(localPath, (char*)lParam);
    if (table[0x38](NULL, localPath, &pw, &ph, 0, 0) != 1)
        MessageBoxA(NULL, "画像ファイルの読み込みに失敗しました…", fp->name, 0x42010);
    else if (pw * ph > trunc(maxCanvasW * maxCanvasH / 2))
        MessageBoxA(NULL, "画像サイズが大きすぎて読み込めません", fp->name, 0x42010);
    lstrcpyA(ex_data+4, localPath);
    sub_10052200(fp, ex_data);
    return 1;
}
```

**`シャドー` とはボタンの添字がずれている** ―― `縁色の設定` は `check[0]` なので
`HIWORD == 0`、`シャドー` の `影色の設定` は `check[1]` なので `HIWORD == 1`
だった。前にチェックボックスが1個あるかどうかの差である。ラベル再構築が
`table[0x4c](fp+0xE4, 5, 1)` と `(fp+0xE4, 5, 0)` を引くこと(種別5 = ボタン、
[`filter_registration.md` §7](../common/filter_registration.md))でも同じ添字が
確認できる。

**2つのメッセージボックスは、表示の直前に `localPath` の先頭へ 0 を書く**
(`0x100521c3`)。したがって読み込みに失敗した / 大きすぎると拒否された画像を
選ぶと、続く `lstrcpyA` が空文字列を書き込み、**それまで設定されていた
パターンも消える**。

画像サイズの上限は `w * h > trunc(最大キャンバス幅 * 最大キャンバス高 / 2)`
([`canvas_growth.md` §1](../common/canvas_growth.md) の `0x10196748` /
`0x101920e0`)。`シャドー` と同じく**このチェックは UI 側にしか無く**、
`func_proc` の読み込み(`0x100517df`)は無検査である。

### 色とパターンは排他

- **色を確定すると `ex_data+4` の先頭に 0 が書かれ、パターンのパスが消える**
  (`0x100520e2`)。
- **パターンが設定されている間、`縁色の設定` ボタンのラベルは空文字列になる**
  (`0x1005226e`。設定されていなければ `"RGB ( %d , %d , %d )"`)。

非対称なのは、色を選ぶとパスが**消える**のに対し、パスを選んでも色のバイトは
`ex_data` に残ったまま表示されなくなるだけ、という点 ―― [`シャドー`
§8](../shadow/README.md) とまったく同じ形である。

ラベル再構築(`0x10052200`)はパスから最後の `:` または `\` の次の文字を探して
ファイル名部分だけをボタンに出す。走査は `IsDBCSLeadByteEx` を使う cp932 対応で、
2バイト文字の後続バイトがたまたま `0x5c`(`\`)でも誤認しない。
`FILTER+0x58`(`0x100522d0`)はラベル再構築を呼ぶだけの5命令。

## 9. 参照テーブル

`サイズ`(カーネル幅とキャンバスの伸び):

| raw | カーネル幅   | 軸ごとの伸び | 事前パディングが起きるオブジェクトの大きさ |
| --- | ------------ | ------------ | ------------------------------------------ |
| 0   | ―(即 return) | ―           | ―                                          |
| 1   |            3 |            2 | 幅か高さが 2 以下                          |
| 3   |            7 |            6 | 幅か高さが 6 以下(既定)                   |
| 10  |           21 |           20 | 幅か高さが 20 以下                         |
| 50  |          101 |          100 | 幅か高さが 100 以下                        |
| 500 |         1001 |         1000 | 幅か高さが 1000 以下                       |

`ぼかし`(`サイズ = 3` のとき):

| raw | gain | `1024/gain` = 飽和に要る不透明サンプル数 | カーネル幅7 に対して |
| --- | ---: | ---------------------------------------- | -------------------- |
| 0   | 1024 |                                      1.0 | 1/7 で飽和(硬い縁)  |
| 10  |  640 |                                      1.6 | 2/7(既定)           |
| 25  |  410 |                                      2.5 | 3/7                  |
| 50  |  256 |                                      4.0 | 4/7                  |
| 100 |  146 |                                      7.0 | 7/7(全面ランプ)     |

`ぼかし = 10`(既定)のとき、`サイズ` が上がるほど利得は下がる ―― `サイズ=10`
で 341、`サイズ=100` で 49、`サイズ=500` で 10。**ランプの割合は `ぼかし` だけで
決まり、`サイズ` はその絶対幅を決める**ように作られている。

既定の `サイズ=3, ぼかし=10` を 48×48 のオブジェクトに掛けた場合:
キャンバス `54×54`、オブジェクトは `(3, 3)`、事前パディングなし
(`simulate_border_reference.py`)。

## 10. 未確定事項

- **`g_101b1e38` が本来何をするはずだったのか。** `4096 - trunc(ぼかし*4096/1000)`
  という形は、被覆マップに対するしきい値や不透明度としてそのまま使える値で、
  `境界ぼかし` の非線形しきい値カーブと同じ Q12 の形をしている。実装が途中で
  利得方式に変わった名残に見えるが、裏付けは無い。
- **`table[0x38]`(`0x1004c8d0`)がサポートする画像形式**と
  **`table[0x3c]`(`0x1004cc40`)が組み立てる相対パスの基準**。
  [`シャドー` §11](../shadow/README.md) と同じ未追跡項目。
- **`flag` の bit30(`0x40000000`)。** SDK では `FILTER_FLAG_MAIN_MESSAGE` だが、
  exedit の内部テーブルで立っている12エントリの共通項が見つかっていない。
  `縁取り` の `func_proc` はこのビットを読まない。
- **`ex_data.file` の 256 バイトと `func_WndProc` の 260 バイトのスタック
  バッファの食い違い。** `lstrcpyA(ex_data+4, localPath)` は最大 260 バイト
  コピーしうるので、259文字のパスは 4 バイトはみ出す。`シャドー` と同じ形だが、
  どちらも実測していない。
- **`fpip+0xEC` / `+0xF0` の実際の値。** 事前パディングと `サイズ` クランプの
  上限そのものなので、「どのくらいの `サイズ` から縁が細り始めるか」は確保の
  され方次第。`拡散光` §4 / `ライト` §2 / `シャドー` §2 と同じ読みを踏襲して
  いるだけで、本エフェクトでも書き込み側は追っていない。
- **x87 の精度制御。** §2 のとおり 50601通り中5通りで 53bit と無限精度の結果が
  食い違う。AviUtl 本体が制御ワードをどう残しているかは確認していない。
- **`imul` 溢れが実物で見えるかどうか。** §4 の条件は総当たりで確定させたが、
  `サイズ ≥ 256` を実際に設定したときにバッファの確保が足りるか
  (= `サイズ` がクランプされずに残るか)は上の `fpip+0xEC` 次第で、実機では
  再現しない可能性がある。

以下は全エフェクト共通の未確定事項:

- `fpip->flag & 0x200`(描画品質を落としてよいフラグ)をこのエフェクトが
  読むかどうかは未確認(`disasm_params.py` の範囲では出てこない)。
- 最終的な YCbCr→RGB 変換とそのクリップは `aviutl.exe` 側にあるため、本
  プロジェクトの解析対象外([`rgb_ycbcr.md` §3](../common/rgb_ycbcr.md))。
