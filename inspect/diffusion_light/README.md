# 拡散光 (Diffusion Light) フィルタ リバースエンジニアリング解析

対象: `data/exedit.auf`(AviUtl 拡張編集の標準フィルタプラグイン)、32bit PE、
`ImageBase = 0x10000000`。以下のアドレスはすべて VA(`RVA = VA - 0x10000000`)。

## 再現方法

すべてのスクリプトは本プロジェクトの `main.py` を踏み台にして実行する。
`main.py` はコマンドラインで指定されたスクリプトに対して、DLLパス
(デフォルト `data/exedit.auf`)とヘッダー一覧(デフォルト `data/filter.h`)を
渡す役割を持つ。

```
uv run main.py inspect/diffusion_light/<script>.py
uv run main.py tools.<tool>            # エフェクト非依存の共通ツール。一覧はリポジトリ直下の README
```

| スクリプト | 確認していること |
|---|---|
| `tools.filter_table --name 拡散光` | `FILTER_DLL` 配列(先頭 `0x100a3e28`)をたどり、`拡散光` の2つの登録エントリを抽出。両方とも `func_proc = 0x1001c330` を共有し、`+0x74` 拡張ブロック(`0x100a21b8`)まで同一 |
| `tools.track_scale --name 拡散光` | 表示スケール(`強さ`=10、`拡散`=1)とスライダーのドラッグ範囲 |
| `decompile_diffusion_light.py` | `0x1001c000`〜`0x1001f000` に絞った `CFGFast` + angr デコンパイル。func_proc と6つのワーカーすべてが復元できる(x87 の除算だけはリフトされない) |
| `disasm_params.py` | func_proc 全体の注釈付きダンプ。`強さ` のマジックナンバー除算、`拡散` の分割定数、キャンバス前処理、ワーカー呼び分け |
| `verify_strength.py` | `強さ` の変換を raw=0〜1000 の全1001通りで `raw*4096//1000` と照合。消費側がオブジェクト版では「拡散層の不透明度」、フレーム版では「単純 lerp の係数」であることを命令列で確認 |
| `verify_radius_split.py` | 定数 `0.44722719141323786` が **`1/2.236` そのもの**であること、`r1 + r2 == 拡散` が全501通りで成り立つこと、`r1 >= r2` が常に成り立つこと |
| `verify_mode_mapping.py` | 3組のワーカー対がそれぞれどの登録・どのバッファ・何バイト/画素を触るか。スレッド分割の軸(列 or 行)から垂直/水平を判定 |
| `verify_canvas_growth.py` | 3ループ/5ループの回数をディスアセンブルから読んで Python で再生し、窓が本当に `clip([d-2r, d])` になること・出力が中心を保つことを確認。`2r+1` 画素ずらしがイン・プレース処理のために必要十分であることも |
| `verify_box_average.py` | ボックス平均に重みテーブルが存在しないこと。色がアルファ加重・アルファが単純平均であること。**除数が3変種で違う**こと(成長版は常にカーネル幅、固定版とフレーム版は実サンプル数) |
| `verify_composite.py` | 合成式。「ぼかし結果の輝度が元より明るいときだけ書き込む」ルールと、色差の輝度加重ブレンド、そしてソースオーバーのアルファ |
| `simulate_diffusion_light.py` | 上記すべてを織り込んだ整数忠実リファレンス実装(3変種すべて)。平坦な不透明画像が**ビット単位で不変**であることなど9項目の自己検証つき |

## 1. 2つの登録エントリと3組のワーカー

`拡散光` は `FILTER_DLL` として2回登録されており、どちらも
`func_proc = 0x1001c330` を共有する。`func_init` / `func_exit` / `func_update` /
`func_WndProc` はすべて NULL、`ex_data` も持たない ―― パラメータはトラックバー
2本とチェックボックス1個で全部である。

| | オブジェクトのフィルタ効果 | フレーム(映像)フィルタ |
|---|---|---|
| `FILTER_DLL` | `0x100a21d0`、`flag=0x20` | `0x100a22f8`、`flag=0x00` |
| チェックボックス | `サイズ固定` | なし |
| 画像バッファ | `*(fpip+0xAC)` / `*(fpip+0xB0)` | `fpip->ycp_edit` (`+4`) / `fpip->ycp_temp` (`+8`) |
| 画素形式 | **8バイト/画素 PIXEL_YCA**(y, cb, cr, **a**) | 6バイト/画素 PIXEL_YC(アルファなし) |
| 幅・高さ | `*(fpip+0xB4)` / `*(fpip+0xB8)` | `fpip->w` (`+0xC`) / `fpip->h` (`+0x10`) |
| 行幅・上限 | `*(fpip+0xEC)` / `*(fpip+0xF0)` | `fpip->max_w` (`+0x14`) |

分岐は `fp->flag & 0x20` と、オブジェクト側の `fp->check[0]`(`サイズ固定`)の
2点だけで、行き先は3組のワーカー対になる(`verify_mode_mapping.py`)。
各対は「垂直パス」と「水平パス＋合成」で、前者は `w` を、後者は `h` を
スレッド間で分割する。

| | 垂直パス | 水平パス＋合成 |
|---|---|---|
| オブジェクト、`サイズ固定` オフ | `sub_1001c710` | `sub_1001cb10` |
| オブジェクト、`サイズ固定` オン | `sub_1001d710` | `sub_1001dbd0` |
| フレームフィルタ | `sub_1001e4f0` | `sub_1001e770` |

ワーカーはどれも `fp->track[]` も `fp->check[]` も読まない。パラメータは
func_proc が書く3つのグローバル経由でしか届かない:

```
g_1011efdc = strength       強さ から作った Q12 の不透明度 (4096 = 100.0)
g_1011efe4 = radius         いま走っているラウンドの半径
g_1011efe0 = kernel width   = 2*radius + 1
```

`tools.xrefs` でこの3アドレスを検索すると、参照はすべて `拡散光` の
func_proc とそのワーカーの中に収まる ―― 他フィルタとの共有はない。

## 2. パラメータ変換(`func_proc` 内、フレームごとに1回)

トラックバーは `fp->track[]` の順に `強さ`(初期値500、範囲0〜1000)、
`拡散`(12、0〜500)。UI に表示される数値との対応は登録構造体 `+0x74` の
exedit 独自ブロックで決まる。ブロックの構造は
[`inspect/common/param_scaling.md`](../common/param_scaling.md) 参照
(`tools.track_scale`):

| トラックバー | 表示スケール | UI表示範囲 | スライダーで届く範囲 | UI既定値 |
|---|---|---|---|---|
| `強さ` | 10 | 0.0〜100.0 | 0.0〜100.0 | 50.0 |
| `拡散` | 1 | 0〜500 | 0〜100 | 12 |

* **`強さ`**: `raw << 12` を全エフェクト共通のマジックナンバー除算
  `0x10624dd3`(`sar 6`、[`param_scaling.md` §2](../common/param_scaling.md))に
  かける。**四捨五入ではなく0方向への切り捨て**:
  ```
  strength = trunc(raw * 4096 / 1000)      // raw=1000 -> 4096 ちょうど
  ```
  raw の上限が 1000 なので strength は 4096 を超えられない ―― `発光` のように
  100% 超のオーバードライブ経路は**コード上に存在しない**。100.0 が
  「拡散光を完全な不透明度で乗せる」で、それ以上は無い。
  `raw == 0` のときは func_proc が画素に一切触れず即 `return TRUE`。
* **`拡散`**: `/1000` 変換は一切されない。生の整数がそのまま画素数として使われ、
  かつ**2つの半径に分割される**:
  ```
  r2 = trunc(拡散 * 0.44722719141323786)   // 定数は 1/2.236 ちょうど
  r1 = 拡散 - r2
  ```
  `r1 + r2 == 拡散` が定義上つねに成り立ち、`r1 >= r2` も全501通りで成立する
  (`verify_radius_split.py`)。つまり **`拡散` は1つのぼかし半径ではなく、
  2回のぼかしの半径の合計**である。

  定数 `0.44722719141323786` は double として `1/2.236` と厳密に一致する。
  `2.236` は √5 = 2.2360679… の小数第3位丸めなので、設計上の意図は
  `r2 = 拡散/√5`、`r1 : r2 = (√5-1) : 1 ≈ 1.236 : 1` と読める。ただし半径は
  整数に切り捨てられるので、3桁丸めによる 3e-5 のずれは結果に出ない。

| `拡散` | r1 | r2 | 実際に走るラウンド |
|---|---|---|---|
| 0 | 0 | 0 | なし(恒等) |
| 1 / 2 | 1 / 2 | 0 | ラウンド1のみ |
| 5 | 3 | 2 | r=3, r=2 |
| 12(既定) | 7 | 5 | r=7, r=5 |
| 50 | 28 | 22 | r=28, r=22 |
| 100(スライダー上限) | 56 | 44 | r=56, r=44 |
| 500(最大) | 277 | 223 | r=277, r=223 |

## 3. ぼかし ― 一様ボックス平均を2ラウンド

1ラウンドは「垂直ボックス平均 → 水平ボックス平均＋合成」の2パス。
これが r1、r2 の順に2回走る。カーネル幅は `2r+1`、重みは一様で、
重みテーブルもガウシアン核もどこにも無い(`verify_box_average.py`)。

**重要なのは、合成が各ラウンドの水平パスの中で行われること**。ラウンド2は
「ラウンド1のぼかし結果」ではなく「**ラウンド1で合成し終わった画像**」を
ぼかす。`発光` の「6段のぼかし結果を蓄積バッファに足し込む」構造とは別物で、
ここでは 2回の "diffuse → merge" が直列につながっている。

### 色はアルファ加重、アルファは単純平均

オブジェクト版の集計・正規化の式(プリマルチプライした加重和、`sum_a` で色を
割ること)は全エフェクト共通の形。詳細は
[`inspect/common/box_blur.md` §1](../common/box_blur.md) 参照
(`verify_box_average.py` が本エフェクトでの検算)。

### 除数が3変種で違う

| | 窓が画像からはみ出したとき |
|---|---|
| `sub_1001c710` / `sub_1001cb10`(成長版) | **常にカーネル幅 `2r+1` で割る** |
| `sub_1001d710` / `sub_1001dbd0`(`サイズ固定`) | 窓に実際に入っているサンプル数(`r+i+1` → `2r+1` → `2r-i`)で割る |
| `sub_1001e4f0` / `sub_1001e770`(フレーム) | 同じく実サンプル数。アルファが無いので y/cb/cr も同じ数で割る |

除数の違いが端の扱いのすべてであることの一般論は
[`box_blur.md` §3](../common/box_blur.md) 参照。`サイズ固定` は「大きさが
変わらない」だけでなく、端の明るさの扱いまで変える。

## 4. キャンバスの拡張(`サイズ固定` オフのとき)

`発光` は exedit 共有の「オフスクリーン描画」(`0x1008a520`)でキャンバスを
広げてから処理するが、`拡散光` は**ぼかしワーカー自身が枠外に書く**方式(方式A)
で広げる。1ラウンドあたり縦横それぞれ `2r`、2ラウンドで `2*(r1+r2) = 2*拡散`、
つまり**片側 `拡散` 画素ずつ**大きくなる。仕組み(クランプ・1行だけのゼロクリア・
`2r+1` 画素の横ずらし)の詳細は
[`inspect/common/canvas_growth.md` §2](../common/canvas_growth.md) にまとめてある
(`verify_canvas_growth.py` が本エフェクトでの検算)。

出力行 `d` の窓は `clip([d-2r, d])`、すなわち出力行 `d` は元画像の行 `d-r` に
対応する。バッファ先頭は動かず上下に r 行ずつ増えるので、**オブジェクトの中心は
保たれる**。

### 半径が画像に対して大きいとき

`2*r1 >= w || 2*r1 >= h || 2*r2 >= w || 2*r2 >= h` のいずれかが成り立つ場合
(`0x1001c45e`)、成長版ワーカーのスライディングウィンドウが成立しないので、
func_proc が**先にキャンバスを広げてしまう**(方式B、
[`canvas_growth.md` §3](../common/canvas_growth.md)):

```
table[0x48](dst, 0, 0, w+2R, h+2R, 0,0,0,0, 2)                 // 新キャンバスをクリア
table[0x44](dst, R, R, src, 0, 0, w, h, 0, 0x13000003)         // 元画像を中央へ転送
バッファを入れ替え、w += 2R、h += 2R                            // R = r1 + r2 = 拡散
以降は サイズ固定 = 1 として扱う (0x1001c4af)
```

`table[0x44]`/`table[0x48]` の実体(`fp+0x64` 経由の描画関数テーブル)と
モード語の分解は [`blend_modes.md`](../common/blend_modes.md) 参照。

この経路を通っても最終的な成長量は片側 `拡散` 画素で変わらないが、以降は
固定サイズ版ワーカーが走るので、**端の除数の扱いだけが変わる**(手順3の表)。

## 5. 合成 ― 「明るくなる方だけ」

`発光` と `拡散光` の設計上の分かれ目はここ。`発光` は先に明部を抽出してから
ぼかして加算するが、`拡散光` は**画像をそのままぼかして、元より明るくなった
ところだけ書き戻す**:

```
gy, gcb, gcr = ぼかし結果(アルファ加重平均)
ga           = (窓のアルファ平均 * strength) >> 12

if gy <= 0:                       元画素のまま
d = gy - max(0, (src.y * src.a) >> 12)
if d <= 0:                        元画素のまま        // 暗くする方向には決して働かない
```

しきい値パラメータが1つも無いのはこのためで、「元画像より明るいか」という
比較そのものがしきい値の役目を果たしている。比較の左辺は**アルファ加重平均
(非プリマルチプライ)**、右辺は**元画素のプリマルチプライ輝度**なので、
半透明な画素ほど `d` が大きくなり、拡散光が強く出る。

書き込む場合、色差は輝度で重み付けしたブレンドになる:

```
base   = gy - d                                     // = max(0, プリマルチプライ輝度)
cb_mix = (((src.cb*src.a)>>12) * base + d * gcb) / gy
cr_mix = (((src.cr*src.a)>>12) * base + d * gcr) / gy
```

つまり「最終輝度 `gy` のうち元画素自身が出していた分だけ元の色相を残し、
残りはぼかした色相を使う」。元画素が真っ暗(`base = 0`)ならぼかした色相
そのもの、元画素が `gy` に近ければほぼ元の色相になる。

最後に `強さ` が `ga` として効く。オブジェクト版は教科書どおりのソースオーバーで、
3つの近道が挟まっている(`verify_composite.py`):

```
if ga >= 4096:            out = (gy, cb_mix, cr_mix, 4096)
elif src.a >= 4096:       out.c = (src.c*(4096-ga) + mix.c*ga) >> 12;  out.a = 4096
elif src.a <= 0:          out = (gy, cb_mix, cr_mix, ga)
else:
    ia = 4096 - ga
    na = (4096*4096 + 2048 - (4096 - src.a) * ia) >> 12      // = ga + a - a*ga/4096(丸めあり)
    w_src  = (ia * src.a) / na
    w_glow = (ga << 12) / na
    out.c  = (src.c * w_src + mix.c * w_glow) >> 12
    out.a  = na
```

`発光` の合成が「アルファに輝度を足して色をそれで割る」独特のものだったのに
対し、こちらは普通の source-over である。出力にクランプは一切無いが、
`gy` は範囲内の値の平均でしかなく、ソースオーバーのアルファも 4096 を
超えないので、そもそもクランプが要らない。

## 6. フレームフィルタ版の違い

アルファが無いので、

* ボックス平均は素の `idiv` 3本(**0方向切り捨て**なので、符号付きの Cb/Cr で
  Python の `//` とはズレる ―― [`integer_semantics.md`](../common/integer_semantics.md)
  参照)。x87 は使われない。
* 比較は `d = gy - max(0, src.y)`、色差ブレンドはプリマルチプライ抜きで同形。
* `強さ` は単純な lerp:
  ```
  if strength >= 4096:  out = merged
  else:                 out.c = src.c + (((merged.c - src.c) * strength) >> 12)
  ```
* 合成先は `ycp_edit` そのもの(イン・プレース)。`ycp_temp` はぼかしの中間
  バッファとしてだけ使われる。

## 9. 未確定事項

* **なぜ `2.236` なのか**。定数が `1/2.236` そのもので、`2.236` が √5 の
  小数第3位丸めであることは確認済みだが、2段ぼかしの比を `(√5-1):1` に
  選ぶ理由(合成カーネルの形、実装当時の見た目の調整、等)は特定できていない。
  等分割(`1:1`)でも2段のガウシアン近似としては悪くないので、単なる好みの
  可能性もある。
* **端の除数の違いが実際の見た目にどう出るか**。成長版がカーネル幅で、固定版が
  実サンプル数で割ることは命令列とリファレンス実装の両方で確認したが、
  AviUtl 上での実測比較はしていない。
* **`sum_a == 0` のときに色を書かない挙動**。アルファが 0 なので通常は不可視だが、
  後段がアルファを無視して色を読む場合に古い値が漏れる可能性がある。実害が
  あるかは未確認。
* `rand()` や `FILTER_PROC_INFO.frame` を読んでいる箇所は見つからなかったので、
  フレームをまたぐ時間的な揺らぎは無い。

以下は全エフェクト共通の未確定事項。詳細は
[`rgb_ycbcr.md` §3](../common/rgb_ycbcr.md) 参照:

* 最終的な YCbCr→RGB 変換とそのクリップは `aviutl.exe` 側にあるため、
  本プロジェクトの解析対象外。
