# 境界ぼかし (Boundary Blur) フィルタ リバースエンジニアリング解析

対象: `data/exedit.auf`(AviUtl 拡張編集の標準フィルタプラグイン)、32bit PE、
`ImageBase = 0x10000000`。以下のアドレスはすべて VA(`RVA = VA - 0x10000000`)。

## 再現方法

すべてのスクリプトは本プロジェクトの `main.py` を踏み台にして実行する。
`main.py` はコマンドラインで指定されたスクリプトに対して、DLLパス
(デフォルト `data/exedit.auf`)とヘッダー一覧(デフォルト `data/filter.h`)を
渡す役割を持つ。

```
uv run main.py inspect/boundary_blur/<script>.py
uv run main.py tools.<tool>            # エフェクト非依存の共通ツール。一覧はリポジトリ直下の README
```

| スクリプト | 確認していること |
|---|---|
| `tools.filter_table --name 境界ぼかし` | `FILTER_DLL` 配列(先頭 `0x100a3e28`)をたどり、`境界ぼかし` の登録エントリを抽出。`ぼかし`/`発光` と違い**登録は1個だけ**(オブジェクト効果のみ、`flag=0x20`)で、フレーム(映像)フィルタ版は存在しない。トラックバー `範囲`/`縦横比`、チェックボックス `透明度の境界をぼかす` を確認 |
| `decompile_boundary_blur.py` | `0x10011b00` 周辺に絞った `CFGFast` + angr デコンパイルで `func_proc` の全体構造を把握。`--extra 0x10011c30 0x10011db0 0x10012060 0x10012200` で4つのワーカーも個別にデコンパイル可能(x87を多用する箇所は angr が一部命令をリフトできないため、以降のスクリプトは capstone の生アセンブリで補っている) |
| `disasm_params.py` | `func_proc` 全体の生アセンブリに注釈を付け、`範囲`/`縦横比` → 半径の変換、クランプ、チェックボックスによるワーカー選択を1命令ずつ確認 |
| `verify_radius_clamp.py` | `ぼかし` と同一のマジックナンバー除算(`0x10624dd3`)であることを400万通り全数検査。半径クランプが `width/2`・`height/2` への独立クランプであり、`ぼかし` のような hi/lo 分割・キャンバス拡張が一切無いことを確認 |
| `verify_ease_table.py` | OFF経路が参照するルックアップテーブルの生成式(`.rdata` の実定数から `table[i]=trunc(2048*(1-cos(i*pi/4096)))` を導出)と、順方向・逆方向2種類の参照が実は同一配列であることをアドレス演算で証明 |
| `verify_off_path.py` | チェックボックスOFF(既定)側のワーカー2つを1命令ずつPythonへ書き写し、丸め・角の丸まり方・ソース側の透明部分を無視することを検証。書き込みポインタが3フェーズを跨いで連続増加する実装のため、**偶数サイズ×半径=サイズ/2 のとき境界の書き込みが1行(列)分バッファ外へ溢れ、上下(左右)非対称になる**という未文書の副作用も発見・再現 |
| `verify_on_path.py` | チェックボックスON側のワーカー2つを1命令ずつPythonへ書き写し、実際にアルファチャンネルをボックスぼかしすること、端がゼロ埋めであること、非線形な再合成式のしきい値的な振る舞いを検証 |
| `simulate_boundary_blur_reference.py` | 上記すべてを織り込んだ整数忠実リファレンス実装。合成アルファ画像に対して実行し、OFF/ON の違いや境界溢れの実例を表示する |

```
uv run main.py inspect/boundary_blur/simulate_boundary_blur_reference.py --range 4
uv run main.py inspect/boundary_blur/simulate_boundary_blur_reference.py --range 4 --aspect 500
uv run main.py inspect/boundary_blur/simulate_boundary_blur_reference.py --range 4 --on
```

## 1. 登録はオブジェクト効果1個だけ

`境界ぼかし` は `FILTER_DLL` として**1回だけ**登録されている(`ぼかし`/`発光`は
オブジェクト効果・フレームフィルタの2登録)。

| | オブジェクトのフィルタ効果 |
|---|---|
| `FILTER_DLL` | `0x100a09e0`、`flag=0x20` |
| `func_proc` | `0x10011b00` |
| `func_init`/`func_exit`/`func_update`/`func_WndProc` | すべて NULL(UI用コード無し。`ぼかし` と同様) |
| トラックバー | `範囲`(初期値5、範囲 0~2000)、`縦横比`(初期値0、範囲 -1000~1000) |
| チェックボックス | `透明度の境界をぼかす`(初期値0 = OFF) |
| 画像バッファ | `*(fpip+0xAC)` |
| 対バッファ | `*(fpip+0xB0)` |
| 幅・高さ | `*(fpip+0xB4)` / `*(fpip+0xB8)` [画素] |
| 行幅 | `*(fpip+0xEC)` [画素] |

フレームフィルタ版が無いので、映像トラック全体に適用することはできず、
個々のオブジェクト(画像・テキスト・図形など)にしか掛けられない。

**このフィルタが読み書きするのは各画素の α(アルファ)チャンネルだけ**
(構造体オフセット `+6` の word、`PIXEL_YCA` の `a` フィールド)。
y/cb/cr は一切参照されない ―― 色そのものは常に元のまま保たれ、
「境界をぼかす」とは実際には「境界のアルファを滑らかに減衰させる」ことを指す。

## 2. パラメータ変換(`func_proc` 内、フレームごとに1回)

UI に表示される数値との対応は、登録構造体 `+0x74` にある exedit 独自の拡張
ブロック(表示スケール / スライダーのドラッグ下限・上限)で決まる。ブロックの
構造は [`inspect/common/param_scaling.md`](../common/param_scaling.md) 参照:

| トラックバー | 表示スケール | UI表示範囲 | スライダーで届く範囲 |
|---|---|---|---|
| `範囲` | 1 | 0~2000 | 0~500 |
| `縦横比` | 10 | -100.0~100.0 | -100.0~100.0 |

`ぼかし` と同じ構成で、違いは `範囲` の上限だけ(`ぼかし` は 0~1000 /
ドラッグ 0~300)。`範囲` は**UIの数値がそのまま生値**、`縦横比` だけが
10で割って表示される。

`範囲 == 0` でも即 return はせず、そのまま `rx=ry=0` としてワーカー呼び出しへ
進む(OFF側は空回り、ON側は窓幅1のボックス平均=恒等コピーになるだけ)。

* **半径の算出は `ぼかし` と全く同じ式**(`disasm_params.py` / `verify_radius_clamp.py`
  で全数一致を確認、マジックナンバーも同一の `0x10624dd3`。
  [`param_scaling.md` §2](../common/param_scaling.md)):
  ```
  rx = ry = 範囲
  縦横比 > 0  ->  ry = trunc(範囲 * (1000 - 縦横比) / 1000)
  縦横比 < 0  ->  rx = trunc(範囲 * (1000 + 縦横比) / 1000)
  ```
* **クランプは `ぼかし` と違い、幅/高さそのものへの単純な独立クランプ**のみ:
  ```
  rx = min(rx, width  // 2)     // *(fpip+0xB4)
  ry = min(ry, height // 2)     // *(fpip+0xB8)
  ```
  `ぼかし` のような hi/lo 分割(半径を2つに割って2パス)は無く、
  各軸1回のワーカー呼び出しで完結する。**キャンバス拡張の呼び出しも
  一切無い** ―― オブジェクトの外接矩形は常にそのままのサイズで、
  変化するのはその中のアルファだけ。
* チェックボックス `check[0]`(`透明度の境界をぼかす`)を見て、
  `exec_multi_thread_func` に渡すワーカーのペアを丸ごと切り替える:
  * OFF(既定)→ `sub_10011c30` → `sub_10011db0`(手順3、幾何学的な角丸め侵食)
  * ON  → `sub_10012060` → `sub_10012200`(手順4、実際のアルファぼかし)

## 3. OFFパス(既定): 幾何学的な角丸め侵食

**ソース画像自身のアルファ値の分布は一切参照せず**、画素の「オブジェクト
外接矩形内での位置」だけから侵食量を計算し、それを元のアルファから引く。
穴が空いた透明部分がすでにあっても、その穴自体は変化しない
(`verify_off_path.py` で実測)。

### 3.1 イージングテーブル

角を丸めるための鍵は、実行時に生成される4097要素のルックアップテーブル
(`0x101dcf78`、シンボル無し、`verify_ease_table.py` で発見・導出):

```
table[i] = trunc(2048 * (1 - cos(i * pi/4096)))     for i = 0..4096
```

このテーブルは `0x1006c680` が生成する3本の共有テーブルの1つで、
`境界ぼかし` 以外の複数のフィルタからも参照される。生成ルーチン・中間点の
浮動小数点誤差・順方向/逆方向参照が同じ配列の左右反転にすぎないことの証明は
[`inspect/common/lut_tables.md`](../common/lut_tables.md) にまとめてある。

### 3.2 縦横それぞれの「軸ランプ」

縦横とも、軸に沿った位置だけで決まる同一形の直線的なランプ(0~4096)を
まず作る。`sub_10011c30`(縦方向)はこれを列ごとに対バッファ
(`*(fpip+0xB0)`)の α チャンネルへ実際に書き込み、`sub_10011db0`
(横方向)は同じ式をその場で計算する(値は書き込まず逆引きテーブルの
インデックスとして使う ― 数学的には同じ計算、詳細は後述):

```
k = 2*r + 1                                       // r = rx または ry
上端/左端: i = 0..r   (r+1回):  val = 4096 - ((r+i+1)*4096) // k
中間:      (length-k) 個:       val = 0                       (k <= length の時だけ実行)
下端/右端: j = 0..r-1 (r回):    val = 4096 - ((k-1-j)*4096) // k
```

縦方向の実装(`sub_10011c30`)では、この3フェーズの書き込みポインタが
単純な加算で連続的に進むだけで、絶対位置から再計算されることは無い。
通常(`k <= length`)は中間フェーズがちょうど埋め合わせるので下端は
「最後の r 個」に正しく着地するが、**軸の長さが偶数かつ半径(クランプ後)が
ちょうど 長さ/2 のとき** `k = length+1 > length` となって中間フェーズの
回数が負(=0回)になり、下端フェーズはポインタが `r+1` 個目から動いて
いないまま追加で r 回書くため、最後の1回が `length` 個目 ―― そのカラムの
バッファの**1個分外**へはみ出す。結果、上端(左端)と下端(右端)のランプが
非対称になる(`verify_off_path.py` で実測、
`simulate_boundary_blur_reference.py --range 4` の
「even-size overrun quirk」でも視認できる)。実害は exedit がバッファを
最大キャンバスサイズで確保しているため通常は無害だが、**上下(左右)非対称の
フェード**という見た目上の副作用は残る。横方向は書き込みポインタを跨がず
その場で計算するので同じ意味でのバッファ外書き込みにはならないが、
数値そのものは縦方向と同じ式で決まるので同じ条件で非対称になる。

### 3.3 縦横の合成 ― `sub_10011db0`

画素ごとに:

```
v = table[縦ランプ値]                           // 手順3.2でバッファBに書かれた値をそのまま引く
h = table[横ランプ値]                            // 横方向はその場で計算(同じ式、逆引きテーブル参照で実装)
dist = trunc(sqrt(v*v + h*h))                    // fild/fsqrt/(切り捨てtrunc、四捨五入ではない)
alpha' = max(元のalpha - 2*dist, 0)
```

`v`・`h` それぞれ単独では単なる直線的な距離だが、テーブルを通した
イージング値の**ユークリッド和(sqrt(v²+h²))**を取ることで、角の部分は
両軸の寄与が重なってより深く侵食され、辺の中央は片方の軸しか効かない
―― これが辺は緩やかに、角は丸く縮む「角丸め侵食」の正体
(`verify_off_path.py` で12x8の矩形を実際に侵食させて確認)。

## 4. ONパス(`透明度の境界をぼかす` 有効): 実アルファのボックスぼかし

OFFパスと異なり、**ソースの α チャンネルそのもの**を2パスのボックス平均で
実際にぼかす。あらかじめ空いていた穴(半透明領域)もちゃんと滲む
(`verify_on_path.py` で実測)。

```
sub_10012060 (縦):   tmp[y][x]  = sum(orig_alpha[y-ry..y+ry][x]) // (2*ry+1)
sub_10012200 (横):   blurred    = sum(tmp[y][x-rx..x+rx])        // (2*rx+1)
```

どちらのパスも、窓が画像外へはみ出す部分は**サンプル数を減らさず常に
フルカーネル幅で割る**―― つまり画像外は透明(0)として数えるゼロ埋め。
`ぼかし` の `サイズ固定` ON 側(生きているサンプル数で正規化)とは異なる。

得られた `blurred`(通常のボックス平均アルファ)は、そのまま出力せず
次の非線形カーブで元のアルファと再合成される(`sub_10012200` 末尾):

```
t = ((元のalpha * blurred) >> 11) - 4096
alpha' = (元のalpha * t) >> 12     if t > 0
       = 0                        otherwise
```

正規化して `a = 元のalpha/4096`, `b = blurred/4096` と置くと
`alpha'/4096 ≈ a * (2ab - 1)`(`b >= 1/(2a)` の時だけ非0)になる。
つまり単純にボックスぼかし結果をそのまま使うのではなく、
**近傍の大半が不透明(`b` が大きい)でなければ急速に0へ落ちる**しきい値的な
カーブを掛け直している。これにより「ただの弱いぼかし」ではなく、
`範囲` にほぼ対応した幅の縁取りフェードになる(`verify_on_path.py` の
`recombine()` 境界値チェックで確認)。

## 5. OFF と ON の違い(まとめ)

| | OFF(既定) | ON(`透明度の境界をぼかす`) |
|---|---|---|
| 参照するのは | オブジェクト内での位置(row,col)のみ | 元画像自身のαチャンネルの値 |
| 内部にすでにある半透明・穴 | 無視される(鋭いまま) | 実際にぼかされて滲む |
| 端の扱い | 幾何学的侵食(位置ベース) | ボックス平均のゼロ埋め |
| 角の形状 | sqrt(v²+h²) による丸い角 | 分離型ボックスぼかしなりの角 |
| 演算コスト源 | ルックアップテーブル + sqrt | 2パスの積分ボックスぼかし + 非線形しきい値カーブ |

いずれも色(y/cb/cr)は一切変更しない。

## 8. 未確定事項

以下は本エフェクト単独ではなく共有 LUT の未確定事項。詳細は
[`lut_tables.md` §6](../common/lut_tables.md) 参照:

* **`0x101daf68` / `0x101def80`(cos 系 / sin 系)の正確な生成式と参照元**。
  `0x101dcf78` のように `.rdata` の実定数から導出したわけではない。

なお「`0x1006c680` の呼び出し元が未特定」だった件は解決している ――
生成ルーチンは **`ノイズ` の `func_init`** で、exedit の効果テーブル初期化
ループ(`0x100315e6`)が起動時に全エントリの `func_init` を呼ぶので、
`境界ぼかし` 側が NULL でも表は埋まる
([`lut_tables.md`](../common/lut_tables.md) 冒頭)。

本エフェクト固有の未確定事項:

* **偶数サイズ・半径=サイズ/2 時のバッファ外書き込みの正確な着地先**。
  `verify_off_path.py`/`simulate_boundary_blur_reference.py` で
  非対称なフェードとしての影響は実測したが、実際に「1行分」の書き込みが
  対バッファのどこに着地するか(隣の列の0行目か、確保領域の未使用末尾か)
  は、対バッファの確保コードまでは追っていないため未確認。挙動そのものが
  クラッシュしないことは exedit が最大キャンバスサイズでバッファを確保する
  設計から推測される(`ぼかし` README の関連する未確定事項と同種の話)。
* 横方向(`rx`)についても縦方向と同じ overrun 条件(`width` が偶数かつ
  `rx` がちょうど `width/2`)が成立するはずだが、`sub_10011db0` は
  横ランプをその場で計算しておりバッファへの書き込みポインタを跨がないため、
  縦方向と全く同じ形の「バッファ外書き込み」にはならない
  (影響は数値のみで、メモリ破壊は起きない)。数値上の非対称自体は
  `edge_ramp()` の共通実装で再現・確認済み。
