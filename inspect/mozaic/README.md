# モザイク (Mosaic) フィルタ リバースエンジニアリング解析

対象: `data/exedit.auf`(AviUtl 拡張編集の標準フィルタプラグイン)、32bit PE、
`ImageBase = 0x10000000`。以下のアドレスはすべて VA(`RVA = VA - 0x10000000`)。

## 再現方法

すべてのスクリプトは本プロジェクトの `main.py` を踏み台にして実行する。
`main.py` はコマンドラインで指定されたスクリプトに対して、DLLパス
(デフォルト `data/exedit.auf`)とヘッダー一覧(デフォルト `data/filter.h`)を
渡す役割を持つ。

```
uv run main.py inspect/mozaic/<script>.py
```

| スクリプト | 確認していること |
|---|---|
| `find_mozaic_addr.py` | `FILTER_DLL` 配列(先頭 `0x100a3e28`)をたどり、`モザイク` の2つの登録エントリ・トラックバー定義・チェックボックスを抽出。両方とも `func_proc = 0x1006b090` を共有 |
| `decompile_mozaic.py` | `0x1006b090` 周辺に絞った `CFGFast` + angr デコンパイル。ループの入れ子構造と整数演算は復元できるが、平均を出す x87 部分は `unsupported instruction` になる |
| `disasm_mozaic.py` | 上記で欠ける部分を含む生逆アセンブル。定数 `4096.0` と3つのグローバルを解決し、`--xref` でそのグローバルがモザイク専用であることを確認 |
| `verify_grid.py` | ブロックグリッドの配置。`(w % (2*size)) / 2` が `(w/2) % size` と恒等であること、つまり**セル境界が必ず画像中心を通る**こと。隙間・重なりなしで敷き詰まることも全数確認 |
| `verify_thread_split.py` | スレッド分割がブロック行を割らないこと、`h >= thread_num` なら完全な分割になること、`h < thread_num` では先頭ブロック行が複数スレッドで重複すること |
| `verify_alpha_average.py` | 平均の取り方。オブジェクト版が**アルファ加重平均**であること、色は `sum_a` で割るのに**アルファだけは画素数で割る**こと、x87 の double 除算が厳密有理数の切り捨てと一致すること |
| `verify_tile_edges.py` | `タイル風` が平均には一切触らず書き戻しだけを変えること。4つの比較の順序(暗が明より優先)、明は輝度のみ・暗は輝度と色差の両方、クランプなし |
| `verify_track_scale.py` | 登録構造体 `+0x74` の exedit 独自拡張ブロックを解読し、`サイズ` の**UI表示値＝生値＝ピクセル数**であることを、表示値が既知のフィルタ(`透明度`/`拡大率`/`発光`)で検算 |
| `simulate_mozaic_reference.py` | 上記すべてを織り込んだ整数忠実リファレンス実装(4経路すべて)。スレッド分割も再現するので `--self-check` で不変性を検査できる |

## 1. 2つの登録エントリとモードの違い

`モザイク` は `FILTER_DLL` として2回登録されており、どちらも
`func_proc = 0x1006b090` を共有する。実行時の分岐は `fp->flag & 0x20` の1点のみ
(`0x1006b0b3 test dl, 0x20`)で、`発光` と同じく**画素フォーマットがそもそも
違う**。

| | オブジェクトのフィルタ効果 | フレーム(映像)フィルタ |
|---|---|---|
| `FILTER_DLL` | `0x100a8858`、`flag=0x20` | `0x100a8980`、`flag=0x00` |
| トラックバー / チェックボックス | 両方とも `サイズ` / `タイル風`(完全に同一) | 同左 |
| 入出力画像 | `*(fpip+0xAC)` | `fpip->ycp_edit` (`+4`) |
| 画素形式 | **8バイト/画素 PIXEL_YCA**(y, cb, cr, **a**) | 6バイト/画素 PIXEL_YC(アルファなし) |
| 行幅 | `*(fpip+0xEC)` [画素] | `fpip->max_w` (`+0x14`) [画素] |
| 幅・高さ | `*(fpip+0xB4)` / `*(fpip+0xB8)` | `fpip->w` (`+0xC`) / `fpip->h` (`+0x10`) |
| ワーカー(`タイル風` オフ) | `sub_1006b180` | `sub_1006b470` |
| ワーカー(`タイル風` オン) | `sub_1006b6b0` | `sub_1006ba40` |

`ぼかし` や `発光` と違い、**作業用バッファを一切使わない**。`ycp_temp` (`+8`) への
アクセスは4つのワーカーのどこにも無く、読み書きは同じバッファに対する完全な
in-place 処理になっている(ブロック単位で「全部読む → 平均を出す →
全部書く」の順序なので、自分が壊した値を読み直すことがない)。
`発光` の `サイズ固定` に相当するオフスクリーン拡張も呼ばない ―
モザイクはオブジェクトの外へにじまないので、キャンバスを広げる必要が無い。

`fpip->frame` (`+0x18`) も `rand()` も参照していないため、同じ入力に対する
出力は完全に決定的で、フレームをまたぐ揺らぎは一切無い。

## 2. パラメータ

トラックバーは `サイズ` 1本(初期値12、範囲1~2000)、チェックボックスは
`タイル風` 1個(初期値オフ)だけ。オブジェクト版とフレーム版で完全に同一。

### `サイズ` の UI 表示値

`発光` の解析では「UI表示値と raw の対応は `exedit.auf` からは確認できない」と
してあるが、これは**コードではなくテーブルに入っている**。`0x100a3e28` の配列が
指す登録構造体は `data/filter.h` の `FILTER` より長く、`+0x74` に exedit 独自の
拡張ブロックへのポインタがある(`verify_track_scale.py`):

```
0x100a88cc (struct + 0x74) -> 0x100a8844
0x100a8844: 0x100a8840 -> int[track_n] = {  1}    表示スケール(生値をこれで割って表示)
            0x00000000                            (モザイクでは NULL)
            0x100a8838 -> int[track_n] = {  1}    スライダーのドラッグ下限
            0x100a883c -> int[track_n] = {200}    スライダーのドラッグ上限
```

スロット `[0]` がスケールであることは推測ではなく、表示値が既知のフィルタで
検算できる ― `透明度`(スケール10、生値0~1000 → 0.0~100.0)、
`拡大率`(スケール100、初期値10000 → 100.00)、`発光` の `強さ`(スケール10、
初期値1000 → 100.0)。いずれも一致する。

したがって **`サイズ` はスケール1、UIに出る数値がそのままブロックの一辺の
ピクセル数**。スライダーで届くのは200までで、それを超える値(201~2000)は
数値入力でのみ指定できる。

参考までに、同じ拡張ブロックを他フィルタにも当てると:

| フィルタ | トラックバー | スケール | UI表示範囲 | ドラッグ範囲 |
|---|---|---|---|---|
| モザイク | `サイズ` | 1 | 1~2000 | 1~200 |
| 発光 | `強さ` / `拡散` / `しきい値` / `拡散速度` | 10 / 1 / 10 / 1 | 0.0~200.0 / 10~2000 / 0.0~200.0 / 0~60 | 0.0~200.0 / 10~800 / 0.0~200.0 / 0~60 |
| ぼかし | `範囲` / `縦横比` / `光の強さ` | 1 / 10 / 1 | 0~1000 / -100.0~100.0 / 0~60 | 0~300 / -100.0~100.0 / 0~60 |
| 境界ぼかし | `範囲` / `縦横比` | 1 / 10 | 0~2000 / -100.0~100.0 | 0~500 / -100.0~100.0 |

### `サイズ = 1` は完全な無処理

```
0x1006b099: cmp eax, 2
0x1006b0a1: jl  0x1006b175   ; -> mov eax,1 ; ret
```

生値が2未満なら画像に触れずに `TRUE` を返す。トラックバーの下限が1なので
UIから到達でき、そのとき「モザイクを掛けているのに何も起きない」ことになる
(1px ブロックは元画像と同じなので結果は正しいが、処理そのものをしていない)。

上限側のクランプは無い。`サイズ` が画像より大きくても弾かれず、手順3の
帰結として 2x2 に分割される。

## 3. ブロックグリッドの配置 ― 画像中心にセル境界が来る

`func_proc` はフレームごとに1回、3つのグローバルを書く。
これらは `0x1006b090`~`0x1006bd26` の外から一切参照されておらず
(`disasm_mozaic.py --xref`)、モザイク専用の状態である。

| グローバル | 内容 |
|---|---|
| `0x101bad24` | `size` = `fp->track[0]` |
| `0x101bad28` | `offset_x` = `(w % (size*2)) / 2` |
| `0x101bad2c` | `offset_y` = `(h % (size*2)) / 2` |

```
0x1006b0b0: lea  esi, [eax + eax]   ; size*2
0x1006b0c0: idiv esi                ; edx = w % (size*2)
0x1006b0c5: sub  eax, edx           ; 符号あり /2 の定型
0x1006b0c7: sar  eax, 1
```

`(w % (2*size)) / 2` は一見すると場当たりな補正値に見えるが、これは
**`(w/2) % size` と恒等**である(`verify_grid.py` で `w=0~4096` ×
`size=2~64` の全数一致を確認済み)。つまりグリッド線は `x ≡ w/2 (mod size)`
の位置に並び、**セル境界が必ず画像中心を通る**。

各ワーカーはこの座標系を

```
for (y = -size; y < h; y += size)      // スレッド分割については手順4
    for (x = -size; x < w; x += size)
        block = [offset_x + x, +size) x [offset_y + y, +size)
        clip to [0,w) x [0,h);  空になったらスキップ
```

の順に走る。`-size` から始めるのは、グリッドが中心基準でずれている以上
一番上・一番左のセルが 0 より手前から始まるため。

この設計の見える帰結が3つある:

* **端の欠けたセルは左右(上下)で同じ幅になる**。あまりが中心対称に分配される。
* **`size` が画像の約数でも1つのセルが2つに割れることがある**。例えば
  `w=36, size=12` は 12×3 ではなく `[6, 12, 12, 6]` の4セルになる
  (`floor(36/12)=3` が奇数なので、中心 x=18 がセルの真ん中ではなく境界に来る)。
* **`size` が画像の半分を超えると、必ず 2x2 の4分割になる**。1枚のベタ塗りには
  決してならない。`1920x1080` で `サイズ=1080` でも `サイズ=2000` でも、
  結果は `960x540` の4ブロックで同じ。

## 4. スレッド分割

`EXFUNC::exec_multi_thread_func`(`exfunc+0xCC`)経由で、
`exec_multi_thread_func(worker, param1=fp, param2=fpip)` として1パス実行する。
各ワーカーの冒頭(`0x1006b186`~`0x1006b1e0`)は自分の担当行を計算する:

```
y_start = ceil(h *  tid      / thread_num / size) * size
y_end   = ceil(h * (tid + 1) / thread_num / size) * size
if (y_start == 0) y_start = -size
```

両端を `size` の倍数に切り上げているのが要点で、これによって
**ブロック行が2つのスレッドに分断されない**。分断されると2つのスレッドが
それぞれ部分ブロックを平均して食い違う値を書き込むことになる。

`if (y_start == 0) y_start = -size` は、中心基準のグリッドで先頭ブロックが
`y = -size` から始まるための補正。ただし判定が `tid == 0` ではなく
**値が 0 かどうか**なので、`h < thread_num` のときは複数のスレッドで
`y_start` が 0 になり、全員が `-size` に書き換えられて**同じ先頭ブロック行を
重複処理する**(`verify_thread_split.py`)。

```
h=2 size=8 thread_num=4:
  tid=0 -> [-8,  0)   tid=1 -> [-8, 8)   tid=2 -> [8, 8)   tid=3 -> [8, 8)
  行 y=-8 を tid=0 と tid=1 が両方処理する
```

書き込む値はどちらもそのブロックの平均なので結果はほぼ一致するが、
一方の書き戻しと他方の読み出しが同期されていないので厳密には競合する。
`h >= thread_num` であれば `h=1..1080` × `size ∈ {2,3,12,64,200}` ×
`thread_num ∈ {1,2,4,8,16,32}` の全組み合わせで、
各ブロック行がちょうど1回ずつ処理されることを確認済み。

## 5. 平均の取り方 ― ここだけがオブジェクト版とフレーム版で本質的に違う

### フレームフィルタ版(`sub_1006b470` / `sub_1006ba40`)

素直な整数平均。3チャンネルの総和を画素数で割るだけ。

```
avg = sum / count            // idiv: 0方向への切り捨て
```

### オブジェクト効果版(`sub_1006b180` / `sub_1006b6b0`)

**アルファ加重平均**になる(`verify_alpha_average.py`)。

```
count = bw * bh                              // 透明画素も数える
for each pixel:
    if (a == 0):  continue                   // 色にもアルファ和にも寄与しない
    sum_y  += (a >= 4096) ? y  : (y  * a) >> 12    // sar: 負の色差では floor
    sum_cb += (a >= 4096) ? cb : (cb * a) >> 12
    sum_cr += (a >= 4096) ? cr : (cr * a) >> 12
    sum_a  += a

if (sum_a == 0):  avg_y = avg_cb = avg_cr = 0
else:             avg_c = trunc(sum_c * 4096.0 / sum_a)   // x87、0方向切り捨て
avg_a = sum_a / count                                     // ← 割る数が違う
```

つまり**色は「プリマルチプライして足し、アルファ総和で割る」正しい
アンプリマルチプライ平均**なのに対し、**アルファだけは画素数で割った素の平均**。
この非対称が、オブジェクトの縁にかかったブロックが
「色は残したまま透明度だけ薄くなる」挙動を生む。もし色も画素数で割っていたら、
縁のブロックは不透明なまま暗く濁っていた。

細かいが結果に効く点:

* **色差の `>>12` は `sar`(floor)、除算は `idiv`/`fistp`(0方向切り捨て)**。
  符号付きの色差に対してこの2つは食い違うので、同じ式の中に両方の丸めが同居する。
* 色の除算は整数ではなく **x87 の double 除算**を通る。`sum * 4096` は最大43bit で
  double に厳密に載るため、丸めが入るのは除算1回だけ。400,000通りの乱数で
  厳密有理数の切り捨てと突き合わせて一致を確認済み。
* `a >= 4096` の分岐は単なる最適化ではない。`data/filter.h` が明記している通り
  画素値は範囲外に出ることがあり、`a > 4096` では色側が `a=4096` 相当で頭打ちに
  なる一方 `sum_a` は生の `a` を積むので、そのブロックだけ暗くなる。
* 全画素が透明なブロックは `sum_a == 0` の分岐で `y=cb=cr=a=0` になる
  (0除算にはならない)。

## 6. `タイル風`

**平均の計算には一切影響しない**。`sub_1006b6b0` / `sub_1006ba40` の集計部分は
`タイル風` オフ版と構造まで同一で、違うのは書き戻しループだけ。各画素を
ブロック内の位置で3種類に分類する(オブジェクト版 `0x1006b962`、
フレーム版 `0x1006bc58`。比較の順序まで同じ):

```
if (x == x_last)  -> DARK           // x_last = offset_x + x + size - 1
if (y == y_last)  -> DARK
if (x == x_first) -> BRIGHT         // x_first = offset_x + x
if (y == y_first) -> BRIGHT
else              -> そのまま

BRIGHT: y  = avg_y  + (avg_y  >> 2)            // 輝度のみ 1.25倍
DARK:   y  = avg_y  - (avg_y  >> 2)            // 輝度   0.75倍
        cb = avg_cb - (avg_cb >> 2)            // 色差も 0.75倍
        cr = avg_cr - (avg_cr >> 2)
alpha:  どの経路でも avg_a をそのまま書く
```

上辺・左辺にハイライト、下辺・右辺にシャドウという古典的なベベル。
要約だけでは取り違えやすい点が4つある(`verify_tile_edges.py`):

* **DARK が先に判定される**。`x_first == x_last` になるセル(幅1px)は
  ハイライトではなくシャドウで塗られる。中心基準のグリッドは端に1px幅の
  セルを実際に作るので、これは机上のケースではない。
* **`x_first`/`x_last` はクリップ前のブロック範囲から作られる**。そのため
  画像の端で切れたセルは、切れた側のベベル線が画像外に落ちて描かれない。
  下の `24x14`、`size=6` の例では、上端の1px行が(`y_last` に当たるので)
  全部 DARK になり、左端の列には BRIGHT が付いていない。
* **BRIGHT は輝度しか触らないが、DARK は色差も落とす**。ハイライトはセルの色を
  保ち、シャドウは灰色寄りに退色する。
* **クランプが無い**(`mov word ptr [ecx], di`)。すでに白いセルの
  ハイライトは `4096 * 1.25 = 5120` と満輝度を超えて書き込まれる。
* `>> 2` は `sar`(floor)なので、**正の小さい値と負の小さい値で挙動が非対称**。
  `0 <= v <= 3` は `v >> 2 == 0` で明暗とも変化しないが、負側は
  `-1 >> 2 == -1` なので `v = -1` でも BRIGHT が `-2`、DARK が `0` になる。
  輝度は負にならないので、これが効くのは色差(DARK)だけ。

```
24x14, size=6  (offset_x=0, offset_y=1)
DDDDDDDDDDDDDDDDDDDDDDDD     B = 輝度 x1.25 (上辺・左辺)
BBBBBDBBBBBDBBBBBDBBBBBD     D = 輝度と色差 x0.75 (下辺・右辺)
B....DB....DB....DB....D     . = 平均そのまま
B....DB....DB....DB....D
B....DB....DB....DB....D
B....DB....DB....DB....D
DDDDDDDDDDDDDDDDDDDDDDDD
BBBBBDBBBBBDBBBBBDBBBBBD
B....DB....DB....DB....D
B....DB....DB....DB....D
B....DB....DB....DB....D
B....DB....DB....DB....D
DDDDDDDDDDDDDDDDDDDDDDDD
BBBBBDBBBBBDBBBBBDBBBBBD
```

アルファを触らないので、`タイル風` はオブジェクトのシルエットや縁の
柔らかさには影響せず、見た目の色だけを変える。

## 9. 未確定事項

* **`h < thread_num` の重複処理**が実害を持つかは未検証。重複するスレッドが
  書く値は同じブロック平均なので通常は同じ結果になるはずだが、
  一方の書き戻し途中に他方が読むと平均が混ざる。AviUtl が実際に使う
  スレッド数と、極小オブジェクトでの再現条件は `exedit.auf` からは分からない。
* **登録構造体 `+0x74` の拡張ブロックのスロット `[1]`**。モザイクでは NULL、
  `透明度`/`拡大率` では全要素0の配列を指しており、既定値と区別が付かないため
  用途を特定できていない。スロット `[0]`(スケール)・`[2]`/`[3]`
  (ドラッグ範囲)は表示値が既知のフィルタで検算済み。
* **最終的な YCbCr→RGB 変換とそのクリップ**は `aviutl.exe` 側にあるため、
  `タイル風` のハイライトが 4096 を超えた分がどう潰れるかは本解析の範囲外。
