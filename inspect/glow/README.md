# グロー (glow) フィルタ リバースエンジニアリング解析

対象: `data/exedit.auf`(AviUtl 拡張編集の標準フィルタプラグイン)、32bit PE、
`ImageBase = 0x10000000`。以下のアドレスはすべて VA(`RVA = VA - 0x10000000`)。

## 再現方法

すべてのスクリプトは本プロジェクトの `main.py` を踏み台にして実行する。
`main.py` はコマンドラインで指定されたスクリプトに対して、DLLパス
(デフォルト `data/exedit.auf`)とヘッダー一覧(デフォルト `data/filter.h`)を
渡す役割を持つ。

```
uv run main.py inspect/glow/<script>.py
uv run main.py tools.<tool>            # エフェクト非依存の共通ツール。一覧はリポジトリ直下の README
```

| スクリプト                     | 確認していること                                                                                                                                                       |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `tools.filter_table --name グロー` | `FILTER_DLL` 配列(先頭 `0x100a3e28`)をたどり、2つの登録エントリ・4本のトラックバー・3つのチェックボックス・8バイトの `ex_data` を抽出。両方とも `func_proc = 0x10054db0` |
| `decompile_glow.py`            | `0x10054db0`〜`0x10058ea0` に絞った `CFGFast` + angr デコンパイル。`グロー` が持つ26関数すべての呼び出し構造                                                               |
| `disasm_params.py`             | 4本のトラックバーが `func_proc` 内でどう変換されるか、およびグローバル `0x101b2010`〜`0x101b203c` の割り当て                                                                |
| `verify_params.py`             | **`強さ` は生値のまま**であること(`func_proc` 内のマジック除算は `しきい値` 用の1個だけ)、`しきい値 = trunc(raw*4096/1000)` が全2001通り一致すること、`通常` の除数 8/6/4/2 |
| `verify_diag_radius.py`        | `0x101b2028` の `sqrt(rx²+ry²)` が**必ず後続のクランプに潰される**こと(全60900組で `min(rx,ry)` と一致)。その結果、斜め光線だけが実距離で約1.41倍伸びること              |
| `verify_extract.py`            | 明部抽出4種の式。`光色=指定なし` はソフトニー付きで**漸近的に恒等写像**、`光色=指定あり` は素のヒンジで光色のYが掛かること                                                 |
| `verify_accumulate.py`         | 全形状が共通で使う「カーネル幅で割らずに `強さ` を掛けて足す」終端処理。輝度8192で頭打ち＋**色差は比を保ったまま再スケール**すること                                        |
| `verify_shapes.py`             | `形状` コンボの6分岐をジャンプテーブル `0x1005551c` とラベル文字列から復元し、8本のストリークワーカーの進行方向を `lea` の形から判定                                       |
| `verify_canvas_growth.py`      | キャンバスが**2回・無条件に**広がること、`サイズ固定` が存在しないこと、フレーム版は代わりに半径をクランプすること                                                        |
| `verify_composite.py`          | 最終合成の3分岐、`光成分のみ` が**不透明なキャンバスを残す**こと、フレーム版が素の16bit加算であること                                                                     |
| `simulate_glow_reference.py`   | 上記すべてを織り込んだ整数忠実リファレンス実装。6形状すべてを ASCII アートで描画し、`通常` のカスケードをパスごとに表示                                                    |

## 1. 2つの登録エントリ

`グロー` は `FILTER_DLL` として2回登録されており、どちらも
`func_proc = 0x10054db0` / `func_WndProc = 0x10058ea0` / `ex_data_def = 0x100a6480`
を共有する。分岐は `fp->flag & 0x20` の1点のみ。構造は `発光` とほぼ同じ
([`filter_registration.md`](../common/filter_registration.md))。

|                | オブジェクトのフィルタ効果                    | フレーム(映像)フィルタ                     |
| -------------- | --------------------------------------------- | ------------------------------------------ |
| `FILTER_DLL`   | `0x100a6528`、`flag=0x20`                     | `0x100a6650`、`flag=0x00`                  |
| チェックボックス | `通常`(=`形状`), `光色の設定`, `光成分のみ`   | `通常`(=`形状`), `光色の設定`              |
| 入力画像       | `*(fpip+0xAC)`、8バイト/画素 PIXEL_YCA        | `fpip->ycp_edit` (`+4`)、6バイト/画素      |
| 行幅           | `*(fpip+0xEC)` [画素]                         | 入力は `fpip->max_w`、作業用は `*(fpip+0xEC)` |
| 幅・高さ       | `*(fpip+0xB4)` / `*(fpip+0xB8)`               | `fpip->w` (`+0xC`) / `fpip->h` (`+0x10`)   |
| 明部バッファ   | グローバルスクラッチ `[0x101a5328]`(`発光` と同じ番地)、**8バイト/画素** | 同左                     |
| 蓄積バッファ   | `*(fpip+0xB0)`、8バイト/画素                  | 同左                                       |
| 最大サイズ     | `0x10196748` / `0x101920e0`(最大キャンバス)   | `0x10178ec0` / `0x101790c8`(**最大フレーム**) |
| 最終合成       | `sub_10058aa0`(`光成分のみ` オフのときだけ)   | `sub_10058de0`(常に実行)                   |

フレーム版が使う `0x10178ec0` / `0x101790c8` は本プロジェクトで初めて出てきた
上限値で、矩形クリア `table[0x48](0x10081f90)` が**6バイト画素のときに選ぶ側**の
グローバルと同じ番地である(`0x10081fd6`)。オブジェクト側の
`0x10196748` / `0x101920e0` と対になる「最大フレームサイズ」とみてよい
([`canvas_growth.md` §1](../common/canvas_growth.md))。

`func_proc` は冒頭に**2つの早期 return** を持つ。`強さ = 0` でも `拡散 = 0` でも
画像にもキャンバスにも一切触れずに `return 1` する(`0x10054dc7` / `0x10054dd9`)。
先頭トラックバー以外にも早期 return があるのは解析済みエフェクトでは本エフェクト
だけ([`param_scaling.md` §3](../common/param_scaling.md))。

## 2. パラメータ

トラックバーは `fp->track[]` の順に `強さ`(初期値400、範囲0~4000)、
`拡散`(30、0~200)、`しきい値`(400、0~2000)、`ぼかし`(1、0~50)。
UI 表示との対応は登録構造体 `+0x74` の拡張ブロックで決まる
([`param_scaling.md`](../common/param_scaling.md)):

| トラックバー | 表示スケール | UI表示範囲 | スライダーで届く範囲 |
| ------------ | ------------ | ---------- | -------------------- |
| `強さ`       | 10           | 0.0~400.0  | 0.0~100.0            |
| `拡散`       | 1            | 0~200      | 0~100                |
| `しきい値`   | 10           | 0.0~200.0  | 0.0~100.0            |
| `ぼかし`     | 1            | 0~50       | 1~10                 |

`func_proc` がこれらに対して行う変換は**1つだけ**:

- **`しきい値`**: `raw * 4096` を全エフェクト共通のマジックナンバー除算
  `0x10624dd3`([`param_scaling.md` §2](../common/param_scaling.md))にかける。
  0方向への切り捨てで `trunc(raw*4096/1000)`。UI 100.0 が満輝度 4096 にあたる。
  クランプは無い(raw=2000 → 8192 で、どの画素も超えられなくなるだけ)。
- **`強さ`**: **変換されない**。`fp->track[0]` がそのまま `0x101b2018` に入り、
  以降は小さい整数倍/整数除算だけを受ける。`func_proc` 全体を走査しても
  マジックナンバー除算は `しきい値` 用の1個しか存在しない
  (`verify_params.py` 第1節)。`発光`・`拡散光`・`閃光` がいずれも
  `強さ` を Q12 に直すのとは違う。
- **`拡散`**: 生値のまま `rx`(`0x101b2024`)と `ry`(`0x101b2020`)の両方になる。
- **`ぼかし`**: 生値のままボックス平均の半径として使われる(手順6)。

### 死んでいる `sqrt`

`func_proc` はこの直後に、このフィルタ唯一の浮動小数点演算をする:

```
0x101b2028 = trunc(sqrt(rx*rx + ry*ry))     // fild / fsqrt / _ftol
...
if (0x101b2028 > rx) 0x101b2028 = rx
if (0x101b2028 > ry) 0x101b2028 = ry
```

`rx` と `ry` は**同じトラックバー**なので `sqrt(2)*d >= d` が常に成り立ち、
`sqrt` の結果は最初のクランプで必ず捨てられる。`0x101b2028` は結局
**`min(rx, ry)` そのもの**である(`verify_diag_radius.py` が到達しうる
全60900組で確認)。

この値は斜めストリーク(手順5)の半径になる。半径は「サンプル数」であって
画素距離ではないので、**斜めの光線だけが実距離で `sqrt(2)` 倍 ―― 約41% ――
長く伸びる**。`クロス(8本)` の8本の腕は等長ではない。

## 3. 明部抽出

`EXFUNC::exec_multi_thread_func`(`exfunc+0xCC`)経由のマルチスレッド1パスで、
入力画像からスクラッチバッファ `[0x101a5328]`(`発光` と同じ番地。`グロー` では
**8バイト/画素**・行幅 `*(fpip+0xEC)` として使う)を作る。式は `光色の設定` で
2つに分かれる(`verify_extract.py`):

- **bit24 セット = 色指定なし(既定)** → `0x10055540`(オブジェクト)/
  `0x100557a0`(フレーム)
  ```
  y, cb, cr = 全部アルファ加重         // オブジェクト版のみ、(c*a)>>12
  b = 0             (y <= T)
    = 2*(y - T)     (T < y < 2T)      // ソフトニー
    = y             (y >= 2T)
  out = (b, c_div(cb*b, y), c_div(cr*b, y), 4096)
  ```
  `y=T` でも `y=2T` でも不連続が無く、明るい画素では**恒等写像に漸近する**。
  つまり `しきい値` は「どこから光るか」を決めるだけで、十分明るい部分の
  明るさは変えない。色差は `b/y` 倍なので**色相と彩度比はそのまま**残る。
- **bit24 クリア = 色を指定済み** → `0x10055690`(オブジェクト)/
  `0x100558e0`(フレーム)
  ```
  y = アルファ加重                     // オブジェクト版のみ。色差は読まない
  d = max(0, y - T)
  out = ((colY*d)>>12, (colCb*d)>>12, (colCr*d)>>12, 4096)
  ```
  ニーが無く、`- T` のオフセットが**そのまま残る**ので、`しきい値` を上げると
  発光全体が暗くなる。さらに光色の Y が掛かるため、暗い光色は効果ごと弱くなる
  ([`rgb_ycbcr.md` §4](../common/rgb_ycbcr.md) と同じ罠)。

どちらも**アルファに 4096 を書き込む**。以降のぼかし・ストリーク・蓄積の
どのワーカーも画素オフセット +6 に書かないので(`verify_composite.py` 第3節が
全ワーカーを走査して確認)、アルファが再び動くのは最終合成だけである。

`光色の設定` の保存形式(`ex_data` 下位24bit = RGB、bit24 = 指定なし)と
BT.601 Q14 の変換ルーチン(`sub_1006fed0` → `sub_1006f520`)は `発光`・`閃光` と
共通 ―― [`rgb_ycbcr.md`](../common/rgb_ycbcr.md)。書き込み先だけが本エフェクト
固有で、Y=`0x101b2030` / Cb=`0x101b202c` / Cr=`0x101b202e`(いずれも int16)。

## 4. 全形状が共通で使う「蓄積」

形状ワーカーが何を合計しようと(列・行・斜め線)、最後は必ずこの形になる。
実体は `sub_10056680` と、`通常` の水平ワーカーにインライン展開された同型
(3フェーズ分で3回)。両者が一致することは乱数20万通りで確認済み
(`verify_accumulate.py`):

```
n.c = ((sum_c >> 4) * strength) >> 10  +  dst.c        // c は y/cb/cr
if n.y > 0x2000:
    n.cb = c_div(n.cb << 13, n.y)
    n.cr = c_div(n.cr << 13, n.y)
    n.y  = 0x2000
dst = n
```

ここに、このフィルタの性格が2つ詰まっている。

- **カーネル幅で割らない。** ボックス*平均*なら `2r+1` で割るところを、
  代わりに `strength / 2^14` を掛けている。したがって**1パスの利得は幅に比例**し、
  `拡散` を上げると発光は広がるだけでなく**明るくなる**。正規化の役割を
  果たしているのは `func_proc` が各パスに渡す `強さ` のスケジュール(手順5)で、
  コードのどこにも「平均」は書かれていない。
- **上限は 4096 ではなく 8192。** 満輝度の2倍で頭打ちになり、超過分は
  色差を `8192/y` 倍して**比を保ったまま**畳む。`発光` は同じ 0x2000 で
  頭打ちにするが色差を**白へ退色**させる([`発光` §4](../luminous/README.md))ので、
  飽和した発光の見え方が正反対になる ―― `グロー` は色を保ち、`発光` は白く飛ぶ。

色差の書き戻しは int16 でクランプ無し。飽和時の色差は `8192 * (Cb/Y)` なので、
`|Cb| > 4Y` になる色 ―― BT.601 では純青の近傍だけ(`#0000ff` で `|Cb|/Y = 4.39`)
―― は**折り返して符号が反転する**(`verify_accumulate.py` 第4節)。

## 5. `形状` ―― 6択のコンボボックス

`check[0]` は `check_default = -2` なのでチェックボックスではなくコンボボックス
(実体は `ex_data.type` = `dword[1]`)。ラベルは `0x100a6790` から始まる連続した
cp932 文字列6つ、静的テキスト `形状` は `0x100a67d4`。`func_proc` は
`0x100551a3` の `jmp [eax*4 + 0x1005551c]` で分岐し、**範囲外なら `return 0`**
(= 何もしなかった)。ジャンプテーブルとラベルの対応は `verify_shapes.py` が
バイナリから復元する。

| `type` | ラベル           | ワーカー                                                     |
| ------ | ---------------- | ------------------------------------------------------------ |
| 0      | `通常`           | `0x10055a10` + `0x10055ed0` を4回(手順5.1)                   |
| 1      | `クロス(4本)`    | `0x10056220`(縦)、`0x100569e0`(横)                           |
| 2      | `クロス(4本斜め)`| `0x100570d0`、`0x10057730`、`0x10057d90`、`0x10058430`       |
| 3      | `クロス(8本)`    | 上記6本すべて(1と2を順に実行するだけで、共用の最適化は無い) |
| 4      | `ライン(横)`     | `0x100569e0`                                                 |
| 5      | `ライン(縦)`     | `0x10056220`                                                 |

### 5.1 `通常` ―― 4パスのカスケード

蓄積バッファ `A`(= `*(fpip+0xB0)`)は switch の手前で
`table[0x48](A, 0, 0, w+2rx, h+2ry, 0, 0, 0, 0x1000, 2)` によって
**不透明な黒**(y=cb=cr=0, a=4096)で埋められる。`通常` はまずスクラッチの
抽出結果を `table[0x44]` で `A` の `(rx, ry)` へ単純コピー(`0x13000003`)し、
そこから:

```
strength = 強さ * 6
for divisor in (8, 6, 4, 2):
    r = c_div(rx, divisor)
    垂直ボックス平均  A -> S   (半径 r、除数 2r+1、半径は H でクランプ)
    if 初回: table[0x48] で A を再びクリア
    水平ボックス和    S -> A   (半径 r、割らずに strength を掛けて A へ加算)
    strength = c_div(strength, 2)
```

**垂直パスが読むのは `A` ―― つまり直前までの蓄積結果そのもの**なので、
パス N+1 はパス N の出力をさらにぼかす。単なるマルチスケールの和ではなく
**カスケード**である(`発光` の6パスも連鎖するが、あちらは
`ycp_temp` と蓄積バッファが別々だった)。

1パスの利得は `(2r+1) * strength / 2^14` なので、4パスの相対比は
おおよそ **1.5 : 1.0 : 0.75 : 0.75**(`verify_params.py` 第3b節)。
狭い前半のパスのほうが重い。

なお水平ワーカー `0x10055ed0` だけは**半径をクランプしない**。`通常` では
`r <= rx` かつ `W = w + 2rx >= 2rx + 1` なので安全だが、垂直ワーカーが
`H` でクランプし `ぼかし` 用の水平ワーカー `0x10055c70` が `W` でクランプする
のとは非対称である。

### 5.2 ストリーク5種 ―― 3スケールを重ねる

`ライン`/`クロス` 系のワーカーはスクラッチを**直接**読み、`(rx, ry)` ずらして
`A` へ加算する(`通常` のような事前コピーは無い)。1本のワーカーは
**同じ線を半径を変えて3回**走る:

| 呼び出し | 半径          | `strength` | 合計利得 |
| -------- | ------------- | ---------- | -------- |
| インライン | `r`         | `強さ`     | `2r * 強さ / 2^14` |
| インライン | `c_div(r,2)` | `強さ * 2` | 同じ     |
| ヘルパー   | `c_div(r,4)` | `強さ * 4` | 同じ     |

**3スケールの利得が等しい**のがこの形の狙いで、細く明るい芯と広い暈が同時に
できる(`verify_params.py` 第3c節)。半径 `r` と `r/2` はワーカー本体に
インライン展開され、`r/4` だけがヘルパー呼び出しになっている。ヘルパーは
方向ごとに別関数(`0x10056700` / `0x10056e00` / `0x10057410` / `0x10057a70` /
`0x10058100` / `0x10058780`)だが中身は同型で、除数 `4` を第4引数で受け取る
(`sub(線の番号, 線の長さ, 行幅, 4)`)。ワーカーは**スクラッチしか読まない**ので
3スケールの間に連鎖は無い。

半径の出どころは方向で違う: 縦は `ry`、横は `rx`、斜めは
`0x101b2028 = min(rx, ry)`(手順2)。各線について**自分の長さでクランプ**
(`2r+1 > len` なら `r = c_div(len-1, 2)`)されるので、短い斜め線ほど半径が
自動的に縮む。

走査方向は `lea` の形1つで決まる(`verify_shapes.py` 第2節):

| ワーカー     | ステップ            | 進む向き | 担当する線                       |
| ------------ | ------------------- | -------- | -------------------------------- |
| `0x10056220` | `stride*8`          | `( 0,+1)`| 各列 `x = 0..w-1`                |
| `0x100569e0` | `+8`                | `(+1, 0)`| 各行 `y = 0..h-1`                |
| `0x100570d0` | `stride*8 + 8`      | `(+1,+1)`| 左端から: `(0, y)`, `y = 0..h-1` |
| `0x10057730` | `stride*8 + 8`      | `(+1,+1)`| 上端から: `(x, 0)`, `x = 1..w-1` |
| `0x10057d90` | `stride*8 - 8`      | `(-1,+1)`| 右端から: `(w-1, y)`, `y = 1..h-1` |
| `0x10058430` | `stride*8 - 8`      | `(-1,+1)`| 上端から: `(x, 0)`, `x = 0..w-1` |

各方向で片方のワーカーだけが開始インデックスを 1 に押し上げる
(`test esi,esi; jne; mov esi,1`)ので、両者が共有する角の対角線は1回しか
描かれない。

各線は `長さ + 2r` 画素ぶん書かれ、書き始めは線の起点の `r` ステップ**手前**
(= キャンバス側の余白の中)である。ウィンドウは常に線内のサンプルだけを含む
ゼロ埋めボックス。

## 6. `ぼかし` ―― 後段の仕上げ

形状が終わったあと、`ぼかし`(`fp->track[3]`)が 0 より大きければ

```
垂直ボックス平均 (0x10055a10)  A -> S
水平ボックス平均 (0x10055c70)  S -> A
垂直ボックス平均              A -> S
水平ボックス平均              S -> A
```

の2ラウンドが走る。どちらも**カーネル幅で割る素のボックス平均**で `強さ` は
関与しない。box⊛box = 三角形カーネルなので、`ぼかし = r` は片側 `2r` 画素の
三角形の暈になる([`box_blur.md` §2](../common/box_blur.md))。
`ぼかし = 0` はこのブロックごとスキップされる。

## 7. キャンバスの拡張 ―― 2回、しかも止められない

`グロー` には `サイズ固定` が無い(`verify_canvas_growth.py` 第1節が
`ぼかし`/`拡散光`/`発光`/`閃光` との対比を出す)。オブジェクト効果版は
2つの理由で2回広がる。

**拡張1 ―― カーネルを収める**(`0x10054f11`、条件付き)。
スライディングウィンドウは `2r+1 <= 寸法` を要求するので
([`box_blur.md` §4](../common/box_blur.md))、足りなければ
[`canvas_growth.md` §3](../common/canvas_growth.md) の方式Bで先に広げる:

```
if (2*rx+1 > w || 2*ry+1 > h):
    bx = c_div(2*rx + 2 - w, 2);  by = c_div(2*ry + 2 - h, 2)
    if (w + (rx+bx)*2 > 最大幅)  bx = c_div(最大幅 - 2*rx - w, 2)      // 最終サイズで判定
    if (h + (ry+by)*2 > 最大高)  by = c_div(最大高 - 2*ry - h, 2)
    bx = max(bx, 0);  by = max(by, 0)
    table[0x48](fpip+0xB0, 0, 0, w+2bx, h+2by, 0,0,0, 0, 2)            // 完全に透明
    table[0x44](fpip+0xB0, bx, by, fpip+0xAC, 0,0, w, h, 0, 0x13000003)
    swap(fpip+0xAC, fpip+0xB0);  w += 2*bx;  h += 2*by
```

**拡張2 ―― 発光そのものの余白**(`0x100554a3`、無条件)。蓄積バッファは
`(w+2rx, h+2ry)` で確保・クリアされ、全ワーカーが `(rx, ry)` ずらして書くので、
最後に必ず `w += 2*rx; h += 2*ry` される。

結果として**`拡散` は常にオブジェクトの外接矩形を変える**。`ライン(横)` で
横方向にしか光らせていなくても、上下に `拡散` 画素の透明な余白が付く。

フレームフィルタ版にはキャンバスが無いので、代わりに半径を
`rx = c_div(w-1, 2)` / `ry = c_div(h-1, 2)` でクランプする(`0x10055072`)。
`発光` と同じ回避策である。

なお `rx`/`ry` は拡張1より前に**最大サイズで先に切り詰められる**
(`0x10054e43` / `0x10054ea9`)ので、最大キャンバスに近い巨大オブジェクトでは
発光が端で切れるのではなく**発光そのものが細くなる**。

## 8. 合成

### オブジェクト効果版 `sub_10058aa0`

蓄積バッファは、この時点では画像ではない ―― 色はプリマルチプライされた発光、
アルファは `table[0x48]` が置いた 4096 のままである。このワーカーが
PIXEL_YCA へ直す。元画像の有無で3分岐(`verify_composite.py`):

```
// (a) 元画像が無い画素 ―― 2rx x 2ry の余白、および src.a <= 0
if g.y <= 0:   dst = (0, 0, 0, 0)
else:          a = min(g.y, 4096)
               dst = (c_div(g.y<<12, a), c_div(g.cb<<12, a), c_div(g.cr<<12, a), a)

// (b) 元画像が不透明 (src.a >= 4096)
dst.y += src.y;  dst.cb += src.cb;  dst.cr += src.cr;  dst.a = src.a

// (c) 半透明 (0 < src.a < 4096)
na = min(g.y + src.a, 4096)
dst.c = c_div(src.c * src.a + (g.c << 12), na)      // y/cb/cr 共通
dst.a = na
```

(a) は `閃光` の終端と同じ**アンプリマルチプライ**で、
**発光の輝度がそのままアルファになる**([`閃光` §5](../glint/README.md))。
(b)(c) は `発光` の合成と同じ式だが**役割が逆**で、あちらは発光がソース・
画像がデスティネーションだったのに対し、ここでは発光がデスティネーション
([`発光` §6](../luminous/README.md))。アルファの合成が `a + b - a*b` ではなく
**単純な和を 4096 でクランプ**する点は共通である。

(a) の割り算は色差を `4096/a` 倍する。発光のいちばん外側では `a` が1桁なので、
蓄積時の `sar 4` が落とした端数がそのまま数千倍に増幅され、彩度の高い光色では
int16 を溢れることがある(`verify_composite.py` 第1b節)。

### `光成分のみ`(オブジェクト版のみ)

`check[2]` が非0なら **`sub_10058aa0` を丸ごと飛ばす**(`0x1005548e`)。
アルファを書くのはこのワーカーと明部抽出だけなので、蓄積バッファは
`table[0x48]` が置いた **a=4096 のまま**出力される。つまり
`光成分のみ` の結果は「透明な発光レイヤー」ではなく、
**不透明な黒地に発光が乗ったキャンバス**である。加算合成の素材としては
そのまま使えるが、通常合成では黒い矩形として見える。

### フレームフィルタ版 `sub_10058de0`

アルファが無いので、蓄積バッファの `(rx, ry)` 以降を読んで元フレームへ
`add word ptr` するだけ。クランプもしきい値も無く、余白は捨てられる。
