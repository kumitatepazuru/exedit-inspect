# モーションブラー (motion blur) フィルタ リバースエンジニアリング解析

対象: `data/exedit.auf`(AviUtl 拡張編集の標準フィルタプラグイン)、32bit PE、
`ImageBase = 0x10000000`。以下のアドレスはすべて VA(`RVA = VA - 0x10000000`)。

## 再現方法

```
uv run main.py inspect/motion_blur/<script>.py
uv run main.py tools.<tool>            # エフェクト非依存の共通ツール。一覧はリポジトリ直下の README
```

| `decompile_motion_blur.py`             | `func_proc` とワーカー3本を range 限定デコンパイル。時間を巻き戻すループとコア側ルーチンの呼び出し構造                                             |
| `disasm_params.py`                     | `func_proc` とワーカー3本、`0x1000ad80` の**全命令**に注釈                                                                                          |

## 1. 何をするエフェクトか

**画素ではなく時間を入力にする**エフェクトで、本プロジェクトでは
[`フェード`](../fade/README.md) / [`ワイプ`](../wipe/README.md) に次ぐ3例目。
ただしこの2つが「時刻から係数を1つ作る」だけなのに対し、
`モーションブラー` は **`fpip` の時計を巻き戻して exedit 本体に
「その時刻でもう一度描いてくれ」と頼む**。時計を動かすエフェクトは
これ1つだけである([`object_time.md` §7](../common/object_time.md))。

やっていることは:

```
毎フレーム、分解能 回:
    t = i == 0 ? 現在 : 現在 - 1 + i/分解能
    その時刻でオブジェクトを描き直す
    蓄積バッファ = (A·蓄積バッファ + (4096-A)·描き直した画像) / 4096
出力 = 蓄積バッファ                      (残像 OFF)
     = 描き直した画像 を蓄積バッファの上に置いたもの   (残像 ON)
```

つまり**サブフレーム標本の指数移動平均**である。蓄積バッファは名前付き
キャッシュに置かれてフレームをまたいで生き残るので、**尻尾は1フレームでは
終わらない**(手順5)。

## 2. 登録2個

`func_proc` は共有(`0x1006bd30`)、分岐は `fp->flag & 0x20`。

| 項目             | オブジェクト効果                         | フレームフィルタ         |
| ---------------- | ---------------------------------------- | ------------------------ |
| `FILTER_DLL`     | `0x100a8b18`、`flag=0x20`                | `0x100a8c40`、`flag=0x00` |
| チェックボックス | `残像` / `オフスクリーン描画` / `出力時に分解能を上げる` | `出力時に分解能を上げる` のみ |
| 描き直し         | `0x1004b200`(別オブジェクトとして描画)  | `0x1004ccf0`(指定時刻のフレームを描く) |
| ワーカー         | `0x1006c0d0`(`残像` ON)/ `0x1006c2e0`(OFF) | `0x1006c500`          |
| 蓄積バッファ     | 8バイト/画素、`w` 詰め                   | 6バイト/画素、`w` 詰め   |

フレーム側は「オブジェクト側の配列の途中を指す」定型
([`filter_registration.md` §2](../common/filter_registration.md))ではなく、
**自前の1要素 `check_name` 配列**(`0x100a8af8`、オブジェクト側の配列の
すぐ手前)を持ち、同じ文字列を指している。`check_default` に至っては
`.rdata` ではなく**書き換え可能な `.data` のゼロ dword**(`0x101bad44`、
このエフェクトのグローバル群の隣)を指す(`verify_registration.py` §1)。

エフェクト固有コードは `0x1006bd30`-`0x1006c64f` の **2336 バイト・4関数**。
画素を触るコードより exedit のコア側を呼ぶコードのほうが目立ち、
直接呼び出しは6本ある(手順7)。

## 3. パラメータ

| トラックバー | 生値の範囲 | 既定 | 意味                                        |
| ------------ | ---------- | ---- | ------------------------------------------- |
| `間隔`       | 0~100      | 1    | **尻尾の長さ**。おおよそ `間隔/3.14` フレーム |
| `分解能`     | 1~25       | 10   | **1フレームを何等分してサンプルするか**     |

どちらも表示スケール 1(生値がそのまま UI の数値)。**`+0x74` の
スライダードラッグ範囲を持たない**ので、スライダーは生値の範囲そのままで
動く(`verify_registration.py` §2)。

チェックボックス:

| 名前                     | 既定 | 効果                                                       |
| ------------------------ | ---- | ---------------------------------------------------------- |
| `残像`                   | OFF  | 現在の姿を前面に残し、尻尾だけを背後に置く(手順6)        |
| `オフスクリーン描画`     | **ON** | 描き直しの前にオフスクリーン描画を1回通す(手順7)        |
| `出力時に分解能を上げる` | OFF  | 出力中(`g_101a52e4 != 0`)は `分解能` を **100** に上書き   |

## 4. サンプルする時刻 ―― `分解能` が決めるもの

ループは `分解能` 回まわり、各周回で `fpip` の**3つの時刻フィールドを同時に**
巻き戻す(`verify_timeline.py` §3):

```
i = 0                  巻き戻さない(= 現在のフレーム)
i = 1..分解能-1        fpip[0x114] += i·100/分解能      // 1/100 フレームの端数
                       fpip[0x1C]--                     // fpip->frame
                       fpip[0xA8]--                     // 絶対フレーム
                       描き直す
                       3本とも元に戻す
```

サンプルする時刻は `{現在} ∪ {現在 - 1 + i/分解能}`、つまり**直前の
1フレームを `分解能` 等分した点**になる。`間隔` はこの計算に一切出てこない。

| `分解能` | 処理順(現在を 0 とする相対フレーム)                        |
| -------- | ------------------------------------------------------------ |
| 4        | `+0.00 → -0.75 → -0.50 → -0.25`                            |
| 10       | `+0.00 → -0.90 → -0.80 → … → -0.10`                       |

**処理順が時刻順ではない**点が効く。ワーカーは指数移動平均なので
**最後に処理したサンプルが最も重く**、いちばん軽いのが最初に処理する
現在のフレームそのものになる。

`i = 0` は**描き直しを行わない**(`0x1006bf7d: je 0x1006c02d`)。
`*(fpip+0xAC)`、つまり通常の経路でこのフィルタに渡ってきた画像を
そのまま入力として使う。描き直した画像と同じワーカーへ同じ扱いで流れる
ので、**描き直しが返すのも「motion blur の入力と同じ表現の画像」**
だと分かる(手順7)。

端数は `trunc(i·100/分解能)` で `fpip+0x114` が 1/100 フレーム単位
([`object_time.md` §1](../common/object_time.md))なので、
**サブフレーム位置は 1/100 フレームに量子化される**。`分解能` が
1 / 2 / 4 / 5 / 10 / 20 / 25 と 100 のときだけ厳密な等分で、たとえば
`分解能 = 3` は `-0.67 / -0.34`、`分解能 = 7` は
`-0.86 / -0.72 / -0.58 / -0.43 / -0.29 / -0.15` と少し不等間隔になる。

3本を同時に動かしていることは、`object_time.md` §1 の「`fpip+0x1C` /
`+0xA8` / `+0x114` は1つの時計の別表現」を直接裏付ける。

## 5. `間隔` が決めるもの ―― 指数移動平均の減衰係数

`func_proc` が作る係数はこれ1つだけ:

```
n = 間隔 × 分解能
A = trunc(4096 - 4096/(1 + n·(1/3.14)))  =  trunc(4096·n/(n + 3.14))
B = 4096 - A
```

定数 `0x1009a748` は `1/3.14` で、**π そのものではなく2桁近似**である。

| `間隔`(`分解能=10`) | 0 | 1 | 2 | 5 | 10 | 30 | 100 |
| -------------------- | - | - | - | - | -- | -- | --- |
| `A`                  | 0 | 3117 | 3540 | 3853 | 3971 | 4053 | 4083 |
| `B`                  | 4096 | 979 | 556 | 243 | 125 | 43 | 13 |

指数移動平均の時定数は `τ = 1/(1 - A/4096)` サブフレーム、フレーム単位では

```
τ[フレーム] = 1/分解能 + 間隔/3.14
```

(`verify_weight.py` §3、A の量子化ぶん 2% 以内で一致)。つまり:

- **`間隔` が尻尾の長さ**を決める。`間隔 = 1` で 0.42 フレーム、
  `間隔 = 10` で 3.3 フレーム、`間隔 = 100` で 31.5 フレーム。
- **`分解能` は尻尾の長さにほとんど効かない**(`1/分解能` フレームぶんだけ)。
  `n = 間隔 × 分解能` という形で `分解能` を `A` に押し込むことで、
  サンプル数が増えても1フレームあたりの減衰が変わらないようにしてある。
  `分解能` が決めるのは**なめらかさ**である。
- **`間隔 = 0` は `A = 0`** ―― 蓄積を毎回捨てるので何もしないのと同じ。

### オブジェクトの端では `A` が縮む

`func_proc` は同じ式を2回追加で評価し、小さいほうを採る:

```
経過 = fpip->frame          // オブジェクト開始からのフレーム数
残り = fp[0x11C] - fpip[0xA8]  // 終了までのフレーム数
経過 < 間隔 なら A = min(A, weight(経過 × 分解能))
残り < 間隔 なら A = min(A, weight(残り × 分解能))
```

**尻尾がオブジェクトの外へはみ出さない**ようにするためで、開始フレーム
(経過 = 0)では `A = 0`、そこから `間隔` フレームかけて本来の値まで
立ち上がる。終了側も対称に縮む(`verify_weight.py` §5)。

### キャッシュが新規なら `A = 0`

蓄積バッファはキー `"*cache%08x[%d]_%dx%d@%d"`(`fp+0xE4`, 種別,
`w`, `h`, `fpip+0x11C`)の名前付きキャッシュ `0x1004d7d0` から取る。
戻り値の第6引数が「既にあったか」を返し、**新規なら `A = 0`** ――
そのフレームは蓄積を捨てる。`w`/`h` が変わるとキーも変わるので、
サイズが変わった直後も同じことが起きる。

## 6. ワーカー ―― `残像` が変えるのは出力先だけ

3本とも「蓄積 と 入力 を `A : B` で混ぜて、蓄積へ書き戻す」ところまでは
同じで、違うのは**出力画像へどう書くか**だけである。

オブジェクト版(8バイト/画素):

```
mixed = ( A·prem(蓄積) + B·prem(入力) ) / (A·a_acc/4096 + B·a_src/4096)
        // prem(p) = a>=4096 ? c : (c·a)>>12。色は sum_a で割り戻す

残像 OFF (0x1006c2e0):  出力[x] = mixed
残像 ON  (0x1006c0d0):  出力[x] = composite_under(出力[x], mixed)
どちらも:               蓄積[x] = mixed
```

`composite_under` は `0x1000ad80` で、**ブレンド関数テーブル
`0x1009fbb0` の `0x12` 番**である(`verify_registration.py` §5)。
[`blend_modes.md` §3](../common/blend_modes.md) が読んでいた
`0x00`(通常)/ `0x11`(加算)/ `0x13`(単純コピー)/ `0x02`(減算)に続く
5本目で、式は `0x10007df0`(通常合成)の src / dst を入れ替えた形 ――
**引数の画素を転送先の「下」に置く**。モード語で言えば `0x12000003`。

したがって `残像` の意味は:

| `残像` | 出力                                     | 見え方                             |
| ------ | ---------------------------------------- | ---------------------------------- |
| OFF    | 蓄積そのもの                             | オブジェクト自身がブレて薄くなる。**完全に不透明な画素が残らない** |
| ON     | 最後に描き直した姿 の**下**に蓄積を置く | 現在の姿はくっきりしたまま、後ろに尻尾が付く |

24x9 で四角を動かした実測(`間隔=2`, `分解能=10`、3フレーム後):
OFF はアルファの最大が 2355 までしか届かないのに対し、ON は現在位置が
4096 のまま(`simulate_motion_blur_reference.py` §2/§3)。

なお `残像 ON` で最後に前面へ残るのは **`i = 分解能-1` のサンプル**、つまり
`現在 - 1/分解能` の姿であって現在フレームそのものではない ―― ループの
処理順(§4)と、`0x1004b200` が `*(fpip+0xAC)` を毎回上書きするという前提
からの帰結である。後者は未確認(手順10)。

### フレーム版だけ四捨五入する

フレーム版(6バイト/画素)はアルファが無いので素の加重平均だが、
**`+0x800` の四捨五入項がある**:

```
out = (入力·B + 蓄積·A + 0x800) >> 12
```

オブジェクト版にはこの項が無く、`idiv` の 0方向切り捨てになる。

## 7. 無限再帰をどう止めているか

描き直し(`0x1004b200` / `0x1004ccf0`)はオブジェクトを一から描き直すので、
**その中でこのエフェクト自身がもう一度走りうる**。放っておけば
「1フレーム前を描くために2フレーム前を描く」の無限後退になる。
止め方は1つではなく、**描き直しの経路3本それぞれに別々の仕掛けがある**
(`verify_registration.py` §7)。

| # | 条件                                        | 描き直しの呼び出し                    | 素性を渡すか | 止め方                            |
| - | ------------------------------------------- | ------------------------------------- | ------------ | --------------------------------- |
| 1 | オブジェクト・`オフスクリーン描画` ON(既定) | `0x1004b200(objID, fpip, 0)`          | 渡さない     | グローバル再入フラグ `g_101bad48` |
| 2 | オブジェクト・`オフスクリーン描画` OFF      | `0x1004b200(objID, fpip, fp->0xE4)`   | **第3引数**  | 呼び出し先が止める(**推定**)     |
| 3 | フレームフィルタ                            | `0x1004ccf0(fp->0xE4, fpip, …)`       | **第1引数**  | 同上(**推定**)                   |

`fp+0xE4` は `(通し番号<<16) | 添字+1`、つまり**エフェクト列の中でのこの
フィルタ自身の位置**である。呼び出し位置は順に `0x1006bfd3` /
`0x1006bfef` / `0x1006c07b`。

### 経路1 ―― 再入フラグ

`func_proc` の先頭にある、このエフェクト特有の仕掛け:

```
if ((fp->flag & 0x20) && check[1]) {          // オフスクリーン描画
    if (g_101bad48 != 0) {                    // 自分が張ったループの中
        fpip->flag |= 0x800
        [0x100b8c60](fp, fpip)                // = オフスクリーン描画の func_proc
        fpip->flag = 元に戻す
        return 0                              // エフェクト列をここで打ち切る
    }
    if ([0x100b8c60](fp, fpip) == 0) return 0
}
```

`g_101bad48` は描き直しの呼び出しを挟んで 1 にされる再入フラグである
(`0x1006bfc9` で 1、`0x1006bfd8` で 0)。つまり:

- **通常の呼び出し**では `オフスクリーン描画`(`0x1008a520`、
  [`canvas_growth.md` §4](../common/canvas_growth.md) の方式C)を1回通してから
  本体へ進む。
- **描き直しの中で自分自身が再び呼ばれたとき**は、オフスクリーン描画だけを
  `fpip->flag |= 0x800` 付きで実行して `return 0` ―― そこで止まる。

`func_proc` が `1` 以外を返すとそのオブジェクトのエフェクト列が打ち切られる
([`フェード` §5](../fade/README.md))ので、`return 0` は
「この描き直しではここまで」を意味する。**再帰の深さはきっちり1段**で、
描き直しが返すのは
**「このエフェクトの手前までのフィルタ + オフスクリーン描画1回」を掛けた姿**
になる。§4 の `i = 0` が描き直しを省いて `*(fpip+0xAC)` をそのまま使うのは
これと辻褄が合う ―― どちらのサンプルも「motion blur の入力」という同じ
表現でワーカーへ渡る。

`fpip->flag` の bit11(`0x800`)の意味は未追跡(手順9)。

### 経路2・経路3 ―― ガードが無い

先頭のガードは `fp->flag & 0x20` と `check[1]` の**両方**が真のときしか
効かない(`0x1006bd41` / `0x1006bd4b` はどちらもガードを飛ばして
`0x1006bd8b` へ行く)。`g_101bad48` の `.text` 参照が読み1・書き2の
**3箇所しかない**ことも、残り2経路が再入フラグをまったく使っていないことを
示している。

代わりにこの2経路は、描画ルーチンへ `fp->0xE4` を渡している ――
経路2 は第3引数として、経路3 は第1引数として。`fp->0xE4` は
`0x1006bf16` で読んで `0x1006bf1d` の `mov [esp+0x18], eax` で退避され、
`add esp, 4` 後のループ本体からは `[esp+0x14]` として見える。

**ガードが無い以上、`0x1004b200` / `0x1004ccf0` がこの ID を
「エフェクト列をここまでで止めろ」として解釈していなければ無限再帰する。**
実機がそうならない以上そう解釈されていると読めるが、これは**逆算であって
直接の確認ではない**(両ルーチンの中身は未読、手順10)。
`シャドー` が同じ `0x1004b200` を `(fp+0xE4, fpip, 0x10fffff)` で呼ぶ
([`シャドー` §11](../shadow/README.md))のと引数の並びが違う点も未解決。

### 尻尾が1フレームより長い理由は再帰ではない

再帰が1段で止まるので、**過去に遡って読むのは常に直前の1フレームだけ**
(§4)。それでも尻尾が何フレームも伸びるのは、蓄積バッファが名前付き
キャッシュでフレームをまたいで生き残るからである(§5)。履歴は時間軸では
なくバッファに溜まっている。副作用として、キーが
`(fp+0xE4, 種別, w, h, fpip+0x11C)` なので**キャンバスサイズが変わると
履歴ごと捨てられて `A = 0`** になる。

## 9. 参照テーブル

`間隔` → 減衰と尻尾(`分解能 = 10`、オブジェクトの中ほど):

| `間隔` | `A` | `B` | τ[フレーム] | τ·ln2 | 実測の半減期 |
| ------ | --- | --- | ----------- | ----- | ------------ |
| 0      | 0    | 4096 | 0.10 | 0.07 | ―(何もしない) |
| 1      | 3117 | 979  | 0.42 | 0.29 | 1 フレーム   |
| 2      | 3540 | 556  | 0.74 | 0.51 | 1 フレーム   |
| 5      | 3853 | 243  | 1.69 | 1.17 | 2 フレーム   |
| 10     | 3971 | 125  | 3.28 | 2.27 | 3 フレーム   |
| 20     | 4032 | 64   | 6.40 | 4.44 | 5 フレーム   |
| 100    | 4083 | 13   | 31.5 | 21.8 | **7 フレーム** |

**`間隔` を上げると、実測の尻尾は τ の予想よりずっと短くなる。**
蓄積の更新が `(x·A) >> 12` の切り捨てなので、アルファが小さいところでは
1回あたり最大 1 ずつ余計に減る。`間隔 = 100` では1フレームあたり
10 サブサンプル × 1 = 10 の定額減衰が、指数の 0.3% 減衰(アルファ 122 で
0.4)を一桁上回ってしまう ―― **尻尾の末端は指数ではなく線形に消える**。

`出力時に分解能を上げる`(`分解能` 10 → 100):

| `間隔` | プレビュー `A` / τ | 出力 `A` / τ |
| ------ | ------------------ | ------------- |
| 1      | 3117 / 0.42f       | 3971 / 0.33f  |
| 10     | 3971 / 3.28f       | 4083 / 3.15f  |

尻尾の長さはほぼ変わらず、サンプルが10倍細かくなる。

## 10. 未確定事項

- **exedit コア側の4本(`0x1004d7d0` / `0x1004b200` / `0x1004ccf0` /
  `0x1002b0d0`)の中身は読んでいない。** `simulate_motion_blur_reference.py`
  が「時刻を渡すと画像を返す関数」を外から与える形になっているのは
  このためで、**再現できているのはワーカーとループだけ**である。
- **描き直しへ渡す `fp->0xE4` が「エフェクト列をここまでで止めろ」の意味か。**
  `オフスクリーン描画` OFF の経路(`0x1006bfe4`)とフレーム版(`0x1006c06b`)は
  再入ガードを持たないので、そう解釈されていなければ無限再帰する ―― という
  逆算でそう読んでいるだけで、`0x1004b200` / `0x1004ccf0` の側は未確認(§7)。
  `シャドー` が同じ `0x1004b200` に渡す `0x10fffff`
  ([`シャドー` §11](../shadow/README.md))との関係も不明で、そもそも
  引数の並び(`シャドー` は第1引数に `fp+0xE4`、`モーションブラー` は
  `0x1002b0d0` が返すオブジェクト添字+1)が食い違っている。
  **この引数の意味が分かれば再帰停止の仕組みが確定する。**
- **`fpip->flag` bit11(`0x800`)の意味。** 再入時にオフスクリーン描画へ
  渡すフラグだが、受け手側は追っていない。
- **`fpip+0x114`(1/100フレームの端数)が加算後に 100 を超えたときの扱い。**
  `i·100/分解能` 自体は 0〜99 に収まるが、元の値が非 0 なら超えうる。
- **`0x1004d7d0` のキャッシュがいつ解放されるか。** `w`/`h` や
  `fpip+0x11C` が変わればキーが変わるので新しいバッファになるはずだが、
  古いほうがどうなるかは追っていない。
- **`0x1004b200` が `*(fpip+0xAC)` を上書きするのか、そこへ描き足すのか。**
  上書きだという前提で「`残像` ON で前面に出るのは `現在 - 1/分解能` の姿」
  と読んでいるが、描き足しなら各サブフレームの合成が残ることになる。
  実機で1フレームぶんの遅れとして見えるかどうかも確認していない。
- **UI 上どう体感されるかは実機で確認していない。**
