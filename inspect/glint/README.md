# 閃光 (Glint) フィルタ リバースエンジニアリング解析

対象: `data/exedit.auf`(AviUtl 拡張編集の標準フィルタプラグイン)、32bit PE、
`ImageBase = 0x10000000`。以下のアドレスはすべて VA(`RVA = VA - 0x10000000`)。

## 再現方法

すべてのスクリプトは本プロジェクトの `main.py` を踏み台にして実行する。
`main.py` はコマンドラインで指定されたスクリプトに対して、DLLパス
(デフォルト `data/exedit.auf`)とヘッダー一覧(デフォルト `data/filter.h`)を
渡す役割を持つ。

```
uv run main.py inspect/glint/<script>.py
uv run main.py tools.<tool>            # フィルタ非依存の共通ツール
```

| スクリプト | 確認していること |
|---|---|
| `find_glint_addr.py` | `閃光` の登録エントリは**1つだけ**(`flag=0x20`、オブジェクト効果のみ)。加えて、登録配列から到達できない**フレームフィルタ版の残骸** `0x100a5b20` を .data 走査で発見し、参照が0件であることを確認 |
| `decompile_glint.py` | `func_proc` と2つのワーカー、および未登録版 `func_proc` の angr デコンパイル |
| `disasm_params.py` | angr が落とす x87 部分の生逆アセンブルと、全定数の実値解決。`0x101a6b7c`〜`0x101a6bac` の状態ブロックの各フィールドの意味 |
| `verify_strength.py` | `強さ` は**掛け算ではなくしきい値**であること。1001通り全部で `trunc(raw*4096/1000)` と一致すること。ワーカーが `strength` を一度も読まないことを xref で確認 |
| `verify_canvas_growth.py` | キャンバス拡張の「4倍」がマジックナンバー除算の産物であることと、その4倍が**光線の到達距離そのもの**であること。2つの上限による切り詰めループ |
| `verify_ray_geometry.py` | 光線が常に中心までの距離の**75%**を走ること(2つの分岐どちらでも)。`R` はコストの上限だが結果的に**画質の上限**になること。`R = trunc(maxd/4)+trunc(maxd/2)` が `trunc(0.75*maxd)` と一致しない値の特定 |
| `verify_output_encoding.py` | しきい値の色差補正と最終正規化が**打ち消し合う**こと(= `強さ` は色を動かさずアルファだけを動かす)。出力が輝度をアルファに移す**アンプリマルチプライ**であること。16bit書き戻しのヘッドルーム。光色指定時の `強さ` 下限 |
| `verify_ex_data_layout.py` | `FILTER+0x70` の `{kind, size, name}` テーブルで `ex_data` を分解。`ex_data` を持つ全49フィルタで合計サイズが `ex_data_size` と一致することを確認 |
| `verify_center_pixel.py` | 中心画素だけが通る経路が、**初期化されていないスタックスロット**をアルファとして使っていること(逆アセンブル上、書き込み1箇所・読み出し1箇所) |
| `simulate_glint_reference.py` | 上記すべてを織り込んだ整数忠実リファレンス実装。ASCIIアートで実際の放射状の光条を描画 |

共通ツール(他の `inspect/` からも使う):

| ツール | 役割 |
|---|---|
| `tools.get_func_address` | `FILTER_DLL` 配列を1行/エフェクトでダンプ |
| `tools.filter_table` | 登録構造体の完全デコード(トラックバー、チェックボックス、`ex_data_def`、`+0x74` 拡張ブロック) |
| `tools.track_scale` | `+0x74` の表示スケール / スライダー範囲 / トラックバーのグループ化マーカー |
| `tools.disasm` | capstone 逆アセンブル + 絶対メモリオペランドの定数解決 |
| `tools.decompile` | angr による範囲限定デコンパイル、`--calls` で呼び出し先列挙 |
| `tools.xrefs` | 任意の VA への参照を全画像から検索し、どのエフェクトのコードかを特定 |
| `tools.pe_image` / `tools.cints` | (単体実行不可のライブラリ)PE の VA 読み出し / C・x86 の整数意味論(`c_div`、`sar`、マジック除算) |

## 1. 登録エントリ ―― 1つだけ、ただし双子の残骸がある

`ぼかし`・`発光`・`モザイク` と違い、`閃光` は `FILTER_DLL` 配列に**1回しか
登録されていない**。したがって `fp->flag & 0x20` による分岐も存在しない。

| | 値 |
|---|---|
| `FILTER_DLL` | `0x100a59f8`、`flag=0x20`(オブジェクトのフィルタ効果) |
| `func_proc` | `0x1004e560` |
| `func_WndProc` | `0x1004f3f0` |
| `ex_data_size` | 8 バイト |
| 入力画像 | `*(fpip+0xAC)`、8バイト/画素 PIXEL_YCA |
| 出力先 | `*(fpip+0xB0)`、同じく PIXEL_YCA。最後に両者を入れ替える |
| 行幅 | `*(fpip+0xEC)` [画素]、入力・出力で共通 |
| 幅・高さ | `*(fpip+0xB4)` / `*(fpip+0xB8)` |

一方 `find_glint_addr.py` は、**配列から到達できない2つ目の登録構造体**
`0x100a5b20` を .data 中に見つける。

* `flag = 0` ―― フレーム(映像)フィルタ版
* トラックバー定義は登録版と完全に同一。チェックボックスは `check_name`/
  `check_default` が登録版の配列の**[1] 番目を指しており**、`光色の設定` 1つだけ
  になる(`発光` のフレーム版が `サイズ固定` を落とすのと同じやり方)
* `func_WndProc` は登録版と共有、`func_proc` だけ独自で `0x1004f260`
* `tools.xrefs` で `0x100a5b20` を検索すると**参照0件**

その `0x1004f260` をデコンパイルすると、パラメータ変換(手順2)までは登録版と
同じことをして、そのあと `fpip->ycp_edit` と `ycp_temp` を入れ替えて `return 1`
するだけで、ワーカーの起動もキャンバス計算も無い。つまり**書きかけのまま
登録から外された移植版**で、現行の exedit では実行されない。

## 2. パラメータ変換(`func_proc` 内、フレームごとに1回)

トラックバーは `fp->track[]` の順に `強さ`(初期値1000、範囲0~1000)、
`X`(0、-2000~2000)、`Y`(0、-2000~2000)。

UI に表示される数値との対応は、登録構造体 `+0x74` にある exedit 独自の拡張
ブロックで決まる(`tools.track_scale` に解読と検算がある):

| トラックバー | 表示スケール | UI表示範囲 | スライダーで届く範囲 | グループ |
|---|---|---|---|---|
| `強さ` | 10 | 0.0~100.0 | 0.0~100.0 | ― |
| `X` | 1 | -2000~2000 | -1000~1000 | `+1` |
| `Y` | 1 | -2000~2000 | -1000~1000 | `-1` |

`強さ` は**UIの数値を10倍したものが生値**(初期値 `100.0` = 生値1000)。
`X`/`Y` は UI の数値がそのまま生値で、単位は**画素**。

拡張ブロックの slot[1](`モザイク` の解析では用途未確定としてあった枠)は、
ここで初めて非ゼロの値を持つ: `X=+1, Y=-1`。全エフェクトを走査すると、この枠が
非ゼロなのは**多成分コントロールを構成するトラックバーだけ**で、必ず
「最後以外は `+1`、最後は `-(要素数-1)`」の形になる(`X,Y,Z` と `拡張色設定` の
`R,G,B` は `+1,+1,-2`)。単独のトラックバーでは常に0。
`uv run main.py tools.track_scale --groups` が全件の証拠を出す。

以下、`func_proc` が生値に対して行う変換:

* **`強さ = 0` は即 return**。`fp->track[0]` が0なら画像にもキャンバスにも
  一切触れない(`test eax, eax; je` @ `0x1004e573`)。
* **`強さ`**: `raw * 4096` をコンパイラ生成のマジックナンバー除算
  (`0x10624dd3` を掛けて `>>38` 相当)にかける。MSVC の符号あり整数定数除算の
  定型で、四捨五入ではなく**0方向への切り捨て**:
  ```
  strength = trunc(raw * 4096 / 1000)     // raw=1000 -> 4096
  T        = max(0, 4096 - strength)      // ワーカーが使うのはこちら
  ```
  1001通り全部で `raw*4096//1000` と一致することを確認済み。
  **`強さ` は輝度への掛け算ではなくしきい値の引き算**で、ワーカーは `strength`
  そのものを一度も読まない(`0x101a6b94` を読む命令は `func_proc` 内の1箇所だけ)。
  `strength` が掛け算として使われるのは**キャンバス拡張量**に対してだけ(手順3)。
* **中心座標**:
  ```
  cx = w/2 + X        // w/2 は0方向への切り捨て
  cy = h/2 + Y
  ```
* **サンプル数上限 `R`**:
  ```
  maxd = max(|cx|, |cy|, |cx-w|, |cy-h|)
  maxd = min(maxd, trunc(sqrt(w*w + h*h)))          // 画像対角線でクランプ
  if (fpip->flag & 0x200) maxd = min(maxd, 50)      // 後述
  R    = trunc(maxd/4) + trunc(maxd/2)
  ```
  `R` は「0.75*maxd」のつもりの式だが、**切り捨てが2回別々に起きる**ので
  `trunc(0.75*maxd)` とは一致しない。`maxd % 4 == 3` のとき常に1小さくなる
  (例: `maxd=7` で `R=4`、`trunc(0.75*7)=5`)。

### `fpip->flag & 0x200`

`data/filter.h` に定義のない、exedit 独自の `FILTER_PROC_INFO` フラグ。
このビットを読むエフェクトを全走査すると、`閃光`・`放射ブラー`・`方向ブラー` は
いずれも**画素あたりのサンプル数を 50 で頭打ちにし**、`凸エッジ` は 16 で
頭打ちにする。どれも「線に沿って何回サンプリングするか」を削る使い方なので、
**描画品質を落としてよいという要求**とみて間違いない。exedit 側のどの条件で
立つのかは `func_proc` の外にあり、本解析では未確定。

## 3. キャンバスの拡張 ―― 「4倍」の出どころ

光は元のオブジェクトの外へ伸びるので、`func_proc` は描画前にキャンバスを広げる。

```
x0 = min(0, cx - 4*cx)              // = min(0, -3*cx)
y0 = min(0, cy - 4*cy)
x1 =         max(0, -3*(cx - w))    // = max(0, 3*(w - cx))
y1 =         max(0, -3*(cy - h))
x0, y0, x1, y1 = それぞれ (値 * strength) >> 12       // sar なので負値は floor
x1 += w ;  y1 += h
```

`4*cx` は逆アセンブル上、`cx` を3つの `lea` と `shl` で1000倍してから
マジックナンバー除算(`sar edx, 4` = /250)にかけた結果として現れる。
`*1000 / 250` は単なる `*4` で、`verify_canvas_growth.py` が -500k~500k で
全一致を確認している。

**この4という数は光線の到達距離そのもの**。ある出力画素は自分から中心へ向かって
距離の75%を走査する(手順4)ので、距離 `D` の画素は `[0.25D, D]` の範囲の
ソース画素を拾う。逆に言えば、中心から距離 `d` のソース画素は
`D = 4d` まで光を伸ばす。左端画素(中心から `cx`)の光条は `cx - 4*cx` で終わる。
つまり**キャンバスは光条の端がちょうど収まる大きさに広げられていて、1画素も
余分ではない**。`verify_ray_geometry.py` の第4節が、実際に光線を歩かせて
「`D/4` より内側へは決して届かない」ことを総当たりで確認する。

拡張量が `strength` 倍される点は注意が必要で、`強さ` は本来しきい値であって
長さではない。**幾何的な到達距離は `強さ` に関係なく4倍のまま**で、
「暗い先端はどうせしきい値を超えないだろう」という前提でキャンバスだけが
切り詰められている。

そのあと2つの上限で切り詰める:

```
while (x1 - x0) > 最大キャンバス幅 (0x10196748)
   || (x1 - x0) > fpip->w + 2*w :
    if (x0 < w - x1)  x0 += 1        // はみ出しが大きい側を1画素ずつ削る
    else              x1 -= 1
```

(高さ側は `0x101920e0` と `fpip->h + 2*h`。この2つのグローバルは
`inspect/blur` でオブジェクトキャンバスの最大幅・最大高と同定済み。)

**`サイズ固定`(`check[2]`)** がオンの場合は、ここまでの結果を全部捨てて
`x0=y0=0, x1=w, y1=h` に戻す(`0x1004e860`)。光線の計算自体は変わらないので、
光条は同じように伸びようとしてオブジェクトの矩形で切られる。

最後に、描画とオブジェクトの再配置:

```
fpip+0xAC ⇔ fpip+0xB0      // 光のバッファを現画像にする
fpip+0xD4 += (w - x1 - x0) * 2048
fpip+0xD8 += (h - y1 - y0) * 2048
fpip+0xB4  = x1 - x0
fpip+0xB8  = y1 - y0
```

`+0xD4`/`+0xD8` の補正量は、新キャンバスの中心に対するオブジェクト中心のずれ
`(w - x1 - x0)/2` 画素をちょうど 4096 倍したものにあたる(対称に広がった場合は
0 になる)。フィールドの単位が 1/4096 画素であること自体は、この式からの推定。

## 4. 光線の走査 ―― 1画素あたりの本体

出力画素 `(x, y)`(座標は元のオブジェクト基準、`x0 <= x < x1`)ごとに:

```
dx, dy = cx - x, cy - y
dist8  = trunc(sqrt(dx*dx + dy*dy) * 8.0)     // 1/8画素単位。_ftol は0方向切り捨て
length = trunc(dist8 * 750 / 1000)

if dist8 > R:                                  // 遠い画素 ― サンプル数を R で頭打ち
    length = trunc(length * R / dist8)
    N      = R
else:                                          // 中心近傍 ― 逆にスーパーサンプル
    m      = 8 if dist8 > 8 else 4 if dist8 > 4 else 2 if dist8 > 2 else 1
    N      = dist8 * m
    length = length * m

if N < 2 or length < 2:  → 中心画素の経路(手順6)

stepx, stepy = (dx << 16) / N, (dy << 16) / N       // 16.16固定小数、0方向切り捨て
fx, fy       = (x << 16) + 0x8000, (y << 16) + 0x8000
```

`dist8` は1/8画素単位、`R` はサンプル数と、**比較する2つの量の単位が違う**。
それでも結果として走る距離は変わらない ―― `length` 個 × ステップ `dist/N` は
どちらの分岐でも `0.75 * dist` になる。**変わるのはサンプル間隔だけ**:

| 中心からの距離 | 分岐 | サンプル間隔 | 実際の意味 |
|---|---|---|---|
| ~0.25px以下 | ― | ― | 中心画素の経路(手順6) |
| 1px | `x4` | 1/32 px | 過剰にスーパーサンプル |
| 4px | `x8` | 1/64 px | 同上 |
| `R` px | `R`で頭打ち | 1 px | ちょうど1画素1サンプル |
| `4R` px | 同上 | 4 px | **3画素飛ばし ― 光条が破線になる** |

つまり `R` は本来コストの上限だが、`dist > R` の領域では**画質の上限**として
効く。中心から離れた細い明部は、連続した光条ではなく点線としてサンプリング
される。`R` はオブジェクトサイズだけで決まり、ユーザーからは触れない。

サンプルループは `length` 回まわり、毎回:

```
sx, sy = fx >> 16, fy >> 16                 // sar なので floor
fx, fy = fx + stepx, fy + stepy
if not (0 <= sx < w and 0 <= sy < h): continue        // 範囲外はスキップ
a = src[sy][sx].a
if a == 0: continue
if a < 4096:  sum += (c * a) >> 12   for c in (y, cb, cr)
else:         sum +=  c
```

**範囲外・アルファ0のサンプルは「読み飛ばす」だけで、割る数は常に `length`**。
オブジェクトの外へはみ出した分は黒として平均されるのと同じことになる。

`c` に何を入れるかだけが2つのワーカーの違い(手順7)。

## 5. 蓄積の平均・しきい値・出力エンコード

両ワーカー共通の後半(`0x1004ec2e` / `0x1004f07c`):

```
avgY = sumY / length
out  = avgY - T                                     // T = 4096 - strength
if out <= 0:  出力 = (0, 0, 0, 0)                    // 完全透明
cb = sumCb/length ;  cb -= T*cb/avgY
cr = sumCr/length ;  cr -= T*cr/avgY
if out < 4096:  出力 = (y=4096,  cb=cb*4096/out, cr=cr*4096/out, a=out)
else:           出力 = (y=out,   cb=cb,          cr=cr,          a=4096)
```

ここに2つ、式を眺めただけでは見えない性質がある。

* **しきい値は色から消える**。色差は `(avgY-T)/avgY` 倍されたあと
  `4096/(avgY-T)` 倍されるので、掛け合わせると `cb * 4096 / avgY` になり
  **`T` が完全に約分される**。光条の面積のほとんどを占める `out < 4096` の領域では、
  **`強さ` を下げても色は動かず、アルファだけが下がる**。
  (`verify_output_encoding.py` 第1節。残差は整数除算の切り捨てで数単位。)
* **これはアンプリマルチプライである**。`y=4096, a=out` は
  プリマルチプライされた色 `(out, cb, cr)` を `out/4096` で割り戻した形そのもの。
  **光の明るさがそのまま不透明度になる**ので、`閃光` は光そのものについては
  合成パスを持たない ―― 書いた時点で合成済みになっている。
  `out >= 4096` ではアルファが飽和し、超過分は輝度側が持つ(超白になる)。

16bit 書き戻し(`mov word ptr [ebp+2], ax`)にクランプは無い。書かれる色差は
`cb * 4096 / avgY` なので、比 `|cb|/y` が最大の色 ―― 純青 ―― でも 17965 で、
`int16` の 32767 には届かない。**通常の画像内容では溢れない**が、上流の効果が
色域外の YC(輝度に対して色差が過大)を残した場合は折り返して色相が反転する。

## 6. 中心画素だけが通る経路(既知の不具合)

`N < 2 || length < 2` は `dist8 <= 2`、つまり中心から **0.25画素以内**でしか
成立しない ―― 実質、中心が乗っている1画素だけ。この経路はサンプリングを一切
せず、直下のソース画素をあるアルファで重み付けして同じエンコードで書く。

そのアルファ `[esp+0x48]` は、**サンプルループの中でしか書かれていない**。
`verify_center_pixel.py` が両ワーカーを逆アセンブルして数える通り、書き込み1箇所
(ループ内、範囲内サンプルのアルファ)・読み出し1箇所(この経路)しかない。
この経路に来るのはループが回らなかったときなので、実際に使われるのは
**同じスレッドが直前に処理した別の画素の最後のサンプルのアルファ**であり、
そのスレッドがまだ一度も範囲内をサンプルしていなければ**未初期化のスタック**。

* 影響は1画素(中心が画素境界に乗ると数画素)
* フレームとスレッド分割が同じなら再現性はある
* **スレッド数を変えると走査順が変わるので値も変わる**
* 光色指定側(`0x1004ee20`)ではもっと露骨で、この経路はソース画像を一切読まず、
  指定色にその借り物アルファを掛けたものを書く

## 7. `光色の設定` と2つのワーカー

`ex_data` は8バイトで、`FILTER+0x70` にある `{u16 kind; u16 size; char *name}`
テーブルが中身を宣言している(AviUtl の `FILTER` では `func_is_saveframe` の
位置。exedit が `+0x74` を表示スケールに流用しているのと同じ流儀):

| offset | size | name | 意味 |
|---|---|---|---|
| 0 | 3 | `color` | R, G, B(Win32 `COLORREF` と同じバイト順) |
| 3 | 1 | `no_color` | 1 = 指定なし(各画素自身の色を使う)。`dword[0]` の bit24 |
| 4 | 4 | `mode` | `前方に合成` ボタンの選択値 0/1/2 |

新規追加時の既定値は `ff ff ff 01 00 00 00 00`(= 指定なし＋未使用の白、
合成モード0)。このテーブルの読み方は、`ex_data` を持つ**全49フィルタで
合計サイズが `ex_data_size` と一致する**ことで裏付けている
(`verify_ex_data_layout.py`)。

`func_proc` は毎フレーム `sub_1006fed0`(`発光` と共有の RGB→YCbCr、係数は
Q14 の BT.601 フルレンジ)で色を `0x101a6bac`(Y)/`0x101a6b90`(Cb)/
`0x101a6b9c`(Cr) に変換したあと、bit24 でワーカーを選ぶ:

* **bit24 セット = 指定なし(既定)** → `0x1004e9c0`
  ```
  sum += (src.y, src.cb, src.cr) * src.a >> 12
  ```
  各画素自身の色で光る。赤いハイライトは赤い光条になる。
* **bit24 クリア = 色を指定済み** → `0x1004ee20`
  ```
  sum += (colorY, colorCb, colorCr) * src.a >> 12
  ```
  **ソースの輝度を一切読まない**。光線が測っているのは被覆率だけなので、
  同じ形なら明るいオブジェクトも暗いオブジェクトも同じように光る。
  `発光` が「指定色 × 抽出した明るさ」なのとは正反対。

この非対称には実用上の落とし穴がある。色指定時に到達しうる `avgY` の上限は
**指定色自身の Y** なので、`T = 4096 - strength` がそれを超えていると
**何も描かれない**:

| 光色 | 色の Y | これを超える `強さ` が必要 |
|---|---|---|
| `#ffffff` | 4095 | 0.1 |
| `#ffff00` | 3629 | 11.5 |
| `#00ff00` | 2404 | 41.4 |
| `#ff0000` | 1224 | 70.2 |
| `#0000ff` | 466 | 88.7 |
| `#000080` | 234 | 94.3 |

暗い青の光は `強さ 88.7` 未満では、どんなに明るいオブジェクトに掛けても
まったく出ない。

## 8. `前方に合成` ―― 3択の合成モード

`check[0]` は `check_default = -2` で、`data/filter.h` の言う通り負値なので
チェックボックスではなくボタンだが、実体は**3項目のコンボボックス**。
選択値は `ex_data` の `mode`(4バイト)に入る。`func_WndProc`(`0x1004f3f0`)は
`0x100a5c5c` から始まる連続した cp932 文字列3つをそこへ流し込む:

| `mode` | ラベル | `func_proc` の動作 |
|---|---|---|
| 0 | `前方に合成` | 元オブジェクトを光のバッファへ `0x11000003` で描画 |
| 1 | `後方に合成` | 同上、モード定数は `3` |
| 2 | `光成分のみ` | 描画そのものをスキップ(`jne` @ `0x1004e8ea`)、光だけが残る |

描画は `(*(fp+0x64))[0x44]` ―― exedit 内部の描画関数テーブル経由で、
```
draw(dst=fpip+0xB0, -x0, -y0, src=fpip+0xAC, 0, 0, w, h, 0, mode)
```
と呼ばれる。つまり**光のバッファの上に元オブジェクトを、拡張後の正しい位置に
置き直している**。`前方`/`後方` の違いは合成モード定数だけで、その定数の
ビット割り当ては exedit 内部のもの(未解読、手順11)。

`func_WndProc` は他に `光色の設定` ボタン(`0x1e1b`)で色選択ダイアログを開き、
ボタンのラベルを `"指定無し (元画像の色)"` / `"RGB ( %d , %d , %d )"` に
書き換えるだけで、`fp->track[]` は一切参照しない。

## 11. 未確定事項

* **合成モード定数 `0x11000003` と `3` のビット割り当て**。どちらがどのUI項目に
  対応するかは `func_proc` の分岐から確定しているが、定数自体を解釈するには
  `fp+0x64` の描画関数テーブル(実行時に埋まる)を追う必要がある。
  `0x11000003` は画像全体で `閃光` の1箇所にしか現れない。
* **`fpip->flag & 0x200` を exedit がいつ立てるか**。読み手側(`閃光`・
  `放射ブラー`・`方向ブラー`・`凸エッジ`)が一様にサンプル数を削ることから
  「品質を落としてよい」フラグと判断しているが、立てる側のコードは未追跡。
* **`fpip+0xD4`/`+0xD8` の単位**。補正量の式から 1/4096 画素と推定しているが、
  他のエフェクトでの使われ方を突き合わせて確認したわけではない。
* **中心画素の借り物アルファの実際の値**。スレッド分割と走査順に依存するので、
  リファレンス実装では「まだ何もサンプルしていなければ0」としている。
  exedit 自身も実行ごとに一致するとは限らない。
* **最終的な YCbCr→RGB 変換とそのクリップ**は `aviutl.exe` 側にあるため、
  超白(`out > 4096`)や色差の折り返しが画面上でどう出るかは推定にとどまる。
