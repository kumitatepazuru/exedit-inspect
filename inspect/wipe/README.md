# ワイプ (wipe) フィルタ リバースエンジニアリング解析

対象: `data/exedit.auf`(AviUtl 拡張編集の標準フィルタプラグイン)、32bit PE、
`ImageBase = 0x10000000`。以下のアドレスはすべて VA(`RVA = VA - 0x10000000`)。

## 再現方法

すべてのスクリプトは本プロジェクトの `main.py` を踏み台にして実行する。

```
uv run main.py inspect/wipe/<script>.py
uv run main.py tools.<tool>            # エフェクト非依存の共通ツール。一覧はリポジトリ直下の README
```

| スクリプト                     | 確認していること                                                                                                                                    |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `tools.filter_table --name ワイプ` | 登録エントリが1個(`0x100be748`、`flag=0x20`)、トラックバー3本・チェックボックス3個(うち1個はコンボ)・`ex_data` 260バイト・`func_WndProc` 持ちであること |
| `decompile_wipe.py`             | `func_init`〜`func_WndProc` まで角括弧域を丸ごと range 限定デコンパイル。手読みした制御フローの独立した裏付け(`横`/`縦` は angr が関数化できず対象外) |
| `disasm_params.py`              | `func_proc` 全命令に注釈。進捗ランプ・3つの出口・パターン分岐・ぼかし呼び出し・最終合成                                                                |
| `verify_ex_data.py`             | `ex_data` 260バイトのフィールド表、既定5パターン名、`func_WndProc` のコンボ選択ハンドラ(共有ハンドラとの違い)                                          |
| `verify_patterns.py`            | 5個の組み込みパターン(円・四角・時計・横・縦)の式を Python 再実装し、進捗との単調性・`横`/`縦`の転置関係・反転フラグの相補性を検算                     |
| `verify_blur.py`                | `ぼかし` のカーネル半径分割(`r_hi=ceil(b/2)`, `r_lo=floor(b/2)`)とパス数(0/2/4)が `ぼかし` エフェクト本体と同じ規則であること                        |
| `verify_custom_pattern.py`      | `transition\*.png` の探索・読み込み・貼り付け・しきい値化。フォルダ探索ヘルパーが `シーンチェンジ` の `func_init` と共有されていること                |
| `simulate_wipe_reference.py`    | 進捗ランプ+5パターン+ぼかしを結合した整数忠実リファレンス。オブジェクト1個分のマスク推移を ASCII で描画                                               |

## 1. 何をするエフェクトか

**対象オブジェクトの画像に「型」を重ねて、型の内と外でアルファの掛け方を
変える**エフェクト。型は5種類の幾何図形(円・四角・時計・横・縦)か、
`transition` フォルダに置いた任意の PNG から選べる。`ぼかし` は型の境界を
やわらげる箱ぼかし、`イン`/`アウト` は境界がどう動くかを決める時間パラメータで、
基本構造は [`フェード`](../fade/README.md) の「2本のランプの min」と同じ。

- 登録は `0x100be748` の1個だけ(`flag = 0x20` = オブジェクト効果)。
  フレームフィルタ版は存在しない。
- トラックバー3本(`イン` `アウト` `ぼかし`)、チェックボックス2個
  (`反転(イン)` `反転(アウト)`)+ コンボボックス1個(`ワイプ(円)`、
  `check_default = -2`)。`ex_data` は **260バイト**(`シャドー`/`縁取り`と
  同じ大きさだが中身の意味は別)。
- `func_init`(`0x100903c0`)と `func_WndProc`(`0x10091710`)を両方持つ ――
  `filter_registration.md` §7 が挙げる「UI コードを持つ9エフェクト」に
  `func_init` まで持つのは本エフェクトだけ。
- エフェクト固有コードは `func_init`(`0x100903c0`)から `func_WndProc` の
  終端(`0x10091794`)まで約5000バイト・14個の関数にまたがる。解析済みの
  中では `発光`/`グロー` 級の規模で、単発の変換ではなく**複数のワーカーを
  切り替えるディスパッチャ**であることが大きさの理由。

## 2. パラメータ

`fp->track[]` の順に `イン`(初期値50、範囲0~1000)、`アウト`(50、0~1000)、
`ぼかし`(2、0~100)。`+0x74` 拡張ブロックは `イン`/`アウト` だけ表示スケール
`100` を持ち、`ぼかし` はスケール`1`(生値そのまま表示)([`param_scaling.md`](../common/param_scaling.md))。

| トラックバー | 表示スケール | UI表示範囲 | 意味                                   |
| ------------ | ------------ | ---------- | -------------------------------------- |
| `イン`       | 100          | 0.00~10.00 | フェードと同じ秒単位の導入時間          |
| `アウト`     | 100          | 0.00~10.00 | 同・終了時間                            |
| `ぼかし`     | 1            | 0~100      | パターン境界の箱ぼかし半径(生ピクセル単位) |

チェックボックス/コンボ(`fp->check[]`):

| インデックス | 名前           | 型                    | 既定 |
| ------------ | -------------- | --------------------- | ---- |
| `check[0]`   | `反転(イン)`   | チェックボックス      | OFF  |
| `check[1]`   | `反転(アウト)` | チェックボックス      | OFF  |
| `check[2]`   | `ワイプ(円)`   | コンボ(`-2`)          | 0 (円) |

`check[2]` はラベルが選択中のパターン名に変わる可変コンボで、詳細は §9。

## 3. 進捗ランプ ―― `イン`/`アウト` から 0..4096 を作る

`func_proc`(`0x10090490`)の前半は [`フェード`](../fade/README.md) §4 と
ほぼ同型([`disasm_params.py`](disasm_params.py)):

```
in_frames  = trunc(イン   * rate / (scale * 100))
out_frames = trunc(アウト * rate / (scale * 100))

t = fpip.0xA8 - fp.0x118              // 現在フレーム - オブジェクト開始
u = fp.0x11C  - fpip.0xA8              // オブジェクト終了 - 現在フレーム

g = 0x1000
if (t < in_frames)  { a = (t+1)*4096/(in_frames+1);  if (a < g) { g = a; invert = check[0] } }
if (u < out_frames) { a = (u+1)*4096/(out_frames+1); if (g > a) { g = a; invert = check[1] } }
```

フェードとの違いは2点:

1. `t` の式に `fpip+0x118`(サブオブジェクト遅延)が乗らない。`フェード` は
   `テキスト` の1文字ずつ表示のために引くが、ワイプはこの項を一度も読まない。
2. `g` をそのままアルファに掛けるのではなく、**どちらのランプが勝ったか**
   (`イン` 側か `アウト` 側か)を覚えておいて、勝った側の `反転` チェック
   ボックスの値をグローバル `g_1024e0b0` に置く。これが §5 の「反転」の
   種になる。

3つの出口も同型([`root README`](../../README.md) が挙げる「`return 0` を
返す20エフェクト」の1つ):

```
g >= 0x1000  -> return 1   // 何もしない。ワーカーすら起動せず、対象はそのまま描かれる
g <= 0       -> return 0   // オブジェクトをまったく描かない
それ以外     -> if (invert) g = 0x1000 - g;  パターン生成へ
```

## 4. 組み込み5パターン

`ex_data.type`(0..4)で選ぶ5種類の形状ワーカーが、`fpip+0xB0`(対バッファ)
のアルファ面(8バイト画素の `+6`)に **0(隠す)〜0x1000(見せる)** のマスクを
書き込む。パターン画像を持たない・持つの分岐は `ex_data.name`(§9)。

| `ex_data.type` | 名前(UIコンボの表示文字列) | ワーカー       |
| --------------- | --------------------------- | -------------- |
| 0 (既定)         | `ワイプ(円)`                | `0x10090d50`   |
| 1                | `ワイプ(四角)`               | `0x10090c00`   |
| 2                | `ワイプ(時計)`               | `0x10090a60`   |
| 3                | `ワイプ(横)`                 | `0x10090ec0`   |
| 4                | `ワイプ(縦)`                 | `0x10090f90`   |

(5個の文字列は `0x100ba6d0` に静的に並んでいて、コンボの選択 index
そのものが `ex_data.type` になる ―― §9。)

式(`w`/`h` はオブジェクトの幅・高さ、`cx=w/2`, `cy=h/2`、`g` は §3 の進捗。
`verify_patterns.py` が命令列からここまで確定し、Python 再実装で自己検算する):

- **円** `0x10090d50`(唯一アンチエイリアスされたパターン): 対角線長の2乗
  `diag2 = w²+h²` から半径2乗 `R² = trunc(diag2*g/4096)` を x87 で作り、
  `fsqrt` で `R` を取って帯幅 `band = 4*R` とする。**距離だけは2倍座標で
  測る** ―― `dx = 2x-w+1`, `dy = 2y-h+1` を列/行ごとに 2 ずつ進める
  (`0x10090e5b` の `sub ecx,ebp` と `0x10090e8b` の `add ecx,2`)。既定
  (未反転)は `R²-dx²-dy² <= 0 -> 0`、`0 < ... < band -> 階調`、
  `>= band -> 0x1000` ―― **中心から塗りが広がる**。2倍座標なので実効半径は
  `R/2` で、`g=4096` でちょうど四隅に届く(`max(dx²+dy²) = (w-1)²+(h-1)² ≲ w²+h²`)。
  中心も `((w-1)/2, (h-1)/2)` で、他4パターンの `(cx, cy)` とは別物。
- **四角**(実体はL1距離のダイヤ形)`0x10090c00`: `threshold = (cx+cy)*g/4096`、
  `d1 = |x-cx|+|y-cy|`。既定は `d1 <= threshold -> 0x1000`、ハードエッジ
  (階調なし)。
- **時計** `0x10090a60`: `fpatan` で `atan2(dy,dx)` を求め
  `-65536/(2π)` 倍して0..65535の角度単位にし、`0x4000`(12時方向相当)を
  基準に測り直した角度 `swept` と、進捗から作った `threshold = g*16` を
  比較する。既定は `swept <= threshold -> 0x1000`。中心を軸にした扇形の
  掃引。中心画素(`x==cx && y==cy`)だけは `fpatan` を呼ばずに無条件で
  `0x1000` を書く分岐がある(`0x10090b15` / `0x10090b83`)。
- **横** `0x10090ec0`: `threshold = trunc(w*g/4096)`。既定は
  `column <= threshold -> 0x1000`、行によらず一様。
- **縦** `0x10090f90`: `横` と `w`↔`h`・`x`↔`y` を入れ替えただけの同一
  コード(`verify_patterns.py` §3 で200ケースの転置一致を確認)。

### 読み間違えやすい点 ―― `setcc` の結果は直後の `dec`+`and` で反転される

四角/時計/横/縦の4パターンは、比較結果を `setcc` で受けたあと**2命令で極性を
ひっくり返してから**マスク値にしている。四角 `0x10090d0d` / 時計 `0x10090bc4` /
横 `0x10090f63` / 縦 `0x1009102f` がすべて同じ形:

```asm
setg dl            ; dl = (d1 > threshold)
dec  edx           ; 1 -> 0 / 0 -> 0xFFFFFFFF
and  edx, 0x1000   ; d1 >  threshold なら 0      (不可視)
                   ; d1 <= threshold なら 0x1000 (可視)
```

つまり **`setg` が立つ側が不可視**。`setg` だけを見て「`>` で可視」と読むと
4パターンとも極性が逆になる。反転側の分岐は `setl` なので、同じ変換を通ると
「`>=` で可視」になる。円はこの形ではなく `test eax,eax; jg`(`0x10090e68`)の
明示的な算術分岐なので、この罠には該当しない。

正しく読むと**5パターンとも向きは揃っており**、既定(未反転)で `g` が増えると
可視画素は**増える**。16x16 での実測(`verify_patterns.py` §2 の出力):

```
円    g=[0, 512, 1024, 2048, 3072, 4095] -> visible=[0, 24, 68, 148, 232, 252]
四角  g=[0, 512, 1024, 2048, 3072, 4095] -> visible=[1, 13, 41, 143, 231, 255]
時計  g=[0, 512, 1024, 2048, 3072, 4095] -> visible=[9, 44, 72, 128, 192, 256]
横    g=[0, 512, 1024, 2048, 3072, 4095] -> visible=[16, 48, 80, 144, 208, 256]
縦    g=[0, 512, 1024, 2048, 3072, 4095] -> visible=[16, 48, 80, 144, 208, 256]
```

`g=4095` でも円が 252、四角が 255 で頭打ちなのは、円の四隅がアンチエイリアス帯に
入ること・四角の `threshold` が 16 に届かないことによる。どちらも「満不透明は
分岐に入らなかったときにしか出ない」という §3 のランプの性質と整合する。

進捗 `g` は(フェードと同様)オブジェクトの**開始直後と終了直前だけ**
4096未満になり、区間の内側では早期リターンでワーカーが起動しない(§3)。
`イン` 側では `g` が 0 から上がり、`アウト` 側では 4096 へ向かって下がるので、
5パターンとも「開始直後はほぼ全域不可視 → 広がる → 区間内側で不透明に飛ぶ →
終了直前に狭まる」という素直な動きになる
(`simulate_wipe_reference.py --pattern 0` と `--pattern 3` の出力で目視できる)。

## 5. `反転(イン)`/`反転(アウト)` ―― 独立した2つの反転が同じチェック値に乗る

`反転` チェックボックスの値は `g_1024e0b0` という1つのグローバルに入り、
**2箇所で別々に参照される**:

1. `func_proc`(`disasm_params.py` の `0x10090576`〜`0x10090581`): 進捗
   そのものを `g = 0x1000 - g` に置き換える(時間方向の反転)。
2. 各パターンワーカー(`verify_patterns.py` §1b, §4): `g_1024e0b0` を見て
   比較演算子を入れ替える(可視領域の極性そのものを反転)。§4 の `dec`+`and`
   を通したあとの実効的な条件でいうと、既定の `<=` が反転側で `>=` になる。

同じ1個の値が両方に効くので、「反転」は単純な逆再生ではなく、**時間方向と
空間方向が同時にひっくり返る**。`verify_patterns.py` §4 は
「`d1 == threshold` の境界画素は invert=False/True の**両方で可視**になり、
それ以外の画素は完全に相補的」であることを200ケースで確認している
(`<=` と `>=` の両方に境界が含まれるため、排他ではなく境界ぶんだけ重複する)。
`simulate_wipe_reference.py` は `--invert-in` を付けると5パターンとも
反対側から現れる(円なら中心からではなく外周から埋まる)ことを数値で示す。

## 6. `ぼかし` ―― パターン境界の箱ぼかし

`sub_10090640` が `ぼかし`(生値0..100)を [`box_blur.md`](../common/box_blur.md)
と同じ規則で `r_hi = ceil(ぼかし/2)`, `r_lo = floor(ぼかし/2)` に分割し、
各半径ぶん2軸(垂直 `0x10090700` → 水平 `0x100908c0`、中間は共有スクラッチ
`[0x101a5328]`)を1ペアとして、`r_hi` 分・続けて `r_lo` 分走らせる
(`verify_blur.py`)。

```
ぼかし == 0        -> 0パス。ハードエッジのまま
ぼかし == 1        -> 2パス (r_hi=1, r_lo=0)
ぼかし >= 2        -> 常に4パス
```

これは `ぼかし` エフェクト本体の固定4パス `V(r_hi)→H(r_hi)→V(r_lo)→H(r_lo)`
と**同じ半径分割規則**([`box_blur.md`](../common/box_blur.md) の分割表)。
対象は `fpip+0xB0` のアルファ面だけで、色は一度も読まない。円パターンだけ
自前のアンチエイリアス帯を持つが、それとは独立に `ぼかし` がさらに階調を
足す ―― 円+`ぼかし`=0 でも境界には `4*R` 幅の帯がすでにある、という点は
`verify_patterns.py` の円の式で確認できる。

## 7. 最終合成

`exec_multi_thread_func(0x10091050, fp, fpip)` が、行分割したワーカーで

```
objAlpha' = floor(objAlpha * patternAlpha / 4096)     // sar 12
```

を **オブジェクト自身のアルファ(`fpip+0xAC` の `+6`)に in-place** で書く。
色(`y`/`cb`/`cr`)は一度も読まれない ―― `フェード` の「アルファに定数を
掛けるだけ」と同じ形を、定数の代わりに画素ごとのマスクで行っている。
`a' <= a` なので、ワイプは(`フェード` 同様)アルファを**減らすことしか
できない**。

## 8. カスタム画像パターン ―― `transition` フォルダ

`ex_data.name`(256バイト)が空でなければ、5パターンの分岐そのものを
飛ばして `sub_10091100` が一括処理する(`verify_custom_pattern.py`)。

### 8.1 フォルダは `シーンチェンジ` と共有

`func_init`(`0x100903c0`)は共有バッファ `g_10230b58` に入っている
`<exedit.aufのフォルダ>\transition\` へ `*.png` を検索(`FindFirstFileA`/
`FindNextFileA` 相当の共通ヘルパー `0x1004e220`/`0x1004e270`、ファイル名
部分を切り出す `0x1004e190`/`0x1004e1d0` も含めて全部共有)し、見つかった
ファイル名(拡張子抜き)を、既存の5個の固定パターン名の**後ろに**追記する
(先頭5個は上書きしない ―― `verify_ex_data.py` §4)。上限256エントリ。

`g_10230b58` 自体は `シーンチェンジ`(`0x10086580`)の `func_init` が
`GetModuleFileNameA` で得た exedit.auf 自身のパスから `transition\` へ
差し替えて作る。`tools.xrefs --addr 0x10230b58` で参照が2エフェクトだけに
閉じていることを確認できる(`verify_custom_pattern.py` §1)。**AviUtl の
`transition` フォルダはワイプとシーンチェンジ両方の共通インフラ**である。

### 8.2 読み込みとサイズ処理

```
if (w > fpip.0x14 || h > fpip.0x18) return 1;   // 拡張後キャンバスの上限超え、no-op
path = "<transitionフォルダ>\<ex_data.name>.png"
table[0x38](fpip+0xB0, path, &imgW, &imgH, 0, 0)     // シャドーと同じ画像ローダ
if (読み込み失敗) return 0;
if (imgW==w && imgH==h) table[0x44](等サイズ矩形転送)  // canvas_growth.md の table[0x44]
else                    table[0x58](4隅Q12指定のワープ転写で w x h に拡縮)
```

### 8.3 グレースケール画像を「しきい値マップ」として使う

読み込んだ画像のチャンネル値をそのまま「その画素をいつ見せ始めるか」の
順序マップとして扱う ―― 市販ノンリニア編集ソフトの「グラデーションワイプ」
と同じ発想:

```
band(ぼかし)      = round(ぼかし * 1920/256) + 128     // ぼかし=0でも128の下限帯を持つ
threshold(g)      = round((band+2048)*g/2048) - band   // g とともに単調増加
sub_10091500: 画素値 v に対し
    v <= threshold-band       -> 0
    threshold-band < v < threshold+band -> 階調
    v >= threshold+band       -> 0x1000
sub_10091310: 3x3ボックス平均(固定 /9)で少し均してから
              objAlpha(fpip+0xAC) *= smoothed >> 12   // 組み込みパターンの sub_10091050 と同じ掛け算だが専用実装
```

`verify_custom_pattern.py` が命令列からこの式(丸め込みのマジックナンバー
`1920/256`・`+2048`・`>>12` まで)を確定し、`band`/`threshold` が
`ぼかし`/`g` それぞれ単調であることを検算している。組み込み5パターンの
`sub_10090640`/`sub_10091050` は一度も経由しない自己完結した経路。

読み込んだ画像の生画素は `fpip+0x08`(SDK では frame filter 用の
`ycp_temp`)に置かれる ―― object 効果専用のワイプがこのフィールドを
「デコード済みRGBバッファ置き場」として流用しているのは、`fp+0x60`/`+0x64`
の再利用(`filter_registration.md` §4)と同じ「SDKのフィールドを別の意味で
借りる」パターンの一例。

## 9. `ex_data` と `ワイプ(円)` コンボ

`ex_data` は260バイト、`+0x70` フィールド表(`0x100ba6c0`)で
`{int32 type; char name[256]}` と宣言されている(`verify_ex_data.py` §1)。
`ex_data_def` は260バイト全ゼロ ―― 新規追加時は `type=0`(円)・`name=""`
(組み込みパターン、カスタム画像なし)。

`check[2]`(`ワイプ(円)`)は `check_default = -2` の**コンボボックス**
([`filter_registration.md`](../common/filter_registration.md) 「`check_default`
が負のチェックボックス」節)。項目名は `check_name[2]` が指す `0x100ba6d0`
から始まる連続文字列で、既定5個 + `func_init` が追記した PNG 名が並ぶ
(§8.1)。

選択変更(id `0x1e1c`)は共有ハンドラ(`ルミナンスキー` などが使う、
`ex_data[0] = lParam` を書くだけの汎用処理、`filter_registration.md`
「コンボボックス1個だけのエフェクトは func_WndProc を共有する」節)**では
なく**、ワイプ専用の `func_WndProc`(`0x10091710`)が処理する:

```
index = lParam                          // CB_GETCURSEL
ex_data.type = index
if (index < 5) { ex_data.name[0] = 0; }               // 組み込み5パターン
else {
    name = 0x100ba6d0 の二重NUL区切りリストの index 番目
    lstrcpyA(ex_data.name, name);       // カスタムパターン
    ex_data.type = 0;                    // 数値側は既定(円)に戻す(name優先で参照されない)
}
```

1個のコンボに「固定 enum」と「動的ファイルリスト」を同居させているのは
解析済みエフェクトの中でワイプだけで、それが専用 `func_WndProc` を持つ理由
になっている(`verify_ex_data.py` §5)。

## 11. 未確定事項

- カスタムパターンの `table[0x58]`(4隅Q12のワープ転写)の正確な座標配置は
  命令列から「全て0で初期化した16個の `int` を渡す」ところまでは追えたが、
  各要素が四隅のどの座標に対応するかまでは1つずつ突き合わせていない
  (`verify_custom_pattern.py` §2 のダンプ参照)。
- `ぼかし` パスの境界(画像端)での挙動は、`box_blur.md` の分類でいう
  「常にカーネル幅」ではなく「生存サンプル数」で割る側に見えるが
  (`0x10090700` のループが3フェーズに分かれ、中段のカウンタが窓の実効幅を
  数えている)、`シャドー`/`ぼかし` 本体のように厳密な式までは詰めていない。
  `simulate_wipe_reference.py` はここをクランプ近似で代用している。
- 時計パターンの角度基準(`0x4000` = 12時方向、という解釈)は式の形から
  推定したもので、実際にどの方向から掃引が始まって見えるかは実機での
  目視確認をしていない。
- §8.3 のカスタム画像パターンは、`threshold` が `g` とともに増えるぶん
  **進捗が増えると可視領域が減る** ―― 訂正後の組み込み5パターン(§4)とは
  向きが逆に見える。しきい値化本体(`0x100915b3`〜)は `setcc` ではなく明示的な
  `jle`/`jge` 分岐なので §4 の罠には該当せず「画素値が大きいほど可視」で
  確かなのだが、`threshold` の式(`0x1009129f`)に渡る `g` が既に反転済みの
  値なのかどうかまでは追えていない。組み込みパターンと揃うかどうかは未確定。
